## 1. 要約

- **行はエピック、バーはその配下のチケット。** 配下は「祖先をたどって最初に見つかるエピック」（`ApiDesign.md` 9.5.1 の `epic`）で決める
- **新しく持つ値は4つ**——チケットの「時間重複チェック」「開始のアンカー」「終了のアンカー」と、「当初計画」。前の3つはチケットの列、当初計画は別表のスナップショットを推奨する（5.1・5.2）
- **連鎖のずらしはサーバが1トランザクションで計算して書く。** 新しい口 `POST /tickets/:seq/reschedule` を足し、試算（`dry_run`）と確定を同じ口で行う（5.4・5.5）
- **ガントは後続を自動でずらさないと決めていた**（`GuiDesign.md` 5.14「依存に反する配置」「採らなかったもの」）。その再検討の条件が「複数のチケットの予定を1回で原子的に更新する API ができたとき」であり、**本件がその API を作ることになる**
- **準リアルタイムは定期取得（5秒）＋ `If-None-Match` で始める。** Web 向けの SSE は今は無い（5.7）
- **メニューの出し分けは `project.settings` のキーで行い、DDL は要らない**（5.3）
- **プラグインは今回は「ビューの登録を1か所に集める」に留めることを推奨する。** 実行時に外部の JS を読み込む方式は、CSP と認証の前提を崩す（5.9）

## 2. 機能の整理

### 2.1 利用者と使い方

**利用者は2種類で、どちらも PC の Web ブラウザだけで使う**（ヒアリング）。

| 利用者 | 見たいもの | 行う操作 |
|---|---|---|
| **本部**（全体を統括） | **全会場を一望**して、どこが押しているか・どこが空いているか。当初計画からのズレ | 行（エピック）を広く表示し、ズレや衝突を探す。アンカーを付ける・外す。当初計画を確定する。イベント後に計画と実績を比べる |
| **進行担当**（会場・出し物） | **自分の会場の行だけ**。次に何が始まるか、いまのものがいつ終わるか | 行を自分の会場に絞る。チケットを開始・完了にする（状態遷移）。終わりを延ばす・縮める（後続が連鎖でずれる） |

**行のフィルタは必須である**（ヒアリング）。進行担当は自分の行だけを、本部は全行を見る。**同じ URL を開けば同じ行が出る**（バックログ・ガントと同じく状態を URL のクエリに置く。`GuiDesign.md` 5.14「表示するチケット」）。

### 2.2 機能の出どころ

| 機能 | 出どころ | 今回 |

| プロジェクト設定でメニューに**タイムラインとガント**を出す・出さない | 本文 | やる |
| 行の表示フィルタ | **ヒアリング（必須）** | やる |

| 依存（`ticket_link` の FS など）による連鎖 | — | **やらない**。8章で起票を提案する |
| エージェント（MCP）からの連鎖のずらし | — | **やらない**。8章で起票を提案する |

## 3. タイムラインの可視化

### 3.1 何を描くか

```
┌────┬────────────────────────────────────────────────────────────────────────────────┐
│ ☰  │ タイムライン [行 ▾ 3/12][絞り込み ▾]   [秒|分|時] [いま] [当初計画 ▾] ⟳ 5秒前     │
│    ├────────────────┬───────────────────────────────────────────────────────────────┤
│    │ 基準 Asia/Tokyo │ 10:00      10:30  ┌10:42┐  11:00      11:30      12:00         │
│    ├────────────────┼───────────────────────────────────────────────────────────────┤
│    │▌体育館         │ ┌──────────┐┌─────────┐ ┌────────┐{──────────┐                 │
│    │                │ │吹奏楽 ✓  ││ダンス ● │ │演劇 ○  │{閉会式 ○  │  ← 時間重複チェック │
│    │                │ └──────────┘└─────────┘ └────────┘{──────────┘                 │
│    │                │   ┌───────┐                  ┌──────┐                          │
│    │                │   │準備 ✓ │                  │片付○│     ← チェック無し（副レーン）│
│    │                │   └───────┘                  └──────┘                          │
│    │▌1年A組 喫茶    │ ┌─────────────────────────────────┐                            │
│    │                │ │営業（午前） ●                   │                            │
└────┴────────────────┴───────────────────────────────────────────────────────────────┘
       行（エピック）          時間軸（{ は開始のアンカー。┌10:42┐ は「いま」）
```

**見た目は pb-295 のモックで決める。** 上は要素の置き場所を示すための図である。

| 要素 | 描くもの | 備考 |
|---|---|---|
| **行** | エピック1つ。見出しに題名と袖章（`GuiDesign.md` 5.4.4。ガント・バックログと同じ32通り） | エピックは行の見出しになり、バーにならない |
| **バー** | 配下のチケット。**高さは一定**（2行ぶん）。中に題名と状態（記号＋名前）。入らなければ題名を省略し、ポインタを載せると全文 | 時刻付き（`all_day = false`）で、開始と終了の両方があるもの（T14） |
| **主レーンと副レーン** | **時間重複チェック付きは主レーン（1本）**に並べる。**チェック無しは、重なったぶんだけ副レーンを足す** | 行の高さはレーンの数で変わる。**バーの高さは変えない**（本文の要件） |
| **完了** | 消さずに残し、沈んだ塗りと ✓ で示す。ガントの完了の描き方（`GuiDesign.md` 5.14「帯」の表）に揃える | |
| **当初計画からのズレ** | 当初計画の位置に細い影（枠線だけ）を描き、いまのバーと食い違えば印を付ける。始まりと終わりのどちらがどれだけずれたかを札で出す | 当初計画が無いエピックでは描かない |
| **当初計画に無かったもの／消えたもの** | 確定後に足したチケットに「計画外」の印。計画にあったが消えたチケットは影だけを残す | スナップショット方式（5.2 の T3 で B）のときだけ描ける |
| **アンカー** | 開始のアンカーは左端、終了のアンカーは右端に、錨の印（図では `{` `}`） | |
| **衝突** | 時間重複チェック付きどうしが重なっていれば、重なった区間を danger で示す | 連鎖のずらし以外の経路で重なりうる（5.6） |
| **押している** | 未完了で終了の予定を過ぎたもの（ガントの「期限超過」と同じ式）。いまの位置までバーの続きを破線で描く | 予定は自動で書き換えない（5.4 の T10） |
| **「いま」の線** | 正確な時刻の位置。時刻の札（見る人のタイムゾーン）。**秒の表示では毎秒、それ以外は毎分**動かす | ガントは60秒ごと（`GanttPage.vue:1314`） |
| **時間軸の拡大縮小** | 秒・分・時の段階と、連続の拡大縮小 | ガントの最小単位は分（下記 3.2） |
| **行のフィルタ** | エピックの複数選択（`?parent=` と同じ部分木。`ApiDesign.md` 9.2.1）。加えて担当・状態・タグ | URL のクエリに置く |
| **最終取得** | 「⟳ 5秒前」。取得に失敗し続けたら警告の面（`GuiDesign.md` 8.4.1） | 準リアルタイムの状態を見せる |

### 3.2 ガントから流用できるもの・できないもの

ガントは `client/src/pages/GanttPage.vue`（2,180行）と `client/src/lib/gantt/`（6ファイル・1,975行）である。

| 部品 | 中身 | タイムラインでは |
|---|---|---|
| `lib/gantt/time.ts`（303行） | タイムゾーンの壁時計（`wall` / `wallParts`）、日の区切り、目盛り（`ticks`）、拡大縮小の段階（`ZOOM_LEVELS`） | **壁時計と日の区切りは流用できる。** ただし**最小の単位が分**である——`ZOOM_LEVELS` の最大は `minute`（2,880px/日）、`PPD_MAX = 5760`（1分＝4px）、目盛りの単位 `TickUnit` は `['min', n]` まで、`wall()` は分までしか取らない（`time.ts:60`）。**秒の段階を足すには目盛りと壁時計に秒を足す改修が要る**。ガントへの影響を避けるため、段階の表はビューごとに渡せる形にする |
| `lib/gantt/edit.ts`（218行） | 吸着（`snapTime`）、ドラッグの結果（`planAt`）、掴む場所（`grabAt`）、依存の輪・違反の判定 | **吸着とドラッグの計算は流用できる。** 吸着の単位は分（`snapTime` は `unit` が分）なので秒の吸着は足す。依存の部分は使わない |
| `lib/gantt/model.ts`（181行） | チケットを `GItem` に直す（`toItems`。状態の区分・完了・期限超過）、ツリーの行（`buildRows`） | **`toItems` の判定（完了・期限超過）は流用できる。** 行の組み立て（ツリー・1チケット1行）は使えない——タイムラインの行はエピックで、1行に複数のチケットが乗る |
| `lib/gantt/render.ts`（691行） | SVG を文字列で組んで1回で差し替える。見えている範囲だけ描く | **方式（文字列の SVG・見えている範囲だけ）は流用する。** 中身は描き直し——行の高さが 28px 固定（`RH = 28`）、バーは 12px、文字はバーの外（右）に出す作り。タイムラインはバーの中に2行の文字を入れる |
| `lib/gantt/excel.ts` ほか | Excel 出力 | **使わない。** タイムラインの Excel 出力は今回の範囲に入れない（必要なら8章） |
| 詳細ペイン | `TicketDetailPane.vue` を浮かせて開く（`GuiDesign.md` 5.14「詳細ペイン」） | **そのまま使う**（5.8 の T12） |
| 編集の送り方 | `PATCH /tickets/:seq` に `If-Match`。409 なら取り直して通知の行に出す（`GuiDesign.md` 5.14「送り方と見え方」） | **口だけが変わる**（`POST /tickets/:seq/reschedule`。5.5）。409 の扱い・破線で「未確定」を示す・トーストを使わない、は同じにする |
| 実装の落とし穴（`GuiDesign.md` 5.14「実装の落とし穴」） | `color-mix` の色相、ポインタの捕捉と `click` など | **同じ穴に落ちるので、そのまま守る** |

| **ガントの Excel 出力** | ブラウザで作る（`lib/gantt/excel.ts`）。列は ID・タイトル・状態・開始・終了・先行（`GuiDesign.md` 5.14「本表」） | **影響なし。** アンカーや当初計画の列を足すかは範囲外 |
| **変更履歴** | `activity` に項目ごと1行。`start_at` / `due_at` / `all_day` は記録する（`tickets_update.go:608-622`）。**`request_id` 列が有る**（`DbDesign.md` 6.8） | 連鎖で動いた行もそれぞれ記録する。**同じ `request_id` で束ねる**と「pb-12 の延長に伴って動いた」が読める。新しい3列も記録の対象にする |
| **バックアップ** | 表の一覧はカタログから引く（`server/internal/backup/catalog.go:34`）。新しい表は自動で載る。ただし**往復のテスト**で確かめる規則（`DbDesign.md` 9.1.1「代償を隠さない」） | 当初計画の表を足すなら、往復のテストに含める |
| **デモデータ** | `deploy/dev/seed/dev-data.yaml`（`DbDesign.md` 7.6） | 文化祭のデモ（エピック数個・時刻付きのチケット）を足すと、画面の確認と e2e が楽になる |

### 4.2 調べて分かった注意点

1. **チケットの `all_day` は既定で `true`**（0047、`ApiDesign.md` 9.3.1「省略時は `true`」）。バックログやモーダルから作ったチケットは終日になる。**タイムラインの上で作るときは `all_day = false` を明示する**必要があり、既存のチケットを当日の進行に使うときも時刻付きへ直す手間がある
2. **ガントは「後続を自動でずらさない」を判断として持っている**（`GuiDesign.md` 5.14）。理由は「1回のドラッグで複数の更新が走り、途中で競合すると一部だけ動いた状態が残る」で、**再検討の条件は「複数のチケットの予定を1回で原子的に更新する API ができたとき」**。本件はその条件を満たす API を作るので、**ガントでも連鎖を使うかを後で問える**（今回はガントを変えない）
3. **ETag はあるが `If-None-Match` を解釈していない。** 定期取得で `304` を返すには実装が要る。また ETag は `ticket.updated_at` から作るので、**当初計画（別表）を変えても動かない**——タイムラインの ETag には当初計画の材料を混ぜる（ガントが依存の件数を混ぜたのと同じ。`ApiDesign.md` 9.2.5）
4. **Web 画面向けの SSE も待ち受けも無い。** 長く待つ口は MCP の `pb_wait` だけで、中身は **MCP 層が REST を3秒ごとに問い合わせる**ものである（`server/internal/mcp/wait.go:23-37`）。サーバ全体の `WriteTimeout` は60秒で、`pb_wait` は自分の要求だけ期限を延ばしている（`server/internal/mcp/sdk.go:50-56`）
5. **メニューはプロジェクトの `settings` を知らない。** ガントの吸着（`gantt_snap_minutes`）はガントの画面が読むだけなので困らなかったが、メニューの出し分けは**全画面で**要る
6. **チケットは物理削除である**（`DbDesign.md` 4.6）。「`updated_at` 以降に変わったもの」を返す差分取得では、**消えたチケットを知る手段が無い**（5.7）
7. **`ticket.plan.edit` は `project_member` に付いていない。** 進行担当を `project_member` にするなら `ticket.edit` で通るが、**予定だけを変えさせたい人**（予定以外は触らせない）を作るには、`ticket.plan.edit` を持つ別のロールが要る（今は組み込みロールしかない）
8. **実際の着手日時は列ではなく遷移の履歴から導く**（`ApiDesign.md` 9.2.1「着手日時を導く」）。一覧の応答には載っていない。振り返りで「実際に始まった時刻」を描くなら、タイムラインの応答に足す（5.5）

## 5. 方式案

**各論点に T 番号を振った。7章の表がその一覧である。** 推奨はあくまで推奨で、**選ぶのは PM である**。

### 5.1 時間重複チェックとアンカーの持ち方（T1）

| 案 | 中身 | 良い点 | 悪い点 |
|---|---|---|---|
| **A：`ticket` の列** | `no_overlap` / `start_pinned` / `due_pinned`（いずれも `boolean NOT NULL DEFAULT false`） | 一覧・詳細・`PATCH`・変更履歴・`version` の仕組みにそのまま乗る。**行ごとに必ず1つ**の値なので表を分ける理由が無い | `ticket` の列が3つ増える（イベント型でないプロジェクトでも持つ） |
| B：別表 `ticket_timeline` | `ticket_id` を主キーに3列 | `ticket` を太らせない | 一覧のたびに結合。`version` をどちらで持つか（別表を変えたときにチケットの版を上げるか）を決める必要がある |
| C：`custom_fields` に入れる | jsonb のキー | DDL が要らない | **カスタムフィールドの設計が未決**（`ApiDesign.md` 11章）。そこに先に意味を持ち込むと、後の設計を縛る。サーバで連鎖を計算するのに型の保証が無い |

**推奨：A。** 連鎖の計算・`PATCH` の検証・変更履歴が既存の列と同じ道を通れる。**列の名前も論点にしない**（`no_overlap` / `start_pinned` / `due_pinned` を仮置きにする。画面の名前は「時間重複チェック」「開始のアンカー」「終了のアンカー」）。

```sql
-- 00xx_ticket_timeline_flags.sql
-- pb-297: タイムラインの時間重複チェックと、開始・終了のアンカー（Timeline.md 5.1）。
-- +goose Up
ALTER TABLE ticket
  ADD COLUMN no_overlap   boolean NOT NULL DEFAULT false,
  ADD COLUMN start_pinned boolean NOT NULL DEFAULT false,
  ADD COLUMN due_pinned   boolean NOT NULL DEFAULT false,
  ADD CONSTRAINT ck_ticket_pins CHECK (
        (NOT start_pinned OR start_at IS NOT NULL)
    AND (NOT due_pinned   OR due_at   IS NOT NULL));
```

- **アンカーは「その端の値がある」ことを CHECK で縛る。** 値の無い端を固定するのは意味を持たない。`PATCH` で固定された端を `null` にしようとすると、CHECK より先にアプリが `422`（`details[].code = "pinned"`）を返す
- **時間重複チェックには CHECK を掛けない。** 開始・終了がそろっていないチケットにチェックを付けても、連鎖の対象から外れるだけにする（作りかけを許す。`DbDesign.md` 6.6 の「子を持たない `story` を許す」と同じ考え）
- **`DEFAULT false` の列追加は既存行を書き換えない**（PostgreSQL 11 以降）。前進のみ（`DbDesign.md` 5.3）

### 5.2 当初計画の保存（T2〜T4）

**当初計画は「ある時点の予定を凍らせたもの」である。** イベントが終わった後に、当日の進行（いまの予定と実績）と比べる。

#### T2：持ち方

| 案 | 中身 | 良い点 | 悪い点 |
|---|---|---|---|
| A：チケットの列 | `baseline_start_at` / `baseline_due_at` / `baselined_at` | 最も小さい。一覧に載せるだけで描ける | **確定し直すと前の当初計画が消える。** 計画の後に消したチケットは比べられない（行ごと消える）。計画の後に足したチケットと区別できるのは `baselined_at` が空かどうかだけ |
| **B：スナップショットの表** | 確定1回を1行（`schedule_baseline`）、その時のチケットの予定を子の行（`schedule_baseline_item`）に写す | **確定し直しても前の版が残る。** 消えたチケット・後から足したチケットが分かる。題名も写すので、後で題名を変えても当時の計画が読める | 表が2つ増える。応答に当初計画を載せる結合が要る |

**推奨：B。** 振り返りは「当日どう変わったか」を見るためのもので、**チケットが消えたり足されたりすること自体が振り返りの材料**である。A では、本番中に中止した出し物（チケットを消したもの）が計画からも消える。名前はガントでも使えるよう、タイムラインに寄せずに `schedule_` とする。

```sql
-- 00xx_schedule_baseline.sql
-- pb-297: 当初計画のスナップショット（Timeline.md 5.2）。
-- +goose Up
CREATE TABLE schedule_baseline (
  id          char(26) COLLATE "C" PRIMARY KEY,
  project_id  char(26) COLLATE "C" NOT NULL REFERENCES project(id) ON DELETE CASCADE,
  epic_id     char(26) COLLATE "C" REFERENCES ticket(id) ON DELETE SET NULL,
  epic_label  text    NOT NULL,          -- 確定した時点の key-seq と題名。エピックが消えても読める
  revision    integer NOT NULL CHECK (revision >= 1),  -- エピックごとの通し番号
  note        text,                       -- 「前日リハーサル後に確定」など
  created_by  char(26) COLLATE "C" REFERENCES actor(id) ON DELETE SET NULL,
  created_at  timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT uq_schedule_baseline_rev UNIQUE (epic_id, revision)
);
CREATE INDEX idx_schedule_baseline_epic ON schedule_baseline (project_id, epic_id, revision DESC);

CREATE TABLE schedule_baseline_item (
  baseline_id char(26) COLLATE "C" NOT NULL REFERENCES schedule_baseline(id) ON DELETE CASCADE,
  ticket_seq  integer NOT NULL,           -- 番号は使い回さない（DbDesign.md 6.4.1）ので、消えた後も指せる
  ticket_id   char(26) COLLATE "C" REFERENCES ticket(id) ON DELETE SET NULL,
  title       text    NOT NULL,
  start_at    timestamptz,
  due_at      timestamptz,
  all_day     boolean NOT NULL,
  no_overlap  boolean NOT NULL,
  PRIMARY KEY (baseline_id, ticket_seq)
);
```

- **更新しない表である**（行の追加と、エピックごとの削除だけ）。`updated_at` も `version` も持たない
- `epic_id` が `NULL`（エピックが消えた）の版どうしは `UNIQUE` で衝突しない（PostgreSQL の既定）。消えたエピックの当初計画は、`epic_label` で読む記録として残る

#### T3：確定の単位

| 案 | 中身 | 推奨 |
|---|---|---|
| プロジェクト単位 | 1回の確定で全エピックを写す | |
| **エピック単位** | エピックごとに確定する。**画面は複数のエピックを選んで一度に確定できる**（中では選んだ数だけ版を作る） | **推奨。** 行（エピック）ごとにズレを比べるので、比べる相手の版が行ごとに決まる。**会場ごとにリハーサルの日が違っても、終わった会場から確定できる** |
| 選んだエピックの集合を1版 | | 版とエピックの対応が多対多になり、「この行の当初計画はどれか」が一意に決まらない |

#### T4：いつ・誰が・確定し直しを許すか

| 論点 | 選択肢 | 推奨 |
|---|---|---|
| いつ | 手動のボタンだけ／イベントの開始時刻に自動 | **手動だけ。** 自動にすると「いつの状態が写ったか」を誰も意識しない。PB は時刻で動く仕組み（ジョブ）を持っていない |
| 誰が | ①`project.edit`（プロジェクト管理者以上）／②新しい権限 `ticket.baseline` を足す／③`ticket.edit`（メンバーも） | **①。** 当初計画は本部が持つもので、会場の担当が書き換えるものではない。権限カタログ（`DbDesign.md` 7.2）を増やさずに済む。会場ごとに任せたいと分かったら②へ移す |
| 確定し直し | 許さない／**許して新しい版を足す**／上書きする | **新しい版を足す。** 画面は既定で最新の版と比べ、`[当初計画 ▾]` で前の版を選べる。消すのは「版を消す」で明示的に行う |

### 5.3 メニュー表示の設定（T5・T6）

#### T5：持ち方

**`project.settings` にキーを足し、DDL を要らなくする。** `gantt_snap_minutes` と同じく「画面が読むだけで SQL から使わない」値である（`DbDesign.md` 6.4 の判断基準）。

| 案 | 形 | 良い点 | 悪い点 |
|---|---|---|---|
| **A：ビューごとの真偽** | `"views": { "gantt": true, "timeline": false }` | 知らないビュー・書いていないビューを既定値で補える。**キーが無いプロジェクトは今と同じ見え方**（ガントは出す、タイムラインは出さない） | 並び順は持てない |
| B：出すビューの配列 | `"menu_views": ["backlog", "gantt", "timeline", "search"]` | 並び順も持てる | 配列に無いビューは「出さない」になり、**新しいビューを足したときに既存のプロジェクトで勝手に消える／出る**の既定を別に決める必要がある |
| C：プラグイン化を見越した形 | `"views": { "gantt": { "enabled": true, "variant": "standard" } }` | 「ガントの種類を選ぶ」（チケット本文の将来構想）まで1つのキーで持てる | 今は `variant` を使わない |

**推奨：A。** 既定値は**ガント＝出す、タイムライン＝出さない**（既存のプロジェクトの見え方を変えない）。**バックログ・検索は対象にしない**（チケットを扱う最小の入口なので消せないほうがよい）。C の形は、プラグイン化（5.9）を作り込むと決めたときに A から移せる——**値が真偽からオブジェクトに変わるだけで、読む関数が両方を受ければ移行の DDL も要らない**。

```jsonc
{
  "repositories": [ /* 既存 */ ],
  "gantt_snap_minutes": 15,
  "views": { "gantt": true, "timeline": true }
}
```

**隠したビューの URL を直接開いたとき。** メニューから消すだけにし、URL は開けるままにすることを推奨する（T5 の付帯）。**権限の境界ではない**（見られて困る情報は無く、`ticket.view` で守られている）。弾くと、共有された詳細の URL（`?from=gantt`）が壊れる。

#### T6：メニューが `settings` を読む手段

| 案 | 中身 | 推奨 |
|---|---|---|
| **A：メニューが選択中のプロジェクトを取る** | `SideMenu.vue`（か `AppShell.vue`）が `:key` の変化で `projectStore.fetchCurrent` を呼ぶ。各ページの呼び出しと重なるので、同じキーの取得中なら待ち合わせる | **推奨。** API を変えない。プロジェクト設定で保存すると `setCurrent` でストアが変わり、メニューも即座に追随する |
| B：`GET /me` の `projects[]` に載せる | ログイン時の応答に `views` を足す（`Design.md` 6.4.4 の `projects: [{ key, role, permissions }]`） | 往復が増えない。ただし**設定を変えても `/me` を取り直すまでメニューが古い**。`/me` は権限の応答であり、表示の設定を混ぜる場所ではない |

### 5.4 連鎖のずらしの規則（T7〜T10、T13）

**対象：同じエピック（行）の、時間重複チェック付きで、開始と終了の両方を持つチケット**（以下「列」）。列は開始の昇順に並ぶ。チェックの無いチケットは**一切動かさない**（準備・片付けは裏で重なってよい。ヒアリング）。

**不変条件：列のどの2つも重ならない**（半開区間 `[start_at, due_at)` どうし。終わりと始まりが同じ時刻は重ならない）。

#### 基本の規則

| 規則 | 内容 |
|---|---|
| きっかけ | **列の1件（T）の終了が Δ だけ動いた**（延ばした・縮めた・バーごと動かした） |
| **ずらす相手** | T より後ろの列のすべて。**同じ Δ だけ、開始と終了をそろって動かす**（長さと隙間を保つ）——「そのまま後ろへ／そのまま前へ」（ヒアリング） |
| 止まる所 | **アンカーの付いたチケット**（下記）、または列の終わり |
| 前の列 | **動かさない。** T の開始を前へ動かして前の列に重なったら、拒む（`422`、`overlaps_previous`）。前の列を押し戻すと、すでに終わったものを書き換えることになりうる |
| 着手済み・完了 | **着手済みの開始と、完了したものの両端は、暗黙のアンカーとして扱う**（T9）。起きたことを予定の書き換えで消さない |
| 「いま」より前 | **前へ寄せても、まだ始まっていないものの開始を「いま」より前に置かない**（T9）。置くと「予定では始まっているのに始まっていない」が生まれる |

#### アンカーに当たったとき

| アンカー | 後ろへずらすとき（Δ > 0） | 前へ寄せるとき（Δ < 0） |
|---|---|---|
| **開始のアンカー**（`start_pinned`） | そのチケットは動かない。**手前の区間（T からアンカーまで）で吸収する**——まず区間内の隙間を詰め、それでも収まらなければ「解けない」（T8） | そこで止まる。アンカーの手前に隙間が空く |
| **終了のアンカー**（`due_pinned`） | **開始だけが後ろへ動き、そのチケットが縮む**。終わりは動かないので、その後ろへは波及しない。最小の長さを割れば「解けない」 | そこで止まる（開始を前へ動かして伸ばすことはしない） |
| 両方 | 動かない。開始のアンカーと同じ | 同じ |

#### 例1：延ばすと、後続がそのまま後ろへ（アンカー無し）

体育館の行。A 吹奏楽 10:00–10:30、B ダンス 10:40–11:10、C 演劇 11:10–11:40（すべてチェック付き）。X 準備はチェック無し。**A の終わりを 10:45 へ延ばす（Δ = +15分）。**

```
  |10:00|10:30|11:00|11:30|12:00            （1文字＝5分）
  [A---]  [B---][C---]              前
      [X---]                        前（チェック無しの X）
  [A------]  [B---][C---]           後：B 10:55–11:25、C 11:25–11:55
      [X---]                        後（X は動かない）
```

A–B の10分の隙間は保たれる。X は重なっても動かない。**書くのは A・B・C の3行で、1トランザクションである。**

#### 例2：縮めると、後続がそのまま前へ

同じ並びで、**A が早く終わり、終わりを 10:20 へ縮める（Δ = −10分）。** いまは 10:20 とする。

```
  |10:00|10:30|11:00|11:30|12:00
  [A---]  [B---][C---]              前
  [A-]  [B---][C---]                後：B 10:30–11:00、C 11:00–11:30
```

**B の新しい開始 10:30 は「いま」（10:20）より後なので置ける。** もし縮めたのが 10:35 に入ってから（いまが 10:35）なら、B は 10:35 より前に置けないので 10:35 で止まり、C も B に続く 11:05 までしか寄らない（「いま」の規則）。

#### 例3：開始のアンカーに当たる

C 閉会式は 11:30 開始を動かせない（開始のアンカー。図では `{`）。A 10:00–10:30、B 10:40–11:10、C 11:30–12:00。

**3a：A を 11:00 まで延ばす（Δ = +30分）——隙間で収まる。**

```
  |10:00|10:30|11:00|11:30|12:00
  [A---]  [B---]    {C---]          前
  [A---------]      {C---]          ずらしただけ（B が C に食い込む）
                [B!--]
  [A---------][B---]{C---]          後（A–B の隙間を使って収める）
```

そのままずらすと B は 11:10–11:40 で C に10分食い込む。**区間（A から C の手前まで）の隙間は A–B の10分と B–C の20分で計30分**あり、**アンカー側から詰めると** B は 11:00–11:30 に収まる。

**3b：A を 11:15 まで延ばす（Δ = +45分）——隙間だけでは15分足りない。** 解けない場合の扱い（T8）で結果が変わる。

```
  |10:00|10:30|11:00|11:30|12:00
  [A---]  [B---]    {C---]          前
  [A---]  [B---]    {C---]          U1 拒む（何も変わらない）
  [A------------][B]{C---]          U2 縮める（B を 15分に）
  [A------------]   {C---]          U3 重ねる（B と C が衝突の印）
                 [B!--]
```

#### 例4：終了のアンカーで縮む

B は体育館の返却があり 14:20 に終えなければならない（終了のアンカー。図では `}`）。A 13:00–13:40、B 13:40–14:20、C 14:30–15:00。**A を 13:50 まで延ばす（Δ = +10分）。**

```
  |13:00|13:30|14:00|14:30|15:00
  [A-----][B-----}  [C---]          前
  [A-------][B---}  [C---]          後（B の頭だけ動き、C は動かない）
  [A------------]}  [C---]          A を 14:15 まで延ばすと B は 5分（最小 10分を割る→解けない）
```

B は 13:50–14:20 の30分に縮み、**終わりが動かないので C へは波及しない。** さらに A を 14:15 まで延ばすと B は5分になり、最小の長さ（T13。例では10分）を割るので「解けない」になる。

#### T7：隙間の扱い

| 案 | 中身 | 推奨 |
|---|---|---|
| **A：同じだけずらす（隙間を保つ）** | 例1・例2の動き。アンカーに当たったときだけ隙間を詰める | **推奨。** ヒアリングの「そのまま後ろへ・そのまま前へ」に合う。休憩や転換の時間（隙間）が保たれる |
| B：押しのけるだけ | 延びたときは重なる分だけ押し、隙間があれば吸収する。縮めたときは寄せない | 公開した時刻が動きにくい。ただし「前倒しなら前へ」と合わない |

#### T8：解けないときの扱い

| 案 | 中身 | 推奨 |
|---|---|---|
| U1：拒む | 何も書かない。`422`（`cannot_fit`）と、詰まったアンカーのチケット番号・足りない時間を返す | **既定は U1** |
| U2：縮める | 隙間を詰めても足りなければ、**アンカーの直前のチケットから順に**最小の長さまで縮める。それでも足りなければ U1 | **要求で明示したときだけ U2**（画面は試算で「B を 15分に縮めれば収まります」を見せ、押したら U2 で送る） |
| U3：重ねる | 書いて、衝突を印で示す。直すのは人 | 採らない。連鎖を作る目的（重ならないこと）に反する |
| U4：アンカーを越えて押す | — | 採らない。アンカーの意味が無くなる |

**推奨：U1 を既定に、U2 を明示の選択で。** 人の判断なしにチケットを縮めない（PM の制約「自動で選ばない」とも合う）。縮める順序は**アンカーの直前から**（比例で縮める案より、誰が割を食うかが読める）。

#### T9：着手済み・完了・「いま」の扱い

| 規則 | 推奨 | 外したとき |
|---|---|---|
| 着手済み（状態が `todo` 区分を出た）の開始は動かさない | 採る | 実際には10:00に始まった演劇の予定が10:15に書き換わり、振り返りで読めなくなる |
| 完了したものは両端とも動かさない | 採る | 同上 |
| まだ始まっていないものを「いま」より前に寄せない | 採る | 予定上は始まっているが実際は始まっていない、が生まれる |

#### T10：実績が予定と違ったとき（早く終わった・押している）

| 場面 | 案 | 推奨 |
|---|---|---|
| 予定より早く完了にした | ①完了にしたら自動で終わりを完了時刻に縮め、後続を寄せる／②**完了の行に `[ここで詰める]` を出し、押したら縮める** | **②。** 来場者に公開した時刻より早く始まると困る出し物がある。寄せるかは人が決める |
| 終わりの予定を過ぎても進行中 | ①一定間隔で自動延長／②**「押している」を描き、`[いままで延ばす]` を出す** | **②。** 自動で書くと、5秒ごとの取得のたびに全員の画面で後続が動き続ける |

#### T13：時間の単位

| 論点 | 選択肢 | 推奨 |
|---|---|---|
| 保存の精度 | 秒（今の `timestamptz` で足りる。REST はミリ秒） | **変えない** |
| 吸着の単位 | プロジェクトの設定 `timeline_snap_seconds`（例：1・10・30・60・300・900） | 既定 60（1分）。`gantt_snap_minutes` とは分ける（ガントは日の単位が主） |
| 最小の長さ（縮めるとき） | 固定 1分／吸着の単位／設定 | **吸着の単位。** 設定を増やさない |
| 拡大縮小の段階 | 秒（例：1秒＝4px）・分・時 | 3段。日以上の段階は持たない（イベント当日の画面なので） |

### 5.5 どこで計算し、どう送るか（API）

**サーバで、1回の要求・1トランザクションで計算して書く。** 複数の担当が同時に触るので、ブラウザで計算して1件ずつ `PATCH` を送ると、途中で競合して一部だけ動いた状態が残る（ガントが連鎖を採らなかった理由そのもの）。

| 案 | 中身 | 推奨 |
|---|---|---|
| **A：サーバで計算・1トランザクション** | 新しい口で、きっかけの変更を受け、連鎖を計算して全行を書く | **推奨** |
| B：画面で計算し、一括更新の口に送る | 画面が全行の新しい予定を作り、`PATCH` の配列を送る | 計算の正本が画面に寄り、MCP やガントから同じ規則を使えない |
| C：画面で計算し、1件ずつ `PATCH` | | 採らない（部分的に動いた状態が残る） |

#### 取得：`GET /api/v1/projects/:key/tickets?view=timeline`

**ガントと同じく、同じエンドポイントに `view` を足す**（「ガントという資源は無いので、パスを分けない」`ApiDesign.md` 9.2.6 に倣う）。

| 項目 | `view=timeline` |
|---|---|
| 絞り込み | 9.2.1 と同じ。**行のフィルタは `parent=12,30`**（エピックの部分木） |
| 件数の上限 | 5,000（9.2.6 と同じ） |
| 足す項目（`items[]`） | `no_overlap` / `start_pinned` / `due_pinned`、**`epic_seq`**（所属エピック。9.5.1 の `epic` と同じ求め方）、**`started_at`**（実際の着手。9.2.1「着手日時を導く」） |
| 同梱するもの | `epics[]`：行になるエピック（`seq`・`title`・`status`・最新の当初計画の `revision` と `created_at`）。`baselines[]`：選んだ版（既定は各エピックの最新）の `schedule_baseline_item` |
| ETag | 9.2.5 の材料に、**当初計画の件数と `MAX(created_at)`** を混ぜる（4.2 の注意3） |

#### 変更：`POST /api/v1/projects/:key/tickets/:seq/reschedule`

**きっかけのチケット1件の新しい予定を受け、連鎖を計算して返す（試算）か、書く（確定）。**

```http
POST /api/v1/projects/fes/tickets/12/reschedule
If-Match: "4"
```
```json
{
  "start_at": 1791594000000,
  "due_at":   1791597600000,
  "on_block": "reject",
  "dry_run":  false,
  "expect": [ { "seq": 13, "version": 2 }, { "seq": 14, "version": 7 } ]
}
```

| フィールド | 意味 |
|---|---|
| `start_at` / `due_at` | きっかけのチケットの新しい予定（エポックミリ秒。片方だけでもよい） |
| `on_block` | 解けないとき。`reject`（既定。U1）／`shrink`（U2） |
| `dry_run` | `true` なら計算だけして書かない（試算） |
| `expect` | **試算で動くと示された行の版。** 確定のときに送る。サーバは計算し直し、動かす行の集合か版が食い違えば `409` |

```json
{
  "applied": true,
  "changes": [
    { "seq": 12, "reason": "target", "before": { "start_at": 1791590400000, "due_at": 1791594000000 },
      "after": { "start_at": 1791594000000, "due_at": 1791597600000 }, "version": 5 },
    { "seq": 13, "reason": "ripple", "before": { "start_at": 1791594600000, "due_at": 1791596400000 },
      "after": { "start_at": 1791598200000, "due_at": 1791600000000 }, "version": 3 }
  ],
  "items": [ /* 動いた行の 9.2.2 形式。画面はこれで差し替える */ ]
}
```

| 状況 | 応答 |
|---|---|
| きっかけの版が違う | `409 conflict`（`PATCH` と同じ文言） |
| `expect` と計算し直した結果が違う（試算の後に誰かが動かした） | `409 conflict`、`details[].code = "stale_plan"`。**応答に新しい試算を載せる**——画面は確認をもう一度出すだけでよい |
| アンカーの付いた端そのものを動かそうとした | `422`、`pinned` |
| 前の列に重なる | `422`、`overlaps_previous`（相手の `seq` を `message` に） |
| 解けない（`reject`） | `422`、`cannot_fit`（詰まったアンカーの `seq` と足りない時間） |
| 縮めても最小を割る（`shrink`） | `422`、`too_short` |
| 終日の予定 | `422`、`all_day`（連鎖は時刻付きだけを扱う） |

**同時更新の扱い。** トランザクションの最初に**エピックの行を `SELECT … FOR UPDATE` で掴み**、同じ行（エピック）への連鎖を直列にする。続いて列の全行を `FOR UPDATE` で読み、計算し、`version = version + 1` で書く。**楽観ロックの版（`If-Match` と `expect`）は「人が見ていた前提が崩れていないか」を確かめるためのもの、行のロックは「計算の途中で他の連鎖が割り込まないこと」を守るためのもの**で、役割が違う。

| 項目 | 決めたいこと |
|---|---|
| 必要権限 | `PATCH` と同じ `ticket.edit` / `ticket.self_edit` / `ticket.plan.edit` の OR をルートに宣言する。エージェントには `planningWriteProblem` を**動かす全行の ID**で掛ける |
| 変更履歴 | 動いた行ごとに `start_at` / `due_at` を記録し、**同じ `request_id`** を付ける。詳細の履歴で「pb-12 の変更に伴う」を出せる |
| 当初計画の口 | `POST /projects/:key/tickets/:epic_seq/baselines`（確定。`note` を受ける）・`GET`（版の一覧）・`DELETE …/baselines/:revision`。エピックもチケットなのでチケットの下に置く |

### 5.6 他の経路で予定が変わったとき（T11）

予定は `PATCH`（詳細ペイン・ガントのドラッグ・MCP の `pb_update_ticket`）でも変わる。

| 案 | `PATCH` で列のチケットの予定を変えたとき | 推奨 |
|---|---|---|
| **A：連鎖しない。アンカーだけ守る** | 連鎖はしない（重なれば衝突の印）。**アンカーの付いた端を変える `PATCH` は `422 pinned`** | **推奨。** 連鎖は試算を見せてから確定する操作で、詳細ペインやガントには試算を出す場所が無い。アンカーは「動かしてはいけない」なので経路を問わず守る |
| B：`PATCH` も連鎖する | `PATCH` の中で 5.5 と同じ計算をする | 詳細で終わりを1分直しただけで他人のチケットが動き、しかも試算が見えない |
| C：アンカーも `PATCH` では守らない | タイムラインの外では自由 | アンカーの意味が画面によって変わる |

**時間重複チェック付きの重なりは、`PATCH` では拒まない**（A の付帯）。チェックを付けた直後や、チケットを別のエピックへ移した直後は重なりうる。**ガントが「依存に反する配置」を拒まずに印で示す**（`GuiDesign.md` 5.14）のと同じ扱いにする。

### 5.7 準リアルタイム（T15）

| 案 | 中身 | 良い点 | 悪い点 |
|---|---|---|---|
| **A：定期取得＋`If-None-Match`** | 画面が5秒ごとに `view=timeline` を同じ条件で取り直す。変わっていなければ `304` | **サーバに新しい仕組みが要らない。** `Requirements.md` 1章（「まずはAPIの短間隔ポーリング（ETag/If-Modified-Since等での差分取得）で対応」）どおり。消えたチケットも、全件を取り直すので反映される | 変わらなくても5秒ごとに一覧の SQL が走る（`304` で減るのは転送だけ）。最大5秒遅れる |
| B：定期取得＋差分（`updated_since`） | `updated_at` が前回より新しいものだけ返す | 応答が小さい | **消えたチケットが分からない**（物理削除。4.2 の注意6）。当初計画・依存の変化も別に要る。新しいクエリパラメータが要る |
| C：SSE | サーバが変化を押し出す | 遅れが小さい | **Web 向けの仕組みがゼロから要る**：変化を知る仕組み（`LISTEN/NOTIFY` か、プロセス内の配信。stg・prod で複数のプロセスが動くなら前者）、`WriteTimeout`（60秒）の延長（`pb_wait` と同じ手当て）、ブラウザの同時接続数（HTTP/1.1 で1オリジン6本）、切断と再接続。**変化を知った後に結局 A と同じ取得をする** |

**推奨：A。** 間隔は**5秒**（設定にしない。`stores/pending.ts` が30秒を定数で持つのと同じ考え）。**タブが見えていないあいだは止め**（`visibilitychange`）、見えたら即座に1回取る。**`304` を返す実装を `tickets.go` に足す**（今は ETag を出すだけ）。負荷の目安：利用者30人が開いていても毎秒6要求で、ガントの実測（5,000件で105ms。`ApiDesign.md` 9.2.6）に比べ、当日の行は数百件に収まる見込み。**SSE は、利用者の規模か遅れの要求が A で足りないと分かったときに移る**（`Requirements.md` 1章の「段階的設計」）。

**編集中の取り直し。** ドラッグ中・試算の確認中に取り直した結果は、**操作が終わるまで画面に当てない**（掴んだバーが消えるとガントと同じくドラッグが壊れる。`GuiDesign.md` 5.14「実装の落とし穴」）。

### 5.9 プラグイン化の見立て（T16）

**今の構成：** client のビルド成果物を Go のバイナリに `embed` し、単一プロセスで配る（`Design.md` 3.4・4.2）。CSP は `script-src 'self'`、`frame-ancestors 'none'`、`X-Frame-Options: DENY`（`ApiDesign.md` 2.12）。認証は Cookie のセッション＋CSRF（`ApiDesign.md` 2.3・2.4）。

**ビューを1つ足すときに触る場所（いま）：** `router/routes.ts`（ルート）・`components/SideMenu.vue`（メニュー）・`lib/ticketViews.ts`（判定）・`pages/TicketViewsPage.vue`（入れ物）・`components/AppShell.vue`（集中モード）・`locales/`（文言）・プロジェクト設定（出す・出さない）の**7か所**。

| 案 | 中身 | 変更範囲（**見積り**） | 危険 |
|---|---|---|---|
| **P1：登録を1か所に集める（切れ目）** | `client/src/views/registry.ts` に、ビューごとの `{ id, パス, メニューの文言とアイコン, 必要権限, 設定キー, 入れ物を使うか, 遅延読み込みの component }` を並べる。上の7か所はこの表を読む。プロジェクト設定の「表示するビュー」も表から作る | 新規1ファイル（約100行）、変更6〜8ファイル（約200〜300行）、e2e の追加（約100行）。**計 8〜10ファイル・400〜500行** | 小さい。**画面の見た目と URL は変えない**ので、既存の e2e がそのまま回帰の確認になる |
| P2：ビルド時のプラグイン | P1 に加え、`client/src/plugins/<名前>/` を置けば `import.meta.glob` で自動で登録される。プラグインが使ってよい部品（API の型・詳細ペイン・権限の判定・時間軸の部品）を「ホストの API」として型で公開し、文書にする | P1 ＋ 15ファイル前後・800〜1,500行（ホストの API の切り出しと文書が大半） | 中。**ホストの API を一度公開すると変えにくい**（互換の約束が生まれる）。足す・外すには**ビルドし直しが要る**ので、利用者が後から足す形にはならない |
| P3：実行時に外部の JS を読む | 管理者がプラグインの束を登録し、画面が動的 `import()` で読み込む。メニューに足す | サーバ：登録・保存・配信・管理画面・監査（2,000〜3,000行）、画面：読み込み・ホストの API の橋渡し・版の照合（1,000〜2,000行）。**計 30ファイル以上・3,000〜5,000行** | **大きい。** 下の表 |

**P3 の危険（同じオリジンで読み込む場合）：**

| 問題 | 中身 |
|---|---|
| 認証 | プラグインの JS は**利用者のセッション Cookie と CSRF トークンをそのまま使える**。プラグインを1つ入れることは、その作者に**全利用者の全権限を渡す**ことに等しい（管理者が開けば管理 API も叩ける） |
| CSP | 同じオリジンから配れば `script-src 'self'` のままで通ってしまう——**CSP が守っていた「自分のコード以外は動かない」が崩れる**。外のオリジンから読むなら CSP を緩める必要がある |
| 隔離する案（iframe） | `sandbox` 付きの iframe に入れ、`postMessage` で絞った API だけを渡す形なら認証の問題は減る。ただし**今は `frame-ancestors 'none'` と `X-Frame-Options: DENY` で自分自身も枠に入れられない**ので、ヘッダの見直しと、プラグイン用の権限を絞ったトークンの発行が要る |
| Vue の共有 | 本体の Vue をプラグインと共有するには import map か外部化が要る。import map はインラインのスクリプトになり、CSP に `'unsafe-inline'` かハッシュが要る |
| 版の互換 | 本体を上げるたびにプラグインが壊れうる。版の照合と、壊れたときに本体を巻き込まない仕組みが要る |

**推奨：今回は P1。** 理由は2つ——①タイムラインを足す作業そのものが7か所に触るので、**同じ手間で登録を1か所に集められる**（後からやると、タイムラインの分も含めて触り直しになる）。②P2・P3 で要る「ビューの一覧を表で持つ」は P1 の表がそのまま土台になり、**P1 は後の選択肢を狭めない**。P2 はガントの種類を選べるようにしたくなった時点で、P3 は「PB の利用者が自分でビューを作って足したい」という要望が実際に出た時点で、**認証の隔離の設計から**始める（8章）。

**P1 で決めておく切れ目：** ①ビューは**公開された REST（`openapi.yaml`）だけ**を使う（内部の型や Pinia のストアに手を入れない）、②ビューの状態は URL のクエリに置く（共有された URL で再現できる）、③メニューに出す・出さないは T5 の `views` で決まり、ビューのコードは知らない。この3つを守っていれば、ビューを P2 のプラグインへ移すときに中身を書き直さずに済む。

## 6. 振り返りの見え方（参考）

**比べる値は3つある。** 当初計画（スナップショット）・いまの予定（`start_at` / `due_at`）・実績（着手は遷移の履歴、完了は `closed_at`）。

| 表示 | 中身 |
|---|---|
| 計画の影 | 当初計画の位置に枠だけの細い影 |
| いまの予定 | 通常のバー |
| 実績 | 完了したバーの上に、実際に始まった時刻から完了した時刻までの細い線 |
| ズレの札 | 開始・終了が当初計画からどれだけずれたか（`+15分` など） |
| 計画外・消えたもの | 確定後に足したチケットの印／計画にあったが消えたチケットの影 |

**どこまで描くかは pb-295 のモックで決める。** 本書では、5.5 の応答がこの3つを1回で返せることだけを決めておく（`baselines[]` と `started_at` を足す理由）。

| MCP に連鎖のずらしを出す（`pb_reschedule_task`） | 5.5 の口をエージェントから使えるようにする。一覧・計画データ（`lighten`・`pb_get_planning_data`）に新しい3列を足す | 今回はエージェントの経路を作らない。エージェントがアンカーを知らずに `PATCH` して `422` を受ける場面が出たら要る |
