# 自律実行（Delegated）設計

**PM が目的と委任範囲を承認し、main エージェントが範囲の内側で完成まで進め、別の評価エージェントが評価する。**
本書はその仕組みの設計の正本である（pb-132）。

| 項目 | 内容 |
|---|---|
| 状態 | **設計（CP1 で確定。2026-10-02）。** 実装は 14章の差分一覧の各チケットで行う。**実装した部分は各設計書（`DbDesign.md` / `ApiDesign.md` / `Design.md` 8章 / `GuiDesign.md`）へ移し、本書から参照する** |
| 方針転換の記録 | `Requirements.md` 10.11 / 10.12、PB の判断の記録「自律実行」 |
| 依存 | 呼び出し方式の実機検証は pb-158。検証が済むまで 10章は「順序だけ確定」である。実装のチケットは 14.2（pb-246〜pb-257） |
| CP1 で決めたこと | 15章の D1〜D7（すべて推奨どおり） |

## 1. 何を変え、何を変えないか

### 1.1 変えること

**人が門番をする単位を、チケットから委任へ移す。** これまでは人がチケットの番号を指定してエージェントを走らせ、
1件ごとに方針を承認し、1件ごとにクローズしてきた（`Requirements.md` 10.2.2、10.8.6）。自律実行では、人は次の3つを持つ。

1. **目的と委任範囲の承認**（何を、どこまで任せるか。計画の中身ではない）
2. **確認待ちへの回答**（止まる条件に当たったとき、後戻りできない操作の前）
3. **最終の受け入れ**（委任の根のチケットの完了）

途中の分解・起票・順序の入れ替え・消化・統合・再計画は main に任せ、**品質は評価エージェントが支える。**

### 1.2 変えないこと

| 原則 | 自律実行での扱い |
|---|---|
| **PB はエージェントのプロセスを起動しない**（pull型。`Requirements.md` 10.2.2） | **維持する。** エージェントが状態変化を知る方法は 10章で選ぶ。Runner は第三候補に留める |
| **段階ごとの可否は API で強制する。プロンプトに頼らない**（`Requirements.md` 10.10.4） | **維持する。** 5章の表が強制の正本である |
| **エージェントから見える面は MCP だけ**（`Design.md` 8章） | 維持する。新しい操作も MCP のツールとして出す |
| **計画を出し、承認を得てから作業に入る**（規約） | **維持する。** 承認の対象を「計画」から「委任範囲」へ上げる（6章） |
| **マージ・push・チケットのクローズは人**（規約） | **根のクローズは人に残す。** 子の完了は 15章 D2 で決める（規約の変更を伴う） |

## 2. 全体像

### 2.1 登場するもの

| 役 | 誰 | PB から見えるもの |
|---|---|---|
| **PM** | 人。委任を作り、委任範囲を承認し、確認待ちに答え、根を受け入れる | 利用者（`app_user`） |
| **main** | エージェント。計画・分解・起票・順序・統合・再計画を行い、全体を管理する | エージェントの principal（`agent`） |
| **評価エージェント** | **main とは別に登録されたエージェント。** 計画・構造の変更・成果を評価する | 別の principal。種類（社）・モデルは問わない |
| **sub** | main の内部のサブエージェント。個々の作業を行う | **見えない。** main のトークンで動くので、PB には main として記録される（9.4） |
| **人の作業者** | 子のチケットの担当として作業する人（例：受験生） | 利用者。通常のチケットと同じ |

### 2.2 2つのループ

```
                     ┌──────────────────── 外のループ（委任範囲）────────────────────┐
                     │                                                              │
   ┌────────┐  ①委任を作る          ┌───────────────────────────┐   ⑧要約・確認待ち  │
   │   PM   │──②委任範囲を承認────▶│            PB              │──────────────────┘
   │  (人)  │◀──────────────────────│ 委任・計画の版・評価記録・  │
   └────────┘  ⑨確認待ちへの回答     │ 確認待ち・引き継ぎノート    │
       │       ⑩根を受け入れる       │ 段階ごとの可否を API で強制 │
       │                            └───────────────────────────┘
       │ 事後の異議                    ▲  │          ▲  │
       │（構造の変更を差し戻す）        │  │④通知 /   │  │④通知 /
       ▼                             │  │ 待ち受け  │  │ 待ち受け
                              ③計画・ │  ▼          │  ▼
                              成果を  ┌──────┐   ⑤評価 ┌────────────┐
                              提出    │ main │        │ 評価エージェ │
                                     │      │        │ ント        │
                                     └──────┘        └────────────┘
                                       │ ▲      ⑥合否と指摘（PB 経由）
                                       ▼ │
                                     ┌──────┐
                                     │ sub  │   main の内部（PB からは見えない）
                                     └──────┘
                     └────────── 内のループ（main ⇄ 評価。合格まで回る）──────────┘
```

- **内のループ**：main が計画・構造の変更・成果を PB に出す（③）→ PB が評価エージェントを呼ぶ（④）→ 評価が合否と指摘を書く（⑤）→
  PB が main を呼ぶ（④）→ 不合格なら main が直して出し直す（③）。**合格するまで回り、往復の上限で外のループへ出る。**
- **外のループ**：PM が委任範囲を承認する（②）→ main が内のループを回す → チェックポイントごとに PB が要約を出す（⑧）→
  止まる条件に当たれば確認待ちで止まる（⑨）→ 最後に PM が根を受け入れる（⑩）。**人を呼ぶ契機は変更ではなく成果である**（6.5）。
- **main と評価は直接話さない。** やり取りはすべて PB の記録を通る。後から「誰が何を根拠に合格させたか」を辿れるようにするためである。

## 3. 用語

| 用語 | 意味 |
|---|---|
| **委任**（delegation） | 根のチケット1件に対して作る。main・評価・委任範囲・状態を持つ |
| **根** | 委任を作ったチケット。目的が書かれている |
| **委任の木** | 根とその子孫。**範囲の中で作られた子孫は委任を引き継ぐ**（4.1） |
| **委任範囲** | PM が事前に承認するもの。目的・指標・自律してよい範囲・予算・止まる条件・報告の周期（4.2） |
| **計画** | main が作るもの。**骨格**（根の直下の枝とその予算配分）と、木の現況からなる（6.2） |
| **評価** | 評価エージェントが計画・変更・成果に付ける合否と指摘（7章） |
| **確認待ち** | PB 上に残る、人への問い。会話ではない（8章） |
| **引き継ぎノート** | 委任ごとに1つ。交代した main が続きから再開するための要約（11章） |

## 4. 委任の器

### 4.1 実行モードの持ち方（D1）

**選択肢**

| 案 | 形 | 得るもの | 失うもの |
|---|---|---|---|
| **A（採用。D1）** | `ticket.execution_mode` に `'delegated'` を足す。**根だけがこの値を持つ。** 委任の中身は `delegation` テーブル（4.4）。子孫かどうかは祖先を辿って決める | 欄が増えない。「このチケットは自律実行か」が1か所で読める。子孫の移動に同期が要らない | 子孫の判定に再帰の問い合わせが要る（木の深さは予算で縛るので重くない） |
| B | 別欄 `ticket.delegation_id` を全子孫に持つ | 判定が1列で済む | 子孫を木の外へ動かしたとき・木の中へ入れたときに同期が要る。同期漏れが権限の穴になる |
| C | `execution_mode` は触らず、`delegation` テーブルだけで表す | スキーマ変更が最小 | 画面とパックが「自律実行か」を知るのに別表を引く。実行モードの一覧から漏れる |

**A を採った。理由は、権限の判定が同期に依らないこと**——B の同期漏れは「範囲の外のチケットをエージェントが動かせる」になる。

**子孫の `execution_mode` は今までどおり持つ。** 根の下で `human_only` の子は人が消化する（例：受験生の演習。13章）。
**委任に属するかどうかと、誰が消化するかは別の軸である。**

**根にできるのは、親を持たないか、親がエピックのチケットである**（pb-282 で PM が判断）。エピックへの所属は親として持つ
（`GuiDesign.md` 5.5「エピック欄」）ので、エピックの直下を除くと、エピックに属するチケットを自律実行にできない。
自律実行の木は根から下だけなので、根の上にエピックがあっても、木の判定（起票の範囲・強制）は変わらない。
**エピック以外の親（子チケット）は根にしない。親のエピックが別の自律実行の木の中にあるときも不可**（木が入れ子になる）。
**直下に根を持つエピックは、種別を変えられない**（根の条件が崩れる）。判定はサーバが行う（委任の作成・根の親の変更・エピックの種別の変更）。

**範囲の中で作られた子孫は委任を引き継ぐ**のは A の帰結である（祖先に根があれば属する）。**委任の木の外へ動かすのは範囲の変更**として扱い、
エージェントには許さない（5章）。

### 4.2 委任範囲の項目

**PM が承認するのはこの表である。計画の中身ではない。**

**`scope` に書くキーは、制約の2つと、指標と要約の周期の2つである**（pb-252 で PM と合意。指標と周期は pb-277）。目的はチケットの説明と完了条件、自律してよい範囲は
チケットのスコープ境界（`ticket.scope`）がそのまま担い、`delegation.scope` に写さない。

| キー | 中身 | 検証 |
|---|---|---|
| `budget` | 数で測れる上限（12.1） | 知らないキー・1未満は 422 |
| `stop_conditions` | 止まる条件。文字列の配列で、複数持てる。**PB は判定しない**——エージェントが読んで守り、当たったら確認待ちを立てて止まる。パックの自律実行の節に載る | 文字列の配列・空の項目なし・20件まで・1件500字まで |
| `metrics` | 指標の定義（成功の測り方）。`{ key, name, unit?, target?, direction }` の配列。**値は PB が測れない**——人（画面）と main（`pb_record_metric`）が入れ、`delegation_metric_value` に追記のみで積む（入れた人を残す）。パックに載る。**PM の判断（2026-10-06）**：定義は承認する制約に置き、変えるのは範囲の変更 | 10件まで・key は `^[a-z0-9_]{1,32}$` で重複なし・name 1〜100字・unit 20字まで・direction は `higher` / `lower` |
| `report_every_days` | 周期の要約の周期（日）。過ぎると PB が checkpoint の確認待ちを立てる（8.3） | 1〜365 の整数 |
| `main_idle_minutes` | main が止まったとみなすまでの分（10.4）。**省略すると30分、0 なら判定しない** | 0〜1440 の整数 |

**指標と周期は pb-277 でキーを持った**（上の表）。チェックポイントを成果で区切る（例：模試の結果が出たとき）のは、まだ骨格の記述に頼る。

| 項目 | 内容 | PB が測れるか |
|---|---|---|
| 目的 | 根の本文。何が達成されたら終わりか | — |
| 成功の測り方（指標） | 指標の名前・現在値・目標・測る周期・誰が入れるか | **値は人またはエージェントが入れる**（13章で外部の値が要ると分かった） |
| 自律してよい範囲 | 触ってよい領域（`scope.allow` / `scope.deny`、タグ）と、機微な領域（8.1 の 4） | 領域はタグとスコープで測る |
| 予算 | コスト（トークン）・期間（期日）・起票数・木の深さ・往復の上限。**期間あたりの上限も持てる**（例：月あたりのトークン。13章）。`scope.budget` に書く（12.1） | トークンは完了レポートの自己申告（12.1） |
| 止まる条件 | 指標の悪化、予算に対する進みの遅れなど。**事象で書く**（「◯◯が起きたとき」） | 指標と予算の値から判定する |
| 報告の周期とチェックポイント | 要約を出す周期（例：週1）と、成果で区切る点（例：模試の結果が出たとき） | 周期は PB が測る。チェックポイントは計画の骨格に載せる |
| main と評価 | どのエージェントか（7.1） | — |

### 4.3 委任の状態

**主状態は4つ**、**関門は3つ**である。関門は主状態に重なる。

```
 計画中 ──(評価の合格 ＋ PM の承認)──▶ 承認済 ──(根の受け入れ)──▶ 終了
   │  ▲                               │  ▲
   │  └───── 範囲の変更の承認 ──────────┘  │ 再開（PM）
   ▼                                  ▼  │
  終了（取り下げ）                      停止（PM、または止まる条件）
```

| 主状態 | 意味 |
|---|---|
| **計画中**（planning） | main が委任範囲の案と計画を出し、評価と PM の承認を待つ。**範囲の変更を出したときもここへ戻る** |
| **承認済**（approved） | 委任範囲の内側で main が自律して進める |
| **停止**（paused） | PM が止めた、または止まる条件・予算の超過で PB が止めた。エージェントの書き込みを受け付けない |
| **終了**（ended） | PM が根を受け入れた、または取り下げた。以後は読むだけ |

| 関門 | 立つとき | 外れるとき |
|---|---|---|
| **評価待ち** | main が計画・構造の変更・成果を出した | 評価エージェントが評価を書いた |
| **差し戻し** | 評価が不合格だった | main が出し直した |
| **確認待ち** | 8章の条件に当たった | PM が答えた |

**関門は列に持たず、開いている評価の依頼・最新の評価・開いている確認待ちから導く。** 列に持つと、評価を書いた・確認に答えた操作と
同じトランザクションで列を直す規則が要り、漏れると「評価は済んだのに評価待ち」が残る。

**受け入れ**：PM が根を完了カテゴリへ遷移すると、それが受け入れである（専用の操作を持たない）。

- **主状態が承認済で、関門の確認待ちが開いていないときだけ通る**（5章の表）。加えて成果の評価が合格していること（7.2）。
  満たさなければ遷移を `403`（`details[].code = "delegation_stage"`）で拒む（`ApiDesign.md` 9.6 の検証8・9）
- **遷移と同じトランザクションで、委任を `ended` にする。** 根の `execution_mode` は `delegated` のまま残す。開いている確認待ち
  （ヒアリングを含む）は `withdrawn` にし、根に `kind=decision` のコメントを残す
- **エージェントへの伝わり方は取り下げと同じ**：コメントで `pb_wait` が変化を返し、`delegation-status` とパックは「終了」を返す
- **受け入れた根を開き直しても、委任は戻らない。** もう一度自律実行にするなら、新しい委任を作る

**取り下げ**（pb-281。PM の判断 2026-10-06）：自律実行ではうまくいかないとき、PM は委任を取り下げて従来の実行モードへ戻せる。

- **計画中・承認済・停止のどれからでも、1回の操作で行える**（停止を挟まない）。取り下げた後は、委任の口（計画・評価・
  確認待ち・引き継ぎノート）が終了として拒む。**木は委任でなくなる**ので、チケットへの通常の書き込みは、従来の実行モードと
  権限のとおりに受け付ける（main だったエージェントも、12.2 の「木の外に起票できない」制約から外れる）
- **1つのトランザクションで、委任を `ended` に、根の `execution_mode` を PM が選んだ従来のモード**（`human_only` / `agent_draft` /
  `agent_only`）**に戻す。** 開いている確認待ちは `withdrawn` にする（答える人がいない問いを画面に残さない）
- **木の中の子チケットは残し、`execution_mode` も変えない**（委任とは別の軸。4.1）。判定を待つ計画の版も消さない（6.2 と同じく履歴）
- **受け入れと取り下げは列で分けない。** 根の `execution_mode` が `delegated` のまま終わったのが受け入れ、従来のモードへ戻ったのが取り下げである。
  根へのコメント（`kind=decision`）にも残す
- **取り下げた根で、もう一度自律実行を始められる。** 新しい委任を作る（前の委任の計画・評価・確認待ちは前の委任に残る）。
  1つの根に**終了していない**委任は1件までである（4.4 の部分一意索引）
- **エージェントへの伝わり方**：取り下げは根に活動とコメントを残すので、`pb_wait` が変化として返す。`delegation-status` とパックは、
  最新の委任が終了した根について「終了」を返す。エージェントは書き込まずに止まり、ローカルの引き継ぎファイル（11.4）を消す

### 4.4 テーブル（D4）

```sql
-- D4 で確定。実装は 14章の pb-246〜pb-250 で、マイグレーションの番号はそのとき振る
CREATE TABLE delegation (
  id                 char(26) COLLATE "C" PRIMARY KEY,
  project_id         char(26) COLLATE "C" NOT NULL REFERENCES project(id) ON DELETE CASCADE,
  root_ticket_id     char(26) COLLATE "C" NOT NULL REFERENCES ticket(id) ON DELETE CASCADE,
                     -- 終了していない委任は根ごとに1件（0058 の部分一意索引。4.3「取り下げ」）
  main_actor_id      char(26) COLLATE "C" NOT NULL REFERENCES agent(actor_id) ON DELETE RESTRICT,
  evaluator_actor_id char(26) COLLATE "C" NOT NULL REFERENCES agent(actor_id) ON DELETE RESTRICT,
  status             text NOT NULL DEFAULT 'planning'
                     CHECK (status IN ('planning','approved','paused','ended')),
  scope              jsonb NOT NULL,     -- 4.2 の委任範囲。承認済みの版の写し
  scope_version      integer NOT NULL DEFAULT 0,  -- 承認された範囲の版。0 は未承認
  created_by         char(26) COLLATE "C" NOT NULL REFERENCES actor(id) ON DELETE RESTRICT,
  created_at         timestamptz NOT NULL DEFAULT now(),
  updated_at         timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT ck_delegation_independent CHECK (main_actor_id <> evaluator_actor_id)
);

CREATE TABLE delegation_plan (          -- 計画の版。前進のみで、差し戻しも新しい版として作る
  id             char(26) COLLATE "C" PRIMARY KEY,
  delegation_id  char(26) COLLATE "C" NOT NULL REFERENCES delegation(id) ON DELETE CASCADE,
  version        integer NOT NULL,
  scope          jsonb NOT NULL,         -- この版が前提とする委任範囲
  skeleton       jsonb NOT NULL,         -- 骨格：根の直下の枝・予算配分・チェックポイント
  body_md        text NOT NULL,          -- 計画の説明
  reason_md      text NOT NULL,          -- 前の版から変えた理由
  declared_class text CHECK (declared_class IN ('minor','structural','scope')),  -- main の申告
  measured_class text CHECK (measured_class IN ('minor','structural','scope')),  -- PB の判定
  status         text NOT NULL DEFAULT 'proposed'
                 CHECK (status IN ('proposed','accepted','rejected','superseded','reverted')),
  reverts_to     integer,                -- 差し戻しで作った版なら、写した元の版
  submitted_by   char(26) COLLATE "C" NOT NULL REFERENCES actor(id) ON DELETE RESTRICT,
  submitted_at   timestamptz NOT NULL DEFAULT now(),
```

## 5. 段階ごとに PB が受け付ける操作

**この表が強制の正本である。** 判定は REST 層で行い、MCP 層に `if` を置かない（`Design.md` 8.1）。
「木」は委任の木（根とその子孫）を指す。木の外のチケットは委任の影響を受けない。

| 操作 | 計画中 | 承認済 | 承認済＋評価待ち（成果） | 承認済＋差し戻し | 確認待ち（どの主状態でも） | 停止 | 終了 |

| 読む（チケット・パック・文書） | 全員 | 全員 | 全員 | 全員 | 全員 | 全員 | 全員 |
| main：計画・範囲の案を出す | **可** | 可（変更として。6.3） | 可 | 可 | **不可** | 不可 | 不可 |
| main：木の中に起票する | **不可** | **可**（予算の内側） | 可 | 可 | **不可** | 不可 | 不可 |
| main：木の中のチケットを直す・並べ替える | 不可 | 可 | 可 | 可 | 不可 | 不可 | 不可 |
| main：木の中のチケットを遷移する（完了を除く） | 不可 | 可 | 可 | 可 | 不可 | 不可 | 不可 |

| 評価：ノートを書く | 可 | 可 | 可 | 可 | 可 | 可 | 不可 |
| 評価：上記以外の書き込み | 不可 | 不可 | 不可 | 不可 | 不可 | 不可 | 不可 |

| PM：前の計画の版へ差し戻す | 可 | 可 | 可 | 可 | 可 | 可 | — |
| PM：根を受け入れる（完了） | 不可 | **成果の評価が合格のときだけ** | 不可 | 不可 | 不可 | 不可 | — |

- **表の「確認待ち」の列は、ヒアリング（8.1 の 8）には当たらない。** ヒアリングが開いていても、関門は立たず、主状態の列のとおりに受け付ける
- **起票は必ず委任の木の中（根の子・孫…）に行う。** 4.1 の「委任を引き継ぐ」は、この制約があって初めて全部の作業を覆う。判定は12.2
- **「計画承認前の起票・完了レポートの拒否」と「評価の合格前は完了させない」が最低限の強制である**（pb-132）。表の太字がそれに当たる
- **「PM：委任範囲を承認・却下する」は、計画中の最新の計画の版に対して行う**（pb-260。`DbDesign.md` 6.25）。承認は、その版が評価に合格した後だけ通る。
  却下は評価を待たずに行え、委任は計画中のまま main の出し直しを待つ。**範囲の変更の版も、評価の合格だけでは反映されない**——提出の時点で委任が計画中へ戻り、PM の承認で承認済へ戻る
- **評価の合格は、根の受け入れの前提条件であって代わりではない。** 根を完了にするのは PM である（`ticket.close`）
- **子のチケットの完了**（D2）：**案 a を採った**——木の中の子は、評価に掛けずに main が `review` 相当まで進め、
  **チェックポイントで PM がまとめて完了にする。** 案 b——子も評価の合格で PB が完了にする。b は「チケットのクローズは人」の規約を変えるので、
  採るなら規約の変更を先に出す。**a でも委任は回る**（人の手間は、子1件ごとではなくチェックポイントごとになる）
  **ワークフローにレビュー相当の状態が無ければ、子は進行中のまま完了レポートを出す。** 一覧の自律実行の印が「報告済み」を出し
  （`ApiDesign.md` 9.2.2 の `reported`）、PM はそれで完了にする子を見分ける
- **拒否の応答は `403 forbidden` に、委任の段階を理由として載せる**（例：「計画が承認されるまで、このチケットの下に起票できません」）。
  `pb_list_transitions` の理由の文と同じ形にし、エージェントが次の一手を読めるようにする（`Design.md` 8.5.3）
- **書き込み可否の判定は「呼び出し元が main か評価か」を `delegation` の列で行う。** `agent.run` や `ticket.*` の権限はその手前で通常どおり効く
  （権限が無ければ委任の段階に関係なく 403）

## 6. 承認の2層と計画の変更

### 6.1 2層

| 層 | 承認する人 | 承認するもの | いつ |
|---|---|---|---|
| **1層目** | **PM** | **委任範囲**（4.2） | 委任の開始時と、範囲の変更のとき |
| **2層目** | **評価エージェント** | **計画の中身**（骨格と、その組み方） | 計画の初版と、構造の変更のとき |

**計画の初版は、評価が先、PM が後である。** main が委任範囲の案と計画の初版を出す → 評価が計画を評価する（範囲の案の妥当性も見る）→
合格したら PM が委任範囲を承認する。**PM が見るのは範囲であり、計画は評価の結果とともに参考として見る。**
PM が範囲を直して承認してもよい（そのときは直した範囲で計画を出し直させる）。

### 6.2 計画の版

- **計画は版で持つ**（`delegation_plan`）。版ごとに「骨格」「説明」「前の版から変えた理由」「変更の段階」を残す
- **骨格**は、根の直下の枝（主な作業の流れ）と、枝ごとの予算配分と、チェックポイントである。**骨格より下の木は main の裁量**で、
  版を出さずに直してよい（6.3 の軽微）
- **PM はいつでも前の版へ差し戻せる。** 差し戻しは前の版を写した**新しい版**として作る（前進のみ。`reverts_to` に元の版）
- **版の一覧と評価記録の一覧は、根で読める**（`GET .../plans`・`.../evaluations`。`ticket.view`。pb-274）。画面の「計画と評価の履歴」が使う
- **差し戻しても、作られたチケットは消さない。** 差し戻しの後、main への次の一手は「骨格に合わないチケットを畳む」になる（9.3）。
  チケットを自動で消すと、人が触った子まで消える

### 6.3 計画の変更の3段階

| 段階 | 例 | 反映の条件 | 人が知る方法 |
|---|---|---|---|
| **軽微** | 順序の入れ替え、骨格の枝の下への小さな追加、説明の手直し | **main の判断で反映する。** 記録は木の履歴に残る | 周期の要約 |
| **構造** | 骨格の枝の追加・中止、予算配分の大きな変更、チェックポイントの移動 | **評価が合格させたら反映する** | 要約で知り、**事後に異議を出して差し戻せる**（6.4） |
| **範囲** | 目的・指標・総予算・自律してよい範囲・main と評価の交代 | **PM の事前承認を要する。** 委任は計画中へ戻る | 確認待ち |

**判定規則（PB が測る）**：版を出すたびに、PB が前の承認済みの版と比べて段階を決める。

| 比べるもの | 段階 |
|---|---|
| 委任範囲（4.2）の項目のどれかが違う | 範囲 |
| 骨格の枝が増えた・減った | 構造 |
| 枝の予算配分のどれかが、総予算の **20%** を超えて動いた | 構造 |
| 機微な領域（8.1 の 4）に触れる枝が増えた | 構造（＋触れる操作は確認待ち） |
| 1つの版で増える子孫が **5件** を超える、または木の深さが増える | 構造 |
| 上のどれにも当たらない | 軽微 |

- **main の申告（`declared_class`）と PB の判定（`measured_class`）の厳しい方を採る**
- **骨格を変えない軽微な変更は、版を出さずにチケットの操作として行える。** その場合も、1回の操作で予算（起票数・深さ）を超えるものは
  PB が拒み、版を出すよう応答で案内する
- **20% と 5件はプロジェクトの設定にする**（`Design.md` 10.3。初期値は上のとおり）。6.5 の記録を材料に調整する
- **評価は分類の妥当性も確かめる**（`class_check`）。評価が「もっと厳しい段階だ」と判定したら、その段階で扱い直す

### 6.4 事後の異議

- **構造の変更は、評価が合格させた時点で反映する。** PM は要約（9.1 の周期）で知る
- **PM は、反映された構造の変更に異議を出せる。** 異議を出すと、その版の前の版を写した新しい版が作られ（6.2 の差し戻し）、
  評価記録に `objected_at` が立つ
- **異議に期限を設けない。** 期限が来ると黙って確定する形は、PM が見ていないことを承認とみなすことになる
- **異議を出せるのは、評価が合格させて PB が反映した構造の変更だけ**（pb-275）。PM が承認した版（初版・範囲の変更）と、
  main の判断で反映された軽微な変更は対象にしない（前の版へ戻すなら 6.2 の差し戻しを使う）。1つの版に異議は1回
- **後に別の版が反映されていれば、差し戻しはせず、異議だけを記録する**（PM の判断 2026-10-06）。後の変更を黙って消さないため。
  どの版へ戻すかは PM が差し戻しで選ぶ。異議は根に `kind=decision` のコメントとして残り、main は `pb_wait` で知る

### 6.5 判定の閾値を調整する材料

**評価エージェントが合格させた構造の変更に、PM が異議を出した割合**を、評価エージェント（とモデル）ごとに記録する。

- 割合が高い → 閾値を締める（構造とみなす範囲を広げ、PM の事前承認へ寄せる）提案を出す
- 割合が低い状態が続く → 閾値を緩める提案を出す
- **提案は PM が採否を決める。** PB は自動で閾値を変えない。これは `Requirements.md` 10.10.3 の信頼度の段階運用を、
  エージェント単体ではなく**組み合わせ**（main と評価）に当てはめたものである

## 7. 評価

### 7.1 指定と独立性の条件

- **評価エージェントは、委任を作るときに PM が指定する。** 範囲の変更として交代もできる
- **条件は、main とは別に登録されたエージェント（別の principal）であること**（`ck_delegation_independent`）
- **種類（社）・モデル・所有者は、同じでも違ってもよい。** 違うほうが望ましい（作った者の見落としを共有しにくい）が、
  条件にすると1社しか使えない参加者が自律実行を使えない。**違いは評価記録に残し、組み合わせごとの質を後から比べる**（7.3）
- **評価エージェントのトークンに要る権限**：プロジェクトの閲覧と、評価を書く権限（D5 の権限キー）。**起票・編集・遷移は要らない**

### 7.2 評価の対象と、合格の意味

| 対象 | 評価の観点 | 合格すると |
|---|---|---|
| 計画の初版 | 目的と指標に照らして骨格が成り立つか、予算に収まるか、委任範囲の案が妥当か、**タスクとゴールの定義が価値観・世界観に沿っているか**、**ヒアリングで目的を掘り下げたか**（PM の書いた目的をそのまま写していないか） | PM の承認待ちになる |
| 構造の変更 | 変更の理由が成り立つか、**分類が妥当か** | 反映される（事後の異議は残る） |
| 成果（根の完了レポート） | **目的と完了条件に照らして**達成しているか。作った側の説明を鵜呑みにしない。**加えて、価値観・世界観にどれだけ寄り添っているか** | PM が根を受け入れられるようになる |

- **評価は観点ごとに書く。** 少なくとも「目的・完了条件」と「価値観・世界観」の2観点を持つ。**合否は観点の判定を合わせて1つ出す**——
  価値観の観点だけが不足する場合も不合格にしてよい。価値観は機械的に照合できないので、どの記述にどう沿う（外れる）かを指摘に書く
- **不合格（`fail`）なら指摘を必ず書く。** 指摘の無い不合格は受け付けない
- **判断できない（`unable`）は確認待ちを立てる**（8.1 の 6）。評価が判断を人へ送る正当な経路として持つ
- **往復の上限**：同じ対象への不合格が委任範囲の上限（初期値 3回）に達したら、確認待ちを立てて止まる
- **成果の評価の対象は、根の最新の完了レポートである。** 評価待ちの間も main は出し直せ、評価されていない古い報告は取り下げ扱いになる
  （評価中の注意に応えた修正を、正式な報告に載せられるようにする）。**取り違えを防ぐため、評価は対象の報告の ID
  （`agent_report_id`）を名指しする。** 最新でなければ `409` で拒み、評価役は新しい報告を読み直す。最新の報告の ID は
  `delegation-status` とパックに載る。名指しは任意で、省くと最新を指す（指示文に従う評価役を止めないため）

### 7.3 評価記録の項目

`evaluation` の各列のとおり。**後から比べるための最小の組は次の6つである。**

| 項目 | 何に使うか |
|---|---|
| 合否と指摘 | 評価の中身 |
| 観点ごとの判定（目的・完了条件／価値観・世界観） | どの観点で落ちやすいかの比較。`findings` の各指摘に観点を付ける |
| 評価者のベンダー（クライアント種別）・モデル・版 | 組み合わせごとの質の比較 |
| main のベンダー・モデル・版 | 同上 |
| 同じ対象への何回目か（`round`） | 往復の回数、上限の判定 |
| PM の事後の異議 | 評価の見落としの率（6.5） |
| 評価に使ったトークン | 評価のコスト |

## 8. 人への確認

### 8.1 確認が要る条件

| # | 条件 | 誰が立てるか |
|---|---|---|
| 1 | **範囲の外への変更**（6.3 の範囲の段階） | PB（版の判定）・main |
| 2 | **後戻りできない操作と外部への作用**：マージ・push・デプロイ・外部への送信・削除 | **main**（PB の外の操作なので、PB は強制できない。9.2 の指示と完了レポートの実行者の内訳で補う） |
| 3 | **憲章の変更** | main（`pb_put_doc` はエージェントのトークンに `doc.edit` を載せなければ PB が拒む） |
| 4 | **プロジェクトが定める機微な領域**への接触（タグ・スコープで定める） | PB（木の中のチケットに機微なタグが付いたとき）・main |
| 5 | **往復・コスト・期間・起票数・深さの上限の超過**、止まる条件への到達 | **PB**（測れるものは PB が立て、主状態を停止にする） |
| 6 | **評価が判断できないとき** | 評価 |
| 7 | チェックポイント（報告の周期ごとの要約の確認） | PB |
| 8 | **ヒアリング**（計画中に、目的・ゴール・制約を掘り下げる問い。何回かに分けて重ねる） | main |

**PB の内側の後戻りできない操作は、PB が拒む。** エージェントはチケットを削除できず（権限）、根を完了にできない（ワークフロー）。
**PB の外の操作（2）は PB からは見えない。** ここは指示と記録に頼る部分であり、強制の代わりは無いと明記しておく。

### 8.2 確認待ちの扱い

- **確認待ちは PB 上の記録として立て、セッションが終わっても残す。** 会話の中の質問にしない
- **確認待ちが開いているあいだ、委任の木への main の書き込みを止める**（5章）。ノートと引き継ぎノートは書ける
- **問いには選択肢と推奨を付ける**（`options`）。規約の「止まるときは選択肢と推奨を出す」と同じ形である
- **画面では、根のチケットとボードに印を出し、PM の通知に載せる**（画面の設計は差分一覧の項目）。印はバックログの行と、
  木の中の子の詳細に出す（pb-276。`GuiDesign.md` 5.4「自律実行の印」。ボード画面はまだ無い）。通知は #105
- **答えると、関門が外れて元の主状態に戻る。** 答えの本文は main のパックの「次の一手」に載る（9.3）
- **ヒアリング（8）は止めない。** 他の確認待ちと違い、答えを待つあいだも main は計画の案を練り、次の問いを立ててよい。
  PB 上に残すのは、問いと答えがセッションを越えて計画の根拠になるからである（11章の引き継ぎノートの「決めたこと」へ入る）
- **PB が立てた確認待ち（5）は、主状態を停止にする。** 答えた後の再開は PM が行う。予算の超過は、答えるだけで続けてよいものではない

### 8.3 周期の要約

**PM は報告の周期ごとに、次の3点の要約を見る。** PB が委任の記録から組み立てる（main に書かせない。書かせると main の自己評価になる）。

1. **計画をどう変えたか**——その周期に作られた版と段階、評価の合否
2. **なぜか**——各版の変えた理由
3. **指標はどう動いたか**——指標の値の推移、予算の消費

**組み立ての口と時機**（pb-277。PM の判断 2026-10-06）

- **`GET .../summary` が期間の要約を返す**（`summary_md` は画面にそのまま出せる Markdown）。期間の既定は、直近の checkpoint の確認待ちから、
  無ければ最初に計画が反映された時刻から、いままで。指標の値は入れた人を添え、エージェントが入れた値を含むときはそう書く
- **PB は定期実行を持たないので、区切りは「読まれたとき」に判定する。** `delegation-status`（画面・パック・main の取り直し）が読まれたとき、
  承認済で、起点から `report_every_days` が過ぎていれば、PB が要約を問いにした checkpoint の確認待ちを立てる。開いている checkpoint は
  委任ごとに1件まで（DB の部分一意索引）。誰も読まなければ立たないが、そのときは誰も動いていない
- **checkpoint は関門を立てる**（ヒアリングと違う）。PM が答えるまで main は木に書き込めない。答えると関門が外れ、次の周期の起点は
  その checkpoint を立てた時刻になる

### 8.4 一時停止の伝わり方

**PM が一時停止すると、根に判断のコメントが残る。** 根で待ち受けているエージェント（`pb_wait`・`pb-wait`）は、それを変化として
その場で受け取る。

- **作業中のエージェントには、MCP の結果に注記を足して知らせる。** main・評価のトークンで MCP のツールを呼ぶと、その委任が
  一時停止中なら、結果に「自律実行（#N）は一時停止中。作業を区切り、ローカルの引き継ぎファイルと PB の引き継ぎノートを書いて
  止まる。再開は PM が行う」の項目が足される（`ApiDesign.md` 2.9.1 の応答ヘッダから組み立てる）。読み取りでも届くので、書き込みで
  拒まれるより先に気づける。先頭の項目には触れない（JSON を置くツールがある）
- **PB に触れない作業の途中は、それが終わるまで気づかない。** MCP の通知ではモデルが起きない（10.2）。その間に止めたいときは、
  利用者がセッションを止める
- **PC を止めるときは、一時停止した後にセッションを閉じてよい。** 再開は同じ一言で続きから始まる（11.4）。チャットで伝えて回らない

## 9. コンテキストパックでの指示

### 9.1 載せ方

- **委任の木のチケットで `pb_get_context` を呼ぶと、パックに「6. 自律実行」の節が自動で載る**（`Design.md` 8.5.5 の5節の後）
- **最新の委任が終了した根では、短い「6. 自律実行」の節だけを載せる**（pb-281）：主状態が終了であることと、main・評価として
  呼ばれたなら書き込まずにローカルの引き継ぎファイルを消して止まること。役割・指示文・vision の全文は載せない（もう委任ではない）
- **役割は呼び出し元と対象のチケットで決める。**

| 呼び出し元 | 対象 | 役割 |
|---|---|---|
| main | 根 | **main** |
| main | 根以外の子孫 | **sub**（main が個々の作業をサブエージェントに渡すと、サブエージェントは子のチケットでパックを取る） |
| 評価 | 木のどれでも | **評価** |
| その他のエージェント | 木のどれでも | **読むだけ**（指示は「この木は自律実行中であり、書き込めない」の1文） |

- **節の中身**：役割と段階に応じた指示文（9.2）、**次の一手**（9.3）、残り予算、開いている評価の指摘、開いている確認待ちと答え、引き継ぎノート（11章）
- **自律実行の節を持つパックには、価値観・世界観（`vision`）を掲載の設定によらず全文で載せる。** main がタスクとゴールを定義し、
  評価が成果を判断する基準そのものだからである（9.2）。掲載しない設定にしてあっても、この節のためには落とさない。
  **`charter_versions` の版が一致しても省かない**（`Design.md` 8.5.5 の省略の例外）。本文は約1,000字と小さく、取り直すたびに基準を確実に手元へ置くほうを取る
- **指示文は PB の文書として持つ**（プロジェクトごとに調整できる）。初期値はテンプレートとして、新しいプロジェクトの文書の木に入れる
  （`DbDesign.md` 8.1.2 の文書テンプレートと同じ置き方）。パスは `delegation-instructions`、見出しは役割と段階の組
- **見出し「共通」は、main と評価のパックに、役割と段階の見出しに加えて載る**（pb-278）。ローカルの引き継ぎファイル・強制停止からの
  再開・止まる条件を守ることは、段階によらず効かせる決まりだからである。sub には載せない（main の内側で動き、手元の状態は main が持つ）
- **指示は強制の代わりではない。** 5章の表が拒むものを、指示で「しないで」と書くのは重ねがけである

### 9.2 初期の文面

**PB の文書テンプレート `delegation-instructions` の本文と同じである**（0055、pb-278 の 0056 で差し替え）。直すときは両方を直す。
**「共通」は、main と評価のパックに、役割と段階の見出しに加えて載る**（9.1）。

**共通**

> **途中で止められても、同じ一言で呼び直せば続きから再開できるように進める。** PM は PB から一時停止でき、ユーザは手元のコンソールからいつでもあなたを止められる。

> - **ローカルの引き継ぎファイル**を、作業ディレクトリ直下の `.pb-local/delegation/pb-<根の番号>-<役割>.md`（役割は `main` か `eval`）に書く。初めて書く前に、`git rev-parse --git-path info/exclude` が返すファイルに `.pb-local/` の行が無ければ足す（`.gitignore` は変えない）。項目は、最終更新時刻・自律実行の状態・直近にしたこと・やりかけのこと（作業中のブランチや worktree、未コミットの変更、未提出の報告や評価）・PB にまだ反映していないこと・次にすること・**最後に受け取った `pb_wait` の `cursor`**。秘密は書かない
> - **書く時機**：計画の提出、評価の提出と受領、完了レポート、確認待ちを立てる前、`pb_wait` に入る前、サブエージェントへ渡す前と戻った後、長い作業の途中（目安30分ごと）。main は同じ区切りで PB の引き継ぎノート（`pb_update_handoff`）も更新する。PB のノートは参加者全員が読む記録、ローカルのファイルは手元の途中状態を強制終了から拾うためのもので、両方書く
> - **呼び直されたら、この順で状況を取り直す**：(1) ローカルの引き継ぎファイルを読む (2) `pb_get_context` で状態・次の一手・**最近の回答**（止められていた間に PM が答えたもの）を読む (3) 食い違えば PB を正とし、ローカルにしか無い途中の作業（未コミットの変更など）を確かめてから続ける。会話の記憶を前提にしない。**待ち受けを再開するときは、残した `cursor` を `pb_wait` の `since` に渡す**（省くと、止めていた間の変化を見逃す）
> - **二重に書かない。** 起票の前に、親の子（`pb_get_task` の children）に同じものが無いかを確かめる。評価の前に、その対象を既に評価していないかを確かめる
> - **止められたら止まる。** 書き込みが 403（`delegation_stage` か `delegation_budget`）で拒まれたとき、`pb_wait` が一時停止を返したときは、ローカルのファイル（main は PB の引き継ぎノートも）を書いて作業を止める。再開は PM が行う
> - **止まる条件**（パックの「止まる条件」）に当たったら、`pb_raise_confirmation` で確認待ちを立てて止まる

**main・計画中**

> あなたはこの自律実行の main である。全体の管理に専念し、個々の作業は使えるならサブエージェントに渡す。いまは計画中である。根のチケットの説明と完了条件（目的）、スコープ境界（触ってよい場所）、制約と止まる条件を読み、範囲の案（`scope` の `budget` と `stop_conditions`）と計画（骨格と、その下の作業の木の案）を `pb_submit_plan` で提出する。**自律実行を指定されるチケットは、PM 自身が内容とゴールを十分に掘り下げられていないことが多い。** 書かれた目的をそのまま受け取らず、計画を定める中で必要に応じて PM にヒアリングし、必要な情報を集める（`pb_raise_confirmation` の `hearing`）。**1回の質問で終わらせない。** 目的・成功の姿・制約・優先・避けたいことなど、多面的な問いを何回かに分けて重ね、答えを受けて次の問いを深める。**タスクとゴールは、プロジェクトの価値観・世界観（憲章の vision）を判断基準にして定義する。** 計画の説明には、どの価値観にどう沿わせたかを書く。**計画が承認されるまで、起票と完了レポートは受け付けられない。** 評価の指摘が返ったら、直して出し直す。

**main・承認済**

> 計画は承認されている。範囲の内側で、サブタスクを起票し、木を組み、順序を調整してよい。**起票は必ず根の子孫として行う**（`parent_seq` に根か、木の中のチケットを渡す）。木の外には起票できない。制約（子チケットの数・階層・期日）を超える起票は PB が拒み、自律実行を一時停止にする。骨格を変えるときは `pb_submit_plan` で版を出す（構造の変更は評価が、範囲の変更は PM が承認する）。各成果は完了レポートで報告する。**根の成果は評価エージェントの合格を得るまで完了しない。** 指摘を受けたら改善して出し直す。完了レポートには、誰が実行したか（あなた自身か、どのサブエージェントか）の内訳を書く。次の条件に当たったら確認待ちを立てて止まる：範囲の外への変更、マージ・push・デプロイ・外部への送信・削除、憲章の変更、機微な領域、止まる条件。

**main・評価待ち**

> 評価を待っている。`pb_wait` で待ち、待つあいだ、成果と関係しない子の作業は進めてよい。評価が出たら、次の一手に従う。

**main・差し戻し**

> 評価が不合格だった。指摘を1件ずつ読み、直したか・直さない理由を書いて出し直す。同じ対象への不合格が上限に達すると、PB が確認待ちを立てて止まる。

**main・確認待ち**

> PM の回答を待っている。木への書き込みは止まっている。回答が来るまで、ノートと引き継ぎノートだけを書ける。`pb_wait` で回答を待つ。

**評価**

> あなたは独立した評価者である。作った側の説明を鵜呑みにせず、目的と完了条件に照らして合否と指摘を書く。**目的とゴールを機械的に照合するだけで終わらせない。** 成果物（計画を含む）がプロジェクトの価値観・世界観（憲章の vision）にどれだけ寄り添っているかも判断基準に置き、観点ごとの判定として書く。目的を満たしていても、価値観から外れていれば指摘する。止まる条件に当たっているのに main が止まっていなければ、それも指摘する。不合格には必ず指摘を付ける。指摘は「何が足りないか」と「どうなれば合格か」を書く。計画の変更を評価するときは、変更の分類（軽微／構造／範囲）が妥当かも確かめる。判断できないときは、判断できない理由を書いて `unable` を返す（人への確認になる）。あなたは起票・編集・遷移を行わない。評価を書いたら、次の対象を `pb_wait` で待つ。

**sub**

> あなたは自律実行の木の中の1件を担当している。このチケットの完了条件だけを満たす。木の構造（起票・並べ替え）と、根の成果の提出は main が行う。範囲の外が要ると分かったら、作業を止めて main に返す。

### 9.3 次の一手

**PB は役割と段階から「次の一手」を1つ返す。** パックの節に載せ、待ち受け（10.2）の応答にも同じものを返す。

| 役割 | 段階 | 次の一手 |
|---|---|---|
| main | 計画中・初版なし・ヒアリングなし | 目的を掘り下げる問いを立てる（ヒアリング） |
| main | 計画中・ヒアリングに答えが付いた | 答えを踏まえて次の問いを立てるか、掘り下げが足りたら計画を提出する |
| main | 差し戻し | 指摘（一覧）を直して出し直す |
| main | 承認済・前の版へ差し戻された | 骨格に合わないチケットを畳み、引き継ぎノートを更新する |
| main | 確認待ちに答えが付いた | 答え（本文）に従って再開する |
| main | 承認済・関門なし | 引き継ぎノートの「次の一手」を続ける |
| 評価 | 評価待ち | 対象（版または完了レポート）を評価する |
| どれでも | 停止・終了 | 何もしない（理由を返す） |

## 10. エージェントの呼び出し

**PB はエージェントのプロセスを起動しない**（1.2）。評価の完了・確認待ちへの回答などを、エージェントが知って動く方法を次の順で確かめて採る。

| 順 | 方式 | 成り立つ条件 | 確かめるチケット |
|---|---|---|---|
| 1 | **MCP の通知**：PB が状態の変化を通知で送り、エージェントがそれを受けて動く | クライアントが通知を受け取り、**待機中でもモデルの発話が始まる** | pb-158 |
| 2 | **待ち受けツール**：エージェントに `pb_wait`（状態の変化か時間切れまで応答を返さない）を繰り返し呼ばせる | クライアントが十分長くツールの応答を待て、繰り返しの消費が予算に収まり、指示で繰り返しを維持できる | pb-158 |
| 3 | **Runner**：端末の常駐プログラム・サーバ側・各社のクラウドでの起動 | 1 と 2 が成り立たないと分かったときに限り検討する | — |

- **確かめるクライアントは Claude Code・Claude Desktop・Codex・VS Code の Copilot である。** 項目は pb-158 の表（通知の受信／待機中の発話の開始／
  ツールの応答を待てる時間／繰り返しの消費／指示による維持）
- **PB は 1 の器を持たない。** プロトコルは公式 SDK に任せた（`Design.md` 8.4 / 8.6。pb-258）が、サーバ発の通知は出さない
  （Stateless。10.2 のとおり、通知はどのクライアントでもモデルを起こさない）。待ち受けの進捗の通知は、SDK の口で応答の SSE に載せられる
- **MCP の通信方式は、着手時点の現行の仕様（Streamable HTTP）で確かめる。** 長く走る処理を扱う仕組みが仕様に入っているかも、そのとき確かめる
  （本書の時点では未確認）
- **2 は「次の一手」（9.3）を返す。** 待ち受けの応答と、パックの節と、通知の中身を同じにする。どの方式で起きても、次にすることは1つに決まる
- **利用枠の時間窓が切り替わったときの再開も、同じ仕組みで扱う。** 再開したエージェントは `pb_get_context`（根）を呼び、次の一手と引き継ぎノートから続ける

### 10.1 MCP 仕様の事実（2026-07-28 版。2026-10-02 に確認）

- **サーバからの通知を受ける口は `subscriptions/listen` だけである。** クライアントが長く開いたままの SSE を張り、受けたい種類を選ぶ。
  選べるのは「ツール・プロンプト・リソースの一覧が変わった」と「**購読したリソース（URI）が更新された**」だけで、独自の通知は無い。
  **PB の状態変化を通知で送るなら、委任を MCP のリソースとして公開し、`notifications/resources/updated` を出す形になる**
- 1つのリクエストの中でだけ流せる通知（進捗 `notifications/progress`）は、そのリクエストの応答ストリームに載る
- 長い処理は公式の拡張 `io.modelcontextprotocol/tasks`（`tasks/get` での問い合わせ）に移った
- **通知を受けたクライアントがモデルを起こすかは、仕様の外である**（クライアントの実装による）

**方式1（通知でモデルを起こす）は、確かめた3つ（Claude Code・Claude Desktop・Codex）のどれでも成り立たない。** Claude の2つは通知を受けるが一覧を取り直すだけで、Codex は通知のストリームを張らない。Copilot は待機中の確認ができていない。

**方式2（待ち受け）は4つとも成り立つ**。違いは1回の待ち受けの長さである。

- **呼び出しに `progressToken` が付く**（Claude Code）なら、進捗の通知を流しながら長く待てる。消費は回数に比例するので、長いほどよい
- **付かない**（Claude Desktop）なら、60秒より短く切って繰り返すしかない。打ち切りのエラーを出すと、モデルが繰り返しをやめる

**したがって `pb_wait` は、待つ長さを PB が決める。** `progressToken` があれば進捗の通知を流して長く待ち、無ければ50秒で返す。
**Copilot は `progressToken` を付けるが、進捗の通知で上限（約5分）が延びるかは確かめていない。** 確かめるまでは、進捗の通知を流しつつ1回を4分で切る。
エージェントへの指示は「`pb_wait` を、次の一手が返るまで繰り返す」の1つで済み、クライアントごとに書き分けない。

**採用する方式は方式2（待ち受けツール `pb_wait`）である**（pb-158、2026-10-03）。**`pb_wait` は実装した**（`Design.md` 8.5.6）。いまは1件のチケットの変化を待ち、委任の木全体と「次の一手」（9.3）は pb-250 で足す。方式1は、クライアントが通知でモデルを起こすようになったら再検討する（事象：いずれかの主要クライアントが、待機中に通知を受けて発話を始めたとき）。方式3（Runner）は検討しない。
通し試験（pb-256）では、main に `pb_wait` で根のチケットを待たせる。

### 10.3 待ち受けをモデルの外へ出す（`pb-wait`）

**`pb_wait` は、変化が無くても50秒か4分で返り、そのたびにモデルが1ターン動いて消費する**（約19時間の自律実行で、評価役だけで
数百回）。**待ち受けをモデルの外の小さな実行ファイル `pb-wait` に任せる。** `pb-wait` は自分で PB の MCP へ `pb_wait` を
繰り返し送り、変化があったら最後の応答（`pb_wait` と同じ JSON）を書いて終わる。

- **エージェントの MCP の接続とは別に動く。** 要るのは実行ファイル・PB の MCP の URL・トークンの環境変数（自己署名なら CA の
  ファイル）だけで、中継（`pb-mcp-bridge`）を使わない接続でも使える。PB の MCP は状態を持たないので、`initialize` を挟まない
- **引数**：`--url` / `--token-env`（既定 `PB_TOKEN`）/ `--ca-file` / `--seq`（根）/ `--since`（前の `cursor`）/ `--max`（既定60分）。
  **終了コード**：0＝変化があった、2＝`--max` まで変化が無かった（最後の `cursor` を書く）、3＝評価役が待つ間に main が止まって
  いた（10.4）、1＝失敗
- **Claude Code はバックグラウンドで走らせる。** バックグラウンドのコマンドが終わるとモデルが起こされるので、**待つ間はトークンを
  使わない**（実機で確認：変化の直後に終了し、セッションが起こされた）
- **Codex は前で走らせる**（コマンドの実行中はターンが進まない）。シェルのコマンドを何分まで待てるかは実機未確認で、`--max 9m` から
  始める
- **使えないとき**（実行ファイルが無い・失敗した）は、これまでどおり `pb_wait` で待つ
- **作り方と置き場**：`deploy/build-bridges.sh` が中継と並べて5つの環境向けに作る（`make build` の `bin/bridges/`、stg の
  `deploy/stg/out/bridges/`）。接続設定の ZIP への同梱は別に定める

### 10.4 main が止まったら、評価役の待ち受けを止める

**利用枠の上限などで main が止まると、評価役は来ない成果を待ち続けて消費する。** PB は main が止まったことを見て、評価役に知らせる。

- **判定**：main のトークンが PB へ最後に要求を送った時刻（`access_token.last_used_at`）から、委任範囲の `main_idle_minutes`
  （省略で30分、0 で判定しない）が過ぎたら「止まっている」とみなす。委任が承認済か計画中のときだけ判定する（停止・終了は対象外）
- **伝え方**：評価役が待ち受けたとき（`pb_wait`）に main が止まっていれば、待たずに `main_stopped: true` と、止まる指示の `next` を
  返す。`pb-wait` は終了コード 3 で終わる。評価役はローカルのファイルを書いて止まる。`delegation-status` は `main_last_seen_at` と
  `main_stopped` を返し、画面とパックは「main が N 分動いていない」と出す
- **再開**：利用枠が戻ったら、利用者が main と評価役をそれぞれ同じ一言で呼び直す（11.4）
- **誤判定を減らす**：main は、PB に何も送らずに長くかかる作業（目安20分以上）の途中で、ノートを1件書く
- **限界**：main が `pb-wait` をバックグラウンドで走らせたまま止まると、その `--max` まで要求が続くので動いていると見える。その間、
  main は何かを待っており、評価役は待ち受けていない

## 11. 長時間の処理と引き継ぎ

**状態を会話ではなく PB に置く。** コンテキストの圧縮に頼らない——圧縮は情報を落とし、クラッシュとベンダーの交代に効かない。

### 11.1 引き継ぎノートの項目

| 項目 | 内容 |
|---|---|
| 目的と現在の計画の版 | 根の目的の1行と、承認済みの計画の版番号 |
| 決めたこと | この委任の中で決めたこと（理由は版とノートにある。ここは見出しだけ） |
| 未決事項 | 決めていないことと、誰の判断を待っているか |
| 進行中の作業 | 木の中で進行中のチケットと、誰が（main・sub・人）持っているか |
| 次の一手 | 再開した main が最初にすること。1つ |
| 予算の消費 | 総予算に対する消費と、周期あたりの消費 |
| 直近の評価 | 最新の評価の合否と、未解決の指摘 |

### 11.2 更新の区切り

1. 計画の版を提出したとき・承認されたとき
2. 評価を受け取ったとき
3. 完了レポートを出したとき
4. 確認待ちを立てる前
5. **セッションを終える前**（利用枠の時間窓の終わりを含む）

**区切り 1〜3 は PB が呼び出しの応答で更新を促す。** 5 は PB から見えないので、指示（9.2）で頼る。

### 11.3 main の交代と再開

- **main は特定のセッションに縛らない。** 同じ principal のまま新しいセッションで再開するなら、`pb_get_context`（根）を呼べば足りる。
  パックに引き継ぎノートと次の一手が載る
- **別の principal（別のエージェント・別のベンダー）に交代するのは範囲の変更**である（6.3）。PM が承認すると `main_actor_id` が変わる。
  交代した main も同じパックから始める
- **交代の前に、前の main の進行中のチケットの `working_agent_id` は残す。** 誰が触っていたかの記録であり、新しい main が遷移すれば上書きされる

### 11.4 ローカルの引き継ぎファイルと、強制停止からの再開（pb-278）

**エージェントはいつ止められてもよい。** PM は PB から一時停止でき、ユーザは手元のコンソールからエージェントを止められる
（応答が長く返らないと、ユーザはセッションを強制的に終えることがある）。**同じ一言で呼び直せば、続きから再開できるようにする。**

| | PB の引き継ぎノート（11.1） | ローカルの引き継ぎファイル |
|---|---|---|
| 置き場 | PB（`delegation_handoff`） | 作業ディレクトリ直下の `.pb-local/delegation/pb-<根の番号>-<役割>.md`（`main` / `eval`） |
| 読み手 | 参加者全員（交代した main も） | そのエージェント自身（呼び直された後） |
| 中身 | 計画・決めたこと・未決事項・次の一手 | 状態・直近にしたこと・やりかけのこと（ブランチ・worktree・未コミットの変更・未提出の報告や評価）・PB に未反映のこと・次にすること |
| 書く人 | main | main と評価 |

- **git の管理外にする。** `.gitignore` は変えず、`git rev-parse --git-path info/exclude` が返すファイルに `.pb-local/` を足す。
  クローンごとの設定で、コミットが要らず、worktree でも効く。**秘密は書かない**
- **書く時機**：11.2 の区切りに加えて、`pb_wait` に入る前、サブエージェントへ渡す前と戻った後、長い作業の途中（目安30分ごと）
- **呼び直されたら**：ローカルのファイル → `pb_get_context` の順に読み、食い違えば PB を正とする。会話の記憶を前提にしない。
  **パックの「最近の回答」**（回答済みの確認待ちの答え。新しい順に5件。main だけに載る）で、止められていた間に PM が答えたものを読む。
  待ち受けを再開するときは、ローカルのファイルに残した最後の `cursor` を `pb_wait` の `since` に渡す
  （pb-278 の確認で、`since` を省いて呼び直した main が、止めていた間の回答を取りこぼして同じ問いを重ねた）
- **二重に書かない**：起票の前に親の子を、評価の前に評価済みかを確かめる（強制終了の直前の書き込みが通っていることがある。冪等キーは #257）
- **PB に止められたら**（403 の `delegation_stage` / `delegation_budget`、`pb_wait` が一時停止を返す）：ファイルとノートを書いて止まる
- **終了したら**（PM が根を受け入れた、または取り下げた。4.3）：PB に書き込まず、ローカルのファイルを消して止まる。
  同じ根で自律実行が始め直されたとき、前の委任のやりかけを続きと取り違えないため
- **起動の一言は、最初も呼び直しも同じ**：Claude Code は `/pb-delegate-main <番号>` / `/pb-delegate-eval <番号>`、
  他の種類は一文（画面の「エージェントの呼び方」。GuiDesign.md 5.5）

## 12. 予算・起票元・リース

### 12.1 予算の測り方

| 予算 | 測る材料 | 正確さ |
|---|---|---|
| コスト（トークン） | 完了レポートの `cost.tokens` と評価の `tokens_used` の和 | **自己申告**。測れない値は空欄になり、合計から漏れる。漏れた件数を要約に出す |
| 期間 | 委任範囲の期日と現在 | PB が測れる |
| 起票数 | 木の子孫の数 | PB が測れる |
| 木の深さ | 根からの段数 | PB が測れる |
| 往復 | 同じ対象への不合格の回数 | PB が測れる |

**予算の超過は、サーキットブレーカー（`Requirements.md` 10.10.5）の委任版である。** 超えたら PB が確認待ちを立て、主状態を停止にする（8.2）。
**`agent_run.retry_count` を使うブレーカー（#172）とは器を共有しない**（pb-253）。#172 は実行1件の失敗の回数、こちらは委任全体の累計で、
測る単位が違う。共有するのは確認待ちを立てる処理だけである。

**予算は委任範囲の `budget` に書く**（pb-253）。どの項目も省略でき、省略した項目は上限を持たない。**知らないキーは拒む**——綴りを誤った上限が
黙って「上限なし」になるのを防ぐ。

| キー | 上限 | 超えたとき |
|---|---|---|
| `tokens` | トークンの総予算 | 完了レポート・評価を**受け付けてから**停止する（報告の後にしか分からない） |
| `tokens_per_month` | 暦月（プロジェクトのタイムゾーン）あたりのトークン | 同上 |
| `due_on` | 期日（`YYYY-MM-DD`）。この日を過ぎたら止める | main の起票・完了レポートを**拒んで**停止する |
| `tickets` | 木の子孫の数（根を含まない） | **超える起票を拒んで**停止する |
| `depth` | 根からの段数（根は0、根の子は1） | 同上 |
| `rounds` | 同じ対象への不合格の往復（省略時は3） | 評価を受け付けて停止する（7.2） |

- **測るのは、数が増える書き込みのその場である**（定期実行を持たない）。期日だけは時間で過ぎるので、main が次に書き込んだときに気づく
- **トークンは、委任を作った後の木の中の実行記録と、評価の和である。** 申告の無い件数を `delegation-status` とパックに出す
- **対話型で動かすエージェントは、自分のトークン数を申告できない。** Claude Code・Codex とも、対話中のモデルが自分の累計を読む口を
  持たない（Claude Code のステータスラインに来るのは累計の費用と、いまのコンテキストの量。累計のトークン数は OpenTelemetry を
  有効にしたときだけ外へ出る。Codex は非対話の `codex exec --json` の `turn.completed` だけが出す）。セッションのログを読めば
  数えられるが、利用者の判断で読まない。**このため全件が欠測でも手順の誤りではない。** 画面は全件が欠測のとき合計の「0」を出さず、
  「申告なし」と出す（`GuiDesign.md` 5.5）
- **停止は、拒んだ書き込みと同じトランザクションで確定させる。** 403 が返ったのに委任が止まっていない状態を作らない
- **再開は PM が行い、確認待ちに答えた後だけ受け付ける**（8.2）。**再開のときに予算を直せる**——停止中は main が範囲の変更を出せないので、
  PM が予算を直す口はここにしかない。直したら範囲の版（`scope_version`）を進め、直前の承認済みの計画の版を写して範囲だけ差し替えた版を、
  PM の承認済みとして作る。作らないと、main が次に出す版が「範囲が違う」と判定されて委任が計画中へ戻る。計画中の委任の予算は、
  計画の却下と出し直しで直す

### 12.2 起票元

- **エージェントが起票したチケットには、起票元が残る。** いまも `ticket.reporter_id` にエージェントの actor が入る
- **委任の木で起票したチケットには、どの委任のどの計画の版の下で作られたかも残す**（監査の記録に委任と版を載せる）。
  エージェントの起票が別のエージェントへの指示になる連鎖（`Requirements.md` 10.10.6）を、後から辿れるようにする
- **委任の木の外への起票は、main にも許さない**（5章）。連鎖が木の外へ漏れる経路を作らない
- **判定**：委任が終了していないあいだ、その委任の main に指定されたエージェントが `pb_create_ticket` を呼ぶと、PB は `parent_seq` を必須とし、
  親がその委任の木の中にあることを確かめる。親を省いた・木の外を指したら `403` で拒み、「自律実行の main は、根（#<seq>）の子孫としてしか起票できません」と返す
- **その代わり、main に指定したエージェントは、委任の外の仕事に同じ principal を使えない。** 委任ごとに専用のエージェントを登録して main にするのを勧める
  （画面で指定するときに案内する）。PB が「この呼び出しはどの委任のためか」を知る口を持たないためである
- **計画の骨格の枝も、根の直下の子として起票する。** 骨格をエピックや木の外のチケットで表さない

### 12.3 リースの再検討条件（`Requirements.md` 10.3.3）

10.3.3 は「自律取得を実装するとき」をリースの再検討の条件に置いている。**自律実行は、委任の木の中で main がチケットを自律的に選ぶので、この条件に当たる。**

**判定：委任の中では、まだリースは要らない。**

- **1つの委任に main は1つである。** 木の中で何を誰に渡すかを決めるのは main だけで、sub は main の principal で動く。
  **排他は main の内部の問題であり、PB が錠を持つ必要が無い**
- 可視性は、いまの `working_agent_id` と、引き継ぎノートの「進行中の作業」で足りる
- 詰まりは、委任の停止と main の交代（11.3）で解ける

**再検討の条件を、消化を複数ベンダーのエージェントに配る段階（2.1 の「次の段階」）へ移す。** そのときは同じ木の中に複数の principal が書き込むので、

## 13. 机上検証：大学受験の例

**目的**：「2027年2月の X 大学の入試に合格する」。PM は受験生本人（または保護者）、main と評価はエージェント。

### 13.1 当てはめ

| 段階 | 起きること | 本書のどこで扱うか |
|---|---|---|
| 委任を作る | PM が根を書き、main と評価を指定する。指標は「模試の判定」「過去問の得点率」、予算は「月あたりのトークン」「起票数 300」「深さ 4」、止まる条件は「模試の判定が2回続けて下がったとき」「計画より2週間遅れたとき」、報告は週1、チェックポイントは模試の結果が出たとき | 4.2 |
| 計画中 | **main がヒアリングを重ねる**——「合格の先に何をしたいか」「得意・苦手の自己認識」「1日に使える時間」「やりたくない勉強法」を何回かに分けて問い、目的を「X 大学の Y 学部に、部活を続けながら合格する」まで掘り下げる。価値観（チャレンジする若者の成長を支える）に照らし、合格だけでなく学び方が身につく計画にする。次に骨格（情報収集／現状の測定／カリキュラム／演習と復習／模試）と予算配分を出す。評価が「測定の前にカリキュラムを固めている」と指摘し、不合格 → main が順序を直して出し直し、合格 → PM が範囲を承認する | 6.1、7.2 |
| 承認済 | main が「数学Ⅲの微積の演習」などを起票する。**消化するのは受験生**（人）で、`execution_mode = human_only` の子として並ぶ | 4.1 |
| 毎週 | 演習の記録が子のチケットに付き、main が順序を入れ替える（軽微）。PB が週の要約を出す | 6.3、8.3 |

| 合格 | main が成果を提出し、評価が合格させ、PM が根を受け入れる | 5章 |

### 13.2 破綻しかけたところと、直したこと

| # | 見つかったこと | 直したこと |
|---|---|---|
| 1 | **消化するのは人である。** 「自律実行＝エージェントが消化する」と読むと、受験生の演習が木に入らない | 委任に属するかと誰が消化するかを別の軸にした（4.1）。委任は**管理の委任**であり、消化の委任ではない |
| 2 | **期間が数か月に及ぶ。** トークンの総予算だけだと、序盤で使い切る・終盤まで気づかない | 予算に**期間あたりの上限**を持てるようにした（4.2） |
| 3 | **指標の値は外から来る**（模試の結果）。PB もエージェントも測れない | 指標に「誰が入れるか」を持たせた（4.2）。入力が途切れたら要約に出す |
| 4 | **セッションは何百回も替わる。** 会話に状態を置くと持たない | 引き継ぎノートと次の一手（11章、9.3）。これが無いと破綻する |
| 5 | **機微な情報**（成績・個人の事情）を扱う | 機微な領域をプロジェクトが定め、触れると確認待ちにする（8.1 の 4） |
| 6 | **組み直しすぎる懸念**。模試のたびに骨格を変えると、計画が定まらない | 再計画はチェックポイント（模試の後）で行う、を指示に書く。PB は構造の変更の頻度を要約に出す |

**判定：上の6点を直せば、設計は破綻しない。** 1 と 4 は直さなければ成り立たなかった。

### 担当割当の管理範囲

担当・実行者を変更できるエージェントは、承認済みで書込可能な委任のmainに限る。変更先は自分の管理する木内とし、確認待ち、評価エージェント、別main、木外への変更を拒否する。子作成時の担当指定にも同じ規則を適用する。通常の権限とプロジェクト所属の検証も必要である。
