# 試験の設計と完了の基準

**何をどこまで検証したら「終わった」と言えるか**を定める。
**実行手順は書かない**——コマンドとツールの使い方は `Development.md` 6章（テスト）と
8章（画面の動作確認）にある。

## 1. 4つの層と使い分け

| 層 | 相手 | 出せるもの | 出せないもの |
|---|---|---|---|
| 単体 | フェイク | 分岐・境界・エラーの形 | 書いた人の想定の外 |
| 結合（`make test-db`） | 実DB | SQL・制約・トランザクション | 書いた人が作ったデータの外 |
| 実サーバ | 起動したプロセス | ルーティング・認証・ミドルウェアの順序 | 描画 |
| ブラウザ（CDP） | 実画面 | 見えるか・操作できるか・組み方 | 大量の組み合わせ |

**層を1つ増やすたびに、前の層が返せない値が現れる。**
実サーバ検証とブラウザ検証は「通し確認」ではなく**別の層のバグ取り**である。
例えば、単体も結合も「優先度を持つチケット」しか作っていなければ、優先度が未設定のチケットで
一覧が 500 になることは実サーバで初めて出る。**拾ったら、その値を下の層の検証にも足す。**

**フェイク（`fake_test.go`）は `gen.Querier` を埋め込んでいるので、未実装のメソッドが
コンパイルを通る。** 呼ばれた瞬間に nil ポインタで panic し、**症状は**「自分が触っていない
既存のテストが落ちる」になるため、原因が遠くに見える。**クエリを1本足したら、
そのクエリを通る既存の経路を数えてフェイクにも足す。**

## 2. 完了と言える基準

- `make test` が PASS し、**件数を前回と比べて増分が説明できる**こと。
  `--- PASS` の総数と `t.Run` の総数は数え方が違うので、**比べるときは同じ数え方を使う**
- 作業の完了条件を**1件ずつ名指しで**満たすこと
- 画面を作ったなら、**スクリーンショットを自分で見た**こと（§6）
- **負の側を1件は測る**こと。権限・入力検証・未定義の入口は、通る側だけでは効いている証拠にならない
- 検証で作った資源を**片付け、片付いたことを測った**こと（§7）

## 3. 期待値の作り方

- **期待値は「対象を数え上げてから」書く。** 並び順なら ①条件に合う行を列挙 ②規則で並べ替え
  ③同値の tie-break まで、紙の上で作る。目で拾うと条件に合わない行が混ざる
- **より良いのは、決め打ちを置かずに DB から読んだ実測値と突き合わせる形にすること**
- **期待値はロール名ではなく実効権限から組み立てる。** 「viewer だから書けないはず」は推論であり、
  権限カタログ（`Design.md` 6.4.2）を引けば事実になる
- **出力を数える前に、その数を決めているものを読む。** `make` の変数は既定値を持つ
  （`RUN ?= Integration`）ので、件数が想定と違うときはコマンドの定義を先に見る
- **「変わったか」を測る前に、測る値の精度を確かめる。** `updated_at` は秒精度で出るので、
  同じ秒に更新すると文字列が変わらない（ETag は `UnixNano` なので実際は変わっている）。
  **秒精度の値で「変わったか」を測るなら1秒待つ**か、**要件が名指ししているものを直接突き合わせる**
- **「無いこと」を測る検査は、あるはずの値を先に入れてから書く。**
  固定データが元から空だと、`Contains` の否定は**何を実装しても通る**。
  **否定の検査を書いたら、逆側を1回作って落ちることを見る**
- **時刻の境界を手で書かない**——`now() - interval` か、実行前に控えた値を使う
- **「◯◯でない」を測るなら、その状態が本当に作れているかを先に確かめる。**
  例えば「未接続」を測るのに、トークンを発行していないエージェントを使うと、
  そもそも接続確認が表示されないので、別の状態を測ってしまう。**否定の状態にも前提がある**
- **仕様を直したら、その場で期待値も直す。** 直後の再実行で出る FAIL は**実装の欠陥ではなく
  期待値の陳腐化**であり、混ぜると「直したのに落ちた」と読んで元へ戻しかねない。
  **FAIL を見たら、まず「仕様と期待値のどちらが新しいか」を言う。**
- **前提に使う文書の表が「どこから来た値か」を1行言えないなら、実物を1回引く。**
  `Development.md` 4.1 のデモアカウント表は YAML の写しであって DB の実測ではない

## 4. 検証が落ちたときの切り分け

- **実装側と検証側をフラットに疑う。** 「まず検証側を疑う」を規約にすると**通すための検証**になる。
  切り分けは順番ではなく方法で行う——**何を測っているかを設計文書の例と突き合わせ**、
  つかなければ両方に当たる最小の再現を作る
- **判定材料は「その検証は、実装を全部消しても落ちるか」**
- **落ちた件数が多いときほど、まず1つ目の原因を見る**——連鎖しているだけのことがある
- **`make test` が落ちたら、まず `git worktree add <tmp> develop` で `develop` でも落ちるかを見る。**
  stash より安全で（未追跡ファイルを巻き込まない）、作業ツリーを触らずに済む。
  **「たぶん元から壊れている」で片付けない。起票済みの既知の失敗でも、
  自分の変更と無関係であることは毎回確かめる**
- **当たらない検査を見たら、まず出力が生きているかを確かめる。**
  共有の出力ファイルを使い回すと「見る前に消えていた」が起きる。症状は `ERR` や空で、
  「見ているものが違う」と区別がつかない
- **「当たらない」ときは受け側を、「効かない」ときは送り側を数える。
  全部落ちるときは、そもそも相手が居るかを1回測る**（`health` を1回引けば分かる）

## 5. 検証スクリプトを書くときの規則

- **検査を書いたら、壊れた入力の前に「正しい入力」を1件通す。**
  偽陽性の側を測って初めて、当たり判定が仕様と合っていると言える。
  **規則を検査に落とすときは適用範囲を1行書く**（「日本語を1行に収める」の対象は
  `GuiDesign.md` 6.6 が定める**画面に出す文字列**であって、手で折り返す設計文書ではない）。
  **強調の閉じ忘れを数えるなら、対象はコードスパンとコードブロックの外**——
  `` `**` `` を書いた行を偽陽性で拾う。**数える単位は段落にする**——行単位で描画すると、
  2行にまたがる強調がすべて偽陽性になる
- **検査を書き終えたら「この行は落ちうるか」を1件ずつ読み返す。**
  `or True` / `assert True` / 比較の無い `check(name, x)` は通すための検証である
- **セレクタは「何に当たるか」を数えてから使う。** 部分一致でボタンやテキストを選ばず、
  `button[form=…]` のように役割で名指しする。`:nth-of-type` は「同じタグの中での順番」なので、
  兄弟のタグが揃っていない箇所では `:nth-child` を使う。
  **当たる先が多いのは検証側だけの問題ではない**——`scoped` スタイルは DOM のクラス名を
  分けないので、**実装側の名前も具体的にする**（`GuiDesign.md` 6.6）
- **既存の API を叩くときは、応答の形を実装か設計文書で先に1回引く。**
  **自分が実装した章ほど引かない**ので、そこでこそ開く
- **共有の出力先を持つ検証は、「呼ぶ」と「読む」の間に何も挟まない。**
  読む値ごとに別ファイルへ落とす
- **HTTP ヘッダは大小を区別せずに引く**（Go は `w.Header().Set("ETag", …)` を `Etag` で書き出す）
- **合否を出すコマンドをパイプへ繋がない。** `cmd -q 2>&1 | head` の `$?` は `head` のもので、
  **本体が落ちても必ず 0 になる**。判定は単体で走らせ、その直後に `$?` を読む
  （繋ぐなら `set -o pipefail` か `${PIPESTATUS[0]}`）
- **シェルで変数の直後に日本語が続くときは必ず `${VAR}`**（`"$BEFORE（…"` は変数名を切り損ねる）
- **長く生かすプロセスと、それを待つコマンドを同じシェルに入れない。**
  `nohup … &` で切り離してから、別のコマンドで待つ
- **「秘密が環境変数にも引数にも出ない」を測るなら、相手を止めてプロセスを生かしたまま読む。**
  DB のコンテナを `docker pause` すると、クライアントは接続待ちで止まる。その間に
  `ps eww -o command= -p <PID>`（mac）か `/proc/<PID>/environ`・`cmdline`（linux）を読む。
  **渡したはずの秘密でない値**（`PGPASSFILE=` や接続先）が見えることを陽性対照にする——
  見えなければ、読んでいるのは終わったあとのプロセスである
- **検査器の対照には、その検査器が実際に落とすと確かめた壊し方を使う。**
  例えば bash 3.2 の `bash -n` は、閉じない配列（`args=(`）を通してしまう。
  落ちると確かめてある壊し方（`fi` の無い `if` など）を対照にする
- **否定の検査は、目当ての条件より先に落ちる別の条件が無いかを見る。** 例えば compose で
  「秘密が無いと止まる」を測るつもりが、イメージを取り込む前だとイメージの取得で先に落ちる。
  **前提を満たしてから、目当ての1つだけを欠く**（§3 の「否定の状態にも前提がある」）
- **Secret を使う検証では、Pod の定義だけでなく Secret 自身も数える。** `kubectl apply` は `stringData` を
  注釈 `last-applied-configuration` に平文で残す——`kubectl describe` には出ず、`-o yaml` に出る。
  値をシェルの変数に読んで `grep -c -F` で数え、**`kubectl create` で入れた対照が 0 件になる**ことを見る

## 6. 画面の検証

- **「要素が存在するか」ではなく「見えて操作できるか」を確かめる。** 実際に遷移して見る。
  位置とサイズを実測する（`getBoundingClientRect()`）
- **スクリーンショットを必ず自分で見る。** 実測は「入るか」しか、検査は「在るか」しか答えない。
  **「変に見えないか」「全部見えているか」「並びが仕様どおりか」は別の確認**である。
  **複数の幅で撮る**（1440px と狭い窓）。自動検証が全 PASS のまま崩れる典型は、
  余白の偏り／ラジオの縦積み／狭い窓で列幅0／日本語の折り返しに空白／
  横スクロールの箱に収まって末尾が見えない／隣の欄と組み方が違う、である
- **「並ぶか」と「読めるか」は別の検査である。** 件数と表題で測れてしまう一覧・ツリー・カードほど、
  中身の検査が抜ける
- **`getBoundingClientRect()` の幅・高さが 0 でないことは「見えている」ではない。**
  親に `overflow` があると、はみ出した要素は**幅を持ったまま**見えなくなる。
  **親の矩形に収まっているかを比べる**（`r.right <= parent.right`）
- **新しい入力欄を足したら、隣の欄と並べて撮る。**
  崩れは「同じ画面の他の欄と組み方が違う」という形で出るので、単体で見ても気づけない
- **入力の検証は、アプリのハンドラではなく「ブラウザの機構」を通す。**
  D&D は `Input.setInterceptDrags` ＋ 実マウス、フォーカスやキーは実キーイベント。
  **「イベントを作って投げる」と「操作する」は別物**で、前者は自分が想定した経路しか通らない
  （合成した `DragEvent` では全件通っても、実際の操作では行が掴めないことがある）
- **文章を組み立てて返す成果物は、見出しの木を出力して確かめる。**
  文字列の一致だけを測ると**構造の壊れは1件も検知できない**——例えばコンテキストパックは
  `## 1.`〜`## 5.` の5節を持つが、埋め込んだ憲章の本文も `##` で始まる。
  行頭の `#` を数えて字下げして出せば、木の形が一目で分かる
- **多段の操作は、1段目の成立を独立した1件にする。**
  「掴めるか」だけを先に測っておくと、後で目印が出なかったときに線を1本外せる。
  **あわせて「起きないはずの側」を同じ道具で1回測る**と、検知そのものが効いている証拠になる

## 7. 状態を変える検証とあとしまつ

- **検査より先に「戻し方」を関数にして、冒頭で呼ぶ。**
  意志で守ると書き捨ての probe で漏れる。関数にすれば呼び忘れが1行で見える
- **関数にすること自体は正しさを保証しない。**
  「作ったものを消す」だけでなく、**「変えた列を戻す」を数える**（`actor.is_active` のような
  状態の列を戻し忘れると、他の結合テストを落とす）
- **現在値は毎回読み直す。** 前の手順の結果を前提に固定値を埋めない
- **使い捨てのスクリプトでも、最初の1回を小さく通してから全体を回す。**
  一発勝負にすると、スクリプト側の不備で副作用だけが残りやり直しが効かなくなる
- **「元に戻した」は、測れる道具があるなら測る。**
  `make dev-seed` は冪等なので「作成 0 / スキップ N」がそのまま「あるべき状態との差分」になる。
  **ただし、その道具が変えた場所を覆っているかを1回数える**
- **検証の前に控えを取り、終了後に `diff` で差分ゼロを確認してから終わる**
- 片付けたことを報告する。作り直しが効くものは畳むのが既定。
  **意図して残すなら、何をなぜ残したかを伝える**（黙って残さない）

## 7.5 生成物（テンプレート）の検証

**配置ファイルのように「PB が文字列を組み立てて配る」ものは、3つを別々に測る。**

| 何を | どこで | 落ちる側の例 |
|---|---|---|
| **組み立ての規則** | 生成器の単体（`internal/agentsetup`） | 未知の種別、本文が種別ごとに分岐していないか |
| **カタログとの一致** | 同上。**マイグレーションの原文と突き合わせる** | DB が「テンプレートを持つ」と名乗るのに生成器が出せない |
| **受け渡しの形** | ハンドラの単体・結合 | 権限、`?client=` の検証、zip のヘッダ |

- **「テンプレートを持っている」と名乗る側と、実際に出せる側が分かれているなら、
  両者を機械で突き合わせる。** 片方だけ足したときの症状は 422 ではなく **500** になり、
  原因が遠くに出る。**マイグレーションの `UPDATE … WHERE key IN (…)` を正規表現で読んで
  Go の定義と比べる**だけで捕まる
- **生成物を実際に置く先で1回描画する。** 「文字列が返る」ことは測れても、
  「読める文になっているか」は描かないと分からない
- **zip は名前まで測る。** 展開した瞬間に既存ファイルを潰す名前になっていないか
  （`CLAUDE.md` がそのままの名前で入っていないか）は、**中身ではなくエントリ名の一覧**で見る
- **差し込んだ前後が日本語として繋がるかは、部分一致では測れない。**
  種別ごとの値から文を組み立てると、値の側に動詞が入っている種別で
  「〜を実行します を実行します」のような二重が起きる。`Contains` の検査は通るので、
  **実サーバから1回落として読む。見つけたら、二重になった文そのものを検査に足す**
- **文言の一覧を2つの書式で配るなら、元が1つであることを機械で測る。**
  読み取りツールの自動承認は Claude Code が `.claude/settings.json`、Codex が
  `.codex/config.toml` と**書式も置き場も違う**。**両方を同じ配列から組み立て、
  件数と中身を突き合わせる**——片方だけ足したときは何のエラーも出ず、
  症状は「Codex だけ毎回確認を求められる」になる
- **強調の描画を測る対象は「画面に出す文字列」だけではない。**
  `GuiDesign.md` 6.6 と `DbDesign.md` 8.1.2 が定める CommonMark の罠
  （`**…。**全角文字` は閉じない）は、**モデルが読む Markdown にも同じように効く**。
  **強調記号を含む文字列を書いたら、出どころ（DB／コード／テンプレート）に
  関わらず1回レンダラに通す。**
  判定は**通る側と落ちる側の両方**で確かめる——既知の失敗形を並べ、
  そちらが `NG` と出ることまで見る

## 7.6 憲章の分量を測る

**`make docs-size` は PB 側の憲章を測らない**（対象は毎セッション読むローカル3文書だけ）。
**規約・価値観・学びと知見（`rules` / `vision` / `learnings`）は全文がコンテキストパックに乗り、
判断の記録（`decisions`）は目次だけが乗る**（`Design.md` 8.5.5）。**PB の文書へ何かを移したら、
そのたびに1回数える。** 判断の材料は `Design.md` 8.6——**3文書の合計が1万字を超えたら切り替え時**
である。判断の記録は数えない。

```bash
curl -s --cacert <証明書> -H "Authorization: Bearer $PB_TOKEN_<接尾>" -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/call",
       "params":{"name":"pb_get_context","arguments":{"seq":<番号>}}}' \
  https://<ホスト名>:8081/mcp/<key> \
| python3 -c '
import sys,json,re
t=json.load(sys.stdin)["result"]["content"][0]["text"]
m=re.search(r"## 3\. 憲章\n(.*?)\n## 4\.", t, re.S)
if not m: sys.exit("憲章の節が取れない")
parts=re.split(r"(?m)^(### .+?（`[^`]+`）)$", m.group(1))
size={re.search(r"（`([^`]+)`）$", parts[i]).group(1): len(parts[i])+len(parts[i+1])
      for i in range(1, len(parts), 2)}
print("パック全体  :", len(t), "文字")
print("憲章の節    :", len(m.group(1)), "文字")
for p, n in size.items(): print("  ", p, n)
print("3文書の合計 :", sum(size.get(p, 0) for p in ("rules", "vision", "learnings")), "文字")'
```

**`charter_versions` を渡さずに叩く。** 渡すと版が一致した文書の本文が省かれ、字数が測れない（`Design.md` 8.5.5）。

**TLS で動いているインスタンスは**、`https` と `--cacert` で叩く（証明書の渡し方は `Development.md` 14.2）。
`http://` で叩くと 400 が返り、JSON を読めずに落ちる。

**チケットを1件選んで測る。** スコープ境界や依存関係の量はチケットごとに違うが、
**憲章の節は全チケットで同じ**なので、どれで測っても構わない。
**文書ごとの字数は、見出しの1行を含めて数える。**

**目安を超えたとき、畳むか選定に切り替えるかは利用者だけが判断する**
（`CLAUDE.md` の「閾値の引き上げを提案しない」と同じ扱い）。

**`rules` と `learnings` と `vision` は、追記のたびに全チケットのパックへ全文で乗る**ので、
**足す前に「これは毎回運ぶ価値があるか」を1度問う**こと。`decisions` は目次の1行ぶんしか増えない。

**「取れない」と出たら、それ自体が異常である**——`## 3. 憲章` と `## 4.` の見出しは
`Design.md` 8.5.5 が定める5節構成なので、取れないなら節の構成が変わっている。

## 7.7 閉じない強調記号を数える

**CommonMark の強調は日本語の約物と相性が悪い**（`DbDesign.md` 8.1.2）。**目視では見つからない**
ので、**`make docs-emphasis` で数える**。`docs/` 配下の Markdown と、エージェント連携の生成物の
テンプレート（`server/internal/agentsetup/templates/` 配下。zip の手引きや手順ファイルになる）を `markdown-it` に通し、
**描画しても `**` が残る段落**を `ファイル:行: 段落の書き出し` の形で並べ、1件でもあれば非ゼロで終わる。

- **文書を書き換えたら打つ。** 測る仕掛けが無いと、一度 0 件にした文書も戻っていく
- **`client/node_modules` が要る。** 描画器は client の依存を使う（本体は `client/scripts/check-emphasis.mjs`）。
  無ければ先に `cd client && npm ci`
- **任意のファイルも見られる。** `make docs-emphasis EMPHASIS_DOCS=path/to.md`（壊した対照を試すときに使う）

**スクリプトが守っている数え方**（直すときに崩さない）：

- **段落単位で見る。** 強調は行をまたぐので、行単位の検査は**開き側と閉じ側を切り離して誤判定する**
- **コードフェンスとコードスパンは除く。** 中の記号は文字であって強調ではない
- **フランキング規則を自分で実装しない。** CJK の扱いが仕様どおりではないため、
  **描画器の出力だけが信用できる**

**直し方は「約物を強調の外へ出す」に統一する。** `DbDesign.md` 8.1.2 が挙げるもう2つは採らない
——**半角空白を入れると画面にその空白が見え、段落を分けると文書の形が変わる**。

- **直したら必ず測り直す。** 1か所の失敗が同じ段落の後続を巻き込むので、**先頭を直すと
  残りが自然に消えることがある**（逆に、直した隣で新しく壊れることもある）
- **見た目の文字列を変えない。** 直す前後で、描画結果からタグと記号を除いた文字列が同じであることを見る

## 7.8 依存の既知脆弱性を照合する

**人の目では見つからない種類の穴である**——依存の先にある CVE は、コードを何度読んでも出ない。
**`make vuln-check` で照合する。** Go 側は `govulncheck`、client 側は `npm audit` を走らせ、
どちらかに残っていれば非ゼロで終わる。

- **依存を足したとき・上げたときに打つ。** 版を動かす変更の前後で1回ずつ見ると、持ち込んだかが分かる
- **`client/node_modules` が要る。** 無ければ先に `cd client && npm ci`
- **片方が落ちても、もう片方は走る。** 素直に2行並べると Go 側で止まって client を一度も見ない
  ——**残りが何件あるかを知りたいのに、最初の1件で調査が打ち切られる**

**govulncheck は到達可能性を見る。** import しているだけで呼んでいない脆弱性は、既定では件数の要約に
しか出ない（全部見るなら `-show verbose`）。**だから「0件」は「危険な依存が無い」ではなく
「危険な経路を通っていない」である。**

**版の固定場所は `server/tools/go.mod` の `tool` ディレクティブ**（goose・sqlc と同じ型）。
**`go install ...@latest` でグローバルに入れない**——版が揃わず、走らせる人によって結果が変わる。
Makefile が `-C` でツールのモジュールと解析対象のモジュールを分けているのはこのためである。

**標準ライブラリの脆弱性は「ビルドに使う Go」で決まる。** その版は `go.mod` の
`toolchain` 行が固定しており（`server/go.mod` と `server/tools/go.mod`）、
**`GOTOOLCHAIN=auto`（既定）の go コマンドが、手元の Go より新しければ自動で取ってくる**。

- **端末の Go を上げる必要はない。** `brew` の Go が古いままでも、`toolchain` が指す版で
  ビルドも試験も走る（初回だけダウンロード、以降はキャッシュ）
- **`deploy/Dockerfile` の `golang:` と揃えること。** ずれると、手元と Docker で
  違う版のバイナリができる
- **標準ライブラリの脆弱性が出たら、直す場所はこの2つである**（依存ライブラリなら `go get`）

## 8. DDL の検証

- **DDL は「在るか」ではなく「破れるか」で測る。**
  列と索引の存在は `pg_indexes` で済むが、`NULLS NOT DISTINCT` や `CHECK` が本当に効くかは
  入れてみないと分からない。**`ROLLBACK` 前提なら実データを汚さない**（残存0件まで確認する）
- **時間で変わる値を1トランザクション内で測らない**——`BEGIN` の中では `now()` が固定される
- **測る前に、既存の表で同じ方法を1回通してコントロールを取る**
- **`DbDesign.md` から転記した DDL は、機械で原文と照合する。**
  「変更せずに転記する」は目で見ても守れているように見えるので、**コメントと空白を落として
  差分を取る**。転記側にしか無い行（`COMMENT ON` など）を除いて0行になれば通っている
