# 試験の設計と完了の基準

**何をどこまで検証したら「終わった」と言えるか**を定める。
**実行手順は書かない**——コマンドとツールの使い方は `Development.md` 6章（テスト）と
8章（画面の動作確認）にある。

`/pb-step` 手順6 はこの文書を参照する。**`/pb-review` でも手順外の作業でも同じ基準が効く。**

## 1. 4つの層と使い分け

| 層 | 相手 | 出せるもの | 出せないもの |
|---|---|---|---|
| 単体 | フェイク | 分岐・境界・エラーの形 | 書いた人の想定の外 |
| 結合（`make test-db`） | 実DB | SQL・制約・トランザクション | 書いた人が作ったデータの外 |
| 実サーバ | 起動したプロセス | ルーティング・認証・ミドルウェアの順序 | 描画 |
| ブラウザ（CDP） | 実画面 | 見えるか・操作できるか・組み方 | 大量の組み合わせ |

**層を1つ増やすたびに、前の層が返せない値が現れる。**
実サーバ検証とブラウザ検証は「通し確認」ではなく**別の層のバグ取り**である——
API だけの手順でも拾ったことがある（優先度が未設定のチケットで一覧が 500。
単体も結合も「優先度を持つチケット」しか作っていなかった）。
**拾ったら、その値を下の層の検証にも足す。**

**フェイク（`fake_test.go`）は `gen.Querier` を埋め込んでいるので、未実装のメソッドが
コンパイルを通る。** 呼ばれた瞬間に nil ポインタで panic し、**症状は**「自分が触っていない
既存のテストが落ちる」になるため、原因が遠くに見える。**クエリを1本足したら、
そのクエリを通る既存の経路を数えてフェイクにも足す**——手順26a（`ReassignComments`）と
26c（`CountAgentRuns`）で同じ形を2回踏んだ。

## 2. 完了と言える基準

- `make test` が PASS し、**件数を前回と比べて増分が説明できる**こと。
  `--- PASS` の総数と `t.Run` の総数は数え方が違うので、**比べるときは同じ数え方を使う**
- 手順の完了条件（`Design.md` 11章）を**1件ずつ名指しで**満たすこと
- 画面を作ったなら、**スクリーンショットを自分で見た**こと（§6）
- **負の側を1件は測る**こと。権限・入力検証・未定義の入口は、通る側だけでは効いている証拠にならない
- 検証で作った資源を**片付け、片付いたことを測った**こと（§7）

## 3. 期待値の作り方

- **期待値は「対象を数え上げてから」書く。** 並び順なら ①条件に合う行を列挙 ②規則で並べ替え
  ③同値の tie-break まで、紙の上で作る。目で拾うと条件に合わない行が混ざる（**3回**）
- **より良いのは、決め打ちを置かずに DB から読んだ実測値と突き合わせる形にすること**
- **期待値はロール名ではなく実効権限から組み立てる。** 「viewer だから書けないはず」は推論であり、
  権限カタログ（`Design.md` 6.4.2）を引けば事実になる
- **出力を数える前に、その数を決めているものを読む。** `make` の変数は既定値を持つ
  （`RUN ?= Integration`）ので、件数が想定と違うときはコマンドの定義を先に見る
- **「変わったか」を測る前に、測る値の精度を確かめる。** `updated_at` は秒精度で出るので、
  同じ秒に更新すると文字列が変わらない（ETag は `UnixNano` なので実際は変わっている）。
  **秒精度の値で「変わったか」を測るなら1秒待つ**か、**要件が名指ししているものを直接突き合わせる**
- **「無いこと」を測る検査は、あるはずの値を先に入れてから書く**（手順27）。
  固定データが元から空だと、`Contains` の否定は**何を実装しても通る**。
  結合テストで「パックにチケット本文を重ねない」を測ったとき、対象の `body_md` が
  `NULL` のままで**空振りの1件**になりかけた。**否定の検査を書いたら、逆側を1回
  作って落ちることを見る**
- **時刻の境界を手で書かない**——`now() - interval` か、実行前に控えた値を使う
- **「◯◯でない」を測るなら、その状態が本当に作れているかを先に確かめる**（手順28b）。
  接続確認（`✓ 接続済み` ／ `未接続`）を測るとき、**トークンを発行していないエージェント**を
  「未接続」の始点に使って FAIL した——**トークンが無い行は接続確認そのものを出さない**ので、
  測っていたのは別の状態だった。**否定の状態にも前提がある**（ここでは「発行済みで未使用」）
- **仕様を直したら、その場で期待値も直す。** 直後の再実行で出る FAIL は**実装の欠陥ではなく
  期待値の陳腐化**であり、混ぜると「直したのに落ちた」と読んで元へ戻しかねない（手順28a。
  `.gitignore` に警告を出さない形へ直した直後、件数の期待値だけが古かった）。
  **FAIL を見たら、まず「仕様と期待値のどちらが新しいか」を言う。**
- **前提に使う文書の表が「どこから来た値か」を1行言えないなら、実物を1回引く。**
  `Development.md` 4.1 のデモアカウント表は YAML の写しであって DB の実測ではない
  （`project_member` を1クエリ引けば済む）

## 4. 検証が落ちたときの切り分け

- **実装側と検証側をフラットに疑う。** 「まず検証側を疑う」を規約にすると**通すための検証**になる。
  切り分けは順番ではなく方法で行う——**何を測っているかを設計文書の例と突き合わせ**、
  つかなければ両方に当たる最小の再現を作る
- **判定材料は「その検証は、実装を全部消しても落ちるか」**
- **落ちた件数が多いときほど、まず1つ目の原因を見る**——連鎖しているだけのことがある
- **`make test` が落ちたら、まず `git worktree add <tmp> develop` で `develop` でも落ちるかを見る。**
  stash より安全で（未追跡ファイルを巻き込まない）、作業ツリーを触らずに済む。
  **「たぶん元から壊れている」で片付けない。起票済みの既知の失敗でも、
  自分の変更と無関係であることは毎回確かめる**（1コマンドで済む。**4回**）
- **当たらない検査を見たら、まず出力が生きているかを確かめる。**
  共有の出力ファイルを使い回すと「見る前に消えていた」が起きる。症状は `ERR` や空で、
  「見ているものが違う」と区別がつかない
- **「当たらない」ときは受け側を、「効かない」ときは送り側を数える。
  全部落ちるときは、そもそも相手が居るかを1回測る**（`health` を1回引けば分かる）

## 5. 検証スクリプトを書くときの規則

- **検査を書いたら、壊れた入力の前に「正しい入力」を1件通す。**
  偽陽性の側を測って初めて、当たり判定が仕様と合っていると言える。
  **規則を検査に落とすときは適用範囲を1行書く**（「日本語を1行に収める」の対象は
  `GuiDesign.md` 6.6 が定める**画面に出す文字列**であって、手で折り返す設計文書ではない）。
  **強調の閉じ忘れを数えるなら、対象はコードスパンとコードブロックの外**——
  `` `**` `` を書いた行を偽陽性で拾う（2026-09-05 に実際に2件拾い、検査のほうを直した）。
  **数える単位は段落にする**——行単位で描画すると、2行にまたがる強調がすべて偽陽性になる
  （同じ2文書で実測 152件 → 段落単位で 13件）
- **検査を書き終えたら「この行は落ちうるか」を1件ずつ読み返す。**
  `or True` / `assert True` / 比較の無い `check(name, x)` は通すための検証である
- **セレクタは「何に当たるか」を数えてから使う。** 部分一致でボタンやテキストを選ばず、
  `button[form=…]` のように役割で名指しする。`:nth-of-type` は「同じタグの中での順番」なので、
  兄弟のタグが揃っていない箇所では `:nth-child` を使う。
  **当たる先が多いのは検証側だけの問題ではない**——`scoped` スタイルは DOM のクラス名を
  分けないので、**実装側の名前も具体的にする**（`GuiDesign.md` 6.6）
- **既存の API を叩くときは、応答の形を実装か設計文書で先に1回引く**（30秒）。
  **自分が実装した章ほど引かない**ので、そこでこそ開く
- **共有の出力先を持つ検証は、「呼ぶ」と「読む」の間に何も挟まない。**
  読む値ごとに別ファイルへ落とす
- **HTTP ヘッダは大小を区別せずに引く**（Go は `w.Header().Set("ETag", …)` を `Etag` で書き出す）
- **合否を出すコマンドをパイプへ繋がない。** `cmd -q 2>&1 | head` の `$?` は `head` のもので、
  **本体が落ちても必ず 0 になる**。判定は単体で走らせ、その直後に `$?` を読む
  （繋ぐなら `set -o pipefail` か `${PIPESTATUS[0]}`）
- **シェルで変数の直後に日本語が続くときは必ず `${VAR}`**（`"$BEFORE（…"` は変数名を切り損ねる。**3回**）
- **長く生かすプロセスと、それを待つコマンドを同じシェルに入れない。**
  `nohup … &` で切り離してから、別のコマンドで待つ

## 6. 画面の検証

- **「要素が存在するか」ではなく「見えて操作できるか」を確かめる。** 実際に遷移して見る。
  位置とサイズを実測する（`getBoundingClientRect()`）
- **スクリーンショットを必ず自分で見る。** 実測は「入るか」しか、検査は「在るか」しか答えない。
  **「変に見えないか」「全部見えているか」「並びが仕様どおりか」は別の確認**である。
  **複数の幅で撮る**（1440px と狭い窓）。自動検証が全 PASS のまま崩れていたことが**6回**ある
  （余白の偏り／ラジオの縦積み／狭い窓で列幅0／日本語の折り返しに空白／
  横スクロールの箱に収まって末尾が見えない／隣の欄と組み方が違う）
- **「並ぶか」と「読めるか」は別の検査である。** 件数と表題で測れてしまう一覧・ツリー・カードほど、
  中身の検査が抜ける
- **`getBoundingClientRect()` の幅・高さが 0 でないことは「見えている」ではない。**
  親に `overflow` があると、はみ出した要素は**幅を持ったまま**見えなくなる。
  **親の矩形に収まっているかを比べる**（`r.right <= parent.right`）。
  手順26b で、担当セルからはみ出した `🤖` が「幅>0」で PASS したまま画面から消えていた
- **新しい入力欄を足したら、隣の欄と並べて撮る。**
  崩れは「同じ画面の他の欄と組み方が違う」という形で出るので、単体で見ても気づけない
- **入力の検証は、アプリのハンドラではなく「ブラウザの機構」を通す。**
  D&D は `Input.setInterceptDrags` ＋ 実マウス、フォーカスやキーは実キーイベント。
  **「イベントを作って投げる」と「操作する」は別物**で、前者は自分が想定した経路しか通らない
  （合成した `DragEvent` で32件 PASS させたが、実機では行が一度も掴めなかった）
- **文章を組み立てて返す成果物は、見出しの木を出力して確かめる**（手順27）。
  文字列の一致だけを測ると**構造の壊れは1件も検知できない**——コンテキストパックは
  `## 1.`〜`## 5.` の5節を持つが、埋め込んだ憲章の本文も `##` で始まるため、
  **後続の節が憲章の中にあるのか外にあるのかが読めない**状態で全 PASS していた。
  行頭の `#` を数えて字下げして出せば、木の形が一目で分かる
- **多段の操作は、1段目の成立を独立した1件にする。**
  「掴めるか」だけを先に測っておくと、後で目印が出なかったときに線を1本外せる。
  **あわせて「起きないはずの側」を同じ道具で1回測る**と、検知そのものが効いている証拠になる

## 7. 状態を変える検証とあとしまつ

- **検査より先に「戻し方」を関数にして、冒頭で呼ぶ。**
  意志で守ると書き捨ての probe で漏れる。関数にすれば呼び忘れが1行で見える
- **関数にすること自体は正しさを保証しない。**
  「作ったものを消す」だけでなく**「変えた列を戻す」を数える**（`actor.is_active` を戻し忘れ、
  他人の結合テストを落としたことがある）
- **現在値は毎回読み直す。** 前の手順の結果を前提に固定値を埋めない
- **使い捨てのスクリプトでも、最初の1回を小さく通してから全体を回す。**
  一発勝負にすると、スクリプト側の不備で副作用だけが残りやり直しが効かなくなる
- **「元に戻した」は、測れる道具があるなら測る。**
  `make dev-seed` は冪等なので「作成 0 / スキップ N」がそのまま「あるべき状態との差分」になる。
  **ただし、その道具が変えた場所を覆っているかを1回数える**
- **検証の前に控えを取り、終了後に `diff` で差分ゼロを確認してから終わる**
- 片付けたことを報告する。作り直しが効くものは畳むのが既定。
  **意図して残すなら、何をなぜ残したかを伝える**（黙って残さない）

## 7.5 生成物（テンプレート）の検証

**配置ファイルのように「PB が文字列を組み立てて配る」ものは、3つを別々に測る**（手順28a）。

| 何を | どこで | 落ちる側の例 |
|---|---|---|
| **組み立ての規則** | 生成器の単体（`internal/agentsetup`） | 未知の種別、本文が種別ごとに分岐していないか |
| **カタログとの一致** | 同上。**マイグレーションの原文と突き合わせる** | DB が「テンプレートを持つ」と名乗るのに生成器が出せない |
| **受け渡しの形** | ハンドラの単体・結合 | 権限、`?client=` の検証、zip のヘッダ |

- **「テンプレートを持っている」と名乗る側と、実際に出せる側が分かれているなら、
  両者を機械で突き合わせる。** 片方だけ足したときの症状は 422 ではなく **500** になり、
  原因が遠くに出る。**マイグレーションの `UPDATE … WHERE key IN (…)` を正規表現で読んで
  Go の定義と比べる**だけで捕まる（手順28a）
- **生成物を実際に置く先で1回描画する。** 手順28a では、マーカーを持たない追記
  （`.gitignore`）に「`<マーカー>` 〜 `<マーカー>` の間だけが」という説明が空欄で出た。
  **単体はどちらも通っていた**——「文字列が返る」ことは測れても、「読める文になっているか」は
  描かないと分からない
- **zip は名前まで測る。** 展開した瞬間に既存ファイルを潰す名前になっていないか
  （`CLAUDE.md` がそのままの名前で入っていないか）は、**中身ではなくエントリ名の一覧**で見る
- **差し込んだ前後が日本語として繋がるかは、部分一致では測れない**（手順28b）。
  「起動の言い方」を種別ごとの値から組み立てたとき、**値の側に動詞が入っている種別が
  あった**ため、Claude Code だけ「`/pb-onboard` を実行します **を実行します**」になった。
  `Contains` の検査は3種別とも通っていた——**実サーバから1回落として読むまで見えない**。
  **見つけたら、二重になった文そのものを検査に足す**（同じ形は必ず再発する）
- **文言の一覧を2つの書式で配るなら、元が1つであることを機械で測る**（手順28b）。
  読み取りツールの自動承認は Claude Code が `.claude/settings.json`、Codex が
  `.codex/config.toml` と**書式も置き場も違う**。**両方を同じ配列から組み立て、
  件数と中身を突き合わせる**——片方だけ足したときは何のエラーも出ず、
  症状は「Codex だけ毎回確認を求められる」になる
- **強調の描画を測る対象は「画面に出す文字列」だけではない**（手順28c）。
  `GuiDesign.md` 6.6 と `DbDesign.md` 8.1.2 が定める CommonMark の罠
  （`**…。**全角文字` は閉じない）は、**モデルが読む Markdown にも同じように効く**
  ——コンテキストパックの断り書きで踏んだ。**マイグレーションの初期本文は描画して測ったのに、
  Go が組み立てる同じ形の文は測っていなかった。**
  **強調記号を含む文字列を書いたら、出どころ（DB／コード／テンプレート）に
  関わらず1回レンダラに通す。**
  判定は**通る側と落ちる側の両方**で確かめる——既知の失敗形を並べ、
  そちらが `NG` と出ることまで見る

## 7.6 憲章の分量を測る

**`make docs-size` は PB 側の憲章を測らない**（対象は毎セッション読むローカル4文書だけ）。
**憲章は全文がコンテキストパックに乗る**ので（`Design.md` 8.5.5）、**PB の文書へ何かを移したら、
そのたびに1回数える**。判断の材料は `Design.md` 8.6——**数千文字なら選定は要らず、万を超えたら
切り替え時**である。

```bash
curl -s -H "Authorization: Bearer $PB_TOKEN_<接尾>" -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/call",
       "params":{"name":"pb_get_context","arguments":{"seq":<番号>}}}' \
  http://localhost:8081/mcp/<key> \
| python3 -c '
import sys,json,re
t=json.load(sys.stdin)["result"]["content"][0]["text"]
m=re.search(r"## 3\. 憲章\n(.*?)\n## 4\.", t, re.S)
print("パック全体 :", len(t), "文字")
print("憲章の節   :", len(m.group(1)) if m else "(取れない)", "文字")'
```

**チケットを1件選んで測る。** スコープ境界や依存関係の量はチケットごとに違うが、
**憲章の節は全チケットで同じ**なので、どれで測っても構わない。

| 測った日 | パック全体 | 憲章の節 | そのときの憲章 |
|---|---|---|---|
| 2026-09-05（手順27） | — | **3,601字** | 4文書 |
| 2026-09-06（手順28c 後、PB #51） | 4,630字 | **3,936字** | 4文書（`agent-onboarding` は除外済み） |
| 2026-09-06（PB #52 後） | 7,538字 | **6,846字** | 同上。`rules` が 1,902 → 8,540 バイト |
| 2026-09-06（PB #54 後） | — | **7,905字** | 同上。`decisions` に判断を3件追記 |

**余裕は縮んでいる。** 1日で 3,936 → 7,905字 まで来た（目安は1万字）。**`rules` と `decisions` は追記のたびに全チケットのパックへ乗る**ので、**足す前に「これは毎回運ぶ価値があるか」を1度問う**こと。

**「取れない」と出たら、それ自体が異常である**——`## 3. 憲章` と `## 4.` の見出しは
`Design.md` 8.5.5 が定める5節構成なので、取れないなら節の構成が変わっている。

## 8. DDL の検証

- **DDL は「在るか」ではなく「破れるか」で測る。**
  列と索引の存在は `pg_indexes` で済むが、`NULLS NOT DISTINCT` や `CHECK` が本当に効くかは
  入れてみないと分からない。**`ROLLBACK` 前提なら実データを汚さない**（残存0件まで確認する）
- **時間で変わる値を1トランザクション内で測らない**——`BEGIN` の中では `now()` が固定される
- **測る前に、既存の表で同じ方法を1回通してコントロールを取る**
- **`DbDesign.md` から転記した DDL は、機械で原文と照合する**（手順26c）。
  「変更せずに転記する」は目で見ても守れているように見えるので、**コメントと空白を落として
  差分を取る**。転記側にしか無い行（`COMMENT ON` など）を除いて0行になれば通っている
