# Project Backyard (PB) 要件・構想

> 本書は PB の**要件と構想の記録**である。第1〜9章がチケット管理ツールとしての機能要件、
> **第10章が AI エージェントに実装を委ねる開発フローへの拡張**を扱う。
>
> 実装設計は `Design.md`（全体）、`DbDesign.md`（DB）、`ApiDesign.md`（API）、`GuiDesign.md`（GUI）
> に分かれており、**実装上の判断はそれらを正本とする**。

> 旧称：スモールライトプロジェクト管理アプリ
> ・第1〜9章：チケット管理ツールとしての基本仕様（人間のPMをAIが支援する位置づけ）
> ・第10章：AI駆動開発への拡張（人間とAIエージェントが共同で使う作業基盤としての設計）

## 1. コンセプト・背景

市販のプロジェクト（チケット）管理製品に代表される既存のツールは、比較的大規模な運用を前提としており、動作が重い・構成が複雑になりがちという課題がある。これに対し、よりシンプルな構成で軽快に動作する、アジャイル（スクラム）・ウォーターフォール・ハイブリッドいずれの進め方にも対応できるチケット管理システムを構想する。

### 想定技術スタック

- **サーバ**：Rust または Go 言語によるAPIシステム
- **DB**：SaaSのRDBMS、またはコンテナ動作のローカルRDBMS
- **Webフロント**：Vue等のJSフレームワークによるWebアプリ。独自Nginx、またはAPIサーバから静的コンテンツとして配信
- **リアルタイム性**：小規模用途を想定し、WebSocket等のTCPストリーム接続は必須とせず、まずはAPIの短間隔ポーリング（ETag/If-Modified-Since等での差分取得）で対応。サーバ負荷や規模に応じて将来的にSSE等へ拡張する段階的設計とする

## 2. データモデルの基本方針

アジャイル/ウォーターフォール/ハイブリッドを単一の体系で扱うため、以下の設計方針を取る。

- チケットは「エピック/ストーリー/タスク」の種別を持ちつつ、根底のデータ構造は共通化する
  - **当初は「フェーズ/WBS項目」も種別に挙げていたが、種別を3値へ減らした**（利用者の判断、2026-08-23）。使い分けの定義がどの設計文書にも無く、実機で選べなかったためである。**フェーズ・WBS項目・バグは、階層（`ticket.parent_id`）とタグで表す**（`DbDesign.md` 6.6 / 6.10）。**共通データ構造という方針そのものは変わらない**——変わったのは種別という語彙の粒度だけで、WBS もガントも同じ `ticket` から描く
- 依存関係（FS/SS/FF/SFの4種）と親子階層を持たせ、同一データをガント・カンバン・WBSいずれの形式でも描画可能にする
- ワークフロー（ステータス遷移）はプロジェクトごとにJSON/YAML等で定義可能にし、スクラムの簡易カンバンからウォーターフォールの承認フロー付きステータスまで対応
- カスタムフィールドはJSONB等で保持し、スキーマ変更なしに拡張可能にする
- 同一データをビュー切り替え（カンバン／ガント／WBS）で編集でき、どこから変更しても即座に他ビューへ反映される設計
- 長期的には「タスク・人・コメント・外部イベント」を1つの関係グラフとして持たせ、依存関係・関連性・貢献度可視化などのAI機能を後から拡張しやすい構造にする（グラフDB採用か、RDB＋定期バッチでの関係抽出かは規模次第で選択）

## 3. PM向け機能

- **ガントチャート**：依存関係の表示、クリティカルパスのハイライト
- **バーンダウン／バーンアップチャート**：スプリント単位・エピック単位
- **WBS編集**：ドラッグ&ドロップでの階層編集、番号自動採番
- **リソース稼働率ヒートマップ**：メンバーごとの割当工数を可視化し、過負荷を検知
- **週次ステータスレポート自動生成**：進捗・遅延・リスクをMarkdown/PDFで自動集計
- **ベロシティ・見積り精度トラッキング**：スプリントごとの見積もりvs実績の乖離を蓄積

## 4. プロジェクト目的達成を早める工夫

- プロジェクト／チケットテンプレート（過去案件からの複製、雛形化）
- ブロッカー可視化（依存関係で停止しているタスクの自動検出・ダッシュボード表示）
- 「今日やることビュー」：個人向けにフィルタされた軽量なタスク一覧
- 期限超過の自動エスカレーション（チャットツールへの通知、Webhook 連携）
- クリティカルパス警告：スケジュール変更時の影響範囲を自動再計算し通知

## 5. チーム共有・エクスポート機能

### Excel出力

- ガントチャート、WBS、スプリントバックログそれぞれの形式でのExcelエクスポートは必須機能とする
- 理想的には**双方向連携**（Excelから一括インポートも可能）とし、Excel文化が根強い現場での導入障壁を下げる
- **WebGUIと同じデザインでの出力**を志向する。実現方式は以下の2案を比較：
  - SVG/HTML→変換型：フロント描画のSVGをサーバでExcelシェイプ/セル結合として再構築（デザイン一致度は高いが実装コスト大）
  - 共通レイアウトエンジン型：日付軸グリッド計算・バー位置/色計算のロジックをWeb描画とExcel出力で共有し（WASM化等でフロント/バックエンド共通化）、片方はSVG、片方はセル背景色として出力（保守性が高く推奨）
- セル1つ＝1日として背景色でバーを表現する方式が実装しやすく、罫線・フォント・色をテーマ変数として一元管理すればWeb側CSS変数と対応づけやすい

### その他共有機能

- 期限付きトークンによる読み取り専用の公開URL（ログイン不要でステークホルダーに共有できる軽量ダッシュボード）
- iCal/Googleカレンダー連携によるマイルストーンの個人カレンダー反映
- 印刷向けCSS（A3横のガント印刷など）
- 市販のプロジェクト管理製品からのマイグレーションツール（乗り換え需要の初速取り込み）
- CLI/TUIクライアント：ターミナルでチケット確認・ステータス更新が完結できる、git的な操作感（`ticket list`、`ticket move <id> in-progress`等）。Neovim/iTerm2文化の開発者層に訴求
- オフラインファースト（PWA）：ネットワークが不安定な環境でも編集でき、後で同期

## 6. AI活用機能

### 基本方針

AI支援は「人間の判断力・記憶力を超えたところ（大量データの継続的な突き合わせ、記録の拾い上げ）」を担う位置づけとし、**推定・提言はするが最終決定はしない**という一貫したポジションを取る。これによりPM・メンバー双方の信頼を得やすくする設計とする。

### 6.1 タスク難易度のAI推定（学習型）

スクラムのプランニングポーカーを補助・代替する機能。

- **特徴量**：タスクのタイトル/説明文の埋め込みベクトル、担当予定者の過去実績、タスク種別、依存タスク数、サブタスク数、DoD項目数など
- **学習ループ**：見積もり（AI予測または人間の合議）と実績（実際の所要時間・ポイント）の差分を蓄積し、プロジェクト/チーム単位で軽量モデル（LightGBM程度で十分）を再学習
- チーム構成変化に対する頑健性のため、「担当者」も特徴量に含めるか、チーム傾向と個人傾向を分けてモデル化する
- 導入初期はAI推定を参考値として提示し、人間の見積もりとの乖離が大きい場合のみハイライトする程度の控えめな介入から始める

### 6.2 終了条件（DoD）の明確化・タスク分割支援

「いつまでも終わらず定常業務化するタスク」問題への対策。

- タスク作成時、タイトル・説明文から**終了条件のドラフトを自動生成**しPMに提案（承認/修正の上で確定）
- 見積期間が閾値超過、または進捗が一定期間更新されないタスクを検知し、サブタスク分割を提言
- 過去のクローズ済みタスクとの類似度が低い（＝定型化されていない曖昧なタスク）場合に警告

**DoDの構造化案：**

- DoDを単純なテキストではなく、構造化されたチェック項目のリストとして保持
- チェック項目の型：
  - 手動チェック型（人間がチェックを入れる）
  - タスク参照型（関連タスク番号を指定し、そのタスクが完了したら自動チェック）
  - 条件式型（将来拡張：CIのビルド成功、テストカバレッジ閾値等、外部システム連携）
- AIによるDoDドラフト生成時、本文中の「〜チケット対応完了後」等の記述から**タスク参照型項目を自動検出・提案**
- 全チェック項目が満たされるまでクローズ操作をブロック／警告表示し、放置タスクをPMダッシュボードで警告表示
- 構造化されたDoDは難易度推定（6.1）の特徴量としても活用可能（DoD項目数・依存タスク数が多いタスクは難易度が高く出る）

### 6.3 タスク間の関係性評価

3段階のレベル分けで整理する。

1. **厳密な構造的関係**：クリティカルパス、重複タスク検出（タイトル・説明文の埋め込みベクトルのコサイン類似度が閾値を超えたペアをアラート）
2. **ゆるい関連性の自動提案**：新規タスク作成・編集時に、既存タスク（特に進行中/直近クローズ）との類似度を計算し関連候補をサジェスト。同一コンポーネント言及、同一担当者等も加味。AIは提案のみ行い、リンク確定は人間が行う
3. **タスクメモへの関連情報の自動反映**：コメント内の「他タスクへの影響を示唆する記述」（例：「〜のAPI仕様を変更したのでフロント実装に影響あり」）をNLPで検知し、関連タスク側にメモとして自動転記・通知。コメント投稿時に軽量なNER/関係抽出（タスクID・コンポーネント名・API名等のエンティティ抽出）を行い、既存タスクとのマッチングをバックグラウンドで実行

### 6.4 メンバー貢献度・成長支援

- **貢献度の可視化**：主担当以外でタスク完了を助けたメンバー（コメント・レビュー頻度、Git連携時のco-authored-by・PRレビュー数等）をタスク単位で「関与度スコア」として算出し、スプリントレトロやプロジェクト振り返り時にPMへレポート
  - ゲーミング対策として、コメント数等の表層指標だけでなく「支援後に対象タスクが実際に進捗・完了したか」との相関で重み付けする
- **評価における二軸設計**：
  - **主軸（評価の中心）**：担当タスクの消化数・消化時間・難易度加重スコア（6.1と連動）。難易度×消化数で重み付けし、単純な件数評価に偏らないようにする
  - **副軸（加点要素）**：他タスクへの支援・関与度スコア。主軸を覆すものではなく、同水準の評価者間の差別化要因、または見えなかった貢献の発掘として機能させる
  - 人事評価への直結は慎重に扱い、まずは「見えていなかった協力関係を可視化し、PM・チームが認識・感謝できるようにする」ポジティブなフィードバック用途を基本とする
- **個人の成長支援**：過去のタスク履歴からスキルの偏りを可視化し、新規タスクアサイン時に「成長機会になりそうなタスク」をPMへ提案。本人向けには「挑戦してみると良さそうな領域」を参考情報として提示
  - 権限設計（本人のみ／PMのみ／両方が閲覧可能か）を機能として最初から意識する

### 6.5 埋もれた情報の自動抽出・要約

市販のプロジェクト管理製品の運用でありがちな「チケットクローズ後に議論の経緯・意思決定理由・成果物の所在等が探しづらくなる」問題への対策。

**情報の類型化：**

- 意思決定記録（Decision）：「〜という理由で〜に決定した」等
- 議論の経緯（Discussion）：誰がどんな意見を出し、どう収束したか
- 成果物の所在（Artifact Reference）：ドキュメントURL、ファイルパス、PR等
- 既知の問題・注意点（Caveat）
- 外部リンク・参照（Reference）

コメント投稿のたびに軽量なLLM分類（few-shot程度）をバックグラウンドで実行し、コメントにメタタグを自動付与する。

**クローズ時の意思決定サマリー自動生成：**

- タスククローズ時、全コメント・変更履歴から上記カテゴリに基づく構造化要約（なぜその仕様にしたか／誰がどう関わって決まったか／成果物の場所）を自動生成し、タスクのサマリー欄として固定化
- クローズ前にPM/Assigneeが確認・修正できるようにし、AI生成のまま確定させない

**プロジェクト全体への集約：**

- 週次/月次プロジェクトダイジェスト（期間内クローズタスクのDecisionを集約、オンボーディング資料としても活用可）
- 意思決定ログ（Decision Log）ビュー：プロジェクト横断で時系列に決定事項を抽出（ADRのプロジェクト管理版）
- 成果物マップ：Artifact Referenceを集約し、プロジェクトの成果物・ドキュメント所在を一覧化
- 自然文検索によるRAG的Q&A機能（「なぜ〜になったか教えて」等でDecision記録を横断検索）
- 実装方針：コメント本文とメタタグをベクトルDB（pgvector等）に格納し、ダッシュボードは定期バッチで事前生成した要約を表示、Q&Aはオンデマンドでのベクトル検索とする

### 6.6 コメントの重み付けと選択的サマリー読み込み

タスクが多数蓄積した状態でプロジェクト全体のサマリー生成を行う際、全コメントを毎回読み込むのはコスト・スケール面で非現実的になる。そのため、コメントに重要度スコアを付与し、サマリー生成時には選択的に読み込む設計とする。

**投稿時のスコアリング（軽量・即時）**

コメント投稿時に、6.5で定義した分類（Decision/Discussion/Artifact Reference/Caveat/Reference）と併せて重要度スコアを算出する。判断材料の例：

- **カテゴリ自体の重み**：Decision > Artifact Reference > Caveat > Discussion > 相槌的なやり取り、のようにカテゴリごとにベース重みを設定
- **内容の情報密度**：固有名詞（ファイル名・URL・タスクID・技術用語）を多く含むコメントは高スコア、単純な相槌は低スコア
- **反応・参照のされ方**：他コメントからの引用、別タスクからの参照リンク、リアクション数など「後から効いている」シグナルによる事後的な加点
- **編集・確定行為との紐付き**：コメント直後にステータス変更・DoD更新・担当者変更等の操作が行われた場合、意思決定の引き金と見なして加点

フルのLLM推論ではなく、軽量な分類器（embedding＋線形モデル程度）での算出を基本とし、コメント数に比例したコスト増大を避ける。

**サマリー生成時の選択的読み込み（階層構造）**

情報を段階的に圧縮する多階層構成とすることで、プロジェクト規模が拡大してもサマリー生成のトークン量が爆発しないようにする。

1. 生コメント（重要度スコア上位N件＋直近M件を抽出）
2. → タスククローズ時サマリー（6.5で定義）
3. → 週次/月次ダイジェスト（タスクサマリーを主入力とし、生コメントまでは遡らない）
4. → プロジェクト全体サマリー（既存サマリーの要約）

低スコアのコメントも破棄はせず、検索用ベクトルインデックスには全件を保持する。サマリーには反映されないが、RAGベースのQ&A機能で個別に参照できる状態を維持する。「サマリーに出るコメント」と「検索すれば出てくるコメント」を役割分担させることで、精度とコストのバランスを取る。

### 6.7 プロジェクトヒストリー（タイムライン）機能

タスク単位のサマリーとは別に、プロジェクト全体の主要な出来事を時系列で振り返れる「プロジェクトヒストリー」を独立した機能として持たせる。新規参加メンバーやステークホルダーへの説明資料としても活用する。

**イベントの種類**

- 意思決定イベント（6.5のDecision抽出と連動）
- フェーズ移行イベント（ウォーターフォールのフェーズ切り替え、スプリント開始/終了、マイルストーン到達）
- ブレイクスルー／問題解決イベント（長期ブロックされていたタスクの解消、大きな障害の解決）
- 体制変化イベント（メンバーのアサイン変更、方針転換）
- 成果物イベント（主要な成果物の確定）

**生成方式**

完全自動生成ではなく、AIがイベント候補を検出してPMに提示し、PMが取捨選択・一言添えて確定する**セミオート方式**とする。「歴史に残すべき出来事か」の判断は文脈依存性が高く完全自動化に不向きであること、ステークホルダー向け資料としてはPMの意図を反映させた方が実用的であることが理由。

候補検出のトリガー例：

- 長期間オープンだったブロッカータスクのクローズ
- 複数タスクにまたがる影響を持つDecisionコメントの検出（6.3の関連タスク自動リンクと連動）
- フェーズ/マイルストーンのステータス変化（構造データとして確実に検出可能）
- クローズタスク数の急増・長期停滞などの節目

**ビューとしての見せ方**

- 横軸を時間としたシンプルな年表形式（ガントとは別の軽量ビュー）
- 各イベントは一言サマリーと関連タスク・関連ドキュメントへのリンクを保持
- オンボーディング用途：新規参加メンバー向けにプロジェクトの経緯を通読できるページとして機能
- ステークホルダー報告用途：期間を絞ってPDF/Markdownでエクスポートし、報告資料の下書きとして活用（Excel出力と同様にエクスポート対応）

**データモデル上の位置づけ**

タスクやコメントとは独立した「プロジェクトイベント」エンティティとして持たせる。

- `event`テーブル：日付、種別（Decision/Phase/Breakthrough/Milestone等）、タイトル、本文、関連タスクID群、作成者（AI提案／手動作成）、承認状態
- タスク側のDecisionコメントやフェーズ変更などの構造イベントから半自動生成する一方、PMが手動でイベントを直接追加できる柔軟性も持たせる

### 6.8 情報アーキテクチャとしての全体構造

6.6・6.7は、「情報の重要度に応じて粒度を切り替え、必要な時だけ深掘りできるようにする」という一貫した設計思想でつながっている。コメント重要度スコアリング、タスク単位サマリー、プロジェクトヒストリーは、粒度の異なる3層の情報として積み上がる構造になっており、この階層設計が6.5の情報抽出・要約機能全体の基盤となる。

## 7. コンテンツ編集・添付ファイル機能

### 軽量Markdownエディタ

市販製品のリッチテキストエディタの重さ・不安定さ・思い通りにならないフォーマットへの不満を踏まえ、以下の方針とする。

- WYSIWYGではなく「Markdownソース＋ライブプレビュー」型を採用し、動作の軽さと予測可能性を両立（GitHub Issue編集画面に近い体験）
- 対応構文はMarkdown標準＋αに絞る：見出し、リスト、チェックボックス、コードブロック、テーブル、リンク、画像埋め込み、独自拡張として`#123`形式のタスク参照記法（DoDのタスク参照型とも連動）
- 実装は軽量ライブラリ（CodeMirror 6、milkdown等）を採用し、フルスクラッチのリッチエディタは避ける
- ペースト画像は自動でオブジェクトストレージへアップロードし、Markdown画像記法に変換

### ファイルストレージ方式の比較

| 方式 | メリット | デメリット | 向いているケース |
|---|---|---|---|
| アプリ内直接保存（ローカル/コンテナボリューム） | 実装がシンプル、外部依存なし | バックアップ・容量管理・スケールが自前運用の負担に | 小規模・オンプレ完結・PoC段階 |
| オブジェクトストレージ（S3互換APIを持つもの） | スケーラブル、コスト安、既存基盤との統一運用が可能 | プレビュー等の実装に一手間必要 | 中〜大規模、既にS3互換基盤がある場合 |
| 既存の共有ディスク連携（企業向けのファイル共有サービス） | 既存の組織のファイル管理・権限体系をそのまま活用、オフィス文書の編集との親和性 | API連携・権限同期の実装が複雑、ベンダーロックイン | 組織側でファイルサーバ運用文化が既に確立している場合 |

**方針**：チケット管理ツール自体はファイル実体を持たず、メタデータ（参照リンク）のみを保持する設計を基本とし、保存先インターフェースをプラガブルにする。コンテナ内蔵の最小構成（オブジェクトストレージ同梱等）をデフォルトとしつつ、企業導入時にはオブジェクトストレージや企業向けファイル共有サービスのアダプタへ差し替え可能にする。これにより小規模利用時は自己完結、大規模化時は既存基盤への接続、という両対応を実現する。

# 10. AI駆動開発への拡張 — Project Backyard (PB)

本章は、本ツールを **Project Backyard（以下 PB）** と改称した上で、これまでの「人間のPMをAIが支援する」という位置づけから一歩踏み込み、**複数の開発者がそれぞれ AI エージェントを伴って1つのプロジェクトを進める**ための設計をまとめる。

第6章までのAI活用機能（難易度推定、DoD支援、情報抽出・要約、コメント重要度スコアリング、プロジェクトヒストリー）は、本章の土台としてほぼそのまま活用される。本章はそれらを「AIエージェントが読む側」に開くための拡張である。

---

## 10.0 PB が解く問題

**本節は、本章に機能を足すかどうかを判断するための基準である。** 個別仕様に迷ったら
「**この機能は、md ファイル1枚では足りない理由を持つか**」をここに照らして決める。

### 10.0.1 単独開発では PB は要らない

開発者が1人であれば、エージェント側の工夫だけでかなり遠くまで行ける。リポジトリに常時読まれる規約ファイル（`CLAUDE.md` / `.github/copilot-instructions.md`）を置き、個人の学びを別のファイルに溜め、必要に応じて手順ファイルを書き足していけばよい。**そこにチケット管理ツールを挟む必然性は無い。**

**この観察を出発点に据える。** PB が価値を持つのは、規模・時間・コストの制約から**複数人で進めることになった時点から**である。単独開発で足りる範囲を PB に作ると、ツールは重くなるだけで誰の役にも立たない。

### 10.0.2 複数人になると壊れるもの

参加者が N 人になり、各人がそれぞれのエージェントを伴うと、以下が同時に起きる。

| # | 壊れるもの | 何が起きるか |
|---|---|---|
| 1 | **個人の学びが共有されない** | 知見は各人の手元のファイルに溜まる。同じ躓きが N 人にそれぞれ1回ずつ起き、**誰の目にも「2回目」に見えないので規約に昇格しない** |
| 2 | **判断が分岐する** | 規約に書かれていない事態で、エージェントは止まって人に聞く。**N 人が別々の場面で別々の人に聞き、別々の答えを得る** |
| 3 | **決めた理由が失われる** | 「なぜこうなっているか」を知るのは決めた本人だけになる。後から入った人とそのエージェントは推測で埋める |
| 4 | **いま誰が何を触っているか分からない** | 同じ領域を2人が同時に触り、片方の作業が無駄になる |

**1 が最も見えにくい。** 規約は「同じことが2回起きたら書く」という形で育つが、**その観測は参加者が1人だから成立する**。N 人に1回ずつ分散した瞬間、規約は永久に育たなくなる。

### 10.0.3 PB が引き受ける役割

上の4つに対し、PB は次を置く。

| 壊れるもの | PB が置くもの | 本章での定義 |
|---|---|---|
| 1. 学びが共有されない | **プロジェクト文書（憲章）**——規約・価値観・判断基準を1か所に置き、全員のエージェントが同じものを読む | 10.6.2 |
| 2. 判断が分岐する | 同上。**規約は既知の事態に答えを与え、価値観は書かれていない事態の拠りどころになる** | 10.6.2 |
| 3. 理由が失われる | 判断の記録と、その出所（誰の・いつの・どのチケットに由来する判断か） | 10.6.2、10.6.4 |
| 4. 状況が見えない | チケット・担当・リース | 10.3.3 |

**エージェントを賢くする方向には進まない。** それは各クライアント（Claude Code / Copilot）の仕事であり、PB が競合しても勝てず、原則1（pull型）にも反する。**PB は参加者の間に立つ。**

## 10.1 コンセプトの転換

### 10.1.1 チケットは「依頼メモ」から「実行契約」へ

従来のチケット管理では、チケットは人間に向けた依頼メモであり、行間や暗黙の前提は担当者が補完することを前提としていた。**書いた人と読む人が同じ文脈を共有していれば**それで足りる。

複数人がそれぞれエージェントを伴う構成では、この前提が二重に崩れる。**読む人は書いた人と同じ文脈を持たず**、さらに**その人のエージェントは行間を推測で埋める**。暗黙の前提は補完されるのではなく、もっともらしい別のもので置き換えられる。

チケットは **実行契約（contract）** となり、以下が機械可読である必要がある。

- **入力**：実装に必要な前提情報（設計方針、過去の決定、既知の注意点）
- **境界**：触ってよい範囲と触ってはいけない範囲
- **完了条件**：DoD（検証可能な形式）
- **出力**：成果物と、そこから得られた知見

曖昧さがそのまま失敗コスト（トークン浪費・手戻り・誤った実装）に直結するため、「チケットの記述品質を上げる仕組み」自体が PB の機能要件となる。

### 10.1.2 三つの中核原則

本章の設計は以下の3原則に貫かれている。以降の個別仕様はすべてこの原則から導かれる。

| # | 原則 | 意味 |
|---|---|---|
| 1 | **PBはエージェントを起動しない（pull型）** | PBは情報とルールを提供する側に徹し、実行はエージェント側の道具に任せる。エージェントがPBに接続しに来る |
| 2 | **静的ファイルには手順のみ、内容は実行時に取得** | リポジトリに置くファイルは「PBに聞け」という案内板に留め、チケット本文・設計情報・履歴は実行時にMCP経由で取得する |
| 3 | **AIは提案し、確定は人間が行う** | 第6章の基本方針を踏襲。エージェントによる実装結果も、知識ベースへの反映前に必ず人間の承認を経る |

原則2が特に重要である。前提情報をプロンプトやファイルに埋め込む方向に進むと、情報更新のたびに配布物を配り直す運用となり、必ず陳腐化する。**静的なものは手順だけ、動的なものはすべてAPI越し** という分離を徹底する。

**Phase 2 の実運用は、開発端末1台の上に PB サーバと参加者1人ぶんが同居する形になる**（PB 自身の開発に PB を使うため）。上図はその特殊な場合であり、**参加者が増えても変わるのは接続URLだけである**（10.2.2）。

### 10.2.2 pull型を採用する理由（push型の検討と棄却）

当初、PBのWeb UIから「AIエージェントによる実装」ボタンを押すとエージェントが起動する、という push 型の設計を検討した。しかし以下の理由により棄却した。

**技術的障壁**：PBサーバはコンテナ内で動作し、Claude Code や Copilot はホストOS上で動作する。対象リポジトリもホストのファイルシステム上にある。コンテナからホストのプロセスを起動する正当な手段は存在せず、Docker socket のマウント等の回避策はセキュリティ的に採用できない。

**回避策とその代償**：ホスト側に常駐ランナー（PB Runner）を置き、ジョブキューをポーリングさせる構成は技術的には可能である。しかしこれを採ると、

- 常駐プロセスの配布・起動・アップデートという運用負担が発生する
- PBの本体が「チケット管理ツール」ではなく「エージェント実行オーケストレータ」になり、ジョブキュー・セッション管理・プロセス監視・異常検知といった高難度の実装が中核を占める
- 第1章の「シンプルな構成で軽快に動作する」というコンセプトと乖離する

**pull型で得られるもの**：エージェント側から PB の MCP サーバに接続しに来る構成に反転すると、コンテナはポートを公開するだけでよく（本来の役割）、ランナーもプロセス監視も不要になる。さらに、

- PBサーバをリモートに移しても、変わるのは接続URLだけで手順は一切変わらない
- PBの状態遷移がエージェント自身のツール呼び出しで駆動されるため、外形監視の仕組みが不要になる
- 実装対象の選択・起動タイミングを人間が握るため、暴走・並行更新衝突・無駄なコスト消費が構造的に起きにくい

**将来の後方互換性**：無人実行（夜間バッチ、複数チケットの並列消化）が必要になった場合も、Runner が行う仕事は「`claude -p "/pb-implement 123"` をヘッドレスで実行する」だけであり、MCPツール群もコマンド定義もそのまま再利用できる。**pull型を先に固めておけば、自動化は後付けのオプション部品になる。** 逆にRunner前提で作ると手動実行が二級市民になる。

## 10.3 MCPサーバ仕様

### 10.3.1 二層構成と境界

| `pb_transition_task` | write | 2 | **`seq`**, `to`, `comment?` | 9.5.1 の応答をそのまま | **状態を進める。** `to` はワークフローのステータスキー。**着手の宣言もこれで行う**（`working_agent_id` が自動で立つ）。手順26b |
| `pb_list_transitions` | read | 2 | **`seq`** | 9.7 の応答をそのまま | **いまどの状態へ進めるか**と、進めない先の理由。手順26b |
| `pb_post_note` | write | 2 | **`seq`**, `body_md`, `kind?` | 9.8 の1件をそのまま | 途中経過・判明した事実の記録。**`refs` は落とした**——`ApiDesign.md` 9.8 に対応するフィールドが無い（`Design.md` 8.5.1） |
| `pb_put_doc` | write | 2 | `path`, `body_md`, `change_reason?` | 10.3 の応答をそのまま | **文書の更新。** 権限を持つ人の指示で呼ぶ（10.6.2）。**本文の全置換**で、`If-Match` は MCP 層が付ける（`Design.md` 8.5.1） |
| `pb_add_reference` | write | 2 | **`seq`**, `repository`, `branch?`, `commit_sha?`, `url?`, `label?`, `note?`, `kind?` | 9.10.2 の1件をそのまま | **作業の跡（ブランチ・コミット）をチケットに積む。** `ticket_reference` の `kind='code'`（`DbDesign.md` 6.12）。**追記専用**で、直す・消すは人が画面から行う。**必要権限は `ticket.reference.edit`**（0027）。pb-68 |
| `pb_submit_result` | write | 2 | **`seq`**, `status`, `artifacts?`, `dod_results?`, `findings?`, `failures?`, `proposed_subtasks?`, `knowledge_impact?`, `cost?` | 9.15 の応答をそのまま（`unsatisfied_dod` を含む） | 完了レポートの返却。**手順26c**（`agent_run` / `agent_report` を Phase 3 から戻した）。**引数は 10.6.1 のレポートを平らにしたもの**で、名前は REST の本体フィールドに揃う（`Design.md` 8.5.4）。**状態は進めずクローズもしない** |
| `pb_claim_task` | write | **3** | `seq` | `lease_id`, `expires_at` | 着手時のリース取得。**Phase 3 へ送った**（2026-09-05。10.3.3） |
| `pb_release_task` | write | **3** | `seq`, `reason` | — | 中断時のリース解放。**Phase 3 へ送った**（同上） |
| `pb_search` | read | 3 | `query`, `scope?`, `top_k?` | 該当コメント/決定/文書 | 履歴横断のRAG検索 |
| `pb_next_task` | read | 3 | `capabilities?`, `agent_id?` | 実行可能なチケット | 依存解決済み・readiness良好なものをPB側が選定 |
| `pb_propose_subtasks` | write | 3 | `task_id`, `subtasks[]`, `rationale` | 提案ID | 分割提案（承認待ちキューへ） |
| `pb_propose_memory` | write | 3 | `scope`, `kind`, `body`, `source_task_id` | 提案ID | 知識候補を承認キューへ |

**read / write の分離**が重要である。Claude Code 側のツール許可設定で「read系は自動承認、write系は都度確認」という運用ができ、エージェントの副作用を人間が段階的に制御できる。

**`pb_get_project` / `pb_list_docs` / `pb_get_doc` は、チケットを持たない参加者のための経路である。** `pb_get_context` はチケット単位でしか呼べないため、**プロジェクトに参画したばかりで担当がまだ無い人**が憲章を読む手段が無かった。10.8.5 の `/pb-onboard` がこの3つを使う。

`kind` の値は第6.5節で定義した情報類型（`decision` / `discussion` / `artifact` / `caveat` / `reference`）をそのまま用いる。**`comment.kind` が既にこの5値を持つ**（`DbDesign.md` 6.7）ため、`pb_post_note` は新しいテーブルを必要としない。エージェントは構造化して報告できるため、人間のコメントより分類の精度が高く、6.5で想定していたLLMによる事後分類のコストを削減できる。

### 10.3.3 リース（lease）モデル — **Phase 3 へ送った**

**Phase 2 では実装しない**（利用者の判断、2026-09-05。手順26b）。**代わりに置いたのは `ticket.working_agent_id`（実行者の自己申告）と、`ApiDesign.md` 9.6 の検証6（エージェントは所有者の担当だけを進められる）である。**

**送った理由は、リースが解こうとしていた3つのうち、Phase 2 で成立するものが無かったことである。**

| 解こうとしていたもの | Phase 2 での判定 |
|---|---|
| **可視性**（いま誰が触っているか。10.0.2 の 4） | **状態・担当・実行者の3欄で足りる。** 下記の TTL 30分は**エージェントのセッションの時間尺度**であり、**PB は分野を問わないプロジェクト管理を目指す**（10.0）。建築・法務・企画の「進行中」に30分の失効は合わない |
| **排他**（同じチケットを2つのエージェントが同時に処理しない） | **Phase 2 では発生しない。** 10.8.6 の `/pb-implement <seq>` は**人がチケット番号を指定し、方針の承認を経てから**走る。エージェントが自律的に拾うのは `pb_next_task`（Phase 3） |
| **詰まり防止**（放置された占有を解く） | 占有しないので詰まらない |

**もう1つの理由は、本節が定めるリースが実際には何も排他しないことである。** 本節自身が「**第一の目的は、いま誰がどのチケットを触っているかを他の参加者に見せること**」「少人数運用では**緩やかな整合**で実害はない」と書いており、**設計文書のどこにも「リース保持中は他者の◯◯を拒む」という規定が無い**（`Design.md` 8.2）。**`lease_token` という名前だけが錠前の語彙を持ち込んでいた。**

**再検討の条件は、自律取得（`pb_next_task`）を実装するときである。** そのときは `working_agent_id` を「宣言」から「条件」へ格上げすれば足り、テーブルを足さずに済む（`DbDesign.md` 6.6）。**TTL による失効（`stale` の検知）が要ると分かった時点で**、`DbDesign.md` 8.2.2 の器を起こす。器は 0019 で既に在る。

以下は Phase 3 で起こすときの設計である。

タスクの take は排他ロックではなく **リース** とする。

- `pb_claim_task` が `lease_id` と TTL（既定30分）を返す
- 以降の write 系ツール呼び出しが暗黙のハートビートとなり、TTLを自動延長する
- TTL 経過後は `stale` 状態としてマークし、Web UI 上で「まだ作業中ですか？」と人間に確認を促す

**リースの第一の目的は、いま誰がどのチケットを触っているかを他の参加者に見せることである**（10.0.2 の 4）。同じ領域を2人が同時に触って片方の作業が無駄になることを防ぐ。**担当者の欄だけでは足りない**——担当は割り当てであって、いま作業中かどうかを表さない。

第二の目的が、放置されたロックでボードが詰まるのを防ぐことである。エージェントはクラッシュ・タイムアウト・ユーザーによる中断が日常的に発生し、人間のように「まだやっています」と自己申告しない。TTL を置くのはそのためである。

Runner による外形監視がないため厳密なハートビートは取れないが、少人数運用では上記の緩やかな整合で実害はない。

### 10.3.4 その他のプロトコル要件

- **冪等性**：**手順26a では受け付けない**（2026-09-05 に改訂）。エージェントは同一操作を再送しがちだが、26a の3ツールは再送が安全側に倒れる——`pb_put_doc` は `If-Match` があるので古い版での再送が `409`、`pb_create_ticket` と `pb_post_note` の重複は画面で見えて人が消せる。**本当の冪等性には「キー → 結果」を持つ器が要り**、`Design.md` 8.1 が「MCP に独自のビジネスルールを置かない」と定める以上、置き場は REST 層＝全クライアントに効く変更になる。**再検討の条件は `Design.md` 8.6** にある（リースが入ったとき／無人実行に踏み込んだとき）
- **エージェント識別**：`agent_id` は PB に登録された principal（10.10.3）。モデル名・バージョンを併せて記録し、モデル更新前後での品質変化を切り分け可能にする
- **同時実行制御**：プロジェクト単位で同時 claim 数の上限を設定できる
- **ワークフローバージョン**：`pb_get_task` の引数にクライアント側のワークフロー定義バージョンを含め、PB側が古いと判断した場合はレスポンスに再取得を促す警告を混ぜる（10.9.3）

## 10.4 コンテキストパック

本章で PB が提供する価値の中核であり、他ツールとの差別化点でもある。

### 10.4.1 設計思想：検索させず、押し付ける

エージェントは**自分が何を知らないかを知らない**。RAG検索ツールを与えても、そもそも検索すべきだと気づかない事項（例：「このモジュールのテストは並列化すると壊れる」）は永久に参照されない。

したがって PB は、タスクの内容から関連情報を能動的に選定し、`pb_get_context` の応答に**あらかじめ詰めて返す**。`pb_search` は補助的な深掘り手段として併置するが、主たる情報供給経路はプッシュとする。

### 10.4.2 構成要素と優先度

| 優先 | 要素 | ソース | 内容 |
|---|---|---|---|
| 1 | **スコープ境界と制約** | チケット | 触ってよい/いけない範囲、遵守すべき規約 |
| 2 | **プロジェクトメモリ（該当スコープ）** | メモリ（10.6.2） | 全体方針、当該コンポーネント固有の約束事 |
| 3 | **既知のCaveat・失敗記録** | 6.5 の分類 + 失敗記録 | 「このアプローチは試したが動かなかった」 |
| 4 | **関連するDecision** | 6.5 Decision Log | なぜ現在の設計になっているか |
| 5 | **依存・関連タスクの状態** | 依存グラフ、6.3 の関連リンク | 前提タスクの成果物、影響範囲 |
| 6 | **類似する過去タスクのクローズサマリー** | 6.5 のクローズ時サマリー | 実装パターンの参考 |
| 7 | **成果物マップの関連部分** | 6.5 Artifact Reference | 触るべきファイル・ドキュメントの所在 |

### 10.4.3 トークン予算制御

**Phase 2 では実装しない**（利用者の判断、2026-09-05。手順27）。**`pb_get_context` は `budget` を
受けず、憲章を全文で載せる。** 決め手は実測で、**stg の憲章は4文書で 3,601 文字**しか
なく、切り詰めが起きる規模に届いていない。**予算制御の器を先に作ると、要らなかったときに
戻せない**（`Design.md` 8.5.5）。**再検討の条件は `Design.md` 8.6** にある——`docs/PROGRESS.md` と
`docs/history/` が PB の文書へ移ったとき、または Phase 3 の `knowledge` が入ったとき。

**そのとき予算は、呼び出し側の引数ではなくサーバ側の上限として置く。** `budget` を引数にすると
**モデルが概算トークン数を1つ発明する**ことになり、値の根拠がどこにも無い。

以下は予算制御を入れるときの設計である。`budget` は概算トークン数を受け取り、以下の順に切り詰める。

1. 優先度1〜3は常に全文を含める（安全性に直結するため）
2. 優先度4〜7は、第6.6節で定義した階層圧縮を適用する
   - 直近・高関連度のものは全文
   - それ以外はクローズ時サマリー
   - さらに古いものは週次/月次ダイジェストの該当箇所
3. 予算超過時は、優先度の低い層から要約レベルを一段階下げる
4. 切り詰めた事実と、深掘り用のクエリ例を応答に明記する（「関連する過去タスクが12件あり、上位3件のみ含めた。`pb_search` で追加取得可能」）

第6.6節で設計した「重要度スコアによる選択的読み込み」と「多階層の情報圧縮」が、そのままエージェント向けのコンテキスト供給機構として機能する。**6.6は人間向けのサマリー生成コスト対策として設計したが、エージェント向けのコンテキスト予算管理と同一の課題であり、実装を共有できる。**

### 10.4.4 効果の計測

どのメモリ・どの情報を含めたときにタスク成功率・手戻り率が改善したかを記録し、コンテキストパックの選定ロジックを実績から学習させる。人間相手には測定できなかったループであり、エージェント運用だからこそ成立する。

## 10.5 タスク記述とDoDの機械可読化

### 10.5.1 Readiness（実行可能性）スコア

人間が書いた曖昧なチケットをそのままエージェントに渡すと高確率で失敗する。チケットの作成・編集時に、PB が LLM で「このタスクはエージェントが自律実行できるか」を判定し、不足を具体的に指摘する。

**判定観点の例**

- 入力（対象ファイル、対象機能）が特定できるか
- 受入条件が客観的に検証可能か（「使いやすくする」等の主観表現の検出）
- 影響範囲・スコープ境界が定義されているか
- 依存する前提タスクが未完了でないか
- 参照すべき設計情報がプロジェクトメモリに存在するか

**表示と運用**

信号機（赤／黄／緑）で表示し、赤のチケットはエージェントへの割り当てをブロックまたは警告する。指摘は「何が足りないか」を具体文で返し、PMがその場で修正できるようにする。

この機能は結果として **PMのチケット記述を鍛える** 効果を持ち、人間が消化する場合の品質にも寄与する。

### 10.5.2 DoDの型（第6.2節の拡張）

第6.2節で定義した3類型を、エージェントが自己検証可能な形に拡張する。

| 型 | 内容 | 検証者 |
|---|---|---|
| `manual` | 人間がチェックを入れる | 人間 |
| `task_ref` | 関連タスクの完了で自動チェック | PB |
| `assertion` | 検証コマンドと期待結果（`pytest tests/auth/` が pass、カバレッジ80%以上） | エージェント／CI |
| `artifact` | 指定の成果物・PRが存在する | PB／エージェント |
| `review` | 人間のレビュー承認が必須であることを明示宣言 | 人間 |

`assertion` と `artifact` の導入により、エージェントは実装後に自己検証ループを回せる。同時に PB 側が客観的に完了判定でき、**「AIが完了と言ったから完了」という状態を回避できる**。

`pb_submit_result` は未充足のDoD項目を応答として返し、エージェントに修正を促す。

**Phase 2 の実装では、これは「レポートの `dod_results` に `passed: true` として現れなかった
項目」である**（`ApiDesign.md` 9.15）。**`dod_item.is_satisfied` は書き換えない**——上表の
とおり `manual` の検証者は人間であり、いま API が開けている型は `manual` だけだからである。
**客観判定（`assertion` / `artifact`）が入るまで、盤面のチェックは人が付ける。**

### 10.5.3 スコープ境界フィールド

エージェントの逸脱防止は、プロンプトの注意書きではなく**構造データ**で行う。

```yaml
scope:
  allow:
    - "src/auth/**"
    - "tests/auth/**"
  deny:
    - "migrations/**"
    - "src/billing/**"
  repositories: ["my-app"]
  external_apis: []
```

チケットに保持し、コンテキストパックの最優先項目として渡す。境界外の変更が必要になった場合、エージェントは実装せず人間に相談する（10.8.2 のコマンド定義に明記）。

**書く経路は `PATCH /tickets/:seq` である**（手順27。`ApiDesign.md` 9.5.2）。列は Phase 1 から
在ったが**どの API も受け付けておらず、手順26c の時点で stg の40件すべてが空だった**——
「構造データで行う」と定めた当のデータに書き手が居なかった。**起票（`POST /tickets`）では
受けない。境界は縛る側が書くもの**であり、起票で受けると `pb_create_ticket` を通じて
**実装するエージェントが自分の境界を書ける経路**になる。

**未設定のときパックは空欄を出さず、「境界は設定されていない。境界の外かもしれない変更が
要ると判断したら、実装せず利用者に相談すること」と書く**（`Design.md` 8.5.5）。空欄を
「制約が無い」と読まれるのは、境界が無いことより悪い。

### 10.5.4 実行主体属性

チケットに実行主体の適性を持たせる。PMが指定するか、PBが推定して提案する。

- `agent-only`：エージェントに任せてよい
- `human-only`：人間が行う（判断の質、責任、機微な領域）
- `agent-draft`：エージェントが下書きし、人間がレビュー・仕上げ

ボード上でアイコン表示し、人間による消化とエージェントによる消化が同一ボード上で自然に併存するようにする。

### 10.5.5 見積りの二系列化

第6.1節の難易度推定に加え、**エージェント実行コスト**を別系列として保持する。

| 系列 | 指標 | 用途 |
|---|---|---|
| 人間工数見積り（6.1） | ストーリーポイント、時間 | 従来通りのスプリント計画 |
| エージェント実行コスト | 推定トークン数、推定ターン数、失敗確率 | 委譲判断、コスト管理 |

同じタスクでも人間とAIで難易度の質が異なる（定型的な大量作業はAIが得意、暗黙の文脈依存はAIが苦手）ため、学習モデルを分ける。**両者の乖離データ自体が「どんなタスクをAIに任せるべきか」という知見**となり、蓄積すれば `agent-only` / `human-only` の推定精度が向上する。

## 10.6 完了レポートと知識の還流

### 10.6.1 構造化完了レポート

`pb_submit_result` に渡すレポートのスキーマ。

**実装では `task_id` を持たない**（手順26c）。チケットは URL が指し（`ApiDesign.md` 9.1）、
MCP の引数では `seq` を受ける。残りのキーはそのまま最上位の引数になる（`Design.md` 8.5.4）。
**`dod_results[].id` は完了条件の ULID である**（`pb_get_task` の応答が返す値）。

```yaml
task_id: 123
status: completed | blocked | partial
artifacts:
  - type: pull_request
    url: "https://github.com/.../pull/45"
  - type: file
    path: "src/auth/oauth.rs"
dod_results:
  - id: dod-1
    type: assertion
    passed: true
    evidence: "pytest tests/auth/ → 24 passed"
  - id: dod-2
    type: review
    passed: false
    note: "人間のレビュー待ち"
findings:                       # 6.5 の情報類型に対応
  - kind: decision
    body: "リフレッシュトークンの保存先をXではなくYにした。理由は…"
  - kind: caveat
    body: "このモジュールのテストは並列実行すると失敗する"
failures:                       # 試して駄目だったこと
  - approach: "ライブラリZのミドルウェアを使う"
    reason: "非同期ランタイムのバージョンが競合"
proposed_subtasks:
  - title: "リフレッシュトークンのローテーション実装"
    rationale: "本タスクのスコープ外だが必要"
knowledge_impact: none | minor | major
cost:
  tokens: 128000
  turns: 34
  wall_clock_min: 42
```

### 10.6.2 プロジェクト文書（憲章）

**10.0.2 の 1〜3 に対する手当がこれである。** タスク横断で有効な知識を、プロジェクトに属する
**文書の木**として保持する。実質的に **`CLAUDE.md` 相当の内容を PB が管理し、全参加者の
エージェントが同じものを読む**設計である。

**PB は文書管理の機構を提供し、型はテンプレートとして配る。** データモデルに
「価値観」「規約」といった語彙を持たせない。プロジェクト作成時にテンプレートから初期の文書を
複製し、以後どう使うかはプロジェクトに委ねる。**ワークフローテンプレート（`DbDesign.md` 7.4）と
同じ機構である**——複製された後は、そのプロジェクトのものになる。

**テンプレートが用意する型**

| 文書 | 中身 | 迷ったときの効き方 |
|---|---|---|
| **価値観・世界観** | なぜこのプロジェクトが存在するか、何を目指し何を大切にするか | **書かれていない事態でも自分で判断できる** |
| **規約** | 守るべきルール、命名、進め方 | 既知の事態で迷わない |
| **判断の記録** | なぜそう決めたか、何を検討して棄却したか | 決着済みの再交渉を防ぐ |
| **学びと知見** | やってみて分かったこと。**うまくいったことと駄目だったことの両方** | 同じ躓きを繰り返さず、効いた手は引き継がれる |
| **エージェントの参画情報** | 作業材料をどう手元に用意するか、参画の合図、資格情報の要否 | **始めるまでに人へ口頭で聞かなくて済む** |

**5件目の「エージェントの参画情報」だけは性質が違う**（手順28c で足した）。上の4件が「判断の拠りどころ」であるのに対し、これは**作業を始めるための手順**である。**PB が完成品として出せるのは「MCP が使える状態になるまで」で、その先は PB が知らない**（10.9.1）ので、書く場所だけを用意して指し示す。**この1件はコンテキストパックの憲章に入れない**（`Design.md` 8.5.5）——**参画時に一度読むもので、チケットごとに毎回運ぶものではない。**

**規約は既知の事態に答えを与え、価値観は書かれていない事態の拠りどころになる。** 後者が無いと、規約に載っていない
場面でエージェントにできるのは「止まる」か「推測する」の2択しかない。**単独開発では価値観が
開発者の頭の中にあるので書かなくても回る。書き出す必要が生じるのは複数人になってからである。**

**後から足す文書は自由でよい。** プロジェクト特有の使い方、設計、それ以外の情報でも構わない。
テンプレートは出発点であって制約ではない。

**章単位で取り出せることを前提に設計する。** 文書は数百行に育つため、`pb_get_doc` が全文しか
返せない設計は、リポジトリの md ファイルより劣る（ファイルなら部分読みができる）。見出しを
アドレスとして持ち、章を指定して取得できるようにする。

**編集は、権限を持つ人とその手元のエージェントが直接行う。** PM がエージェントと議論し、
PM が「文書へ反映せよ」と指示したときに `pb_put_doc` が呼ばれる。**人が同席しているため、
提案と承認を分ける必要がない**——承認者はその場にいる。全変更をリビジョンとして保持し、
誰の・どの指示による変更かを残す。

**失敗の記録を第一級の資産とする。** 「このアプローチを試したが動かなかった」を残すことは、
人間向けPMツールでは軽視されがちだが、エージェントは同じ失敗を平然と繰り返すため効果が大きい。
**うまくいったことも同じ場所に置く**——「効いた手」を持ち帰れるのは書いた本人だけで、
書き残さない限り他の参加者には届かない。

**陳腐化と矛盾の検出**：長期間参照されていない記述、新しい決定と矛盾する記述を検出して提示する。
**古い知識が残り続ける方が、知識がない状態より危険**である。**これは Phase 3 で扱う**——
検出の材料（参照実績）が、運用を始めるまで手に入らないため。

**粒の細かいエンティティ化は Phase 3 へ送る。** 知識を1件1事実の行として持ち、スコープと種別で
絞ってコンテキストパックに全文で載せる構想（`scope` / `kind` / `usefulness` を持つ
プロジェクトメモリ）は有用だが、**まず文書として運用し、押し付けたい粒度が実測で見えてから**
エンティティに切り出す。先に器を作ると、要らなかったときに戻せない。

#### 憲章とリポジトリの役割分担（利用者の判断、2026-09-06）

**プロジェクトの規約の正本は PB 側に置く。** 理由は、`CLAUDE.md` が **Claude にしか効かない**ことである。エージェントの種別は増えていく（10.8.2）ので、**種別によらず MCP で取れる場所に正本を持つ。**

| 正本 | 何を | なぜそちらか |
|---|---|---|
| **PB（憲章）** | **進め方の規約**——絶対規則、ブランチ運用、命名と形式、振り返りの約束 | **参加者とエージェントの種別によらず同じものが読める。** 版と履歴が付く |
| **リポジトリ** | **設計文書**（`docs/*.md`） | **プロジェクトの成果物である。** 作った結果であって、進め方の取り決めではない |
| **リポジトリ** | **コマンド文書**（`.claude/commands/` 等） | **PM が推進のために用意した手順であり、これも成果物である。** 種別ごとの入口の違いは、常時コンテキストが差し替える（10.8.8） |
| **リポジトリ** | `make` のターゲット、技術スタック、構成、設計文書の索引 | **そのリポジトリの中でしか意味を持たない** |
| **各自の手元** | エージェント個体の学習（`LEARNINGS.md`） | **個体ごとの学習であって、共有する規約ではない**（利用者の判断、2026-09-06）。個人のセッション履歴から抽出した内容を含む |

**常時コンテキストのブロックは必ずローカルに要る**（10.8.8）。**これはブートストラップであり、読む前のエージェントは PB の存在すら知らない。** ここだけは写しであることを受け入れ、版番号で陳腐化を検出する（10.9.3）。

**設計文書を PB へ複製することは禁じない。** git を使えない参加者がいるなど、利便のために `docs` 配下へ複製したいプロジェクトはありうる。**そのときは「複製する」ことをそのプロジェクトの決定として規約に書く**（利用者の判断、2026-09-06）——**黙って二重に持たない**ことが要点である。

**この分担が無いと何が起きるかは実測されている**（2026-09-06、PB #31）。`rules` と `CLAUDE.md` が同じ規約を別の粒度で持ち、どちらが正本か書かれていなかった結果、**エージェントはローカルのほうを読んだ**——PB から読んだのは `pb_get_task` と `pb_get_context` の2回だけで、`pb_list_docs` / `pb_get_doc` は0回だった。**PB 側が古いままでも作業は回ってしまい、誰も気づけない。**

### 10.6.3 承認キューと合意形成

**承認キューの目的は、規約や設計の変更が全員を縛る前に、チームが見て決めることである。**

改訂前の本節は、この機構を「エージェントの誤った推論がプロジェクトメモリに入り、後続の
エージェントに伝播して増幅すること」への対策として位置づけていた。**人が同席する前提では、
この危険は主たるものではない**——エージェントの出力はその場で人が見ている。残る本質的な問題は
**「1人が決めたことが、他の N−1 人を黙って縛る」ほうである**。

| 対策 | 内容 |
|---|---|
| **提案止まり** | 承認されるまで確定させない。承認前のものはコンテキストパックに含めない |
| **差分レビューUI** | 更新提案は差分形式で表示し、承認・修正・却下を選択する |
| **出所の記録** | どのタスク・誰の・どのエージェント（モデル・バージョン）の提案かを常に保持 |
| **ロールバック** | 全変更を履歴として保持し、任意の時点に戻せる |
| **直列化** | 同一対象の更新は直列処理し、並行更新の衝突を防ぐ |

**承認粒度の設計が成否を分ける。** 全件を承認制にすると承認者がボトルネックになり、無承認だと
1人の判断が黙って全員に効く。**分ける軸は影響範囲である**——そのコンポーネントに閉じる変更か、
プロジェクト全体の約束を変える変更か。改訂前は `kind`（`caveat` は自動採用、`convention` は
承認必須）を軸に置いていたが、これは汚染対策としての軸であり、合意形成の軸ではない。

**本節の機構は Phase 3 で作る**（`Design.md` 11章）。Phase 2 では文書の編集を権限で直接行う
（10.6.2）ため、承認の対象になるものが揃わない。

### 10.6.4 プロジェクトヒストリーとの接続

第6.7節のプロジェクトヒストリーに対し、エージェントの完了レポートは良質なイベント候補源となる。`knowledge_impact: major` のレポート、長期ブロックされていたタスクのクローズ、複数タスクに影響するDecisionは、イベント候補として PM に提示する。セミオート方式（AIが候補提示、PMが取捨選択）は 6.7 の方針をそのまま踏襲する。

## 10.7 開発フロー

### 10.7.1 全体の流れ

```
[フェーズ0] セットアップ
  A. リポジトリの初回接続（1リポジトリにつき1回）
     PBのセットアップ画面 → 設定ファイルを配置してコミット
  B. メンバーの参画（参加者ごとに1回）
     トークン発行 → clone → export PB_TOKEN → /pb-onboard で接続確認
       → pb_get_project / pb_list_docs / pb_get_doc で憲章を読む
       → pb_list_tasks(assignee=me) で自分の担当を知る

[フェーズ1] タスク定義（ブラウザ、または対話するエージェント）
  チケット作成（画面から、あるいは議論の結果を pb_create_ticket で起票）
  → 「AI支援チェック」→ readiness判定・DoDドラフト・スコープ提案
  → 人が修正・確定 → 実行主体属性を指定

[フェーズ2] 実装（開発者とそのエージェント、ターミナル/IDE）
  /pb-implement 123
  → エージェントが pb_get_task / pb_get_context で契約と前提を取得
  → 不明点を人間に確認（対話）
  → 実装方針を提示・承認 → pb_transition_task（進行中へ）
  → 実装（重要判断は都度 pb_post_note）
  → DoD自己検証 → pb_submit_result

[フェーズ3] 完了と還流（ブラウザ）
  DoDの review 項目を確認 → チケットをクローズ
  → 知見を憲章へ反映する（権限を持つ人が、自分のエージェントに指示して pb_put_doc）
  → 6.5 のクローズ時サマリー生成、6.7 のヒストリーイベント候補提示
```

### 10.7.2 フェーズ1：AI支援チェック

「AI支援（チェック）」ボタンで起動する処理は、実装セッションとは**性質の異なるジョブ**である。この区別は設計上重要である。

| | AI支援チェック | 実装セッション |
|---|---|---|
| 寿命 | 短命（数秒〜数十秒） | 長命（数十分〜数時間） |
| 対話 | なし | あり |
| 副作用 | なし（冪等） | あり（コード変更） |
| 実行場所 | PBサーバ内（LLM API直接呼び出し） | ホストのエージェント |
| 権限 | 読み取りのみ | 書き込み含む |
| UI | 何度でも気軽に押せる | 同時実行数を制限 |

同じ「AIボタン」に見えても内部では別物として設計する。AI支援チェックは PB サーバから LLM API を直接呼ぶ形で実装でき、エージェント連携を必要としない。

**チェックの対象**

- 個別チケット：readiness判定、DoDドラフト生成、スコープ境界の提案、類似タスク・重複の検出（6.3）
- プロジェクト全体：依存関係の矛盾、放置タスクの検出、ドキュメントとチケット群の整合性

### 10.7.3 フェーズ2：作業ディレクトリの分離

1台のマシンで複数タスクを並行実行する場合、同一リポジトリの同一ブランチで複数エージェントが動くと即座に破綻する。

**タスク単位で git worktree を切る**運用を推奨する。

```
git worktree add ../my-app-pb-123 -b feature/pb-123-<スラッグ>
```

- **ブランチ名にチケット番号を含める**ことで、PBのチケットとブランチが1対1で対応する
- 完了時にマージし、worktree を破棄する
- コミットメッセージに `PB-123` を含める規約とすれば、Gitの履歴からPBへの逆引きも成立する

**接頭辞（`feature/` / `fix/` / `docs/`）は残す。** 改訂前は `pb/<チケットID>` に統一する案だったが、
**バージョン番号を上げる規則が接頭辞で決まる**（`Design.md` 11.1。`feature/` はマイナー、
`fix/` と `docs/` はビルド）。接頭辞を落とすと、`make bump-*` のどちらを打つかを git から
判断できなくなる。**チケット番号は接頭辞の後ろに置く**ことで、両方の要求を満たせる。

| 種別 | 形式 | 例 |
|---|---|---|
| 手順の実装 | `feature/step-<2桁>-<スラッグ>` | `feature/step-20-stg-instance` |
| 手順外の機能 | `feature/pb-<番号>-<スラッグ>` | `feature/pb-73-excel-export` |
| 機能を変えない修正 | `fix/pb-<番号>-<スラッグ>` | `fix/pb-57-seed-activity` |
| 設計文書のみ | `docs/pb-<番号>-<スラッグ>` | `docs/pb-81-ticket-api` |

**手順の実装は既に番号を持っている**（`step-20`）。ドッグフーディングでは**この番号がそのまま
チケット番号になる**ため、書式を変える必要がない。

この手順はコマンド定義（10.8.2）に含める。**正本は `Design.md` 11.0 である**——本節は
エージェント側の手順を書くために要る分だけを写している。

### 10.7.4 フェーズ2：会話ログの扱い

エージェントとの対話はターミナル/IDE側で完結するため、放置すれば PB には何も残らない。**エージェントとの会話は、なぜその実装方針にしたか・どの案を検討して棄却したかが人間同士のチケットコメントより遥かに高密度で現れる**ため、これを失うのは本設計の実質的な損失である。

対策は2段構え。

1. **要点を書かせる（両クライアント共通）**：`pb_post_note` のツール説明に「重要な判断をしたら都度呼ぶこと」と明記する。全文ログより、エージェントが選別した要点の方が質が高い場合も多い
2. **セッション終了時のフック（Claude Code のみ）**：セッション終了フックでトランスクリプトを PB に POST する。常駐プロセスではなく設定ファイルのみで実現でき、Runner とは負担が全く異なる

Copilot 側に同等のフック機構がないため、**Claude Code では全文が残り、Copilot では要点のみ残る**という非対称は受け入れる。

### 10.7.5 フェーズ3：ドキュメント更新の起動タイミング

当初、タスク完了イベントを契機に PB から独立したエージェントを起動し、設計ドキュメント・重要事項・履歴を自動更新する構想を検討した。pull型への転換に伴い、この自動起動は行わない。代替として以下を採る。

| 方式 | 内容 | 適用 |
|---|---|---|
| **同一セッション内で完結** | `/pb-implement` の手順末尾で、知見を `pb_post_note` に残す。**憲章へ反映するかは人が決め、指示されたときだけ `pb_put_doc` を呼ぶ** | 既定。文脈を保持したままのエージェントが書くため質が高い |
| **後でまとめて処理** | 溜まったノートを見ながら、区切りのよいところで `/pb-sync` を実行して憲章を整える | 複数タスク完了後、文書全体の整合を取りたい場合 |

**憲章の更新は、人が「反映せよ」と指示したときにだけ行われる**（10.6.2）。エージェントが自分の判断で文書を書き換えることはしない。**ただしそれは「提案として登録して承認を待つ」という意味ではない**——指示した人がその場にいるので、承認者はすでに同席している。

自動起動を諦めた結果、**並行更新の衝突・無駄な起動によるコスト消費・レビュー負荷の増大という懸念が同時に解消された**。人間が起動タイミングを握ることが、そのままガードレールとして機能している。

## 10.8 プロジェクトに初期配置するファイル

### 10.8.1 三層分離の原則

配置するファイルは、**接続設定・資格情報・手順**の三層に厳格に分離する。

| 層 | ファイル | 中身 | Git | モデルのコンテキストに載るか |
|---|---|---|---|---|
| 接続設定 | `.mcp.json`（Claude Code）<br>`.vscode/mcp.json`（Copilot）<br>`.codex/config.toml`（Codex） | サーバURL、トランスポート、認証ヘッダの**参照** | **コミットしない**（下記） | **載らない**（MCPクライアントが処理） |
| 資格情報 | 環境変数 / OSキーチェーン | トークンの実体 | **コミットしない** | **載らない** |
| 手順 | `.claude/commands/*.md`<br>`.github/prompts/*.prompt.md`<br>`.agents/skills/*/SKILL.md`（Codex） | ツール名と呼び出し順序のみ | コミットする | 載る |
| 常時コンテキスト | `CLAUDE.md`<br>`.github/copilot-instructions.md`<br>`AGENTS.md`（Codex） | プロジェクトの前提とPBへのポインタ | コミットする | 載る（毎セッション） |

#### Git 列を決める基準（利用者の判断、2026-09-06）

**その層が個人の情報または個人のカスタマイズを含みうるなら、履歴管理に入れない。** 上の表の値は、
すべてこの1行から導かれる。

**接続設定を「コミットしない」へ改めた**（改訂前は「コミットする」だった）。理由は2つで、
どちらも**接続設定が「人によって変わる層」だから**である——三層分離がこの層を独立させたのは、
まさにそのためだった。

| 起きること | 具体 |
|---|---|
| **個人環境の流出** | 各人のネットワーク事情でエンドポイントを書き換えて使う。それをコミットすると、**自宅や社内のホスト名・ポートが履歴に残る** |
| **上書き合戦** | PB 自身のリポジトリが実例である。`.mcp.json` は stg（`:8081`）を指しているが、dev（`:8080`）だけを動かす参加者は書き換えるしかなく、その書き換えをコミットすると今度は前者が壊れる |

**経験の浅い参加者の混乱も、この列で防ぐ**（同じく利用者の指摘）。「自分のエージェントに関する
ファイルがコミットされる」と読めること自体が事故のもとなので、**PB が生成する `.gitignore` の
追記で接続設定を名指しし、「これは各自の環境。共有しない」とコメントを添える**。

**手順と常時コンテキストはコミットする。** 個人環境に依存せず、しかも**各人の手元に置くと
10.9.2 の理由3 に正面から当たる**（N 人が少しずつ違う指示文を使い、誰も差に気づかない）。
**コミットする値打ちは「全員が同じものを持つ」ことではなく、ずれたときに `git diff` で見える
ことにある**——10.8.8 が言うとおり、危険なのは写しそのものではなく**検出手段のない写し**である。

**接続設定を落としても、リポジトリから PB への入口は消えない。** `CLAUDE.md` / `AGENTS.md` /
`copilot-instructions.md` のブロック（コミットする）がプロジェクトキーと `/pb-onboard` を
指し示す。**clone した人が「このリポジトリは PB で管理されている」と知る手がかりはそちらである。**

**手順ファイルには URL もトークンも一切書かない。** 手順ファイルの内容はプロンプトとしてモデルに読み込まれるため、そこに秘密を書けばトランスクリプトに残り、会話ログをPBに送る設計では PB の DB にも残り、エラー出力でそのまま echo される可能性があり、プロンプトインジェクションで抜かれる経路が開く。

**「モデルが読むファイルには秘密を書かない」** を原則として徹底する。

**PB が手順のテンプレートを持つのは3種別である**（`DbDesign.md` 8.2.1.1 の
`has_setup_template`）。`gemini` と `other` は種別として選べるが、配置ファイルを出さない。

`/me/agents` のエージェント欄から何度でも取り直せる（10.9.1 の系統B）。

**`pb-sync.md` は一覧から外した**（改訂前は Claude Code の行にあった）。差し替える対象である
10.9.3 の陳腐化検出が未実装で、**呼んでも何も起きないコマンドを配ることになる**ため。
検出の仕組みを入れる手順で戻す。

**クライアントが混在するリポジトリでは、3種別ぶんの手順ファイルが同居する。** 各クライアントは
自分のものしか読まないので衝突しない。**接続設定は誰の手元にも1枚ずつある**が、履歴には入らない。

#### Codex だけ入口の形が違う

**Codex には、リポジトリにコミットできるスラッシュコマンドが無い。** `/名前` で呼ぶ
「カスタムプロンプト」は `~/.codex/prompts`（**ユーザ単位・共有不可**）にしか置けず、しかも
非推奨で、後継の**スキル**へ誘導されている。スキルは `.agents/skills` をリポジトリルートまで
遡って探すので**コミットすれば全員に届く**が、起動は**説明文（`description`）による誘発**である。

**したがって Codex では `/pb-onboard` と打たない。**「PB に参画して」のように言うと、
`description` に合致したスキルが立ち上がる。**10.9.2 の理由3（各人が自分の手元に指示文を持つ）
には当たらない**——リポジトリに1つあり、全員が同じものを読むためである。

### 10.8.3 `.mcp.json`（Claude Code）

```json
{
  "mcpServers": {
    "pb": {
      "type": "http",
      "url": "http://localhost:8080/mcp/my-app",
      "headers": {
        "Authorization": "Bearer ${PB_TOKEN_MY_LAPTOP}"
      }
    }
  }
}
```

- `${PB_TOKEN_MY_LAPTOP}` は起動時にMCPクライアントが環境変数から展開する。**ファイルに実体は残らない**
- URLパスにプロジェクトキー（`my-app`）を含めることで、**手順ファイルをプロジェクト非依存に保てる**（10.8.9）
- PBサーバをリモートに移す場合、変更点はこのURLのみ。**このファイルは履歴管理の対象外**なので、
  書き換えても他の参加者に影響しない（10.8.1）

#### 環境変数名はエージェントごとに変える（利用者の判断、2026-09-06）

**変数名の接尾は、エージェントの登録時に本人が決める**（`agent.token_env_suffix`。
`DbDesign.md` 8.2.1、`ApiDesign.md` 4.5.2）。接頭の `PB_TOKEN_` は PB が付ける。

**固定名（`PB_TOKEN`）では足りない。** 環境変数は `~/.zshrc` の平らな名前空間に同居するため、
**同じ端末で2つ以上のエージェントを使うと衝突する**。衝突した状態の症状は
`404 not_found`（トークンのプロジェクトと URL のプロジェクトが食い違う。`Design.md` 8.3）で、
**利用者からは「トークンが古いのか、URL が違うのか、権限が無いのか」が見分けられない。**

**プロジェクトキーから導く案は採らない**（同 2026-09-06）。エージェントが増える主な軸は**端末**で、
「ノートPC の Claude Code」と「デスクトップの Claude Code」は**プロジェクトもクライアント種別も
同じ**になる——導出では区別できない。**表示名から導く案も採らない**——表示名は一意でなく
（キーは4つ組。`ApiDesign.md` 4.5.4）、日本語が通る一方で環境変数名は `[A-Za-z_][A-Za-z0-9_]*`
に限られ、かつ**改名できる**ので、`~/.zshrc` の行が黙って効かなくなる。

**「どの端末か」は PB が知らない情報である。** `ApiDesign.md` 4.5.1 が `display_name` を
「どの端末のどのクライアントかを**本人が**思い出すための手がかり」と定めているのと同じ理由で、
**利用者にしか書けないものは利用者に書いてもらう。**

### 10.8.4 `.vscode/mcp.json`（VS Code / Copilot）

```json
{
  "inputs": [
    {
      "id": "pb-token",
      "type": "promptString",
      "description": "Project Backyard アクセストークン",
      "password": true
    }
  ],
  "servers": {
    "pb": {
      "type": "http",
      "url": "http://localhost:8080/mcp/my-app",
      "headers": {
        "Authorization": "Bearer ${input:pb-token}"
      }
    }
  }
}
```

VS Code は初回にトークン入力を求め、以降は安全に保存する。ファイルに実体は残らない。

**この形式だけ環境変数を使わない**ので、10.8.3 の変数名の話は当たらない。ワークスペースごとに
別のトークンを保持できるため、同じ端末で複数のプロジェクトを開いても衝突しない。

### 10.8.4.1 `.codex/config.toml`（Codex）

```toml
[mcp_servers.pb]
url = "http://localhost:8080/mcp/my-app"
bearer_token_env_var = "PB_TOKEN_MY_LAPTOP"
default_tools_approval_mode = "prompt"
enabled_tools = ["pb_get_project", "pb_list_docs", …]

[mcp_servers.pb.tools.pb_get_project]
approval_mode = "auto"
```

- **Codex はリポジトリ直下の `.codex/config.toml` をプロジェクトスコープとして読む**（信頼済みの
  プロジェクトに限る）。`~/.codex/config.toml` はユーザ単位の同じ形式である
- **`bearer_token_env_var` は変数名そのものを書く**（`${…}` の展開ではない）。Codex が接続時に
  その環境変数を読み、`Authorization: Bearer …` として送る
- **3クライアントのうち、変数名を設定ファイル側で指定できるのは Codex だけ**である

#### ツールの許可も、このファイルに同居する（2026-09-06 に一次情報で確認）

**Codex はツールの自動承認を接続設定と同じファイルに書く。** `[mcp_servers.pb]` の直下に
`enabled_tools`（許可リスト）・`disabled_tools`（`enabled_tools` の後に適用される拒否リスト）・
`default_tools_approval_mode`（`auto` / `prompt` / `writes` / `approve`）を置き、
個別の上書きは `[mcp_servers.pb.tools.<ツール名>]` の `approval_mode` で行う。

**これは三層分離に対して、Claude Code と非対称である。**

| | 許可を書く場所 | Git |
|---|---|---|
| Claude Code | `.claude/settings.json`（接続設定とは**別のファイル**） | **コミットする** |
| **Codex** | **`.codex/config.toml`（接続設定と同じファイル）** | **除外**（10.8.1） |
| GitHub Copilot | **コミットできる仕組みが無い**（サンドボックス有効時は自動承認、他は UI・組織ポリシー） | — |

**帰結**：**Codex では「全員で共有したいツール許可」が各人の手元にしか置けない。**
逆に言えば、**それを配れるのは系統B（`ApiDesign.md` 4.5.8）だけ**である——**接続設定を出すときに
同じファイルへ一緒に書く。** 系統A（`.claude/settings.json`）と読み取り7件を揃える。

**Copilot には出せない。** 種別によって「できること」が違うのは PB の都合ではなく
クライアントの仕様なので、**無いものを補う工夫はしない**（利用者が VS Code の UI で承認する）。

### 10.8.5 `.claude/commands/pb-onboard.md`

**プロジェクトに参画したとき、および間が空いたときに実行する。** 憲章・自分の担当・リポジトリの所在を、その時点の内容で読み込む。

**読み取りしかしないコマンドである。** Claude Code のツール許可設定で read 系を自動承認にしておけば、確認を挟まず一息に走る（10.3.2）。

```markdown
---
description: PBのプロジェクトに参画する（規約と担当を読む）
allowed-tools: mcp__pb__pb_get_project, mcp__pb__pb_list_docs,
               mcp__pb__pb_get_doc, mcp__pb__pb_list_tasks
---

<!-- pb-workflow-version: 1 -->

このプロジェクトの前提を PB から読み込む。以下の手順を順守すること。

## 1. プロジェクトを知る
- `pb_get_project` でプロジェクト名・説明・リポジトリ・自分の役割を取得する
- 応答に警告が含まれていたら、そのままユーザーに伝える（10.9.3）

## 2. 憲章を読む
- `pb_list_docs` で文書の目次を取得する
- **価値観・規約・判断基準にあたる文書は全文を読む**（`pb_get_doc`）
- **「エージェントの参画情報」（`agent-onboarding`）があれば必ず読む。** 作業材料の取り方と参画の合図が書かれている。**無ければ利用者に尋ねる**——PB は取り方を知らない
- それ以外は目次の見出しだけを控え、必要になった時点で章を指定して読む
- **文書を全文まとめて読み込まない。** 目次から必要な章を特定して、その章だけを読む

## 3. 自分の担当を知る
- `pb_list_tasks` で自分に割り当てられた未完了のチケットを取得する

## 4. 報告と確認
- 読み取った規約・価値観のうち、**この作業場所での作業に効くものを要約して提示する**
- **作業材料がまだ手元に無いなら、参画情報に書かれた取り方を提示し、実行してよいかを確認する。** 勝手に取得しない
- 担当チケットを一覧で提示する
- **憲章の記述で意味が取れなかった箇所、矛盾していると思った箇所を挙げる**
- 以降、チケットに着手するときは `/pb-implement <id>` を使うことを案内する

## 禁止事項
- **PB を更新してはならない。** 本コマンドは読み取りのみである
- **憲章に書かれていないことを、書かれているかのように要約してはならない**
- 規約を要約する際に、原文の条件・例外を落としてはならない
```

`.github/prompts/pb-onboard.prompt.md` と `.agents/skills/pb-onboard/SKILL.md` も**同一内容**とし、
フロントマターのみ各クライアントの形式に合わせる（10.8.2）。**本文を3通り持たない**——
写しを3つ置けば必ずずれる。

**手順2 と 4 に参画情報の行を足したのは手順28c である**（10.9.1）。**PB が完成品として
出せるのは「MCP が使える状態になるまで」で、材料の取り方は PB が知らない。** 書かれた文書を
読ませる先が無ければ、文書を作っても誰も読みに行かない。**「勝手に取得しない」と書くのは、
参画が読み取りのコマンドだからである**——取得は作業場所を書き換える。

**あわせて「このリポジトリ」を「この作業場所」へ改めた。** リポジトリを持たないプロジェクト
（10.9.1 の MCP 型）でも同じ文面が使われる。

**手順4 の「意味が取れなかった箇所を挙げる」が実質的な価値である。** 憲章は人が書くため、書いた人には自明で読む人には分からない箇所が必ず残る。**それを最初に読むのがエージェントであれば、人が躓く前に洗い出せる。**

### 10.8.6 `.claude/commands/pb-implement.md`

**手順のみを記述し、30〜40行程度に収める。** 内容（チケット本文、DoD、設計情報）は一切書かず、すべて実行時に MCP で取得する。

```markdown
---
description: PBのチケットを実装する
argument-hint: <ticket-id>
allowed-tools: mcp__pb__*, Bash(git *), Read, Edit, Write
---

<!-- pb-workflow-version: 1 -->

チケット #$1 の実装を行う。以下の手順を順守すること。

## 1. 契約の取得
- `pb_get_task` でチケット本文・DoD・スコープ境界・実行モードを取得する
- `execution_mode` が `human_only` の場合、実装せずユーザーに報告して終了する
- `readiness` が `red` の場合、不足点を提示し、実装に進んでよいかユーザーに確認する

## 2. 前提情報の取得
- `pb_get_context` で設計方針・過去の決定・既知の注意点・失敗記録を取得する
- 不足があれば `pb_list_docs` で憲章の目次を見て、`pb_get_doc` で該当章を読む
- **プロジェクトの経緯を推測で判断しない。必ずPBに問い合わせる**

## 3. 確認と方針提示
- チケットの記述に不明点・曖昧さがあれば、**実装を始める前に**ユーザーに質問する
- 実装方針（変更するファイル、アプローチ、想定される影響）を提示し、承認を得る

## 4. 着手
- 承認後、`pb_transition_task` で状態を進行中へ進める（**他の参加者からボードで見える**。
  同時に `ticket.working_agent_id` が自分になる。`ApiDesign.md` 9.6）
- **進められるのは、自分の所有者が担当になっているチケットだけである。** 担当が付いて
  いなければ、実装せず利用者に伝える（`ApiDesign.md` 9.6 の検証6）
- 作業用の worktree とブランチを作成する
  `git worktree add ../<repo>-pb-$1 -b <接頭辞>/pb-$1-<スラッグ>`
  接頭辞は作業の種別で決める（`feature` / `fix` / `docs`。10.7.3）

## 5. 実装
- スコープ境界（`scope.allow` / `scope.deny`）の外にあるファイルは変更しない
- 境界外の変更が必要と判明した場合、実装せずユーザーに相談する
- 重要な判断・判明した事実は、その都度 `pb_post_note` で記録する
- タスクが大きすぎると判断した場合、**分割の案を提示してユーザーの判断を仰ぐ**

## 6. 検証
- DoD の各項目を検証し、結果を証跡として残す
- **人間の確認が必要な項目は、その旨を明示して報告する**
- コミットメッセージには `PB-$1` を含める

## 7. 報告
- `pb_submit_result` で構造化レポートを返す
  - 成果物、DoD各項目の判定と証跡、判明した事実、**試して駄目だったこと**、コスト
  - `knowledge_impact` を自己申告する
- **応答の `unsatisfied_dod` は自己申告との突き合わせであって、盤面は動いていない**
  （`ApiDesign.md` 9.15）。挙がった項目を直して再提出する

## 8. 知識の還流
- 次に同じ領域を触る人が知っておくべき知見を `pb_post_note` に残す
- 規約・設計判断・注意点・失敗事例を対象とする
- **憲章そのものへ反映すべきと考えたら、そう提案してユーザーの判断を仰ぐ。**
  指示された場合にかぎり `pb_put_doc` を呼ぶ

## 禁止事項
- **チケットをクローズしてはならない。** 完了判定は人間が行う
- **指示されていない文書の更新を行ってはならない。** 憲章は全参加者を縛るため、
  更新は権限を持つ人が明示的に指示したときにだけ行う
- スコープ境界外への変更を独断で行ってはならない
```

`.github/prompts/pb-implement.prompt.md` と `.agents/skills/pb-implement/SKILL.md` も**同一内容**とし、
フロントマターのみ各クライアントの形式に合わせる。

**本節の記述は、実装済みのツールに合わせて改訂した**（2026-09-06、手順28a）。改訂前は
`pb_propose_subtasks`（Phase 3。存在しない）を呼ばせ、実行モードを `human-only`、readiness を
「赤」と書いていた（実装値は `human_only` / `red`）。**手順ファイルは実行されるプロンプトである**
——存在しないツール名を書けばエージェントは毎回そこで詰まるか、代わりを発明する。

### 10.8.7 `.claude/commands/pb-refine.md`（補助コマンド）

```markdown
---
description: PBのチケット記述を改善する
argument-hint: <ticket-id>
---

<!-- pb-workflow-version: 1 -->

チケット #$1 の記述を、AIエージェントが自律実行できる水準まで引き上げる。

1. `pb_get_task` で現在の記述と readiness 判定を取得する
2. `pb_get_context` で関連する設計方針・過去の類似タスクを取得する
3. 以下の観点で不足を洗い出し、改善案を提示する
   - 対象ファイル・対象機能が特定できるか
   - 受入条件が客観的に検証可能か（主観表現の排除）
   - スコープ境界が定義されているか
   - DoD に `assertion` 型を追加できないか
4. 改善案はユーザーに提示し、承認を得た上で `pb_post_note` に記録する
5. **チケット本文の直接編集は行わない。** 修正はPBのUIで人間が行う
```

**Claude Code にだけ配る。** 10.8.2 の一覧が Copilot / Codex 版を挙げておらず、
**補助コマンドなので入口が揃っていなくても通しの経路は壊れない**（`/pb-onboard` と
`/pb-implement` の2つが揃っていればよい。10.9.4）。要望が出た時点で他の2種別へ広げる。

### 10.8.8 `CLAUDE.md` への追記ブロック

**憲章の本文をここに書き写してはならない。** PB のプロジェクト文書と二重管理になり、必ず乖離する。**ただし、絶対に読み飛ばされてはならない数行だけは例外とする。**

```markdown
<!-- PB:BEGIN v1 (Project Backyard が生成・管理します。手動編集は上書きされます) -->
<!-- 貼る前に: git pull して、リポジトリに新しい版が入っていないか確かめる -->
<!-- 貼った後に: git diff でこのブロックを見て、他の人の更新を潰していないか確かめる -->
## プロジェクト管理 — Project Backyard

本プロジェクトのタスク・規約・設計判断・履歴は Project Backyard (PB) で管理している。
MCPサーバ `pb` 経由でアクセスできる。

- **参画したとき、および間が空いたときは `/pb-onboard` を実行する**
- チケットに着手する際は `/pb-implement <id>` を使う
- チケットの記述を改善したいときは `/pb-refine <id>` を使う
- **「なぜこうなっているか」を推測で判断せず、まずPBに問い合わせること**
- チケットのクローズは行わない。**憲章の更新は、指示されたときにだけ行う**

プロジェクトキー: `my-app`
<!-- PB:END -->
```

**版番号は `v1` から始める**（改訂前の本節は `v3` と書いていたが、その数字の由来はどこにも無かった。
2026-09-06 に改めた）。

#### 反映するときの注意（利用者の要望、2026-09-06）

**ブロックの2行目・3行目は、生成物そのものに埋め込む注意書きである。** 常時コンテキストは
**コミットされ全員で共有される**のに対し、**それを自分のリポジトリへ貼るのは各人の手作業**である
——この非対称が事故を生む。

| いつ | 何を確かめるか | なぜ |
|---|---|---|
| **貼る前** | `git pull` して、リポジトリに自分の手元より新しい版が入っていないか | 他の参加者が先に取り直してコミットしているかもしれない。**古い版を上から貼ると巻き戻る** |
| **貼った後** | `git diff` でマーカー内の差分を見る | **自分の更新のつもりが、他人の更新を消していないか。** マーカーの外を巻き込んでいないか |

**同じ注意書きを、セットアップ画面の該当行にも出す**（`GuiDesign.md` 5.11）。生成物の中だけに
書くと、**貼り終えた後にしか読まれない。**

**「推測で判断せず、まずPBに問い合わせる」が実質的な価値である。** エージェントの最も危険な挙動は「分からないことを推測で埋める」ことであり、参照先の存在を常時コンテキストに刻んでおく意味がここにある。

#### 写しを禁じる原則と、このブロックの関係

原則2（静的ファイルには手順のみ）に照らすと、このブロックは写しに見える。**禁じるべきものと、そうでないものを分ける。**

| | 危険な写し | このブロック |
|---|---|---|
| 中身 | 憲章の本文（規約の詳細、判断の記録） | **禁止事項と入口の案内だけ**。数行 |
| 古くなったとき | **気づけない。** 読んだ人は正しいと信じる | **検出できる**（下記） |
| 更新のたびに | 配布物を配り直す運用になる | ブロックだけ差し替える |

**危険なのは「写し」そのものではなく、「検出手段のない写し」である。** 版番号を付けて古さを検出できるなら、これはキャッシュであって二重管理ではない。

**陳腐化の検出**は 10.9.3 の仕組みをそのまま使う。

1. ブロックの先頭に `<!-- PB:BEGIN v1 -->` として版番号を埋める
2. `pb_get_project` / `pb_get_task` の呼び出しにその版番号を渡す
3. PB 側が古いと判断したら、応答に警告を混ぜて返す
4. ブロックを最新版へ差し替える

**2〜4 はまだ実装していない**（手順28a の時点）。**1 だけが動いている**——生成物に版番号が
埋まるので、後から突き合わせる材料はできた。**当面の運用は「気づいた人が
`/p/:key/settings/agents` から取り直して差し替え、コミットする」である**。

#### 誰が・いつ差し替えるか（利用者の指摘、2026-09-06）

**常時コンテキストは共有物なので、編集の契機と担い手を決めておかないと誰も直さない。**
正本は三段になる。

| 段 | 実体 | 誰が変えるか |
|---|---|---|
| 設計の正本 | **本節**（何を書いてよいか＝絶対規則にあたる数行だけ） | PB の開発 |
| 生成の正本 | PB サーバに埋め込んだテンプレート。版番号が上がる | 同上 |
| 配置された写し | 各リポジトリの `CLAUDE.md` などのマーカー内 | **気づいた人**（下記） |

- **マーカーの外は誰の自由でもよい。** PB は触らない
- **マーカーの中は PB の管理範囲。** 手で書いても次の差し替えで消える
- **差し替えの契機は、版番号が上がったとき。** 気づいた人がセットアップ画面から取り直して
  コミットする。**差し替えは1人が1回行えば全員に届く**（コミットされるため）

**ブロックに入れてよいのは、絶対規則にあたる数行だけである。** 「これを読み飛ばすと事故になる」ものに限る。判断に迷う規約や、その理由は憲章に置き、`/pb-onboard` で読ませる。**ブロックが育ち始めたら、それは憲章へ移すべき内容である。**

`<!-- PB:BEGIN -->` / `<!-- PB:END -->` のマーカーで囲むことで、PBによる再生成時に手書き部分を破壊しない。**`.github/copilot-instructions.md`（Copilot）と `AGENTS.md`（Codex）にも同一のブロックを置く。**

### 10.8.9 手順ファイルをプロジェクト非依存に保つ

手順ファイルは `/pb-implement 123` としか指定しないため、「どのプロジェクトの123か」をどこかで解決する必要がある。手順ファイルに `project: my-app` と書く方法もあるが、以下の理由で**接続層で解決する**方針を採る。

- **トークンにプロジェクトスコープを持たせる**：PBのプロジェクト設定画面で「このリポジトリ用のトークン」を発行し、トークン自体がプロジェクトに紐づく
- **URLパスに含める**：`http://localhost:8080/mcp/my-app`（トークンとの整合性はサーバ側で検証）

これにより手順ファイルが完全にプロジェクト非依存となり、**すべてのリポジトリで同一の雛形を使い回せる**。10.9 の配布も単一の配布物で済む。トークンにスコープを持たせる設計は、10.10.3 のエージェント権限管理とも一貫する。

### 10.8.10 資格情報の配置

```bash
# ~/.zshrc あるいは direnv (.envrc)
export PB_TOKEN_MY_LAPTOP="pb_agt_xxxxxxxxxxxxxxxx"
```

- **変数名はエージェントごとに変わる**（10.8.3）。接尾は登録時に本人が決め、接頭の `PB_TOKEN_` は
  PB が付ける。**エージェントを N 件持つ人は、この行を N 行並べる**
- `.envrc` を使う場合は `.gitignore` に追加する（PB が生成する `.gitignore` の追記に含まれる）
- **PBのセットアップ画面でこの行をそのままコピーできるようにする。** 平文のトークンは発行時に
  一度しか表示されないので、**画面が出すのは変数名までで、値はプレースホルダである**
  （`GuiDesign.md` 5.8.2）。失った場合は再発行する

## 10.9 配布と初期セットアップ

### 10.9.1 生成場所：PBのセットアップ画面

配置ファイルは **PB のセットアップ画面**で生成する。プロジェクトキー・サーバURLはPB側が知っているため、利用者が編集すべき箇所のない完成品を出力できる。

**2系統ある。** 起きることが違い、必要なものも、**置き場所も違う**。

| 系統 | いつ | 誰が | どこで | 何が要るか |
|---|---|---|---|---|
| **A. リポジトリの初回接続** | プロジェクトとリポジトリを結ぶとき。**1リポジトリにつき1回** | プロジェクトを作った人 | **プロジェクト設定**（`/p/:key/settings/agents`） | **コミットする配置ファイル**（手順・常時コンテキスト・`.gitignore`） |
| **B. メンバーの参画** | 新しい参加者が加わるたび。**そのあと何度でも** | **参加する本人** | **自分の設定**（`/me/agents` のエージェントごと） | **自分の接続設定**、clone コマンド、自分用のトークン、`export` 行 |

**接続設定は系統B にしか出ない**（10.8.1 の Git 列を改めたことの帰結、2026-09-06）。
履歴管理に入れないと決めた以上、**リポジトリに置くものを作る場（A）で出しても置き場がない。**
各人が自分のエージェントの欄から取る。

**系統Bを本人の設定に置く**（利用者の判断、2026-08-30。手順24）。改訂前は2系統ともプロジェクト設定に置いていたが、3つの理由で分けた。

1. **トークンは発行時に一度だけ全文表示される。** プロジェクト管理者が受け取って本人へ転送する経路は、10.10.1 の三層分離（秘密をモデルにも余計な経路にも通さない）と噛み合わない
2. **エージェントは所有者の権限を基準に動く**（10.10.3、`Design.md` 6.5 の委譲）。本人の操作にしておけば、**自分の権限を超えるエージェントを自分では作れない**——上限が自分自身になる
3. **エージェントは端末側の実体である**（10.2.1）。どのクライアントをどのモデルで使っているかは、端末を持っている本人しか知らない

系統Aは**リポジトリに置くファイル**を作る作業で、コミットされる成果物であり、プロジェクトに1回だけ起きる。こちらはプロジェクト設定に残る。

**A：リポジトリの初回接続**（`/p/:key/settings/agents`。必要権限は `agent.register`）

1. **クライアント選択**（`has_setup_template` を持つ種別を複数選べる。10.8.2）
2. **配置ファイルの表示**：各ファイルの内容をパス付きで表示し、ファイルごとのコピーボタンと一括zipダウンロードを提供
3. **`.gitignore` への追記内容**（接続設定と `.envrc` の除外を含む）

**この画面はトークンを扱わない。** 出るのは全員で共有するファイルだけである。

**B：メンバーの参画**（`/me/agents` のエージェントごと。必要権限は本人）

1. **トークン発行**：有効期限を指定して発行。**発行時に一度だけ全文表示**し、以降はマスクする。**トークンは参加者ごとに発行する**（10.10.3）
2. **自分の接続設定**：そのエージェントの `client_kind` に対応する接続設定を表示し、コピーとzipで渡す
3. **環境変数の設定行**：`export PB_TOKEN_<接尾>=...` をコピーボタン付きで表示
4. **接続確認**：「エージェントを起動して参画の手順を実行してください」と案内し、初回接続を検知したら画面上でチェックが付く
5. **作業材料の取り方への導線**：**PB は取り方を知らない。** プロジェクトの文書「エージェントの参画情報」（`agent-onboarding`）へ深リンクする（下記）

**改訂前の 1 は「clone コマンド」だった**（利用者の指摘、2026-09-06）。**PB が想定するのは
ソフトウェア開発だけではない**ので、`project.settings.repositories` から clone を組み立てる形は、
**リポジトリを持つプロジェクトにしか当てはまらない。** 想定するのは少なくとも3通りある。

| 型 | 材料の取り方 |
|---|---|
| リポジトリ型 | `git clone <URL>`（GitHub 等、あるいはローカルの git） |
| 配布型 | zip などで各端末へ配られたものを展開する／既定のパスに置く |
| **MCP 型** | **手元に材料を持たない。** PB の文書を `pb_get_doc` で読むことが作業そのもの |

**したがって、取り方はプロジェクト管理者が指定する**（利用者の判断、2026-09-06）。
**置き場は PB の文書である**（`settings` ではない）。理由は2つ。

1. **MCP 型で辻褄が合う唯一の置き場である。** 「手元に材料を持たず PB から読む」型では、
   **取り方の説明そのものも PB から読めなければならない。** `settings` に置くと画面にしか出ず、
   エージェントは自力で辿り着けない
2. **同じ1枚が人とエージェントの両方に届く。** 人は画面で読み、エージェントは `pb_get_doc` で読む

**その文書は文書テンプレートの5件目として配る**（手順28c で実装。`DbDesign.md` 8.1.2）。

| | 決めたこと |
|---|---|
| `slug` / 表題 | **`agent-onboarding`** ／ **「エージェントの参画情報」** |
| 並び | `sort_order` 50（憲章4件の後ろ） |
| 初期本文 | **空にしない。** 3つの型を並べ、「当てはまらない型は消してよい」と書く |
| コンテキストパック | **載せない**（`Design.md` 8.5.5）。参画時に一度読むもので、チケットごとに毎回運ぶものではない |
| 無いとき | **必須にしない。** 複製が走るのはプロジェクト作成時だけなので、**それ以前のプロジェクトには入らない**（`DbDesign.md` 8.1.2）。画面の導線は `✕ 指定された文書が見つかりません` を出し、文書ツリーは残る |

**必須にできないことは制約ではなく、この文書の性質である。** 中身を書けるのはプロジェクト管理者だけで、**PB が用意できるのは「書く場所」までである。**

#### MCP 型では系統A に置き場が無い

**系統A が作るのは「リポジトリにコミットする配置ファイル」**（手順・常時コンテキスト・`.gitignore`）だが、**MCP 型にはコミットする先が無い。** 手順ファイル（`.claude/commands/pb-onboard.md`）はリポジトリの中にある前提で書かれている。

**手当ては、参画情報の文書に「参画の合図」を書くことである**（利用者の判断、2026-09-06）。**手順ファイルが置かれていないなら、エージェントには「PB に参画して」と一文で伝えれば足りる**——これは Codex に対して既に採っている形であり（10.8.2。Codex はスラッシュコマンドを持たない）、**①立ち上げ相で専用コマンドを作らないと決めたのと同じ判断である。**

**系統A の口をメンバーへ開く案は採らなかった。** `agent-setup` の必要権限（`agent.register`）を下げても、**画面は 5.11＝プロジェクト設定の中にあり `project.edit` が要る**ので参加者には届かない。**足りないのは口ではなく受け取り面である。** 作るなら独立した1画面として設計する（**再検討の条件は、MCP 型のプロジェクトで参加者が実際に手順ファイルを欲しがったとき**）。

#### 系統B には二相がある（利用者の指摘、2026-09-06）

| | ① 立ち上げ相 | ② 参画相 |
|---|---|---|
| 誰が | PM と、その補佐をするエージェント | メンバーと、その実装エージェント |
| 文書の状態 | **雛形のまま**（`DbDesign.md` 8.1.2 の初期本文） | 書き込まれている |
| 最初の仕事 | **PM とエージェントで文書を書く** | 文書を読んで**自分で**整える |
| トークンに載せる権限 | **`doc.edit` を足す**（`ApiDesign.md` 4.5.3。発行モーダルのチェック） | 既定8件のまま |

**②では、材料の取得をエージェント自身が行える。** 文書に取り方が書かれているためで、
**人の手作業は「MCP が使える状態にする」までで終わる**（上の 1〜4）。

**①には専用のコマンドを作らない**（利用者の判断、2026-09-06）。PM がチャットで
「docs 配下の文書を読んで、作り上げるのを支援して」と言えば足りる。**スラッシュコマンドは
共通の仕組みではなく**（Codex は持たない。10.8.2）、**3種別ぶんの写しを作ることになる**。
**10.9.2 の「貼り付け運用を採らない」にも当たらない**——貼るのは一文で、
**中身は文書テンプレートとして PB にあり、実行時に MCP で取得される**（原則2）。

**5 を足したのは利用者の要望である**（2026-09-06）。理由は2つ。

| 理由 | 具体 |
|---|---|
| **同じ人でも、エージェントごとに置き場が違う** | `client_kind` が決めるのは**設定ファイルの置き場**である（`DbDesign.md` 8.2.1.1）。Claude Code なら `.mcp.json`、Codex なら `.codex/config.toml`。**「自分は何を置けばよいか」は、プロジェクト設定側からは答えられない**——そちらはその人がどのクライアントを使っているかを知らない |
| **壊れたときに取り直せる必要がある** | 端末を替えた、設定を消した、機種変更した。**何度でも開けること自体が要件**である |

**トークンの平文はここに出ない。** `GET /me/agents` は返さない（`ApiDesign.md` 4.5.1）し、
**何度でも開ける画面に平文を置くのは 10.10.1 に反する**。`export` 行は変数名までを出し、値は
プレースホルダにする。**失った場合の復旧経路は再発行である。**

**B が必要な理由**：**エージェントは自分をブートストラップできない。** 手順ファイル（`.claude/commands/`）はリポジトリの中にあるため、clone より前には使えない。**clone コマンドとトークンと接続設定をどこかで人が受け取る必要があり、その場が `/me/agents` である。** 改訂前の本節は A だけを想定しており、「既にあるリポジトリに人が加わる」場面の記述が無かった。

**Bの1（トークン発行）は手順24 で先に実装した。** 登録・発行・失効は `ApiDesign.md` 4.5 にあり、画面は `GuiDesign.md` 5.8.2 のエージェントタブである（手順24b で実装済み）。**2・3・4 は手順28b**（`ApiDesign.md` 4.5.8）、**5 は手順28c** である。

**「閲覧用＝read only」のトークンは作らない**（利用者の判断、2026-09-06。改訂前は本節の 2 に
「用途（実装用=write可 / 閲覧用=read only）」と書いていた）。**情報を見るだけのエージェントが
何をするのかが Phase 2 では決まっていない**ため。**再検討の条件は、read だけを持つ
エージェントの役割が現れたとき**——そのとき `ApiDesign.md` 4.5.3 の `scopes` を絞る用途として
設計する（`client/src/lib/agents.ts` の写しはそのために絶対指定のまま置いてある）。

### 10.9.2 配布方式の比較

| 方式 | 内容 | 評価 |
|---|---|---|
| **UIからダウンロード／コピー** | セットアップ画面でzip配布とクリップボードコピー | 実装が最も軽い。**初期はこれで十分** |
| CLIで初期化 | `pb init` がカレントリポジトリに配置。既存ファイルはマーカー部分のみ更新 | 体験は良いがCLI配布・更新の手間 |
| MCPツールで取得 | `pb_get_workflow` を用意し、手順ファイルは「まずこれを呼べ」の3行スタブ | 常に最新。ただし1往復増え、手順の可読性が下がる |

小規模・ローカル利用を主眼とする本ツールでは、**ダウンロード＋クリップボードコピー**を採用する。**手順と常時コンテキストはリポジトリにコミットされる**ため、チーム利用時も自然に共有される（接続設定だけは各人の手元に残る。10.8.1）。

**セッションごとに指示文を貼り付ける運用は採らない。** 「新規参加者向けの指示サンプルを用意し、
毎回チャットの冒頭に貼る」という方式も検討したが、以下の理由で棄却した。

| # | 理由 |
|---|---|
| 1 | **原則2 に反する。** 貼り付けたテキストは静的な写しであり、必ず陳腐化する。しかも 10.9.3 の陳腐化検出は `<!-- pb-workflow-version: N -->` を**ファイルに埋めて**成立するため、貼り付け運用では検出が効かない |
| 2 | **毎セッション、プロジェクトの中身がトランスクリプトに載る。** トークンを消費し、10.10.6 のプロンプトインジェクションの面も広がる |
| 3 | **各人が自分の手元に指示文を持つ形になる。** N 人が少しずつ違う指示文を使い、誰も差に気づかない。**これは 10.0.2 の 1 と同じ形の問題であり、PB を導入する理由そのものを損なう** |

**したがって、参画時の指示も「コミットされたコマンドファイル」として配る**（`/pb-onboard`、10.8.5）。貼り付けが要るのは初回セットアップの1回だけで、その成果物はコミットされる。

**この判断は、規約の正本を PB へ移したあとも維持する**（利用者の判断、2026-09-06。10.6.2）。**コマンド文書は PM が推進のために用意した成果物**であり、規約そのものではない。**`pb_get_workflow` で手順を毎回取りに行く案を復活させる必要は無い**——**種別ごとの入口の違いは、常時コンテキストのブロックが既に差し替えている**（10.8.8。`onboardRef` / `implementRef` が種別ごとに変わる）ので、**3種別ぶんの写しにはならない。**

**規約は PB、手順はリポジトリ、という切り分けである。** 手順の中で「どう判断するか」に当たる部分——問いの立て方、推奨の出し方、振り返りの型——は**規約なので PB 側に置く**。手順ファイルはそれを**呼ぶ順序**を持つ。

### 10.9.3 ワークフローバージョンの陳腐化検出

配布物が古いまま使われ続ける問題を防ぐため、軽量な仕組みを組み込む。

1. 生成した手順ファイルの先頭に `<!-- pb-workflow-version: N -->` を埋め込む
2. 手順の冒頭で呼ぶ `pb_get_task` に、そのバージョンを渡す
3. PB側が古いと判断した場合、レスポンスに警告を混ぜて返す
   ```
   warning: "ワークフロー定義が古い（v1、最新v3）。PBのセットアップ画面から再取得を推奨"
   ```
4. Web UI 側でも、接続してきたクライアントのバージョンを表示する

実装は数行だが、運用上の効果は大きい。

### 10.9.4 利用者の手順（まとめ）

**A：リポジトリの初回接続（1リポジトリにつき1回）**

```
1. PB Web UI でプロジェクトを作成し、プロジェクト設定にリポジトリURLを登録する
2. 「エージェント連携セットアップ」画面を開く（/p/<key>/settings/agents）
3. 使うクライアント（Claude Code / Copilot / Codex）に印を付ける
4. 設定ファイル一式をダウンロードし、リポジトリ直下に展開
   （既存の CLAUDE.md / AGENTS.md 等がある場合はマーカーブロックのみ追記。
     貼る前に git pull、貼った後に git diff。10.8.8）
5. .gitignore の追記内容を反映し、生成ファイルをコミットする
   → 接続設定（.mcp.json 等）はここに含まれない。各人が B で受け取る
```

**B：メンバーの参画（参加者ごとに1回。以降、必要になるたび何度でも）**

```
1. PB にログインし、/me/agents で自分のエージェントを登録する
   （クライアント種別と、トークンの環境変数名の接尾を決める）
2. トークンを発行する（発行時に一度だけ全文表示される）
3. 作業フォルダを用意する
   → 取り方はプロジェクトの文書「エージェントの参画情報」にある
     （接続の手順の 1 からリンクされている）。リポジトリ型なら clone する。
     配布型なら展開する。MCP 型ならエージェントを動かす場所を1つ決めるだけでよい
4. 同じエージェントの欄の接続設定（.mcp.json / .vscode/mcp.json /
   .codex/config.toml）を落として、3 のフォルダへ置く（履歴管理の対象外）
   → zip の中では別名になっている。展開してから元の名前へ戻す
5. 表示された export 行を ~/.zshrc あるいは direnv に追記し、2 の全文を入れる
   → Copilot だけはこの手順が無い（VS Code が初回に入力を求める。10.8.4）
6. エージェントを起動し、参画の手順を実行する（Claude Code と Copilot は
   /pb-onboard、Codex は「PB に参画して」と伝える。10.8.2）
   → プロジェクト概要・憲章・自分に割り当てられたチケットを読む
   → PB の画面に「接続済み」のチェックが付く
```

**4 が増えたのは、接続設定を履歴管理から外したためである**（10.8.1）。**手順が1つ増える代わりに、
各人が自分のネットワーク事情に合わせて書き換えても他の参加者に影響しない。**

**3 と 4〜5 の順序に意味がある**（利用者の指摘、2026-09-06）。**PB が完成品を出せるのは
「MCP が使える状態になるまで」**（4〜6）で、**3 は PB が知らない**。改訂前は 3 を
「clone コマンドをコピーして実行する」と書いてリポジトリ型を前提にしていた。

**以降、セッションは `/pb-onboard`（参画直後や間が空いたとき）と `/pb-implement <id>`（チケットに着手するとき）の2つで始まる。** PB の画面からターミナルへ貼り付けるものは無い——**手順はリポジトリの中にあり、内容は実行時に MCP で取得される**（原則2）。

**Codex だけは打鍵が違う**（10.8.2）。スラッシュコマンドではなく、「PB に参画して」のように
言うとスキルが誘発される。**読むものと呼ぶ順序は3種別で同一である。**

## 10.10 セキュリティとガードレール

### 10.10.1 秘密をモデルのコンテキストに入れない

10.8.1 の三層分離が本項の中核である。加えて、

- **エージェント向けの経路はMCPに一本化する**。REST API を直接叩かせる設計を採らない。`curl -H "Authorization: Bearer ..."` を組み立てさせた時点で、資格情報がモデルのコンテキストを通過する
- REST API は Web UI と将来の自動化用途のために残すが、エージェントから見える面は MCP のみとする
- MCPサーバは、トークン・接続情報・他プロジェクトのデータを返すツールを一切持たない

### 10.10.2 ネットワークと認証

- PBサーバは `127.0.0.1` にのみバインドする（`0.0.0.0` にしない）
- localhost であっても認証は必須とする。同一マシン上の任意のプロセスがポートを叩けるため
- プロジェクト単位の長期トークンを発行し、失効可能とする
- トークンは環境変数（`~/.zshrc` または direnv）に置き、ファイルにも Git にも残さない

### 10.10.3 エージェントの権限モデル

エージェントは人間アカウントの借用ではなく、**独立した principal** として登録する。

- 属性：エージェント名、モデル名、モデルバージョン、能力タグ、**どの参加者に付いているか**
- トークンにスコープを付与：プロジェクト、許可操作（read / write）、有効期限
- 操作単位の制限：「チケットのクローズは不可」「憲章の更新は指示されたときのみ」
- **履歴に「どのモデルのどのバージョンが実施したか」を残す**。モデル更新後に品質が変化した際の切り分けに必要

**トークンは参加者ごとに発行する**（10.9.1 の系統B）。1リポジトリに1本ではない。参加者が N 人いれば N 個の principal が並び、**事故の追跡が「どのモデルが」ではなく「誰の環境で」から始められる**。同じ人が Claude Code と VS Code の両方を使う場合も、クライアントごとに分ける。

**信頼度の段階運用**：新規に登録したエージェント／モデルは低権限から始め、成功率とレビュー通過率の実績に応じて権限昇格を提案する。

### 10.10.4 承認ゲート

ワークフロー定義（第2章）に `requires_human_approval` を第一級要素として持たせる。エージェントは `in_review` までしかステータスを進められず、これは PB 側で API レベルに強制する。プロンプトでの約束に依存しない。

### 10.10.5 サーキットブレーカー

以下の条件で自動停止し、PM にエスカレーションする。

- 同一タスクのリトライ回数が閾値超過
- 連続失敗回数が閾値超過
- 累積トークンコストがプロジェクト設定の上限を超過

無限ループによる課金事故は現実的なリスクであり、`pb_submit_result` のコスト情報を用いて PB 側で監視する。

### 10.10.6 プロンプトインジェクション

**チケット本文はそのままエージェントへの指示になる。** 外部（顧客、Webフォーム、メール連携、他のプロジェクト管理製品からの移行データ）からチケットを起票できる構成にすると、攻撃経路が成立する。

- チケットに `source`（起票元）を保持し、信頼できない起票元にはフラグを立てる
- フラグ付きチケットは、エージェント実行前に人間の確認を必須とする
- 第5章の「期限付きトークンによる公開URL」を書き込み可能に拡張する場合は、特に注意する

### 10.10.7 監査ログ

事故時に「エージェントが何を見て、何を判断し、何を変更したか」を再現できることが重要である。

- どのエージェントが、いつ、どのコンテキストパック（含めた情報のID一覧）を受け取ったか
- どのツールを、どの引数で呼んだか
- どの知識を更新提案し、誰が承認したか

コンテキストパックの内容を記録しておくことは、10.4.4 の効果計測にもそのまま使える。

## 10.11 この方式の限界

正直に記載しておく。

| 限界 | 内容 | 将来の対応 |
|---|---|---|
| **無人実行を設計に含めない** | 夜間バッチ、スケジュール実行、複数チケットの並列消化は行わない。**当面、チケットの消化には人間が同席し、エージェントと協力して進める**前提を採る | Runner を後付けする。MCPツール・コマンド定義はそのまま再利用でき、`claude -p "/pb-implement 123"` をヘッドレス実行するだけ（10.2.2） |
| **会話ログ回収の非対称** | Claude Code はフックで全文回収可能、Copilot は要点のみ | Copilot 側の機能追加を待つ／要点記録の質を上げる |
| **ハートビートが弱い** | 外形監視がないため、エージェントの異常終了を即座に検知できない | リースTTLと人間への確認で緩やかに整合（10.3.3） |
| **Copilot コーディングエージェント（クラウド型）は別経路** | GitHub上でIssueをアサインしてPRを作らせる形式は、ローカル実行型とモデルが異なる | 「PBチケット ↔ GitHub Issue の双方向同期 + PR完了のWebhook受信」という別統合として設計する |
| **単独開発では価値が出ない** | 10.0.1 のとおり、参加者が1人なら `CLAUDE.md` 相当のファイルで足りる。**PB を入れる手間のほうが大きい** | 対応しない。**これは限界ではなく設計上の割り切りである** |

**「チーム利用時の同時実行」を本表から外した**（2026-08-29）。改訂前はここに「ローカル単独運用を前提としている」と書いていたが、**複数人での利用は本章の前提そのものになった**（10.0）。同時 claim 数の制御は限界ではなく要件であり、10.3.4 に置く。

## 10.12 MVPスコープ

pull型を採用したことで、当初懸念した「PBがオーケストレータ化する」問題は回避され、MVPは大幅に縮小した。第1章の「シンプルで軽快」というコンセプトとも矛盾しない。

**第1段階（AIエージェント連携の最小構成）**

1. チケット管理の基本機能（既存章のとおり、AI機能なしでも完成度の高い状態）**← Phase 1 で完了**
2. **プロジェクト文書（憲章）とテンプレート**（10.6.2）。全参加者のエージェントが同じ規約と価値観を読む
3. **MCPサーバ**（REST APIの薄いラッパ。10.3.2 の Phase 2 列にあるツール）
4. **コンテキストパックの生成**（初期は「憲章の該当章＋スコープ境界＋依存タスク」程度の単純な選定でよい）
5. **セットアップ画面と設定ファイル生成**（`.mcp.json`、`.claude/commands/`、`CLAUDE.md` ブロック）。**「リポジトリの初回接続」と「メンバーの参画」の2系統**を出す（10.9.1）

ジョブキュー、セッション管理、プロセス監視、Runner は**いずれも不要**である。

**承認キューUI を第1段階から外した**（2026-08-29）。承認の対象だった知識更新候補は、まず文書として運用する方針へ変えた（10.6.2）。**第1段階に残る承認対象はサブタスク提案だけになり、画面を作る理由が薄い。**

**第2段階**

6. **承認キューUI**（10.6.3。合意形成の機構として作り直す）
7. Readiness判定とDoDドラフト生成（AI支援チェックボタン）
8. プロジェクトメモリのエンティティ化と有用性スコアリング（10.6.2 の末尾）
9. DoD の `assertion` / `artifact` 型と自己検証
10. トランスクリプト回収フック

**第3段階**

11. エージェント実行コストの学習モデル（10.5.5）
12. コンテキストパック選定の実績学習（10.4.4）
13. Runner による無人実行（必要になった場合のみ）
