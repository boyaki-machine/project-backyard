## 2. 何が問題だったか

### 2.1 設計文書と実装の食い違い

設計文書を先に書いてから実装したので、実装の途中で「文書に書いていない」「文書どうしが食い違う」が毎日のように出た。
**Phase 1 だけで、判断を要した食い違いは500件を超えた。** 多くは小さなもので、例えば次のようなものだった。

- エラーコードの表に、本文で使っている `already_exists` や `immutable_field` が載っていない
- ETag の例 `"W/proj-…"` が HTTP の構文として誤っていた（`W/` は引用符の外に置く）
- プロジェクトキーの予約語が、文書によって7語と11語に分かれていた
- 画面のワイヤーフレームと、同じ節の表の記述が食い違っていた
- マイグレーションの番号を、Phase 2 用に予約していた番号とぶつけて使った（2回）

**「直すのは原則として文書が先」を規約にした。** 食い違いに気づいたら、コードだけを先に変えず、文書の修正案を出してから直す。

### 2.2 依存とツールの版

- goose や sqlc を入れるたびに、`go.mod` の Go の版が勝手に引き上げられ、間接依存が60〜80件に膨らんだ。**ツールを別の `go.mod`（`server/tools/`）に隔離して解決した**
- `npm install` が入れた TypeScript 7 が、型検査の道具（vue-tsc）と組み合わせられなかった。TypeScript を 5 系に固定した
- パスキーの検証に使うライブラリが新しい Go を要求したので、Go の最低版を 1.26 に上げた

### 2.3 自動の検証が通っても、画面は壊れていた

いちばん繰り返した失敗である。

- 自動検証が全部通ったのに、スクリーンショットを見ると、トークンの末尾が見えない・幅 900px でタイトルが0幅に潰れる・表の区切り線が切れる、ということが何度もあった
- **バックログの行が一度もドラッグできない状態で出荷した。** 検証は、合成したドラッグのイベントを投げる形で32件すべて通っていた。イベントを作って投げることと、ブラウザで実際に操作することは別物だった
- 検証の側のセレクタが、意図と違う要素（パスワード表示の切り替えボタンなど）を拾い、「ログインできない」ではなく「ログイン画面のまま先へ進む」形で後続がすべて失敗した

**画面を変えたら、複数の幅でスクリーンショットを撮って目で確かめる。入力は、ブラウザの実際の操作として通す。** この2つを手順に組み込んだ。

### 2.4 認可とキャッシュ

コードレビューで、自動の試験が捕まえなかった欠陥がまとめて見つかった。

- 実効権限のキャッシュの書き戻しが、ロール変更による無効化を追い越せた（古い権限が残る）
- トークンに付けた「このプロジェクトだけ」という制限を、読むコードが1つも無かった
- 実サーバで確かめると、閲覧専用のはずのロールでチケットを作れた

偽物の DB で行う単体試験では SQL が一度も実行されないので、**実際の DB を使う結合試験を別に用意した**。

### 2.5 1回の作業の大きさ

「1手順＝1言語（API か画面のどちらか）」で区切るつもりが、画面1枚が API 7本ぶんの分量になることがあり、区切りとして働かなかった。
**着手の前に分量を見積もり、大きければ分ける**ことにした（手順16 は a〜d の4つ、17・18 もそれぞれ分けた）。

### 2.6 文書が増えすぎた

エージェントは毎回、決まった文書を読んでから作業を始める。記録を足し続けた結果、読み込む量が膨らんだ。

- 進捗の文書が 182KB・995行に達し、作業の立ち上がりが重くなった。過去の記録を別の文書へ分けた
- エージェントの教訓を溜める文書は、目安を 8KB → 40KB → 80KB と3回引き上げた。**掃除より先に目安のほうが動いた。** 以後、目安の引き上げは作者だけが判断することにし、定期的な棚卸しを手順に入れた
- 教訓は「同じことが繰り返し起きたら規約に昇格させ、しばらく起きなければ捨てる」運用にした。Phase 1 の完了時には66件から32件へ畳んだ
- PB の規約・価値観などの文書（コンテキストパックに全文が載る）が1万字に届きかけ、判断の記録を目次だけにするなどして畳んだ

### 2.7 規約が2か所にあった

規約を `CLAUDE.md` と PB の文書の両方に持ち、どちらが正本か書いていなかった。**エージェントはローカルの `CLAUDE.md` を読み、PB の側が古いままでも作業が回ってしまった。**
`CLAUDE.md` は Claude Code にしか効かないので、**規約の正本を PB に置き、`CLAUDE.md` は取扱説明と案内だけにした。**

### 2.8 前提を反転した

最初は「一人の開発者がエージェントに実装を任せる」ツールとして設計していた。作ってみると、一人なら `CLAUDE.md` などのファイルを工夫するだけで足りる。
**PB が要るのは、文脈を共有しない参加者が複数になってから**である——規約は「同じことが2回起きたら書く」で育つが、参加者が N 人になると、同じ失敗が各人に1回ずつ起き、誰の目にも「2回目」に見えない。これを出発点に、Phase 2 の要件を書き直した。

### 2.9 触ってみて変わったバックログ

作者が画面を実際に触って、設計の段階では見えなかった問題が出た。

- チケットの種別が6つあったが、使い分けが分からない → 3つに減らし、フェーズや WBS は階層とタグで表す
- エピックがバックログの行として並ぶのは不自然 → エピックは行にせず、絞り込みの軸にする
- 全件を1段で並べると、いま取り組むものが埋もれる → 「オンステージ」と「バックログ」の二段にする
- チケット ID の `-31` が負の数に見える → 完全な形 `demo-31` で出す
- 詳細を開くと一覧が消え、バックログへ戻れない → 一覧を残したまま右に開く

### 2.10 日本語と Markdown の強調

CommonMark の強調（`**…**`）は、日本語の約物（「。」や「（」）と隣り合うと閉じないことがある。設計文書に閉じない強調が溜まり、描画が崩れた。
正規表現で一括して直そうとして2回失敗し（別々の強調の閉じと開きを1組と読んだ）、最終的には56か所のうち43か所を道具で、13か所を手で直した。**以後は、閉じない強調を検査するコマンドを用意した。**

### 2.11 自己署名証明書と Codex

PB を TLS で動かすと、Codex の標準の MCP クライアントが自己署名や社内認証局の証明書を受け付けず、接続できなかった。
OS の信頼ストアに登録しても解決しなかったので、**手元で動く中継（stdio ブリッジ）を用意して繋ぐ**形にした。
