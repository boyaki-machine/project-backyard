# 1. 設計原則

| # | 原則 | 具体的な帰結 |
|---|---|---|
| 1 | **縦方向のピクセルを死守する** | ノートPCでの利用を前提とする。アプリ側の固定ヘッダを持たない（2章）。装飾的な余白より情報密度を優先する |
| 2 | **軽快さを最優先する** | `Requirements.md` 1章の「JIRAは重い」への回答。初期表示1秒以内、画面遷移でフルリロードしない |
| 3 | **最初はシンプルに** | 検索・表示切替・カスタマイズは、必要性が実運用で確認できるまで実装しない |
| 4 | **権限で「見えない」を作る** | 使えない機能はグレーアウトではなく非表示。ただし判定の正本は常にサーバ |
| 5 | **人間とエージェントを同じボードに並べる** | 担当者アバターの隣にエージェントを同格で表示する。別画面に隔離しない |
| 6 | **AIの出力は視覚的に区別する** | AI提案は破線・バッジ・AI専用色（紫）で示し、確定済みの情報と混同させない |
| 7 | **キーボードで完結できる** | `Requirements.md` 5章のCLI/TUI志向のユーザー層に配慮し、主要操作にショートカットを割り当てる |

原則1は本改訂で最上位に置いた。**画面の縦は最も希少な資源**であり、そこを削る設計判断は他の利便性に優先する。

## 1.1 UIコンポーネントの方針

Vue 3 を使うことは確定。**Phase 1 は自前の軽量実装で通す**（下の暫定方針のとおり手順7〜15 で実装しきった）。Phase 2 のガント／カンバン着手時に、UIライブラリの採用可否を再評価する。

| 方式 | 利点 | 欠点 |
|---|---|---|
| UIライブラリ採用（PrimeVue / Naive UI 等） | テーブル・日付・モーダル等が即座に揃い、Phase 1 が速い | バンドルが重く原則2と衝突しやすい。ガント等の独自描画とデザインが乖離する |
| 自前の軽量コンポーネント（Tailwind等） | 軽い。ガント/カンバンの独自描画と一貫させやすい | データテーブル・日付ピッカーの実装コストが高い |

**当初の見立て**：Phase 1 で必要なコンポーネントは「テーブル、モーダル、フォーム部品、ドロップダウン」に限られ、いずれも自前で数百行の範囲に収まる。本書のワイヤーフレームはどちらでも実装可能な粒度で記述する。

**この見立ては手順7〜15 で成り立った。** 実装したのは 6.1 の一覧のとおりで、外部のUIライブラリを1つも入れていない。**バックログ（手順16）で `SortableList`（ドラッグ&ドロップ）が加わる**——ここが自前で通るかどうかが、Phase 2 の再評価にそのまま効く。

# 2. グローバルレイアウト

## 2.1 アプリ固定ヘッダを持たない

**PB はアプリケーション共通のヘッダ行を持たない。** ブラウザのUI（タブバー、アドレスバー、ブックマークバー）の下にさらにアプリのヘッダが積まると、縦方向の可用領域が大きく損なわれるためである。

**13インチクラス（1440×900相当）での実測見積り**

| 要素 | 高さ |
|---|---|
| ブラウザのタブ＋アドレスバー | 約 90px |
| ブックマークバー（表示時） | 約 35px |
| ~~アプリ共通ヘッダ~~ | ~~48px~~ → **廃止** |
| ~~パンくず~~ | ~~32px~~ → **廃止** |
| ページヘッダ（コンテンツペイン内） | 48px |

アプリヘッダとパンくずの廃止により**約80px（テーブル2行分）を回復**する。実効コンテンツ高は 640px 前後から 730px 前後へ、率にして約12%増える。

**パンくずを廃止できる理由**：階層はメインメニューが常時示している（どのプロジェクトの、どの画面にいるか）。パンくずは同じ情報の二重表示であり、削っても迷子にならない。

**チケット詳細に `←` の戻りリンクは置かない**（本改訂で撤回した）。詳細は一覧を消して置き換わるのではなく、**一覧の右に開く**ようになったため（2.2.1）、戻る対象がそもそも画面から消えていない。閉じる手段は詳細側の `✕` と、**一覧ペインのヘッダ**（5.4）の2つである。

### 2.2.1 詳細ペイン（マスター・ディテール）

**チケット詳細は画面を置き換えず、一覧の右に3枚目のペインとして開く**（本改訂で新設）。

```
【詳細を閉じている】
┌────────┬──────────────────────────────────────────────┐
│ メニュー │ ⠿ │ ID │ タイトル      │ 状態 │ 優先 │ 担当 │ 期限 │
│  240   │                    残り全幅                    │
└────────┴──────────────────────────────────────────────┘

【詳細を開いている】
┌────────┬───────────────────┬──────────────────────────┐
│ メニュー │ [⤢] バックログ [+]│ ☑ my-app-31     [⋯] [✕] │
│        │ ID │ タイトル │ 状態│                          │
│  240   │       約450px      │  残り（既定 750px 前後）   │
└────────┴───────────────────┴──────────────────────────┘
           ↑ 一覧は縮み、列が3つになる
```

**採る形は「押し込む」であり、重ねない。** 詳細が一覧の上に乗る（オーバーレイ）形は採らない。

| | 左に残る帯（約450px）に見えるもの | 判断 |
|---|---|---|
| **押し込む** | `ID` `タイトル` `状態` の3列が**収まる** | **採用**。次にどれを開くか決めるのに要るのは状態である |
| 重ねる | `⠿` `ID` `タイトル`（途中で切れる）。**状態が覆われる** | 不採用。覆われた列は「読めないのに在る」状態になり、**クリックできる範囲と見える範囲が食い違う** |

**この形にする理由は、`Requirements.md` 5章 の PM が「バックログを起点にチケットの進捗を順に確認していく」作業にある。** 1件ごとに画面が入れ替わると、戻るたびにスクロール位置と視線の位置を作り直すことになる。**一覧に居たまま次の行をクリックすれば詳細が差し替わる**ので、閉じる操作そのものが要らなくなる。

**メインメニューを自動で折りたたまない。** 2.3.3 が折りたたみ状態を `localStorage` に保存すると定めているため、画面が勝手に畳むと**次回ログイン時も畳まれたまま**になる。利用者が変えていない設定を副作用で書き換えることはしない。畳むかどうかは利用者が `[` で決め、その分だけ詳細が広がる。

| メインメニュー | 詳細ペインの幅（1440px の窓） |
|---|---|
| 展開のまま（既定） | 約 750px |
| 利用者が畳んだとき | 約 934px |

**詳細ペインの幅は境界のドラッグで変えられ、`localStorage` に保存する**（キーは `pb.detail_pane_w`。`pb.theme` / `pb.menu_collapsed` と同じ置き場）。狭くすれば一覧側にタイトルの幅が戻る。

**この構成を採れるのは、一覧の固定列が 594px あるためである**（`⠿` 68 + ID 116 + 状態 104 + 優先 56 + 担当 130 + 期限 120。5.4）。タイトルとタグを加えた実用幅は約 850px で、**1440px の窓で列をそのまま残したまま右に詳細を置くと、詳細に 350px しか残らない。** 一覧を縮めることが前提条件になっている。

## 2.3 メニュートグルの配置

**トグルボタンはメインメニュー自身の最上行に置く。** 独立した浮遊レイヤーにはしない。

```
【展開 240px】                      【折りたたみ 56px】
┌──────────────────────┐            ┌────┐
│ ☰  Project Backyard  │            │ ☰  │  ← トグルは常に同じ位置
├──────────────────────┤            ├────┤
│ ⌂  プロジェクト一覧    │            │ ⌂  │
│                      │            │    │
│ ── my-app ────── ▾   │            │ ▤  │
│ ▤  ダッシュボード      │            │ ☑ ⁴│  ← バッジは小さく右上に重ねる
│ ☑  チケット      [12] │            │ ⚙  │
│ ⚙  プロジェクト設定    │            │    │
├──────────────────────┤            ├────┤
│ 👤 田中            ▴ │            │ 👤 │
└──────────────────────┘            └────┘
```

### 2.3.1 採用理由と代替案の検討

| 案 | 内容 | 判断 |
|---|---|---|
| **A. メニュー最上行に内包** | 折りたたみ時もレール（56px）が残るため、ボタンが常に同じ位置に存在する | **採用**。z-index管理もコンテンツとの衝突も発生しない |
| B. 独立レイヤーの浮遊ボタン | `position: fixed; top:8px; left:8px; z-index:50` | 不採用。メニュー幅0を許すことになり、コンテンツ左上40px程度を常に空ける必要が生じ、ページタイトルと衝突する。半透明背景やホバー時フェードインなど追加の状態管理が必要になる |
| C. 完全非表示＋左端ホバー復帰 | メニュー0px。左端8px以内へのマウス接近でオーバーレイ表示 | **集中モードとして併用**（2.3.2） |

案Bは技術的には何の問題もなく実装できるが、**案Aで足りる場面で採る理由がない**。案Aは折りたたみ状態でもアイコンレールが残るため、「メニューを消したが戻し方が分からない」という事故が構造的に起きない。

### 2.3.2 集中モード（Phase 2）

ガント・WBS・カンバンのように横も縦も必要な画面向けに、**メニューを完全に0pxまで畳むモード**を別途用意する。

- 起動：ページヘッダの「全画面」ボタン、または `Shift + [`
- 復帰：`Esc` / `Shift + [` / 左端8px以内へのマウス接近（オーバーレイでスライド表示）
- 常用モードではなく一時的な表示状態として位置づけ、リロードで解除する（`localStorage` に保存しない）

通常のトグル（案A）と役割を分けることで、案Bで懸念した「戻し方が分からない」問題を回避する。

### 2.3.3 状態の永続化

折りたたみ／展開の状態は `localStorage` に保存し、次回ログイン時も維持する。集中モードは保存しない。

## 2.4 ブレークポイント

| 幅 | メニュー | コンテンツ |
|---|---|---|
| ≥ 1280px | 展開（既定） | 最大幅制限なし |
| 768〜1279px | 折りたたみ（既定） | — |
| < 768px | 非表示。`☰` は左上に浮遊表示（この幅でのみ案Bを採る） | テーブルはカード表示へ切替 |

768px未満でのみ浮遊ボタンを使うのは、メニューをオーバーレイにせざるを得ず、レールを残す余地がないためである。**この幅ではページタイトルとの衝突を許容し、タイトル行の左にボタン分の余白を確保する。**

Phase 1 ではデスクトップ（≥1280px）を主対象とし、768px未満は「破綻しない」水準に留める。

**詳細ペイン（2.2.1）が並ぶかどうかは、窓の幅ではなくコンテンツペインの幅で決める。**

| コンテンツペインの幅 | チケット詳細の出方 |
|---|---|
| **≥ 960px** | 一覧（約450px）と詳細（残り）が**並ぶ** |
| < 960px | **詳細が全幅**になり、一覧は隠れる（`✕` で一覧へ戻る） |

**窓の幅で決めない理由は、同じ窓幅でもメニューの折りたたみで使える幅が 184px 変わるためである**（240px → 56px）。1280px の窓はメニューを展開したままだと 1040px、畳めば 1224px になり、**窓を基準にすると「畳んだのに並ばない」が起きる。**

閾値の 960px は、一覧の 450px に詳細の下限 510px を足したものである。510px は 5.5 のメタ情報が2列で収まる下限として置いた。

## 2.5 コンテンツペインの構造

すべてのページは以下の2ブロックのみを持つ。

```
┌─────────────────────────────────────────────────────┐
│ チケット                          [+ 新規チケット]   │ ← ページヘッダ 48px, sticky
├─────────────────────────────────────────────────────┤
│                                                     │
│                （スクロール領域）                      │
│                                                     │
└─────────────────────────────────────────────────────┘
```

1. **ページヘッダ**（48px）：画面タイトル（左）＋主要アクション（右）。副次アクションは `⋯` へ集約。**ペイン内で sticky** とし、スクロールしても消えない
2. **コンテンツ**：スクロール領域

スクロールはコンテンツ領域内のみで発生し、メニューとページヘッダは常時表示される。

| `/p/:key/sprints` | スプリント管理（バーンダウン・ベロシティ） | `ticket.view` | 2 | プレースホルダ |
| `/p/:key/insights` | 進捗分析（消化状況・残存チケット） | `project.view` | 3 | プレースホルダ |
| `/p/:key/approvals` | 承認キュー | `proposal.review` | 2 | プレースホルダ |
| `/p/:key/knowledge` | プロジェクトメモリ | `knowledge.view` | 2 | プレースホルダ |
| `/p/:key/settings/agents` | エージェント連携セットアップ | `agent.register` | 2 | プレースホルダ |
| `/p/:key/history` | プロジェクトヒストリー・要約 | `project.view` | 3 | プレースホルダ |
| `/admin/system` | システム設定・認証プロバイダ | `authprovider.manage` | 3 | プレースホルダ |

**URL設計の判断**

- `/` は画面を持たず、**ログイン後の初期画面である `/projects` へリダイレクトする**（3.1 の遷移図）。権限判定はリダイレクト先で行うため、`/` 自体には必要権限を置かない
- プロジェクト配下を `/p/:key/` と短く切ったのは、チケットURLを口頭・チャットで共有しやすくするため（`/p/my-app/tickets/123`）
- **チケットを見る「視点」は、`?view=` ではなくパスで分ける**（`/backlog` `/board` `/gantt`）。視点ごとにメニュー項目・権限・件数バッジを持てるようにするためであり、`?view=gantt` ではメニューから視点の存在が見えない。**チケット詳細だけは視点を持たず `/p/:key/tickets/:seq` に据え置く。** どの視点から開いても同じ画面であり、共有URLとして既に確定しているため
- **`/p/:key/tickets` は画面を持たず `/p/:key/backlog` へリダイレクトする。** 改訂前はここがチケット一覧だった。**リダイレクトを置くのは、既存のブックマークと `docs/history/` の記録を壊さないため**である
- チケットは内部ID（ULID）ではなく**プロジェクト内連番 `seq`** でルーティングする。`DbDesign.md` 6.6 の `UNIQUE (project_id, seq)` がこれを支える
- モーダルはURLを持たない。ただし新規プロジェクト作成のみ `/projects?new=1` を許容し、直リンクでモーダルを開けるようにする
- **チケット詳細は一覧の右に開くが、URL は `/p/:key/tickets/:seq` のまま変えない**（2.2.1）。**バックログのフィルタは詳細の URL にそのまま持ち回る**

  ```
  バックログ       /p/:key/backlog?status=in_progress&group=tag
  行を選ぶ      →  /p/:key/tickets/31?status=in_progress&group=tag
  閉じる        →  /p/:key/backlog?status=in_progress&group=tag
  共有された URL   /p/:key/tickets/31        （フィルタ無しの一覧＋詳細で開く）
  ```

  **2つの要件が衝突するのを、これで両立させている。** 本節は「チケット詳細は共有URLとして既に確定している」と定め、5.4 は「フィルタ条件をURLに載せて共有可能にする」と定める。詳細を開いた瞬間にクエリを捨てると**フィルタが共有できなくなり**、逆にバックログのURLのまま詳細を表すと**チケット単体のリンクが作れなくなる**。詳細の URL がフィルタを運ぶ形なら、どちらのリンクも成立する。**クエリを解釈できない相手（共有された素のURL）でも壊れない**——一覧がフィルタ無しで並ぶだけである

### 4.1.1 チケットは「視点」で並べる

改訂前はここが `☑ チケット` という1項目で、その下に `ボード` `ガント` が並んでいた。**「チケット」だけが実体の名前で、他は見せ方の名前という不揃いな並び**になっていた。

本改訂では、**チケットを見る視点をすべて同じ高さに並べる**。

| 視点 | 何のための見え方か |
|---|---|
| **バックログ** | 全体を並び順・階層・グループで見て、**次に何をやるかを決める** |
| **カンバン**（P2） | ステータスごとに置いて、**いま何がどこで詰まっているかを見る** |
| **ガント**（P2） | 時間軸に置いて、**期日と依存関係を見る** |
| **チケット検索**（P2） | 条件と全文で**特定のチケットを探す** |
| **進捗分析**（P3） | 消化状況・残存チケットから**プロジェクトの進み具合を測る** |

前の3つは**同じデータの別の描き方**であり（`Requirements.md` 2章「同一データをビュー切り替えで編集でき、どこから変更しても即座に他ビューへ反映される」）、`GET /projects/:key/tickets`（`ApiDesign.md` 9.2）という同一のエンドポイントから描く。後の2つは性質が違い、**探す**（1件に辿り着く）と**測る**（集計を読む）である。

**セクション見出し（`─── チケット ───`）を足さない。** 見出し1行は約28px を常に消費し、設計原則1（縦方向のピクセルを死守する）に反する。プロジェクト配下の項目はすべてそのプロジェクトについてのものであり、視点であることは項目名から読める。

**グループ化の軸は視点をまたいで共有する。** バックログで「タグでグループ化」を選んだら、カンバンのスウィムレーンとガントの行グループも同じ軸になる（Phase 2）。**軸を選び直す操作を視点ごとに繰り返させない。**

```
        │     半角英小文字・数字・ハイフン、2〜20文字。      │
        │     ⚠ 作成後は変更できません。                   │

        │  説明                                          │

        │  ( ● シンプル（未着手 / 進行中 / 完了）          │

        │  ( ○ 承認フロー付き（ウォーターフォール向け）      │

        ├────────────────────────────────────────────────┤
        │                        [ キャンセル ] [ 作成 ]  │
        └────────────────────────────────────────────────┘
```

**プロジェクトキーは明示入力とし、変更不可とする。**

| 項目 | 仕様 |
|---|---|
| API | `POST /api/v1/projects` |
| 入力補助 | プロジェクト名から候補を自動入力する（英数小文字＋ハイフン化）。**ユーザーは必ず内容を確認・確定する**（フィールドを隠さない） |
| 検証 | 形式（`^[a-z0-9][a-z0-9-]{1,19}$`）と重複を、debounce 後に `GET /api/v1/projects/check-key?key=` で即時確認 |
| 予約語 | `admin` `api` `mcp` `login` `logout` `me` `p` `new` `projects` `static` `assets` はルーティングと衝突するため拒否（正本は `ApiDesign.md` 5.2） |
| 変更不可の明示 | 入力欄直下に用途一覧と警告を常時表示する |

**キーの判定表示**

`check-key` は使えない理由を `reason` の enum で返すのみで、文言を持たない（`ApiDesign.md` 5.2）。表示する文言は画面側が持つ。**形式と予約語の判定そのものはフロントに複製しない**（二重管理になり、片方だけ変わると食い違う）。

| `check-key` の結果 | 表示 |
|---|---|
| `available: true` | `✓ 使用可能です` |
| `invalid_format` | `✕ 半角英小文字・数字・ハイフン、2〜20文字で入力してください` |
| `reserved` | `✕ このキーは予約できません` |
| `already_exists` | `✕ このキーは既に使われています` |

**エラーの文言を画面側が持つのはここだけ**である。サーバが `message` を返す経路（作成時の 409 など）では、`ApiDesign.md` 2.5 のとおりその文言をそのまま出す。状態を色だけで示さないため（9.2）、記号（`✓` / `✕`）を必ず添える。

**なぜ変更不可か**（設計判断の記録）

キーはチケット表示番号の接頭辞として使われ、その番号は**PBの外部に流出する**。コミットメッセージ（`PB-123`）、ブランチ名、チャットでの会話、外部ドキュメントへの引用、`.mcp.json` の設定内容。キーを変更するとPB内部のリンクはリダイレクトで救えるが、**すでに外部に散らばった参照は直せない**。JIRAがプロジェクトキーの変更を強く抑制するのと同じ理由である。

入力を必須とし、作成時に一度だけしっかり考えてもらう方が、後の不整合より安価である。

### 5.3.1 AI要約をダッシュボードに置かない判断

「プロジェクトの現況をAIが要約して見せる」案を検討したが、**ダッシュボードには置かず、プロジェクトヒストリー画面（Phase 3、`/p/:key/history`）に集約する。**

理由は3点。

1. **生成コストとレイテンシ。** ダッシュボードは最も頻繁に開く画面であり、開くたびにLLM推論を走らせるのは現実的でない。事前バッチ生成＋キャッシュが前提になるが、そうすると表示されるのは「昨日時点の要約」になり、統計の即時性と混在させると誤解を招く
2. **利用者と場面が異なる。** 要約が真価を発揮するのは「久しぶりに見る人」「新規参加メンバー」「ステークホルダー報告」であり、毎日開くPMには「昨日から何が変わったか」＝最近の動きの方が有用である。この用途は`Requirements.md` 6.7のプロジェクトヒストリーがすでに担っている
3. **Phase 1 では作れない。** AI機能はPhase 3であり、要約の材料となるコメント・決定記録・履歴が蓄積されていない段階では「特に動きはありません」しか出力されない

ダッシュボードは**数値と一次情報**、ヒストリー画面は**文脈と経緯**、という役割分担とする。

**カードの並び替え・カスタマイズは実装しない。** 原則3に従い、必要性が実運用で確認できてから検討する。

### 並べ替えられる相手

**「同じ親」ではなく「同じ**表示上の親**」で判定する。** 表示上の親とは、`parent_seq` の
指す行が**結果の中に居ればその行**、居なければ**「根」**である。

| 掴んだ行 | 落とせる相手 |
|---|---|
| 表示上の根（親を持たない、または**親が結果に居ない**） | **他の根すべて** |
| インデントされている行 | **同じ親の下の兄弟だけ** |
| 段をまたぐとき | 移動先の段の**根**（上記「二段」の規則が先に効く） |

**当初は「同じ `parent_seq` を持つ行」としていたが、エピックを行から出さなくなった時点で
成り立たなくなった**（利用者の実機確認、2026-08-23）。エピック配下のチケットは
`parent_seq` を持ったまま**表示上は根として並ぶ**ので、`parent_seq` で判定すると
**画面上で同じ深さに見える行どうしが入れ替えられない**。実際、エピック3つのプロジェクトでは
根が3つ以上の群に割れ、大半の組み合わせが禁止になっていた。

**旧規則の理由づけ（「別の親の下へ落としても表示は動かない」）も、根どうしには当てはまらない。**
根は `sort_key` の順に並ぶので、`move` の結果はそのまま表示に出る。**表示が動かないのは
インデントされている行**——親の下で組み直されるため、兄弟の外へ動かしても位置が変わらない。
制限が要るのはこちらだけである。

### ドロップ先の見せ方

**掴んでいる間、落ちる位置に 2px の挿入線を出す**（利用者の要望、2026-08-23）。

| 落とし先 | 見せ方 | 結果 |
|---|---|---|
| 行の**上半分** | その行の**上端**に線 | その行の直前へ |
| 行の**下半分** | その行の**下端**に線 | その行の直後へ |
| 段の見出し | 見出しの**下端**に線 | **その段の先頭へ**（`position: "first"`） |
| **空の段**の枠 | 枠を実線にする | **その段へ**（`position: "last"`） |
| 落とせない相手 | **線を出さない**（カーソルが禁止の形になる） | — |

**段の末尾へ置くときは、最終行の下半分へ落とす。** 「末尾へ」という専用の
落とし場所を別に置かない（下記「掴んだ瞬間に要素を差し込まない」）。

**落ちる位置はポインタが指した位置で決まる**（掴んだ行がどこから来たかに依らない）。
Finder・VS Code・JIRA・Trello が同じ形で、**線の見えている場所と着地が一致する**ことが
この形の要点である。「掴んだ行が相手を越えた向き」で決める案は、行の下半分を指しても
上に入ることがあり、線を出した意味がなくなる。

**行を面で塗らない。** 行を塗ると「その行**に**入る」（親子にする）と読める。PB の `move` は
`sort_key` だけを変えて親子を変えない（`ApiDesign.md` 9.4）ので、**行と行の間**を示す
挿入線でなければ意味が食い違う。

**線の色は `--pb-accent`**（ベース色相のステップ9。8.3）。8.6 が禁じているのは
danger / warning / ai の**意味色**であり、`--pb-accent` は進行中バッジや主ボタンと同じ
**操作の色**である。**線は罫線ではなく `box-shadow` の内側で描く**——罫線を足すと
行の高さが 2px 変わり、掴むたびに表全体がずれる。

**段の見出しが「先頭へ」なのは、線の位置と結果を一致させるためである。** 見出しは段の
上端にあるので、ここへ落として末尾へ飛ぶと、見えている場所と着地が食い違う。
**末尾へ置きたいときは、掴んでいる間だけ出る末尾の帯へ落とす。**

**見出しと空の段の枠は、表示上の根を掴んでいるときだけ受け取る。**
インデントされた行は**段の中の位置を持たない**——`position: "first"` / `"last"` を送っても、
その行は親の下で兄弟の端へ動くだけで、「その段の先頭／末尾へ」という表示と食い違う。

### 掴んだ瞬間に要素を差し込まない

**ドラッグが始まったことをきっかけに、落とし場所を新しく描き足してはならない。**
掴んだ行の位置が `dragstart` の直後にずれると、**Chrome はドラッグを取り消す**
（`dragstart` の 1ms 後に `dragend` が来て、以後 `dragover` が一度も起きない）。

**手順16d-b で実際に起きた**（利用者の実機確認、2026-08-24）。「〜の末尾へ」の帯を
掴んだ瞬間に上下の段へ出していたため、**オンステージ側の帯がバックログ表の上に入り、
バックログの行だけ一度もドラッグできなかった**。オンステージの行は帯が自分より下に
入るのでずれず、そちらだけ動いていた。

**変えてよいのは見た目だけである**（掴んだ行を薄くする、線を引く）。落とし場所は
**掴む前から画面にあるもの**——行そのもの、段の見出し、空の段の枠——に限る。

### 二段（オンステージとバックログ）

**この画面は上下二段である。**

| 段 | 意味 |
|---|---|
| **オンステージ**（上） | **いま仕掛り中で、直近のスプリントで消化すべきもの。** ここだけを見れば仕掛りが全部わかる |
| **バックログ**（下） | **プロジェクトが行うべき仕事すべての保管庫** |

**行は片方にしか出ない。** オンステージへ上げた行はバックログから消える。同じ行が2か所にあると、片方でドラッグしたときにもう片方がどう動くのかが決まらず、**上下を見比べる作業が毎回発生する**。

**段の実体は `ticket.staged_at` である**（`DbDesign.md` 6.6）。`NULL` がバックログで、値が入っているものがオンステージ。**進捗（状態）とは独立した軸**であり、「未着手だがオンステージ」を表せる。ステータスやスプリントで代用しない。

| 規則 | 内容 |
|---|---|
| **段に置けるもの** | **表示上のトップレベルだけ**——親を持たないもの、または**親がエピックのもの**。配下は親と一緒に運ばれ、**オンステージには子の行を出さない**（フラットな消化順リストになる）。**バックログ段にも出さない**（下記「配下の行き先」） |
| **段の行き来** | 行頭の `⠿` を**もう一方の段へドラッグ**する。段と位置は1回の `move`（`ApiDesign.md` 9.4.1 の `staged`）で同時に決まる |
| **並び順** | 両段とも**上から優先的に消化する順序**で、ドラッグで並べ替えられる。`sort_key` は**二段で1本を共有する**（9.4） |
| **優先度と順序は一致しない** | 優先度が高くても開始条件が整わなければ下に置く。だから優先度列とは別に手で並べる手段が要る |
| **フィルタ** | **上下の両方に効く。** 片方だけ絞られないと、「Sprint 3 だけ見る」ときに上に別スプリントの行が残り、上下の合計が総件数と合わなくなる |
| **取得** | **1回で取り切って手元で二段に分ける**（`ApiDesign.md` 9.2.1）。2本に分けると件数・`ETag`・並べ替え後の再取得がすべて2本になる |
| **グループ化中** | **二段をやめて1つの表に戻す**（下記 5.4.1） |

**エピックはどちらの段にも出ない**（次項）。

**配下の行き先。** オンステージへ上げた行の配下は、**どちらの段にも行として出ない**（利用者の判断、2026-08-23）。バックログ段に残す案は採らなかった——親と一緒に運ばれた以上、片方の段にだけ子が残ると、上下を見比べる作業がここで復活する。

**この結果、Phase 1 では配下に画面から到達する手段が無い期間がある。** 承知のうえで選んでいる。手順17 のチケット詳細に**親から子の詳細を開く導線**を置いて解消する。**バックログのツリーの折りたたみ（5.4）が実際に有効だと分かれば、オンステージ段への展開も検討する**（同じ判断）。

**下部の総件数は、出していない配下を含む。** サーバが返す `total` はフィルタに合致したチケットの実数であり（9.2.2）、画面が配下を出さない分だけ上下の件数の合計より大きくなる。5.4.1 のタグの重複（合計のほうが多くなる）と逆向きの食い違いである。

### エピックをフィルタにする

**`type='epic'` のチケットは行として出さず、フィルタ行の `エピック[…]` に複数選択できる形で置く。** JIRA がバックログの左に置いているものを、PB ではフィルタ行へ集約する。

| 規則 | 内容 |
|---|---|
| **絞り込みの実体** | `ApiDesign.md` 9.2.1 の `parent`（部分木）。**種別ではない**（`DbDesign.md` 6.10）。複数選択は `?parent=12,30` の OR |
| **エピック自身** | 部分木に含まれて返るが、画面が行として捨てる。**種別フィルタが「すべて」のときは `type=story,task` を送る**——画面側で捨てると下部の総件数と食い違う |
| **新規チケット** | **エピックで絞り込み中に作ったチケットは、そのエピック配下になる**（5.4.3） |
| **編集** | エピック自体もチケットである。**フィルタの選択肢からチケット詳細へ遷移できる導線を置く**（`/p/:key/tickets/:seq`。詳細画面は手順17） |

**エピックを行として出さない理由。** エピックはグルーピング専用であり（`DbDesign.md` 6.6）、行として並ぶと**「やるべき仕事」の数に混ざる**。バックログは次に何をやるかを決める画面なので、**手を動かせない行**が上位に居座ると走査の妨げになる。

### 詳細を開いているときの一覧

**詳細ペイン（2.2.1）が並ぶと、一覧は約450pxへ縮み、列が3つになる。**

| | 全幅のとき | 詳細を開いているとき |
|---|---|---|
| 列 | `⠿` `ID` `タイトル` `状態` `優先` `担当` `期限` | **`ID` `タイトル` `状態` の3列** |
| `⠿`（並べ替え） | 出す | **出さない**（幅が無く、詳細を見ている間の操作でもない） |
| 期限超過 | `⚠ 2026-08-14` | **`⚠` のみ**をタイトルの後ろに出す（日付は詳細側に出ている） |
| タグ | タイトルの後ろに出す | **出さない**（450px ではタイトルが省略記号で切れたうえにタグが枠の途中で切れ、**読めないのに在る**状態になる。タグは詳細側に出ている） |
| フィルタ行 | 出す | **畳む**（`[絞り込み ▾]` の1行にする） |

**落ちる列は、いずれも詳細側に出ているものである。** 一覧に残すのは「次にどれを開くか」を決めるのに要るものだけでよい。`状態` を残すのは、この作業が**進捗を順に確認していく**ものだからである（2.2.1）。

**行の縦位置は変わらない。** 行の高さも順序も動かさないので、**選んだ行はクリックした場所に留まる。** 幅だけが変わる。

### 一覧へ戻る導線

**縮小中の一覧ペインのヘッダが、そのまま「全幅へ戻す」の当たり所になる。**

```
┌───────────────────┐┌─────────────────────────┐
│ [⤢] バックログ  [+]││ ☑ my-app-31    [⋯] [✕] │
└───────────────────┘└─────────────────────────┘
  ↑ この帯の左側全体
```

| 項目 | 仕様 |
|---|---|
| クリック領域 | ヘッダ左側（アイコン＋「バックログ」の文字）**全体**。`[+]` は別ボタンとして右端に置き、当たり判定を食い合わせない |
| 見せ方 | hover でその領域の背景が `--pb-hover` に変わる。`aria-label="バックログを全幅に戻す"` |
| 全幅のとき | **ボタンにしない。** 押しても何も起きないものをボタンに見せない |
| `[+ 新規チケット]` | 縮小中はラベルが入らないので `[+]` のアイコンのみにし、`aria-label` を付ける（9.2） |
| 押したとき | 一覧が全幅（7列）へ戻り、**詳細は閉じる**。URL も `/p/:key/backlog?<フィルタ>` へ戻る |

**新しい要素を差し込まず、既にある 48px のページヘッダ（2.5）を使う。** 詳細を開いたときに一覧側へ帯を足すと、**行の縦位置がずれる**——5.4 の「掴んだ瞬間に要素を差し込まない」と同じ根の問題である。

**詳細側の `✕` も残すが、それだけでは足りない。** 「バックログを見たい」と思っている利用者に、**その反対側にある閉じるボタンを押させる**のは意識の向きと逆である（利用者の指摘、2026-08-27）。**戻る導線は戻りたい先の側に置く。**

**戻したときに保つもの**——スクロール位置、フィルタ・グループ化・ソート（URL が持つ）、ツリーとセクションの開閉（`localStorage`。5.4.1）、そして**詳細で変更した内容を反映した行**。

**詳細を「開いたまま裏に隠す」形は採らない。** 見えない詳細が残っていると、次に行をクリックしたときに何が起きるかが読めなくなる。

### 5.4.1 グループ化

フィルタ行の右端に**グループ化セレクタ**を置く。

| 軸 | セクション見出しになるもの |
|---|---|
| **なし**（既定） | — |
| 親チケット | 親のタイトル。親を持たないものは「トップレベル」 |
| タグ | タグ名。タグの無いものは「未分類」 |
| スプリント | スプリント名。未割当は「スプリント未設定」 |
| 担当 | 担当者名。未割当は「未割当」 |
| 状態 | ステータス名 |

**既定を「なし」にする。** 初期状態でセクションに畳まれていると、開いた瞬間に「チケットが無い」ように見える。原則3に従い、必要になったときに選ばせる。

**タグでグループ化したとき、複数タグを持つチケットは各セクションに重複して現れる。** 上の図の `-44 ログイン画面` は `[GUI]` と `[設計]` の両方を持ち、両方のセクションに出る。**これを避けない。**

避ける方法は「タグに軸（`tag_group`）を持たせて軸ごとに単一選択とする」ことだが、その必要性はバックログを実際に使ってみるまで分からない。フラットなタグから軸付きへは前進マイグレーション1本で移れるが、逆は難しい（`DbDesign.md` 6.10）。**重複表示が実際に読みにくいと分かってから足す。**

セクション見出しの件数（`(3)`）は**そのセクションに表示されている行数**であり、重複を含む。画面下部の総件数（`48件`）は**チケットの実数**で重複を含まない。両者が一致しないことがある。

**グループ化を切り替えても並び順は変わらない。** `sort_key` はプロジェクト内で1本であり、グループは表示上の区切りにすぎない（`ApiDesign.md` 9.4）。グループごとに別の順序を持たせると、軸を変えるたびに手で並べた結果が失われる。

**グループ化を選んだら、二段をやめて1つの表に戻す。** 二段とセクションの入れ子は、**上下どちらのセクションへ落としたか**が読めなくなる（同じ見出しが上下に2つ並ぶ）。グループ化はチケット全体を別の軸で切り直す操作であり、「いま仕掛り中か」という軸とは同時に使わない。オンステージのものを見分けたいときは、グループ化を「なし」へ戻す。

**グループ化している間は、親子のインデントを行わない**（5.4 の「階層表示」）。親と子が同じ軸の値を持つとは限らず（タグは片方だけ付いていることがあり、担当は別人であることが普通である）、親子を優先すると軸の意味が壊れるためである。階層で読みたいときはグループ化を「なし」へ戻す。

セクションの開閉状態はブラウザに保持する（2.3.3 と同じ扱い）。**軸ごとに別々に覚える**——軸を変えるとセクションの顔ぶれが変わるためである。**ツリーの折りたたみ（5.4 の「折りたたみ」）とは別に持つ**。ツリーの開閉は軸に依らず、1つに混ぜると軸を切り替えたときにツリーの開閉まで巻き添えになる。

### 5.4.2 ページャを置かない

**この画面はページングしない。** フィルタ後の全件を1回で取得し、件数だけを下部に出す。

理由は、**グループ化・階層のインデント・ドラッグ&ドロップの並べ替えがいずれもページ境界をまたげない**ことにある。25件目と26件目の間で親子が切れると、子だけが孤立して2ページ目の先頭に現れる。1ページ目の末尾へ2ページ目の行をドラッグすることもできない。

上限は `ApiDesign.md` 2.6 の `per_page` 上限と同じ **200件**。超えた場合は件数の隣に出す。

```
│ 1,204件中 200件を表示しています。フィルタで絞り込んでください        │
```

**エラーにはしない。** 見えている200件は正しく、操作もできる。

**フィルタで親が結果から落ちた子は、インデントせずトップレベルに並べる**（`ApiDesign.md` 9.2.4）。サーバは親を補完しない。補完すると、フィルタに合致しない行が一覧に現れて件数と食い違う。

### 5.4.3 新規チケット

`[+ 新規チケット]` はモーダル（URLを持たない。3.2）。

| 欄 | 扱い |
|---|---|
| 種別・タイトル | 必須。**種別の選択肢はストーリーとタスクの2つ**（エピックはフィルタであり、ここからは作らない） |
| 説明・優先度・担当・親・タグ・スプリント・見積・開始日・期限 | 任意 |
| 状態 | **出さない。** ワークフローの入口が自動で決まる（`ApiDesign.md` 9.3） |
| 段 | **出さない。** 作ったチケットは必ずバックログに入る（`ApiDesign.md` 9.3）。オンステージへ上げるのは人が段へドラッグしたときだけである |

| 欄 | 選択肢の出どころ |
|---|---|
| 担当 | `GET /projects/:key` の `members[]`。**プロジェクトのメンバーに限る**（`ApiDesign.md` 9.3 は非メンバーを `422 not_a_member` で弾く） |
| 親 | **いま一覧に出ているチケット**から選ぶ（`my-app-12 DB設計` の形）。バックログは最大200件を既に手元に持っており、追加の往復を要しない。**エピックで絞り込み中は「そのエピック配下かつ未完了」に絞る**——絞り込んで作業しているときに、視野の外のチケットを親に選べても選ぶ理由がない |
| タグ・スプリント | 5.9.4 / 5.9.5 で定義したもの。**ここから新規作成はできない**（5.5 のサイドバーと同じ扱い） |
| 見積 | **ポイント**（`estimate_point`）。5.5 のサイドバーが `5 pt` と出す項目である |

**説明欄には初期値としてテンプレートを入れる**（利用者の判断、2026-08-23）。

```markdown
# 概要

# ゴール条件

# 制約条件
```

**`placeholder` ではなく本文の初期値にする。** placeholder は1文字打つと消えるため、**書かせたい項目には機能しない**（見出しごと消える）。本文に入れておけば、書きたい欄から埋めて残りを消せる。

**プロジェクトごとに変えられるようにはしない。** 必要になってから決める（`project.settings` に置く案は見送った）。

グループ化中にセクション内から作成した場合、**その軸の値を初期値に入れる**（タグでグループ化して「設計」セクションの `[+]` から作れば、タグ「設計」が入った状態で開く）。**エピックで絞り込み中は、そのエピックが親の初期値に入る**（5.4「エピックをフィルタにする」）。

### 編集の単位

**画面全体を編集モードにしない。** 変えたい項目だけをその場で変える。

| 種類 | 操作 | 確定 |
|---|---|---|
| 選択できるもの（状態・担当・優先度・種別・スプリント・タグ・**親**） | ドロップダウンで選ぶ | **選んだ時点で `PATCH`** |
| 文字・数値・日付（タイトル・説明・見積・実績・開始・期限） | **その領域をクリックすると編集モードに入る** | `[保存]` を押す、**または別の領域をクリックしてフォーカスを外す** |

**親は選択式である**（本改訂で「文字・数値」から移した）。親の実体は `parent_seq` の数値であり、**番号を手で打たせる形はどの画面にも無い**。候補は 5.4.3 の新規チケットと同じ「**いま一覧に出ているチケット**」＋「親を外す」で、バックログが最大200件を既に手元に持っているため追加の往復を要しない。**自分自身は候補から落とし、子孫はサーバの `422 parent_cycle` に任せる**（`ApiDesign.md` 9.5.2）——画面は部分木の全体を持っているとは限らない。

**タイトル行の `[編集]` ボタンは置かない**（本改訂で撤回した）。一覧から開いて1項目だけ直す操作が最頻になるため、そのたびに「編集 → 保存」を踏ませるのは重い。

**書かれていない場合の扱いを4つ決めておく。**

| 論点 | 決めたこと |
|---|---|
| 確定が失敗したら（409 / 422 / `not_stageable`） | **編集モードのまま留め、その欄の直下にサーバの `message` を出す。入力値を捨てない**（6.4） |
| 取り消す手段 | **`Esc` で編集前の値へ戻す。** 別の領域をクリックするのは保存であって取消ではない |
| 値が変わっていないとき | **送らない。** フォーカスが外れるたびに `PATCH` すると `version` が無駄に進み、次の編集が 409 になる |
| 説明欄もフォーカスを外して保存するか | **する。** 「保存ボタンを押し忘れて書いた内容が消えた」ほうが実害が大きい |

**`If-Match` は毎回、直前の応答が返した `version` を使う**（`ApiDesign.md` 9.5.2）。項目ごとに個別に送るので、**応答の `version` を1か所で受けて持ち回る**（`ProjectSettingsPage.vue` と同じ形）。

### 説明欄

**Markdownソース＋ライブプレビューである**（`Requirements.md` 7章）。ペインの幅が 750px 前後に制限されたため（2.2.1）、**ソースとプレビューは横に並べず縦に積む。**

| 状態 | 出るもの |
|---|---|
| 読み取り | **レンダリング結果のみ。** 本文が空なら「説明はまだありません」の1行 |
| 編集（領域をクリック） | 上に CodeMirror 6 のソース、**その下にプレビュー**。打つたびにプレビューが追随する |
| 確定 | フォーカスを外すか `[保存]`。**`Esc` は編集前の値へ戻す**（上表と同じ） |

**横2枚に割らない。** 750px を半分にすると各 350px になり、`Requirements.md` 7章が対応すると定めた**表とコードブロックがどちらも読めない幅**になる。縦なら幅を保ったまま両方が見える。

**プレビューは `dompurify` を通してから描く**（`Design.md` 3.1）。`markdown-it` は既定で安全側に倒れているが、**本文の書き手は人だけではない**——エージェントが MCP 経由で書き込む一次資料であり（`Requirements.md` 10章）、描画の直前にもう一段通す。

**本文の見出しは3段下げて描く**（`#` が `<h4>`）。9.2 が「**ページヘッダの `<h1>` が唯一のページ見出しとなる**」と定めているため、本文の `#` をそのまま `<h1>` にすると**利用者が書いた文字がページの見出し階層に割り込む**。見た目の大小は CSS が作るので、段を下げても「概要」が小さくなるわけではない。`###` 以下は `<h6>` に畳まれる——1カラム 750px で4段の見出しを描き分ける必要は無い。

**対応するのは `markdown-it` の既定（CommonMark ＋ 表・取り消し線）だけである。** `Requirements.md` 7章が挙げる構文のうち、**チェックボックス（`- [x]`）・`#123` 形式のタスク参照記法・画像のペーストは Phase 1 では実装しない。** チェックボックスはプラグイン（依存の追加）が要り、`#123` は DoD のタスク参照型（手順18 以降）と連動する記法、画像はファイルストレージの方式が未確定である。**`- [x]` は箇条書きの項目になり、`[x]` はそのまま文字として残る**（実測）——チェックボックスとしては描かれないので、Phase 1 の説明欄ではこの記法を使わない。

**チケットから PB の外を指す2つのセクション**（`ApiDesign.md` 9.10.2、`DbDesign.md` 6.12）。**手順17c で実装する。**

**行の操作は `[編集]` / `[削除]` の文字列を行の右端に置く**（利用者の判断、2026-08-27）。5.9.1 のリポジトリ表は行クリックで編集モーダルを開くが、ここでは**行そのものがリンクである**ため、クリックの意味を2つ持たせられない。

**書き手のアイコン（`🤖` / `👤`）は出さない**（利用者の判断、2026-08-27）。このセクションが表すのは**「このチケットの成果物としてリポジトリ・ブランチ・コミットが紐づいている」という関係**であって、その行を PB へ登録したのが誰かではない。**`created_by` はコミットの committer でもない**——PB はリポジトリへ問い合わせないため（5.9.1「PBがこのURLを使って自動で何かを行うことはしない」）、committer を出す手段がそもそも無い。**API は `created_by` を返し続け、DB にも残す**（`ApiDesign.md` 9.10.2）——将来エージェントの書いた行を区別したくなったとき、データが無いと遡れないため。

**コードの追加を画面に置かないのは、この欄がエージェントの作業記録だからである**（利用者の判断、2026-08-27）。人が手で書くものではない。**削除だけは置く**——誤って積まれた行を人が始末できないと詰む。

**Phase 1 ではエージェント用のアクターも MCP も無い**（`Design.md` 11章 手順21・22）。それまでの書き手は**人の API トークンを持つクライアント**であり、PB 自身の開発では Claude Code がこれにあたる。

**0件のときの扱いは2つで違う。** コードは**見出しごと出さない**（子チケットと同じ。画面から追加できないので、空の枠は何もできない箱になる）。**参考リンクは常に出す**——`[+ 追加]` がこのセクションへの唯一の入口であり、隠すと機能へ到達できない。0件のときは「参考リンクはまだありません」の1行を置く。

**変更は `activity` に記録する**（`ApiDesign.md` 9.1.1 / 9.10.2）。手順19 の変更履歴が「誰がいつどのコミットを紐づけたか」を読めるようにするためで、**`action` は `update`、`field` は `reference.code` / `reference.doc`** である。

（`ApiDesign.md` 6.1 の `sort`）。**ロールは五十音順ではなく `role.sort_order` の順**
（オペレータ→アドミニストレータ）、**状態は昇順で無効が先**である。理由は 6.1 にある。

**検索欄はロールの表示名にも当たる**（「アドミニストレータ」と打つと絞れる）。
ただし**エージェントの「エージェント」という表示は画面が作っている文字列**で
（`system_role` が `null` のときの代替表示）DBに無いため、検索では当たらない。

**検索と絞り込みは常時表示する。** 件数によって出し入れすると、それ自体が制御として無駄であり、
入力欄だけが消えて帯に空きができる。占有は1行（36px）で、原則1（画面の縦は最も希少な資源）とも折り合う。
**種別の絞り込みは置かない**——タブで分かれるため。

**列幅は見出しの境目をドラッグして変えられる。** 既定幅では長いメールアドレスが読めないことがあり、
どの列を広げたいかは利用者と場面による。**保存はしない**——ページを読み直すと既定に戻る。これが幅を
戻す手段でもある（`Design.md` の原則3。専用のリセット操作を置かない）。

**表の総幅は表示領域に一致させる。** 規則は次の4つで、いずれも「総幅＝表示領域」から導かれる。
**ただし操作列（`[⋯]`）は幅調整の対象外**である——内容の長さに依存しないので広げる動機がなく、
可変にすると窓を広げるたびにメニューの周りだけ空きが増える。以下の「列」は操作列を除いた並びを指す。

| 場面 | 挙動 |
|---|---|
| 余りがある | **最後の列（作成）が受け取る。** 表の右に空きを作らない |
| ウィンドウ幅が変わった | 差分を最後の列が吸収して追従する |
| つまみをドラッグした | **右隣の列と融通する。総幅は変わらない**（他の列の幅も動かない） |
| 下限の合計が表示領域を超えた | そのときだけ**表が横スクロールする**（ページ全体は横に流れない） |

**融通する相手を右隣に限る**のは、動く列を1つに絞ると結果が予測できるからである。全列へ按分すると、
1つ広げたつもりが表全体の見た目が変わる。右隣が下限に達したらそこで止まる——総幅を崩さないため。
**最後の列につまみは無い**（右隣が無く、融通する相手がいない）。

**無効なユーザーは行を背面へ下げる**（8.2「完了したものは彩度を失って背景に沈む」）。具体的には、
行の文字を `--pb-11`（文字・弱）にして**輝度の階層で一段下げ**、種別アイコンの**彩度を落とす**。
8.3 の12段スケールは各段の値が固定されており、11段（文字・弱）は 12段（文字・強）より
背景に近い一方で彩度は高い。**行全体の彩度だけを下げる段はスケールに無いため、輝度で下げる**
（独自の色を作らない）。状態列の「無効」という文字は残す（9.2 の「状態を色だけで示さない」）。

**今後、詳細画面のブロックに現れない操作や、関連情報へのひも付きが増えたらここへ足す。**

「認証手段」ブロックが `DbDesign.md` 6.2 の `user_identity` に対応する。Phase 3 で IdP を追加すると、このブロックに行が増えるだけで画面構造は変わらない。

**操作の結果は、その状態が載っているブロックへ出す**（6.4）。`[⋯]` はページヘッダにあるが、
無効化の結果は「基本情報」の状態行のそばに、リセットの結果は「認証手段」に、失効の結果は

表の直上に結果を出す。

**セッションは行ごとに失効させられない。** 一覧は参照のみで、操作は `[ すべてのセッションを失効 ]` の1つだけである。管理者が他人の1セッションを選んで切る場面は考えにくく、怪しいセッションが1つあるなら全部を切るのが実務の動きであるため、対応するAPIを持たない（`ApiDesign.md` 6.7）。**本人が自分のセッションを切る画面も持たない**（5.8）。セッションの管理は管理者の作業であり、このブロックがその場所である。

**自分自身に対する「ロール変更」「無効化」「削除」は、消さずに `disabled` で出す**（押せない理由を添える）。`ApiDesign.md` 6.4 / 6.5 が同じ操作を `409` で弾くのは、UIを迂回して直接APIを叩かれても壊れないようにするためであって、UIから項目を消す理由ではない。**在るはずの操作が黙って消えるより、押せない理由が読めるほうがよい。**

### 表の規則（5.6 の一覧とは別）

**この表に 5.6 の列幅の規則を適用しない。** 5.6 は「総幅＝表示領域」「つまみで右隣と融通」を定めるが、それは列の内容の長さが読めない一覧のための規則である。マトリクスのロール列は `✓` か `—` しか入らず、広げる動機が無い。

| 場面 | 挙動 |
|---|---|
| 列幅の調整 | **できない**（つまみを置かない） |
| 表示領域に収まらない | **ロール列だけが横スクロールする。権限列は左端に固定して動かさない** |
| 縦にスクロールした | **ヘッダ行（グループ見出しとロール名）を上端に固定する** |
| 群（`scope`）の切れ目 | **境目に縦罫を1本引く**（ヘッダから本体まで通し）。あわせて群の見出しの下罫を一段強くする |

**縦罫は群の境目にだけ引く。** 中央寄せの見出しだけでは、どこまでが「システム」で
どこからが「プロジェクト」なのかが読めない（利用者の実機確認、2026-08-22）。
一方で全列に引くと格子になり、5.6 の一覧や 5.9.2 のメンバー表が横罫だけで
組まれているのと見た目が揃わない。**読みたいのは群の範囲であって、隣り合う列の
区切りではない。** ヘッダだけでなく本体まで通すのは、下までスクロールしたときに
切れ目が分からなくなるのを防ぐため（ヘッダ行を固定したのと同じ理由）。

**権限列を固定するのは、`✓` が付いているのが何の権限なのかを見失わせないため**である（利用者の判断、2026-08-22）。ヘッダ行を固定するのは同じ問題の縦方向で、権限28行＋カテゴリ小見出し8行は表示領域より高くなり、下へスクロールすると `✓` がどのロールの列か読めなくなる。

```
└───────────────────────────────────────────────────────────────────────┘
```

**タブは一般タブと同じものを出す**（ページ見出しも「自分の設定」のまま）。切替が URL の
遷移になる点は 5.8 と同じである。

| 列 | 内容 |
|---|---|
| 名前 | 発行時に本人が付けた名前。**どの端末・どの用途かを本人が思い出すための唯一の手がかり**である |
| 接頭辞 | `token_prefix`（先頭8文字）。平文は二度と出ない（`ApiDesign.md` 4.4.1） |
| 発行 / 最終利用 / 有効期限 | 一度も使われていなければ最終利用は `—` |
| 状態 | `● 有効` / `期限切れ`。**色だけで示さない**（9.2）ので記号か文言を必ず添える |

**失効済みの行は出さない**（`ApiDesign.md` 4.4.1）。`[失効]` を押した行はその場で消える。
**期限切れは出す**——更新が要ることに本人が気づく必要があり、また上限5本を占めているためである。

**行の操作は `[失効]` の1つだけなので `[⋯]` を使わない**（5.6 の一覧とは違う）。
項目が1つのメニューは、開く手間が増えるだけである。

**上限に達したら `[ + 発行 ]` を `disabled` にし、理由をその場に出す**
（「5本まで発行できます。新しく発行するには、いずれかを失効させてください」）。
**在るはずの操作が黙って消えるより、押せない理由が読めるほうがよい**（5.6.2 と同じ）。

#### 発行モーダル

```
┌─ アクセストークンを発行 ──────────────────────┐
│ 名前 *      [ CLI (MacBook)              ]    │
│ 有効期限    ( ○ 30日  ● 90日  ○ 365日 )       │
│             2026-11-20 まで有効です            │
│                        [ キャンセル ] [ 発行 ] │
└───────────────────────────────────────────────┘
```

**スコープは選ばせない**（`ApiDesign.md` 4.4.2）。常に「絞り込みなし」＝本人の権限そのままで
発行する。どの権限をまとめて選ばせるかは、トークンで実際に何をするか（Phase 2 の MCP 連携）が
決まってから設計する。**選択肢を先に作ると、使われ方を知る前に語彙が固まる。**

**選んだ日数から算出した期日をその場に出す。** 「90日」と「2026-11-20」では、後者しか
カレンダーと突き合わせられない。

## 5.9 プロジェクト設定 `/p/:key/settings`

**必要権限**：`project.edit`（プロジェクト管理者以上。4.3 の出し分けと同じ）

（本節は画面の遷移順では 5.5 の次に来るが、**節番号は末尾に採った。** 5.6〜5.8 を繰り下げると
`ApiDesign.md`・`Design.md`・実装のルート定義にある参照が一斉にずれるためである。）

タブは **「一般」「メンバー」「タグ」「スプリント」の4つ**。ワークフローとエージェント連携は Phase 2 である（3.1 の遷移図）。

**タグとスプリントは `ApiDesign.md` 9章の確定にともなって加わった**（5.9.4 / 5.9.5）。どちらも「プロジェクトの分類軸・区切りを決める」行為であり、個々のチケットではなくプロジェクト全体の語彙を決める点でワークフローと同じ性格を持つ。**運用（バーンダウンを含むスプリント管理、10章）とは別画面**であり、ここは定義だけを扱う。

**タブはURLを持たない。** 3.2 のルーティング表が持つのは `/p/:key/settings` の1行だけであり、5.6 のタブ（ユーザー／ロールと権限）も同じ扱いである。Phase 2 の `/p/:key/settings/agents` だけが別ルートとして予約されている。

| 用途 | 呼ぶAPI |
|---|---|
| 表示（一般・メンバー） | `GET /projects/:key`（`ApiDesign.md` 5.4）。**この2タブはこれ1本で足りる**（メンバーもワークフローも同じ応答に含まれる） |
| 保存 | `PATCH /projects/:key`（5.5）。`If-Match` に取得時の `version` |
| アーカイブ | `POST /projects/:key/archive` / `unarchive`（5.6） |
| タグ | `GET|POST /projects/:key/tags`、`PATCH|DELETE /projects/:key/tags/:id`（`ApiDesign.md` 9.11） |
| スプリント | `GET|POST /projects/:key/sprints`、`PATCH|DELETE /projects/:key/sprints/:id`（`ApiDesign.md` 9.12） |

**タグとスプリントは、そのタブを最初に開いたときに取得する。** 画面のロード時に3本まとめて投げない——一般タブしか見ない利用者に、使わない2本を払わせないためである。

ページヘッダは `プロジェクト設定`。プロジェクト名を冠するのはダッシュボードだけである（5.3）。

**並びは「プロジェクト名」を先頭とする。** キーは一意に指すための識別子だが、**プロジェクトの一属性にすぎない**。利用者が名付けた名前より上に置くと、画面の主題がキーであるかのように読める。

| 項目 | 仕様 |
|---|---|
| プロジェクト名 | 1〜100文字。必須。**ブロックの先頭に置く** |
| プロジェクトキー | **読み取り専用**。名前の下に置く。変更できない理由は 5.2.1 に記す（外部に流出した参照を直せないため） |
| 説明 | 0〜1000文字。空にすると `PATCH` は `"description": null` を送る（5.5 が「消す」と「据え置く」を区別する） |
| リポジトリ | **0件以上。複数を前提とする。** 各行は表示名（任意）とURL（必須） |
| ワークフロー | **参照のみ。** 名前とステータスの並びを出す。切り替えは Phase 2 の「ワークフロー」タブ |
| プロジェクトの状態 | `active` / `archived` と切替ボタン。`project.archive` を持たない場合は**ブロックごと出さない**（原則4） |
| `[保存]` | **変更があるときだけ有効。** 押すと変更されたフィールドだけを1回の `PATCH` で送る |

**保存を「一般タブに1つ」とする。** ブロックごとに `[保存]` を置くと、そのたびに `version` が進み、`If-Match` の持ち回りが増える。1回の `PATCH` にまとめれば、競合の判定も再取得も1本の経路で済む。

#### リポジトリ

**PBがこのURLを使って自動で何かを行うことはしない**（Phase 1）。用途は次の2つに限る。

1. 画面にリンクとして出し、利用者がクリックして遷移できる
2. MCP経由で、実装を担うエージェントがプロジェクトの情報として取得できる（**説明を含む**。下記）

| 項目 | 仕様 |
|---|---|
| 保存先 | `project.settings`（jsonb）の `repositories` キー。構造の正本は `DbDesign.md` 6.4 |
| URL | 必須。`https://…` と `git@host:org/repo.git` の双方を受ける。**形式の検証は「空でないこと」に留める** |
| 表示名 | 任意。省略時はURLをそのまま見せる |
| 説明 | 任意・200文字まで。**ラベルは `説明` とする。** そのリポジトリとプロジェクトの関係を書ける欄だが、画面の文言で用途を狭めない |
| 並び | 入力した順（配列の順）。並べ替えのUIは置かない（原則3） |
| リンク | **`https://` または `http://` で始まるものだけ**をリンクにする。SSH形式（`git@host:org/repo.git`）は**文字列として表示し、コピーできるようにする**（ブラウザから開けないため）。判定の正本は `client/src/lib/url.ts` の `isWebUrl` 1つで、5.5 の外部参照と共有する |
| 上限 | 10件。1件のURLは1000文字まで |

**一覧は表とし、編集はモーダルで行う。** 入力欄を並べて置くと、件数が増えるほど一般タブが縦に伸び、他の設定項目が画面から押し出される。

| | |
|---|---|
| 一覧 | `URL` / `表示名` / `説明` の3列と `[削除]`。行をクリックすると編集モーダルが開く |
| モーダル | 入力は `URL`（必須）→ `表示名` → `説明` の縦積み。`Modal.vue`（6.1）を再利用する |
| リンク | 表の URL セルのうち `isWebUrl` が真のものはリンクにする。**行クリック（編集）と競合しないよう、リンクのクリックは伝播させない** |
| 保存 | モーダルの確定は**画面上の一覧を書き換えるだけ**で、サーバへは送らない。永続化は一般タブの `[保存]` 1つに集約する |

**`http://` もリンクにする**（本改訂で `https://` だけから広げた。利用者の判断、2026-08-27）。この規則が線を引いている理由は**ブラウザから開けるかどうか**であって、スキームの安全性ではない。SSH形式はクリックしても何も起きないので文字列に留めるが、`http://` は開ける。手順11b の実装（`^https?://`）が最初からこの形で、**文書のほうが実装より狭かった**——実装に合わせて文書を直している。

**この配置は暫定である。** 設定項目が増えて一般タブが窮屈になったら、独立したタブへ移すことを含めて見直す（`GuiDesign.md` 11章の未解決事項）。

**説明はエージェントにも効く。** MCP経由でプロジェクト情報を取得したエージェントは、リポジトリが複数あるとき「どれを触ればよいか」をURLだけからは判断できない。**関係を書いた文が、そのまま判断材料になる。**

**`settings` は `PATCH` で丸ごと置き換わる**（`ApiDesign.md` 5.5）。画面は**取得した `settings` を保持し、`repositories` だけ差し替えて全体を送る**。知らないキー（Phase 2 の設定など）を落とすと、他の機能の設定が消える。

#### ワークフローの表示について（暫定）

**この表示は暫定である。** 参照のみで置いてみて、実際の画面を見たうえで、**拡充するか削除するかを後で決める**。Phase 2 の「ワークフロー」タブの設計に引き継ぐ。

**将来は、この画面からメンバーを追加・削除できるようにする。** `ApiDesign.md` 6.8 が Phase 2 で `POST /projects/:key/members` を追加すると定めている。ユーザー個別ではなく**まとまり（グループ）単位で権限を与えたい**という要求もあるが、現在の設計に「グループ」という概念は無い（`actor` は user / agent / system、権限の束は `role`）。11章の未解決事項として扱う。

### 5.9.3 保存・競合・アーカイブ

**4状態**（6.2）を持つ。読み込み中はスケルトン、取得に失敗したら原因と再試行、権限エラーは 403 ページへ。

**操作の結果はトーストではなく、操作した場所に出す**（6.4）。

| 応答 | 画面の振る舞い |
|---|---|
| `200` | サーバが返した内容で入力欄と `version` を更新し、`[保存]` の隣に `✓ 保存しました` を出す |
| `409 conflict` | サーバの `message` をそのまま出し、`[最新の内容を取得]` を添える。押すと再取得して入力欄を最新の値に置き換える |
| `422 validation_failed` | `details[].field` に従って各入力欄の下に出す（2.5） |
| `403` / `404` | それぞれのエラーページへ送る（7.2 と同じ規則） |

**アーカイブは確認ダイアログを挟む**（6.3 が「プロジェクトのアーカイブ＝確認ダイアログ」と定める）。

成功しても**画面から離れない。** 状態表示が `アーカイブ済み` に変わり、ボタンが `[アーカイブを解除]` になる。`ApiDesign.md` 5.6 が「`204` にしないのは、画面が `status` と `version` を1往復で更新できるようにするため」と書いており、その場で反映することを前提としている。**API は冪等**なので、二重送信しても状態は壊れない。

### 5.9.4 タグタブ

チケットの横断的な分類（`DbDesign.md` 6.10）を定義する。

```
┌───────────────────────────────────────────────────────────────────────┐
│ タグ                                                    [+ 追加]      │
│ ┌────┬──────────────┬────────────┬──────────────────────────────────┐ │
│ │ ⠿  │ 名前          │ 使用中      │                                  │ │
│ ├────┼──────────────┼────────────┼──────────────────────────────────┤ │
│ │ ⠿  │ 設計          │ 12件        │              [名前を変更] [削除] │ │
│ │ ⠿  │ GUI           │  8件        │              [名前を変更] [削除] │ │
│ │ ⠿  │ MCP           │  0件        │              [名前を変更] [削除] │ │
│ └────┴──────────────┴────────────┴──────────────────────────────────┘ │
│ ⓘ タグはチケットを横断的に分類します。「どの大きな仕事の一部か」は       │
│   チケットの親子関係で表します                                         │
└───────────────────────────────────────────────────────────────────────┘
```

| 項目 | 仕様 |
|---|---|
| API | `GET|POST /projects/:key/tags`、`PATCH|DELETE /projects/:key/tags/:id`（`ApiDesign.md` 9.11） |
| 必要権限 | 閲覧は `ticket.view`、変更は **`project.edit`**。タブ自体はこの画面（`project.edit`）の中にある |
| 名前 | 1〜30文字。プロジェクト内で一意。重複は `409` を受けてその場に出す |
| 並べ替え | `⠿` のドラッグ。バックログのグループ化セクションの順序になる |
| 色 | **持たせない**（8.6） |
| 削除 | 確認ダイアログに**使用中の件数**を出す（6.3）。使用中でも削除でき、チケットからタグが外れるだけでチケットは消えない |

**タグをここで定義するのは、それが「プロジェクトの分類軸を決める」行為だからである。** ワークフローと同じく、個々のチケットではなくプロジェクト全体の語彙を決める。チケット詳細（5.5）からは**既存のタグを付け外しできるだけで、新規作成はできない。** 作れるようにすると、綴り違いの重複タグ（`GUI` と `gui` と `ＧＵＩ`）が増えて分類として機能しなくなる。

### 5.9.5 スプリントタブ

```
┌───────────────────────────────────────────────────────────────────────┐
│ スプリント                                              [+ 追加]      │
│ ┌──────────────┬─────────────────────┬────────┬──────────┬─────────┐ │

└───────────────────────────────────────────────────────────────────────┘
```

| 項目 | 仕様 |
|---|---|
| API | `GET|POST /projects/:key/sprints`、`PATCH|DELETE /projects/:key/sprints/:id`（`ApiDesign.md` 9.12） |
| 必要権限 | 変更は `project.edit` |
| 状態 | `planned` 計画中 / `active` 進行中 / `completed` 完了 |
| 進捗 | 完了チケット数 / 総チケット数。**グラフは出さない**（バーンダウンは Phase 2 の `/p/:key/sprints`） |

**バーンダウン・ベロシティを含むスプリント管理画面は Phase 2 の `/p/:key/sprints`**（10章）。ここは**定義だけ**を扱う。定義（プロジェクト設定）と運用（管理画面）を分けるのは、タグ・ワークフローと同じ考え方である。

## 6.2 状態パターン

すべてのデータ表示領域は4状態を持つ。**空状態とエラー状態を後回しにしない。**

| 状態 | 表現 |
|---|---|

| 正常 | — |

## 6.3 破壊的操作の確認

| 操作 | 確認方法 |
|---|---|
| チケット削除 | 確認ダイアログ。**子チケットの件数を出す**（子は消えず、親を失ってトップレベルへ上がる。`ApiDesign.md` 9.5.3） |
| タグ削除 | 確認ダイアログ。**使用中のチケット件数を出す**（5.9.4） |
| スプリント削除 | 確認ダイアログ。**チケットは消えずスプリント未設定に戻る**旨を明記（5.9.5） |
| 外部参照（コード・参考リンク）の削除 | 確認ダイアログ。**どちらも人が入れ直せるとは限らない**——`code` は画面に追加の導線が無く（5.5）、`doc` はURLを控えていないと戻せない。誰も締め出さないので文言は1行でよい |
| プロジェクトのアーカイブ | 確認ダイアログ |
| ユーザー削除 | **ユーザー名の入力を要求**（誤操作防止） |
| トークン失効 | 確認ダイアログ。失効後は復元不可の旨を明記 |
| ユーザーのパスワードリセット | 確認ダイアログ。**現在のパスワードが使えなくなり、全セッションが失効する**旨を明記（`ApiDesign.md` 6.6） |
| ユーザーの無効化 | 確認ダイアログ。本人が次のリクエストからログインできなくなる旨を明記 |

**確認を挟むかどうかは「取り消せるか」ではなく「誰に影響が出るか」で決める。**
上の2件は手順13b で追加した。どちらも操作した本人ではなく**対象の利用者**が
締め出される側で、押し間違いに気づくのが遅れる。逆に、**有効化・プロジェクト
権限の付与と剥奪・アーカイブの解除には確認を置かない**——同じ画面ですぐ元へ戻せる。

## 6.4 操作結果の伝え方（トーストを使わない）

**操作の結果は、操作した場所に出す。** 画面の隅に浮かぶ通知（トースト）は採らない。

| 理由 | |
|---|---|
| 原則1 | **画面の縦は最も希少な資源**である。浮遊する通知は、ただでさえ狭い作業面をさらに圧迫する |
| 集中 | 視野の周辺で動くものは注意を奪い、作業中の集中を削ぐ |
| 通知の向き | **通知は、利用者が行動を起こして見に行ったときに初めて出るべきである。** 押し付ける形にしない |

| 状況 | 出し方 |
|---|---|
| 保存が成功した | 保存した場所（ブロック内・ボタンの近く）に結果を出し、画面の値をサーバ応答で更新する |
| 保存が失敗した | 同じ場所にサーバの `message` をそのまま出す（`ApiDesign.md` 2.5）。入力欄に紐づく誤りは `details` に従って欄の下に出す |
| 状態が変わった | 状態表示そのものを更新し、操作ボタンの文言を次の操作へ変える（例：アーカイブ後は「アーカイブを解除」になる） |

**保存操作は楽観的更新を行わず、サーバ応答後に反映する**（ずれた状態を見せない）。

**結果表示を入力の監視で消さない。** 成功時にサーバ応答をフォームへ書き戻す／入力欄を空へ戻すと、
その書き戻し自体が監視を発火させ、出したばかりの結果が消える。**「サーバの値と一致している
間だけ出す」「空である間だけ出す」と宣言的に書く**と、発火の順序に依らなくなる。

**画面が消える操作だけは、次に着地する画面へ渡す**（削除 → 一覧。`history.state`）。
実装例は `ProjectSettingsPage.vue` の保存ブロック、`UsersPage.vue` の表の直上（追加と `[⋯]` の
結果を1つの欄で使い回す）、`UserDetailPage.vue` の**ブロックごとの結果**（ヘッダの `[⋯]` から
始めた操作も、状態が載っているブロックへ返す）。

画面をまたぐ通知（他者の操作・エージェントの完了など）が必要になった場合は、
**このパターンの拡張ではなく独立した課題として扱う**（11章「通知の扱い」）。

## 6.5 プレースホルダページ

**設計が未確定・未実装の画面には、空白や404ではなくプレースホルダページを表示する。**

### 実装

単一のコンポーネント `PlaceholderPage.vue` を用意し、ルート定義から内容を渡す。**画面ごとにファイルを作らない。**

```ts
// router/routes.ts

    permission: 'project.view',

      title: 'プロジェクトダッシュボード',

        '要対応（放置検出・期限超過）',
      ],
    },
  },
}
```

**実装時はこのルート定義を実コンポーネントに差し替えるだけ**で済み、`meta.placeholder` を削除すれば移行が完了する。どのルートがまだプレースホルダかは `routes.ts` を grep すれば一覧できる。

### 規約

| 項目 | 規約 |
|---|---|
| 見出し | `<画面名>のページ予定` を必ず含める。議論のときにこの文言で画面を特定できる |
| 設計文書の参照 | 対応する章番号を必ず表示する。未定義なら「設計未確定」と明記する |
| 予定内容 | 設計文書に書かれている項目を転記する。**プレースホルダ側で内容を創作しない** |
| 権限 | 実画面と同じ `meta.permission` を設定する。**権限による遷移制御はプレースホルダ段階から効かせる** |
| 配色 | `--pb-text-muted` を基調とし、`--pb-warning` や `--pb-ai` を使わない（未実装は警告でもAI由来でもない） |

**権限を実画面と同じにしておくことが重要である。** プレースホルダのうちにルーターガードとメニュー出し分けを検証でき、実画面に差し替えた時点で権限まわりの動作が保証される。

## 6.6 クラス名の衝突を避ける

**scoped スタイルは見た目を分けるが、DOM のクラス名は分けない。** 同じ名前が別の画面や
共有の正本に付いていると、検証のセレクタが両方に当たり、CSS は詳細度で競合する。

| 規則 | 起きたこと |
|---|---|
| **部品の中の役割名は部品名を冠する**（`.split-primary`） | `.primary` / `.secondary` / `.danger` は `base.css` が持つ**ボタンの正本**（手順13b）。`SplitPane` のスロット用 div に `class="primary"` と書いたら**一覧ペイン全体が `--pb-accent` で塗り潰された** |
| **画面の中の区画名も画面名を冠する**（`.group-section`） | `SideMenu.vue` が「管理」の見出しに `.section` を使っており、バックログで同じ名前を使ったら検証の `querySelectorAll('.section')` が両方に当たって11件が同時に FAIL した |
| **要素セレクタにレイアウト値を書かない** | `input[type='text'] { width: 100% }`（詳細度 0,1,1）は `.repo-name { width: 160px }`（0,1,0）に勝つ。同じことが `.corner` と `.matrix thead th` の `z-index`、`.group` と `.matrix th, .matrix td` の `text-align` でも起きた——**自分で書いた要素セレクタに、直後に自分で負ける** |

**DOM に在ることを見る検証では拾えない。** 位置と幅は `getBoundingClientRect()` で測る。

---

## 6.7 レイアウトの落とし穴

いずれも `getBoundingClientRect()` は妥当な箱を返すため、**座標を測る検証では拾えない**。
スクリーンショットを見るか、実機で触って初めて分かる種類のものである。

| 規則 | 起きること |
|---|---|
| **負の余白で要素を重ねたら `z-index` を必ず添える** | `SplitPane` の境界（`.divider`）を `margin-right: -9px` で重ねたら、DOM 順で後ろの詳細ペインが上に載り**一度も掴めなかった** |
| **`flex` の主役には `flex: 1 1 auto` と `min-width` を添える** | `overflow: hidden` を書くだけでは `0 1 auto` のままで、隣の `flex: none`（バックログではタグ）が残り**主役のほうが先に0幅まで潰れる**（`BacklogPage.vue` の `.title` は `min-width: 6em`） |
| **`th` / `td` に `display: flex` を掛けない** | 表のレイアウトから外れ、**行の区切り線が操作列の手前で切れる**（1440px と 900px の両方）。並べるのは中の入れ物（`.row-actions`）の役目にする |
| **見出しに階層を作ったら、その範囲を線か面で示す** | 中央寄せは位置の情報であって範囲の情報ではない。「群の見出しがどこまでを覆っているか分からない」という形で表に出る |
| **画面に出す日本語は1行に収める** | テンプレートで行を折り返すと**その位置に空白が入る**（`…メンバーでなくても すべての…`）。素の HTML でも同じ |

## 6.8 ドラッグ＆ドロップ

| 規則 | 理由 |
|---|---|
| **落とし場所は掴む前から画面にあるものに限る**（行・見出し・空の枠） | 掴んだ行の位置が `dragstart` の直後にずれると **Chrome がドラッグを取り消す**（`dragstart` の 1〜2ms 後に `dragend` が来て、`dragover` は一度も起きない） |
| **受け取れる相手の上でだけ `dragover` の既定動作を止める** | HTML の D&D は「既定を止めた要素」だけがドロップ先になる規約で、すべて受け取ってから弾くと**落とせるように見えて何も起きない**。落とせない行ではカーソルが禁止の形になるのが正しい（`BacklogPage.vue` の `onDragOver`） |

**検証は合成した `DragEvent` ではなく `Input.setInterceptDrags` で本物を回す**
（`Development.md` 8.2）——合成イベントは自分のハンドラを呼ぶだけで、
**ドラッグが始まるかを測れない**。

# 7. 状態管理とルーターガード

## 7.1 ストア構成（Pinia）

|---|---|

## 7.2 ルーターガード

```
router.beforeEach:
  1. 未認証 かつ 保護ルート
       → /login?redirect=<元のパス>
  2. :key のプロジェクトにアクセス権が無い
       → /404 （403 ではない）
  3. ルート定義の meta.permission が auth ストアに無い
       → /403
  4. 通過
```

**手順2で 404 を返す**のは `Design.md` 6.4.5 の方針に従う。403 を返すと「そのキーのプロジェクトが存在すること」自体が漏れるため。

**プロジェクトの到達可否（手順2）を権限判定（手順3）より先に置く。** 逆順にすると、非メンバーのプロジェクトでは先に「権限が無い」と判定されて 403 になり、404 に倒した意味が失われる。サーバ側の `RequireProjectPermission` も同じ順序で判定する（`Design.md` 6.4.5、非メンバーかつ非アドミニストレータ → 404、到達できるが権限が無い → 403）。**画面とサーバで応答が食い違わないようにする。**

**401 は `error.code` で分ける**（`api/client.ts`）。`unauthenticated` だけがセッション失効で、
`invalid_credentials` は「いま打った資格情報が違う」である。**分けないと、パスワードを
打ち間違えた人がログイン画面へ飛ばされる**（`POST /me/password` が、認証済みで
`invalid_credentials` を返す最初のエンドポイントだった）。

`meta.permission` を照合する相手は、`:key` を持つルートでは当該プロジェクトの実効権限（`GET /me` の `projects[].permissions`）、それ以外のルートではシステムロール由来の実効権限（同 `permissions`）とする（`Design.md` 6.4.1 の三層構造）。

## 7.3 権限による表示制御

```vue
<PermissionGate permission="ticket.create">
  <button>+ 新規チケット</button>
</PermissionGate>

<!-- または -->
<button v-if="can('ticket.create')">+ 新規チケット</button>
```

フロントの制御は**利便性のためのものであり、セキュリティ境界ではない**。同じ判定をサーバ側でも必ず行う（`Design.md` 6.4.4）。

## 7.4 `<script setup>` の書き方

| 規則 | 起きること |
|---|---|
| **`immediate: true` の `watch` はスクリプトの末尾に置く** | setup のその場でコールバックが走るので、上に置くと**まだ宣言されていない `const`（ref）に触れて TDZ の `ReferenceError`** になる。関数宣言は巻き上がるが、その関数が参照する `const` は巻き上がらない。**Vue は `console.error` に流すだけで画面は出る**ため、症状は「中身が真っ白」になり原因が読めない |
| **`type="number"` の値を文字列として扱う前に `String()` を通す** | `v-model` は `type="number"` の値を自動で数値へ変換する（Vue 3 の `vModelText` が `el.type === 'number'` で数値化）。`ref('')` の型は `Ref<string>` のままなので**コンパイルでは捕まらず**、`.trim()` が実行時 `TypeError` になる。**しかもハンドラの中で投げるので画面は何も言わない**（保存されないだけ） |

## 7.5 日時と日付の出し方

`client/src/lib/datetime.ts` の2つを使い分ける。

| 対象 | 使う関数 |
|---|---|
| `timestamptz`（その瞬間） | `formatDate` |
| `date` 列（その日） | **`formatPlainDate`** |

**`date` 列に `formatDate` を使うと、UTC より西の地域で前日へずれる。**
`new Date('2026-08-19')` は仕様上 UTC の0時と解釈される一方 `getDate()` はローカルを返すため
（`America/New_York` で `2026-08-18` になることを実測）。期限は「その日」であって
「その瞬間」ではない。**`Asia/Tokyo` の端末では再現しないので、ふだんの検証では拾えない。**

# 8. ビジュアルデザインとデザイントークン

## 8.1 方針：モノクロマティックを基調とする

PB は**単一色相のスケール（モノクロマティック）を基調**とし、有彩色は限定された3つの意味にのみ使う。

チケット管理ツールは1日に何時間も注視され続ける画面である。色数が多いUIは、開いた瞬間の印象は華やかでも、**色そのものが情報を持ってしまうため、見るたびに「この色は何を意味するか」を解釈する負荷**がかかる。色を減らし、情報の階層を輝度と彩度の差で表現すれば、この解釈コストが消える。

| | 方針 |
|---|---|
| 基調 | 単一色相の12段スケール。背景・境界・文字・アクセントのすべてを同一色相から取る |
| ベース色相 | **ブルー（既定, h=245）／グリーン（h=135, 新緑・茶葉）** を切り替え可能とする（8.3） |
| 有彩色 | **危険（赤）・警告（黄）・AI（紫）の3つのみ**。それ以外の意味に色を割り当てない |
| 階層表現 | 輝度（L）で情報の前後関係を、彩度（C）で状態の強さを表す（8.2） |
| 純色の禁止 | 純白（#fff）・純黒（#000）・彩度0のグレーを使わない。すべてベース色相をわずかに含ませる |

## 8.2 輝度と彩度の役割分担

**この2軸の役割を混ぜないことが、モノクロマティック設計を成立させる鍵である。**

| 軸 | 表すもの | 例 |
|---|---|---|
| **輝度（L）** | 情報の**階層・前後関係**。背面ほど背景に近く、前面ほどコントラストが高い | 背景 → 面 → 境界 → 文字 の順に L が離れていく |
| **彩度（C）** | 状態の**強さ・活性度**。関与しているものほど彩度が高い | 未着手（C≈0.01）→ 進行中（C≈0.02）→ 選択中（C≈0.12） |

この規則から自然に導かれる帰結として、**完了したものは彩度を失って背景に沈む**。視線は自動的に未処理の情報へ向かい、「終わったタスクが目立ち続ける」ことがなくなる。

## 8.3 ベース色相スケール（12段）

Radix Colors と同様の12段構成を採り、各段の役割を固定する。値は **OKLCH** で定義する。OKLCH は知覚的に均等なため、**色相を変えても各段の「見た目の明るさ」が変わらない**。これがブルー／グリーン切替を変数だけで成立させる根拠である。

| step | 用途 | 説明 |
|---|---|---|
| 1 | アプリ背景 | 最背面。ページ全体の地 |
| 2 | 面（subtle） | カード・サイドメニューなど、地から一段浮く面 |
| 3 | UI要素の背景 | バッジ、入力欄、選択行 |
| 4 | hover | 要素のホバー状態 |
| 5 | active | 要素の押下・選択状態 |
| 6 | 境界（弱） | テーブルの罫線、区切り線 |
| 7 | 境界 | 入力欄・カードの枠線 |
| 8 | 境界（強）／フォーカス | フォーカスリング、強調枠 |
| 9 | solid | 主要ボタン、選択中インジケータ。**白文字が載る** |
| 10 | solid hover | 同上のホバー |
| 11 | 文字（弱） | 副次テキスト、ラベル、メタ情報 |
| 12 | 文字（強） | 本文、見出し |

**輝度（L）は全色相で共通とし、彩度（C）のみ色相ごとに係数で調整する。** 緑は青に比べて同一彩度でも知覚的に鈍く（無彩色寄りに）見えるため、グリーンでは彩度に 1.12 を掛ける。これにより両色相で「同じ濃さに感じられる」状態を保つ。

## 8.4 意味色（有彩色は3つのみ）

| 意味 | 色相 | 表現の主体 | 用途 |
|---|---|---|---|
| **danger** | h = 25（赤） | 文字・枠線 | 破壊的操作、期限超過、失敗、エラー |
| **warning** | h = 92（黄） | **面（チップ・左罫）** | 注意喚起、承認待ち、放置検出 |
| **ai** | h = 300（紫） | 点・線（小バッジ、破線枠） | **未確認のAI出力**であること（8.4.2） |

### 8.4.1 warning は「文字」ではなく「面」で表現する

黄は本質的に**高輝度でしか黄に見えない色相**である。文字として使える暗さ（L≈0.48）まで落とすと、sRGB では彩度が 0.098 までしか伸びず、`#715b00` のような黄土色・オリーブに転ぶ。従来案の橙寄り（h=72）が茶色く見えていたのはこれが理由である。

そこで**警告は明るい黄の面として表現し、その上に暗い文字を載せる**設計に改める。

| トークン | light | dark | 用途 |
|---|---|---|---|
| `warning` | `#f9ce32` | `#e9c025` | チップの地、左罫、マーカー。**上に載る文字はベースの step 12** |
| `warning-bg` | `#fdf4d8` | `#2d240b` | 「要対応」ブロックの背景 |
| `warning-border` | `#ebd696` | `#554614` | 同上の枠線 |
| `warning-text` | `#715b00` | `#d5b85e` | 例外的に文字を黄にする場合のみ。使用は最小限に |

`warning` の面に step 12 の文字を載せたときのコントラストは **10.7:1**（ダーク 10.9:1）で、十分に読める。

```
┌─ 要対応 ───────────────────────────────────────────┐   ← 枠線 warning-border
│▌3件のチケットが14日以上更新されていません   確認する →│   ← 左罫 warning（黄）
│▌my-app-12 が期限を超過しています           確認する →│      文字は通常のベース色
└────────────────────────────────────────────────────┘   ← 背景 warning-bg
```

**この変更は他の2色にも一般化できる。** danger は文字・枠線で、warning は面で、ai は点・線で表現する。役割を分けることで、3色が同一画面に並んでも階層が壊れない。

### 8.4.2 紫（AI）が画面を埋め尽くさないための設計

AI活用が進むほど紫が増え続ける、という懸念は妥当である。放置すると「紫＝AI」という記号が意味を失い、単なる背景ノイズになる。以下4点で抑制する。

**1. 紫の意味を「AI由来」から「未確認のAI出力」へ変更する**

これが最も効く。**人間が承認・採用した時点で紫を外し、通常の情報として扱う。**

| 状態 | 表現 |
|---|---|
| AIが提案した、まだ人間が見ていない | 紫のバッジ＋破線枠 |
| 人間が承認・採用した | **紫を外す**。通常のリンク・コメントとして表示 |
| 人間が却下した | 非表示（履歴には残る） |

結果として、**画面上の紫の総量が「レビューが追いついていない量」を表すシグナル**になる。紫が増えたら、それは色の問題ではなく承認が滞っている状態そのものであり、`Requirements.md` 10.6.3 で懸念した「PMがボトルネックになる」現象が可視化される。**懸念を機能に転化する。**

**2. 恒常的に表示される要素からは色を外す**

エージェントのアバターは、紫の縁取りではなく**形状**で区別する（人間＝円、エージェント＝角丸四角）。担当者列やコメント欄に常時並ぶ要素は、色ではなく形で識別させる。色は「今この瞬間の状態」に予約し、「属性」には使わない。

**3. 面を持たせず、点と線に限定する**

紫の使用は 1px の破線枠と小バッジのみとし、背景の塗りつぶしには使わない（`ai-bg` はモーダルなど単一箇所に限る）。同じ色でも面積が小さければ視覚的な支配力は生じない。

**4. 同種の提案が連続する場合はまとめる**

一覧上で同じ種類のAI提案が3件以上並ぶ場合、行ごとにバッジを出さず、**グループ見出しに1つだけ**表示する（「AI提案 5件」＋展開トグル）。

| トークン | light | dark |
|---|---|---|
| `ai` | `#8259bf` | `#a07cdb` |
| `ai-text` | `#674698` | `#bca1ed` |
| `ai-bg` | `#f4efff` | `#251f31` |
| `ai-border` | `#d8ceee` | `#473b5e` |

**OKLCH の対応状況**：主要ブラウザは対応済み。PB はローカル環境での利用が前提であり互換性の懸念は小さいが、念のためビルド時に hex フォールバックを生成する（`@supports not (color: oklch(0 0 0))` ブロック、または PostCSS プラグイン）。

## 8.6 有彩色を使ってよい場所・いけない場所

| 使ってよい | 色 | 理由 |
|---|---|---|
| 削除・失効など**取り消せない操作**のボタン | danger | 誤操作の防止は最優先 |
| 期限超過・エラー・失敗 | danger | 即座の認知が必要 |
| 承認待ち・放置検出・要対応ブロック | warning（面） | 行動を促す必要がある |
| **未確認の**AI提案・AI生成要約 | ai（点・線） | 人間の確定情報と混同させないため |

| 使ってはいけない | 代替 |
|---|---|
| チケットのステータス | 輝度差＋記号（8.7） |
| 優先度 | 記号のみ（8.7） |
| チケット種別 | アイコン形状 |
| **エージェントであること（属性）** | 形状（人間＝円、エージェント＝角丸四角）。8.4.2-2 |
| **承認済みのAI由来情報** | 通常色。紫を外す。8.4.2-1 |
| ラベル・タグ | 枠線＋文字。**ユーザーによる任意色の指定も許さない** |
| プロジェクトの識別 | 名前のみ |
| グラフの系列 | 同一色相の輝度違い。3系列を超える場合は破線・点線を併用 |
| 装飾・ブランディング | — |

**ラベルに任意色を許さない**のは意識的な判断である。JIRA等では便利に見えるが、実際にはユーザーごとに色の意味が食い違い、一覧が虹色になって輝度による階層が崩壊する。PB では**色は常にシステムが意味を保証するもの**とする。

## 8.7 ステータスと優先度を色なしで表現する

### ステータスバッジ

```
┌──────────────┬─────────────────────────────────────────────┐
│ ○ 未着手      │ 背景なし / 枠線 --pb-border / 文字 --pb-text-muted │
│ ● 進行中      │ 背景 --pb-elevated / 文字 --pb-text / ドット --pb-accent │
│ ◐ レビュー中   │ 背景 --pb-hover / 文字 --pb-text / ドット中空       │
│ ✓ 完了        │ 背景なし / 枠線なし / 文字 --pb-text-muted          │
└──────────────┴─────────────────────────────────────────────┘
```

**進行中のものほど濃く、終わったものほど淡くなる。** 8.2 の彩度の規則をそのまま適用した結果であり、一覧を眺めたときに視線が自然と未処理へ向かう。完了タスクは情報として「退場」する。

### 優先度

**色を使わず記号のみで表す。** 文字色は常に `--pb-text-muted`。

| 優先度 | 表示 |
|---|---|
| 最高 | `▲▲` |
| 高 | `▲` |
| 中 | （無表示） |
| 低 | `▽` |
| 最低 | `▽▽` |

中を無表示にすることで、**一覧上で目に入るのは高いものと低いものだけ**になり、走査の負荷が下がる。優先度を赤で表示する設計を採らないのは、danger を「期限超過・破壊的操作」に限定して意味の希釈を防ぐためである。

### 例外

期限超過のみ `danger` を使う（`⚠ 8/11` を赤字）。これは優先度ではなく**事実として発生した問題**であるため。

## 8.8 長時間注視への配慮

| 項目 | 方針 |
|---|---|
| 純白・純黒の禁止 | ライトの地は L=0.990、ダークの地は L=0.170。純黒背景はハレーションを起こしやすく、ダークモードでこそ避ける |
| 本文コントラスト | 15.7:1 程度に収める。純黒文字（21:1）は過剰で、長時間では眩しさとして知覚される |
| 大面積の彩度制限 | 彩度の高い step 9/10 は**ボタン・選択インジケータなど小面積に限定**。ヘッダやサイドメニュー全体を accent で塗らない |
| danger の面積 | 画面あたり 5% 以内を目安。赤が広いと常時緊張を強いる |
| warning の面積 | 黄は面で使うため、**1画面に1〜2ブロックまで**。一覧の行に黄の帯を敷かない |
| ai の面積 | 点・線のみ。承認済みは色を外す（8.4.2） |
| 罫線 | テーブルは**横罫線のみ**（`--pb-line`）。縦罫線を引かない。枠で囲むより余白で区切る |
| 影 | `--pb-shadow-1` を基本とし、モーダル以外で `shadow-2` を使わない |
| アニメーション | 150ms 以下、`ease-out`。点滅・パルスは使わない |
| 自動更新 | ポーリングによる再描画で行がちらつかないよう、差分のみ更新する |

## 8.9 コントラストと色覚多様性

- 本文・ラベルは **4.5:1 以上**、大きい文字（18px以上）は 3:1 以上
- `--pb-text-muted`（step 11）は step 1〜3 の上でのみ使用する（5.0〜5.8:1）。step 4 以降の濃い背景には載せない
- **状態を色だけで示さない。** ステータスは色＋記号＋文字、期限超過は色＋`⚠`、AI由来は色＋バッジ文字を必ず併用する
- 有彩色3つ（赤 h25／黄 h92／紫 h300）は輝度が大きく異なる（0.555 / 0.865 / 0.555）ため、第1色覚・第2色覚でも輝度差で判別できる。加えて意味ごとに記号を付す
- `prefers-reduced-motion` でアニメーションを無効化、`prefers-contrast: more` で step 11 → 12、境界を step 7 → 8 に引き上げる

# 9. キーボード操作とアクセシビリティ

## 9.1 ショートカット（Phase 1）

| キー | 動作 |
|---|---|
| `[` | メインメニューの折りたたみ切替 |
| `Shift + [` | 集中モード切替（Phase 2） |
| `g` `p` | プロジェクト一覧へ |
| `g` `b` | バックログへ |
| `g` `d` | ダッシュボードへ |

| `j` / `k` | 一覧の行を上下移動、`Enter` で開く |

`g` を前置キーとする2ストローク方式は、`Requirements.md` 5章が想定する Vim/ターミナル文化のユーザー層に合わせたもの。`/`（検索）は Phase 2 で全文検索を実装した際に追加する。

**`g` `t`（チケット一覧へ）は `g` `b`（バックログへ）に変えた。** 4.1.1 でチケットの視点を並列にしたため、`t` が指す先が一意でなくなった。Phase 2 で足す視点も**画面名の頭文字**に揃える（カンバンは `g` `k`、ガントは `g` `g`）。

## 9.2 アクセシビリティ

- すべての操作要素がキーボードで到達可能。フォーカスリングを消さない
  - **例外：一覧の列幅を変えるつまみ（5.6）はドラッグのみで操作する**（利用者の判断、2026-08-18）。幅は表示上の都合であり、**列の内容は横スクロールで到達できる**ため、情報への到達は妨げられない。保存もしないので、読み直せば既定に戻る
- モーダルはフォーカストラップし、閉じたら元の要素へフォーカスを戻す
- **折りたたみ時のアイコンボタンに `aria-label` を必ず付与**（テキストが消えるため必須）
- ページヘッダの `<h1>` が唯一のページ見出しとなる（アプリヘッダ廃止により見出し階層が単純化した）
- **状態を色だけで示さない**。ステータスバッジは色＋文字、期限超過は色＋`⚠` を併用
- コントラスト比 4.5:1 以上
