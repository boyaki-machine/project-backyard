チケット #$1 を根とする委任で、あなたは **main** である。設計の正本は `docs/design/Delegation.md`。

## 0. この手順は運用で回す版である

**PB はまだ自律実行の段階を強制していない**（器の実装は pb-246〜pb-250）。計画の承認前に起票しても、評価の合格前に成果を出しても、
PB は拒まない。**`Delegation.md` 5章の表を、あなた自身が守ること。** 器の代わりに、次の置き換え先を使う。

| 器（未実装） | 運用での置き換え先 |
|---|---|
| 計画の版（`pb_submit_plan`） | 根に `pb_post_note`（`kind=decision`）。見出しは `## 計画 v<版>：<段階>` |
| 評価（`pb_submit_evaluation`） | 評価エージェントが根に書く（`/pb-delegate-eval`）。見出しは `## 評価 <対象> 第<回>回：<合格／不合格／判断不能>` |
| 確認待ち・ヒアリング（`pb_raise_confirmation`） | 根に `pb_post_note`（`kind=discussion`）。見出しは `## 確認待ち：<条件>` または `## ヒアリング <回>`。**会話でも利用者に同じ問いを出す** |
| 回答 | 利用者が会話で答えたら、あなたが同じコメントの続きとして `## 回答` を根に書き写す |
| 引き継ぎノート（`pb_update_handoff`） | 根に `pb_post_note`（`kind=progress`）。見出しは `## 引き継ぎノート v<版>` |
| 呼び出し（通知・`pb_wait`） | **人が伝える。** 評価を頼むときは、利用者に「評価エージェントに `/pb-delegate-eval $1` を走らせてください」と頼んで止まる |

**規約は PB の「規約」に従う。** 本手順は自律実行の進め方だけを書く。

## 1. 前提の取得と、いまの段階の判定

1. `pb_get_context(seq=$1)` で憲章を読む。**価値観・世界観（`vision`）は全文を読む**——タスクとゴールを定める判断基準である
2. `pb_get_task(seq=$1)` で根の目的と完了条件を読む
3. 根のコメントから、上の見出しの最新のものを拾い、段階を決める

| 根のコメントの状態 | 段階 | 次の一手 |
|---|---|---|
| 計画もヒアリングも無い | 計画中 | 2.1 ヒアリング |
| ヒアリングに回答がある・計画がまだ無い | 計画中 | 2.1 の続き（次の問い）か 2.2 計画の提出 |
| 最新の計画に評価が無い | 評価待ち | 3. 待つ |
| 最新の計画の評価が不合格 | 差し戻し | 5. 直して出し直す |
| 最新の計画が合格し、利用者が委任範囲を承認した（`## 承認` のコメント） | 承認済 | 4. 進める |
| 開いている確認待ち（`## 回答` が無い）がある | 確認待ち | 6. 待つ |
| 根の成果を出し、評価が無い | 評価待ち | 3. 待つ |

**判断がつかなければ、引き継ぎノートの最新版の「次の一手」に従う。** それも無ければ利用者に尋ねる。

## 2. 計画中

### 2.1 ヒアリング

**自律実行を指定されるチケットは、PM 自身が内容とゴールを十分に掘り下げられていないことが多い。** 書かれた目的をそのまま受け取らない。

- **1回の質問で終わらせない。** 目的の先にあるもの・成功の姿・制約・優先・避けたいこと・使える資源など、多面的な問いを**何回かに分けて**重ねる
- 答えを受けて次の問いを深める。1回の問いは3つ程度までにし、選択肢と推奨があれば添える
- 問いと答えは根に残す（0章の置き換え先）。**セッションが替わっても計画の根拠になる**
- 掘り下げが足りたと判断したら、そう述べて 2.2 へ進む

### 2.2 委任範囲の案と計画の提出

1. **委任範囲の案**を書く（`Delegation.md` 4.2 の項目）：目的・成功の測り方（指標と、誰が値を入れるか）・自律してよい範囲・予算（コスト・期間・期間あたり・起票数・木の深さ・往復の上限）・止まる条件（**事象で書く**）・報告の周期とチェックポイント
2. **計画**を書く：骨格（根の直下の枝・枝ごとの予算配分・チェックポイント）と、その下の作業の木の案
3. **計画の説明に、どの価値観にどう沿わせたかを書く**
4. `## 計画 v1：初版` として根に書き、評価を頼んで止まる（0章）

**計画が承認されるまで、根の下に起票しない。完了レポートも出さない。**

## 3. 評価待ち

評価を待つ。待つあいだ、成果と関係しない子の作業は進めてよい（承認済のときだけ）。**評価が出たと利用者から伝えられたら、1 からやり直す。**

## 4. 承認済

- **全体の管理に専念する。** 個々の作業は、使えるならサブエージェントに渡す。サブエージェントには、子のチケットの番号を渡して `/pb-implement` 相当で進めさせる
- 委任範囲の内側で、根の下に起票し、木を組み、順序を調整してよい
- **起票は必ず根の子孫として行う。** `pb_create_ticket` の `parent_seq` を省かず、根か木の中のチケットを渡す。骨格の枝も根の直下の子として作る。**木の外への起票は、PB がまだ拒まないが、しない**
- **起票数・木の深さ・期間を、自分で数える**（PB はまだ止めない）。上限に近づいたら確認待ちを立てる
- 計画を変えるときは段階を決める（`Delegation.md` 6.3）

| 段階 | 例 | すること |
|---|---|---|
| 軽微 | 順序の入れ替え、骨格の枝の下への小さな追加 | そのまま反映し、引き継ぎノートに書く |
| 構造 | 骨格の枝の追加・中止、予算配分を総予算の20%を超えて動かす、1回に5件を超えて起票する、木を深くする | `## 計画 v<n>：構造` を書いて評価を頼む。**合格するまで反映しない** |
| 範囲 | 目的・指標・総予算・自律してよい範囲・main と評価の交代 | `## 計画 v<n>：範囲` を書き、評価の後に**利用者の承認を待つ** |

**迷ったら厳しい方の段階にする。**

- 子の成果は、子のチケットに完了レポート（`pb_submit_result`）で報告する。**`findings` に実行者の内訳**（あなた自身か、どのサブエージェントか、人か）**を1行書く**
- 子は review に相当する状態まで進める。**完了にするのは利用者である**（チェックポイントでまとめて行う）
- 根の目的を果たしたら、根に完了レポートを出し、評価を頼んで止まる。**評価が合格するまで、根は完了しない**

## 5. 差し戻し

評価の指摘を1件ずつ読み、**直したか、直さない理由**を書いて出し直す。同じ対象への不合格が委任範囲の往復の上限（定めが無ければ3回）に達したら、
直さずに確認待ちを立てて止まる。

## 6. 確認待ち

**次のどれかに当たったら、確認待ちを立てて止まる。**

1. 委任範囲の外への変更
2. 後戻りできない操作と外部への作用（マージ・push・デプロイ・外部への送信・削除）
3. 憲章の変更
4. プロジェクトが定める機微な領域への接触
5. 往復・コスト・期間・起票数・深さの上限の超過、止まる条件への到達
6. 評価が判断できない（`判断不能`）と返したとき

問いには選択肢と推奨を付ける。**回答が来るまで、木への書き込み（起票・編集・遷移・完了レポート）をしない。** ノートと引き継ぎノートは書いてよい。

## 7. 引き継ぎノート

**次の区切りで更新する**：計画の版を出したとき、評価を受け取ったとき、完了レポートを出したとき、確認待ちを立てる前、**セッションを終える前**。

```
## 引き継ぎノート v<版>
- 目的と現在の計画の版：
- 決めたこと：
- 未決事項（誰の判断待ちか）：
- 進行中の作業（チケット番号と、main・sub・人のどれが持っているか）：
- 次の一手（1つ）：
- 予算の消費（総予算に対して、周期あたり）：
- 直近の評価（合否と、未解決の指摘）：
```

## 8. 試行の記録

運用で回しているあいだは、通し試験（pb-256）の材料として次を引き継ぎノートとは別に数えておく：**利用者が介入した箇所、往復の回数、
コスト、ずれ**（意図と成果の食い違い）、**PB が強制していないために自分で守った箇所**。
