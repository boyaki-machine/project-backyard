$1 の実装が設計文書に一致しているかを検証する。**修正は行わず、報告のみ行う。**

## 手順

1. 対象範囲を特定する（手順番号なら `docs/design/Design.md` 11章、領域名なら `docs/README.md`「領域と正本の対応」）
2. 該当する設計文書の章を読む
3. 実装コードを読み、以下の観点で突き合わせる

| 観点 | 確認内容 |
|---|---|
| スキーマ | マイグレーションのDDLが `docs/design/DbDesign.md` 6〜7章と一致するか（列名・型・制約・インデックス） |
| API | パス・メソッド・リクエスト/レスポンスのフィールド名が `docs/design/ApiDesign.md` と一致するか |
| 権限 | 全エンドポイントに必要権限が宣言されているか。`docs/design/ApiDesign.md` の「必要権限」と一致するか |
| 不変条件 | 自己変更の禁止、最後の管理者の保護（`docs/design/ApiDesign.md` 6.4）が実装されているか |
| 秘密 | 平文のトークン・パスワードが保存・ログ出力されていないか |
| エラー | `docs/design/ApiDesign.md` 2.5 の形式とステータスコードに従っているか |
| 命名 | snake_case、ULID、`_json` 接尾辞なし（`CLAUDE.md` の規約） |
| 画面 | ルート・必要権限・セクション構成・部品の使い分けが `docs/design/GuiDesign.md` と一致するか。**数・条件・既定値が書いてある規則は、その数のまま実装されているか**（列数・上限・閾値） |
| 実装規約 | クラス名の衝突（`GuiDesign.md` 6.6）、レイアウトの落とし穴（同 6.7）、日時と日付の出し方（同 7.5）に反していないか |

4. 差異を一覧で報告する。各差異について**どちらが正しいかの判断を添える**
   - 実装が誤っている → 修正案を提示（実行はしない）
   - 設計文書が古い・誤っている → 設計文書の修正案を提示

## 禁止事項
- この場で修正を実行してはならない。報告と提案までとする
- 「おそらく問題ない」で済ませず、実際にコードと文書を読んで確認すること
