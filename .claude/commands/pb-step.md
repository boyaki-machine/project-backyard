Phase 1 の手順 **$1** を実装する。以下を順守すること。

## 1. 前提の確認
- **`LEARNINGS.md` を読む**（過去のセッションから得た進め方の教訓。短い）。
  **これは追跡対象外のローカル文書**なので、無ければ見出しと空の表だけ作って始める
- `docs/PROGRESS.md`（現況のみ・短い）を読み、手順 $1 より前が完了しているか確認する
- **「次の手順への引き継ぎ」に手順 $1 の行が無いか必ず見る。** あれば計画に含める
- **`docs/history/` は読まない。** 過去の判断の詳細が要るときだけ grep して該当箇所を引く
- 未完了の前提があれば、実装せずユーザーに報告する
- `git status` で作業ツリーが綺麗であることを確認する。未コミットの変更があれば報告し、指示を仰ぐ

## 2. 仕様の取得
- `docs/Design.md` 11章から手順 $1 の内容を確認する
- 手順 $1 に関係する設計文書の**該当章のみ**を読む。全文を読まない
  - DB・マイグレーション → `docs/DbDesign.md` の該当章
  - API → `docs/ApiDesign.md` の該当章
  - 画面 → `docs/GuiDesign.md` の該当章
  - 認証・認可 → `docs/Design.md` 6章

## 3. 計画の提示
- 変更・作成するファイルの一覧、実装方針、検証方法を提示する
- **作成する feature ブランチ名も計画に含める**（`feature/step-<2桁>-<スラッグ>`）
- **ユーザーの承認を得るまで実装を開始しない**
- **仕様を読む段階で「設計文書に書かれていないこと」を数え上げ、実装前に一括で確認する。**
  実装しながら見つけて都度止まると、そのたびに往復が要る。選択肢・推奨・**そう考えた理由**を
  添えて、まとめて1回で出す。**回答の重さで層に分ける**と1回で着地する——
  A（回答が要る）／B（確認だけ）／C（次セッションで決める）／D（文書改訂）／E（新たに生じた実装判断）。
  12a・13b・14・15a・15b・16a の6回で**実装中の設計相談はいずれもゼロ**だった。
  **推奨がそのまま通る前提で組まない**——12b は11件中5件で利用者の判断が推奨と違った。
  「設計文書どおり」を推す前に、**利用者が将来どう使うか**を1行添える
- **問いを出す前に「これは何を表すものか」を1行で書く。** 書けないなら、まだ理解していない。
  選択肢を3つ並べても、**前提が外れていれば3つとも外れる**——17c の「コードの行に
  書き手のアイコンを出すか」は、設計文書が「書き手を示す」と書いていることから出発し、
  3案（seed に agent アクターを作る／人のアクターで入れる／両方）を並べたが、
  利用者の答えは**「アイコン自体が要らない」**だった。**この欄が表すのは
  「チケットの成果物としてリポジトリ・コミットが紐づいている関係」であって、
  登録者ではない**——それを1行書いていれば、問い自体が立たなかった。
  **利用者は欄の意味から考えて答える**（「コミットの committer を表しているなら出してよい」）ので、
  こちらも同じ土俵に立ってから問う。**同じことが 12b・15a でも起きている**（3回目）
- **章を実装する前に、その章が「応答の形」を持っているかを数える。**
  `ApiDesign.md` は節ごとに粒度が違い、**JSON 例のある節と、本体の検証しか
  書いていない節が混在する**（18a では 9.10.1 と 9.10.2 が例を持ち、9.8 と 9.9 が
  持たなかった）。**例の有無は、実装が判断を強いられるかどうかの指標**である——
  無い節は一括確認で「文書に無いもの」として数え上げ、**先に応答例を書いてしまう**。
  18a・18b はこれで**実装中の設計相談がゼロ**だった
- **文書に在るものを作る前に、「誰が何のために使うか」を1行で書く。**
  文書間の整合を取っただけで、**その機能が要るかを一度も問わない**ことが起きる——
  15a は `ApiDesign.md` 8章の対応表に `GET|DELETE /me/sessions` があるので
  「5.8 にセッション一覧を足す」改訂を提案したが、利用者の判断は
  **「その機能自体が不要」**（セッション管理は管理者の作業）で、APIごと削除になった。
  **在ることは、要ることの根拠にならない**
- **手順の分量が大きいと判断した場合は、分割案（例：4a / 4b）を提示する。**
  1回のセッションで扱う量が多いほど、後半の実装品質が落ちるため。
  **分けるなら a の完了時に検証・記録・コミットまで行って止まる。そこまでやらないなら分けない**
  （`Design.md` 11.2.1）。「a で作りかけ、b で仕上げる」は、a の時点で何が動くのかが
  分からなくなる。分けること自体に手間がかかるので、**既定は「分けない」**

## 5. 実装
- **文書を直す手順では、コードより先に文書を当てて終わらせる。** 手順3の一括確認で
  決めたことを、**そのまま設計文書へ書き写す工程**にしてからコードへ入る。
  「あとで直す」にすると、実装中に「文書はどう書いたか」を思い出す作業が挟まる。
  **この型は8回続けて効いている**（16c・17c・18a・18b では実装中の設計相談がゼロだった）
- 設計文書の記述を**そのまま反映**する。独自の設計判断を加えない
- **ただし「そのまま反映」は「機械的に写す」ではない。写す前に、その規則が
  この画面・このAPIで何を起こすかを1行で言う。** 言えないなら、まだ理解していない——
  14 では 5.6 の「超えたら横スクロール」を写しただけで、**`✓` が何の権限か読めなくなる**
  ことを考えていなかった。17c では 5.5 が「2列のグリッド」と**数を書いている**のに
  `auto-fit` で可変にし、750px のペインで3列になって意味の組が割れた。
  **数・条件・既定値が書いてある規則は、その数のまま写す**
- 手順 $1 のスコープ外のファイルを変更しない。必要が生じたらユーザーに相談する
- DDL は `docs/DbDesign.md` 6〜7章の記述を変更せずに転記する
- 秘密（パスワード・トークン・接続文字列）をコードに書かない
- **APIを追加・変更した場合は `docs/openapi.yaml` も同じブランチで更新する。**
  このファイルは設計の写しではなく**実装済みAPIの現状**である（`docs/ApiDesign.md` 1.3）。
  実装したエンドポイントだけを、実装したとおりに記述する
- **自分が書いたものを、自分で破らない。** 手順書（`docs/Development.md`）のとおりに実行し、
  自分がコメントや設計文書に書いた注意を別の層でも守る。**同じ根の失敗が4回起きている**——
  `make` をリポジトリ直下以外から実行して無音で失敗／古いサーバを止めずに `make run` して
  `bind: address already in use` に気づかない／**サーバ側に「`date` を `timestamptz` として
  扱うと前日へずれる」と書いた直後に、クライアントで `date` 列を `new Date()` へ通す**。
  **曖昧さが残るなら手順ではなく `make` のターゲットにして機械に守らせる**
  （`make stop-server` / `make restart` / `make test-db` はそうして生まれた）
- **コマンドは cwd に依存しない形で書く。** `cd` した状態は次の Bash 呼び出しへ持ち越され、
  そこから先の相対パスが静かにずれる。**同じ失敗が6回起きており、「気をつける」では止まらない**
  ——うち3回は1セッション中の再発で、2回目以降は「次から絶対パスで書く」と決めた直後である。
  **規約にした後も3回再発した**（17b・18b。18b では `cd client && npx vite build` の数手あと、
  無関係に見える `python3` のヒアドキュメント内の相対パスが `FileNotFoundError` になった）。
  **壊れるのは次の1コマンドではなく、そのセッションの残り全部である。**
  **守るのは意志ではなく書き方の既定にすること**——`-C` や `--prefix` を持たない道具に
  出会ったときこそ、**代替の形を先に調べる**（下表）

  | 書くもの | 既定 |
  |---|---|
  | `make` | `make -C <リポジトリ直下>` |
  | `go` | `go -C <モジュール>` |
  | `npm` / `npx` | `npm --prefix <ディレクトリ> run <script>`（`npx` には `-C` が無い。**ここで手が `cd` を打つ**） |
  | ファイルパス | リポジトリ直下からの絶対パス |
  | `-f` / `--file` の引数 | 同上（`docker compose -f` は cwd に付いてくる） |
  | 検証スクリプトが作るファイル | スクラッチパッドの絶対パス（Cookie jar をリポジトリ直下へ落とした前例がある） |

  **`cd A && B` の形を最初から書かない。** 1コマンドで済ませたいときも、`cd` ではなく
  `-C` かフルパスで書く

## 6. 検証
- 実行するコマンドと期待される結果を示し、実際に実行して確認する
- ビルド・テストが通ること、および手順ごとの確認項目を満たすことを確認する
- **「要素が存在するか」ではなく「見えて操作できるか」を確かめる。** 画面は実際に遷移して見る。
  位置とサイズを実測する（`getBoundingClientRect()`）。**手順書を書いたら自分で上から実行する。**
  自動検証が全 PASS でも、入力欄が画面外という崩れは拾えない（手順11b で実際に起きた）
- **画面を作ったら、スクリーンショットを必ず自分で見る。** 実測は「入るか」しか答えない。
  **「変に見えないか」「全部見えているか」「並びが仕様どおりか」は別の確認**であり、
  座標を測っても出てこない。**複数の幅で撮る**（1440px と狭い窓）。
  手順12b・15a・15b で、自動検証が全 PASS のまま崩れていたことが**5回**ある
  （余白の偏り／ラジオの縦積み／狭い窓で列幅0／日本語の折り返しに空白／
  横スクロールの箱に収まって末尾が見えない）
- **検証側のセレクタは「何に当たるか」を数えてから使う。** 部分一致でボタンやテキストを
  選ばず、`button[form=…]` のように役割で名指しする。`:nth-of-type` は「同じタグの中での
  順番」なので、兄弟のタグが揃っていない箇所では `:nth-child` を使う。
  **落ちた件数が多いときほど、まず1つ目の原因を見る**——連鎖しているだけのことがある
  （手順15b で、`+ 発行` に当たったクリック1つが7件の FAIL を生んだ）。
  **当たる先が多いのは検証側だけの問題ではない**——`scoped` スタイルは見た目を分けても
  DOM のクラス名は分けないので、**実装側の名前も具体的にする**。その規約は
  `docs/GuiDesign.md` 6.6 にある（部品名を冠する／画面名を冠する）
- **層を1つ増やすたびに、前の層が返せない値が現れる。** フェイクは書いた人の想定しか
  返さず、結合テストは書いた人が作ったデータしか含まない。**実サーバ検証・ブラウザ検証は
  「通し確認」ではなく別の層のバグ取りである**——12b で2件（401 をすべて失効として扱う／
  成功メッセージが自分の後片付けで消える）、16b では **API だけの手順でも**1件拾った
  （優先度が未設定のチケットで一覧が 500。単体も結合も「優先度を持つチケット」しか
  作っていなかった）。**拾ったら、その値を下の層の検証にも足す**
- **検証が落ちたら、実装側と検証側をフラットに疑う。** 「まず検証側を疑う」を規約にすると
  **通すための検証**になりかねない。切り分けは順番ではなく方法で行う——
  **何を測っているかを設計文書の例と突き合わせて確かめ**、つかなければ両方に当たる最小の再現を作る
- **状態を変える検証は、途中で落ちても続きから再開できる形にしてから走らせる。**
  現在値は毎回読み直す（前の手順の結果を前提に固定値を埋めない）。本文と
  ステータスのように、別々に扱うものを同じ出力へ混ぜない。
  **使い捨てのスクリプトでも、最初の1回を小さく通してから全体を回す。**
  一発勝負にすると、スクリプト側の不備で副作用だけが残り、やり直しが効かなくなる
- **シェルで変数の直後に日本語が続くときは必ず `${VAR}`。** 検証スクリプトも同じ規則で書く
  （`"$BEFORE（…"` は変数名を切り損ねる。手順11b・12a で2回起きた）

## 7. 成果物の振り返り

**コミットの前に、このセッションの成果物を振り返る。** 目的は感想ではなく、
**次のセッションが同じことを調べ直さずに済む状態を作る**ことにある。

以下を**上から順に、1件ずつ**見る。該当が無い項目は「該当なし」と述べる（黙って飛ばさない）。

| 見るもの | すること |
|---|---|
| 今回**消化した**引き継ぎ | `docs/PROGRESS.md`「次の手順への引き継ぎ」から該当行を**消す**。結果は `history/decisions.md` へ |
| 今回**生まれた**約束 | 先送りしたこと・「次で扱う」と言ったこと・**再利用を前提に作った部品**を、同表に1行で足す |
| 設計文書との食い違い | `history/decisions.md` に追記する。**修正提案をまだ出していなければ、ここで出す**（コードだけ直して終わらせない） |
| 迷った点・却下した案 | 同上。「なぜ採らなかったか」は次に同じ議論を繰り返さないために残す |
| 作ったファイル・検証結果の全文 | `history/steps.md` の末尾へ |
| 新しく分かった環境の制約 | `docs/PROGRESS.md` の「環境メモ」へ。**再現できる手順になるものは `docs/Development.md`** へ |
| 手順の範囲外で気づいた問題 | `docs/PROGRESS.md`「手順外の作業」に**起票する。この場で実装しない** |
| 検証で作った資源 | サーバ・コンテナ・DBに入れたデータ・スクラッチパッドを**片付け、片付けたことを報告する**。作り直しが効くものは畳むのが既定。**意図して残すなら、何をなぜ残したかを伝える**（黙って残さない） |
| 作業ツリー | `make clean-webui`（`make build` した場合）と `git status` で汚れが無いことを確認する |
| `docs/PROGRESS.md` の分量 | **80KB を超えていたら掃除する**（下記） |
| 次のセッションの入口 | 次の手順に着手する人が **`docs/PROGRESS.md` だけで前提を把握できるか**、書いた内容を読み返す |

- 最後に**5〜10行の要約を画面に出す**。何をどこへ書いたか、片付けた資源、次のセッションへの申し送り
- **書かないと判断したものも1行で述べる**（判断を隠さない）

### `docs/PROGRESS.md` が閾値を超えたら

**閾値は 80KB。行数は数えない**——毎セッション読む負担の目安はバイト数で足りる
（`LEARNINGS.md` が 2026-08-18 に同じ理由で行数をやめた前例に揃えた。日本語は1文字3バイトで、
行の長さがそろわない表形式では行数が量を表さない）。

**閾値は上限ではなく掃除の合図である**（2026-08-18 に182KB まで肥大化させた再発防止）。
超えたら次の順に行う。**いきなりファイルを分割しない。**

1. **完了して今後の手順に不要な情報を `docs/history/` へ移す。** 「手順外の作業」の完了行、
   マージ済みのビルド番号一覧など。**日付と結果が確定していて、もう変わらないもの**が対象
2. **重複を削る。** 機械が答えられる事実を手で写していないか見る
   （ビルド番号は `make version` が正本、`git rev-list` の実測である）
3. 1と2で収まらないときに、初めて分割を検討する

**進行管理に必要な情報は、量が多くても残す。** 「次の手順への引き継ぎ」は本文書の主目的であり、
Phase 2 以降に効く行も含めてここに置く。**別ファイルへ切り出すと、着手時に開かれる保証が無くなる**
（`docs/history/` は「過去の判断を調べるときだけ grep する」文書であり、未消化の約束の置き場ではない）。
**分割は読む量を減らすように見えて、どちらを読むかの判断と導線の維持を増やす。**

**閾値を 40KB から 80KB へ上げた**（2026-08-23、利用者の判断）。40KB は約13,500トークンで、
毎セッション読む4文書（`CLAUDE.md` / `LEARNINGS.md` / `PROGRESS.md` / 本ファイル）の合計が
約32,600トークン——コンテキスト窓の16%にあたる。80KB にしても合計は約20%で、**設計文書を1つ
全文読む（`GuiDesign.md` で約55,700トークン）ほうが3〜4倍重い**。読み込みはプロンプトキャッシュにも
載るため、トークン上の実害は小さいと実測した。**これは当面の対処であり、Phase 1 の完了時に
「効果と書くべき内容のバランス」を取り直す**（同じく利用者の判断。`docs/PROGRESS.md` の
「次の手順への引き継ぎ」に起票してある）。

## 8. 進め方の振り返り

**手順7が成果物を扱うのに対し、ここでは「利用者と自分のやり取り」そのものを扱う。**
次のセッションの体験と成果を上げることが目的で、改善対象はコードや文書ではなく**進め方**である。

見るのは**このセッションの会話そのもの**。以下を1件ずつ見て、該当が無ければ「該当なし」と述べる。

| 見るもの | 具体 |
|---|---|
| 手戻り | 完成させた後に直させた箇所。**なぜ最初からそうしなかったか**まで書く |
| 往復の多かった論点 | 3往復以上した話題。前提が欠けていたのか、説明の順序が悪かったのか |
| 利用者が自分で見つけた問題 | 文書をなぞって・画面を触って指摘されたもの。**私が先に気づくべきだった** |
| 私の空振り | やり直した作業・失敗した検証・無駄にした時間 |
| 指示の解釈 | 意図と違うことをした箇所。**確認すべきだったのに進めた／進めてよいのに止まった** |
| 利用者に手を動かさせた場面 | 自分でファイルを消した・コミットした・ビルドした等 |
| うまくいった型 | 再現したいやり方も残す。**悪かったことだけを書かない** |

- 気づきは **`LEARNINGS.md` の表に1行**で追記する（`観測1`）
- **同じことが2回目なら `昇格候補` に変え、`CLAUDE.md` か本ファイルの規約にする提案を出す**（2回ルール）
- **昇格した項目は `LEARNINGS.md` から消す。** 規約側の文書に書かれている前提でよく、二重に持たない
  （どこへ何を移したかは `docs/history/decisions.md` に残る）
- `LEARNINGS.md` が **40KB** を超えたら、次の順に検討する。**行数は数えない**——
  毎セッション読む負担の目安はバイト数で足りる（2026-08-18 に「80行 / 8KB」から変更。
  日本語は1文字3バイトで、8KB は約15行にしかならず、80行と5倍ずれていた）
  1. **まず内容を整理する。** 退役候補を挙げ、重複を削り、昇格できるものを規約へ移す
  2. それでも超えるなら、**基準そのものを変えるか、優先度に従って情報を削るかを検討する**
- 画面には3〜5行で要約する

## 9. 記録とコミット

**記録は3つに書き分ける。** `docs/PROGRESS.md` に全部書くと肥大化し、毎セッションの
読み込み量が増える（2026-08-18 に分割した理由）。

| 書くこと | 書き先 |
|---|---|
| 状態・完了日・検証の要約（**1行**） | `docs/PROGRESS.md` の Phase 1 表 |
| 次の手順以降に持ち越す約束 | `docs/PROGRESS.md` の「次の手順への引き継ぎ」 |
| 判断の経緯・設計文書との食い違いとその対応 | `docs/history/decisions.md` の表の末尾 |
| 作ったファイルの一覧・検証結果の全文 | `docs/history/steps.md` の末尾 |
| いま効いている環境の制約 | `docs/PROGRESS.md` の「環境メモ」 |

- 設計文書との差異が生じた場合、**コードではなく設計文書を直す提案**を出す
- **上記の更新を同じブランチに含めて**コミットする

```
git add -A
git commit -m "step $1: <要約>"
```

- `git log --oneline` と `git status` を示し、コミット内容を報告する

## 10. マージの提案
以下を**提案するだけ**とし、実行はユーザーの承認後に行う。

```
git switch develop
git merge --no-ff feature/step-<2桁>-<スラッグ>
```

## 禁止事項
- 承認前に実装を始めてはならない
- **`develop` に直接コミットしてはならない**
- **マージ・push・ブランチ削除を独断で実行してはならない**
- 設計文書に書かれていない仕様を発明してはならない。不明なら質問する
- 手順 $1 のスコープを超える変更を独断で行ってはならない
- `docs/PROGRESS.md` の更新を省略してはならない
- **振り返り（手順7・手順8）を省略してはならない。** 「特に無い」で済ませず、表の項目を1件ずつ見る
- **一度きりの事象で規約を増やしてはならない。** 2回目に起きてから昇格させる（`LEARNINGS.md`）
