`docs/design/Design.md` 11章の手順 **$1** を実装する。以下を順守すること。

## 1. 前提の確認
- **PB の「規約」を読む**（`pb_list_docs` → `pb_get_doc`）。**規約の正本は PB にある**
  （`CLAUDE.md`「規約の正本は PB にある」）。**MCP に繋がらないなら、そこで止めて利用者に伝える**
- **`LEARNINGS.md` を読む**（進め方の教訓。短い）。**追跡対象外のローカル文書**なので、
  無ければ見出しと空の表だけ作って始める
- `Design.md` 11章で、手順 $1 より前が完了しているか確認する
- **手順 $1 に関わる引き継ぎを、stg の PB のチケットから引く**（`pb_list_tasks` で未完了を取り、題名と本文で探す）。当たったチケットは計画に含める
- 未完了の前提があれば、実装せずユーザーに報告する
- `git status` で作業ツリーが綺麗であることを確認する

## 2. 仕様の取得
- `docs/design/Design.md` 11章から手順 $1 の内容を確認する
- 関係する設計文書の**該当章のみ**を読む。全文を読まない
  （DB→`DbDesign.md` / API→`ApiDesign.md` / 画面→`GuiDesign.md` / 認証認可→`Design.md` 6章）
- **後から入った概念は、それより前に書かれた章を全部疑う。** 読む章が「いつ書かれたか」を見て、
  後から入った軸と総当たりで突き合わせる。**1つの大きな変更は、同じ場所を2回以上壊す**

## 3. 計画の提示

**ユーザーの承認を得るまで実装を開始しない。** 変更・作成するファイルの一覧、実装方針、
検証方法、feature ブランチ名（`feature/step-<2桁>-<スラッグ>`）を提示する。

**計画の冒頭に「この手順で何を作るのか」を置く。** ファイル一覧より先に、
**①一言でいうと何か ②なぜ要るのか ③誰が・いつ・どう触るか**（人とエージェントの行動を時系列で）
を書く。**あわせて、その手順のキーとなる用語を3〜6語ひろって1行ずつ説明する。**
成果物の設計は、それが何のためのものかが共有されていないと評価できない。

**設計文書に書かれていないことを数え上げ、実装前に一括で確認する。**
実装しながら都度止まると、そのたびに往復が要る。選択肢・推奨・**そう考えた理由**を添えて
1回で出す。**回答の重さで層に分ける**——A（回答が要る）／B（確認だけ）／C（次セッションで決める）
／D（文書改訂）／E（新たに生じた実装判断）。

**章を実装する前に、その章が「応答の形」を持っているかを数える。** `ApiDesign.md` は節ごとに
粒度が違い、JSON 例のある節と本体の検証しか書いていない節が混在する。**例の有無は、実装が判断を
強いられるかどうかの指標**である——無い節は「文書に無いもの」として数え上げ、**先に応答例を書く**。

**一括確認は「実装前に見えるもの」しか捕まえられない、と織り込んで組む。**
単体はフェイクを相手にするので、層をまたいで初めて出る相談は残る。
**「相談が1件出る前提」で残り時間を見る**。

問いを立てるときの規則：

- **「これは何を表すものか」を1行で書いてから問う。** 書けないなら、まだ理解していない。
  **前提が外れていれば選択肢は3つとも外れる**
- **文書に在る区分を、そのまま問いの枠にしない。** 上の1行を書くとき、**文書の見出しを写すと
  枠ごと借りてしまう**。**枠が狭ければ選択肢は3つとも狭い。** **自分の言葉で1行書き直してから問う**
- **「この問いは選択式に落ちるか」を見る。** 落ちるのは**軸が決まっていて範囲だけを選ぶ**問い。
  **軸そのものが未定なら選択肢は思考の幅を狭める**（推奨と理由だけ述べて開いた問いにする）。
  落ちるなら**3案が共有している前提を1行書いてから**聞く
- **選択肢を渡された側でも「並べていない4つ目」を1回探す。**
  3案が排他とは限らない——役割で分けられないかを試すと、両立することがある
- **回答が2通りに読めたら、割れ方の重さで確認するかを決める。**
  軽い側（表現の違い）は推奨で進め、**スキーマ・API の作り直しに化ける読みだけ**を二択で出す。
  判定は「外したときに何を捨てることになるか」
- **構造を変える回答をもらったら、実装前に絵で返す。** 文章では「ペインが何枚か」は合意できても
  「その枚がどこから生えているか」は一致しない。**絵は省略した前提を強制的に描かせる**

推奨を出すときの規則：

- **「変えない」「作らない」「文書どおり」を推すときこそ、根拠を声に出して点検する。**
  この3つは無コストに見えて、**間違ったまま画面が増える**ぶん後で高くつく。根拠が
  「やり直しが要る」「文書に在る」だけなら根拠ではない——**利用者が何を得ようとしているかを
  1行書く**まで推奨を出さない。**「文書に在る」を無言の前提にして問いから外すのも同じ失敗**である
- **成果物は名前でなく「受け渡しの形」で書いてから作る。** 「誰が・いつ・どこで・どうやって
  これに触るか」を1行。**時系列に並べると落ちが見える**
- **文書に在るものを作る前に「誰が何のために使うか」を1行書く。** 在ることは、要ることの根拠にならない
- **規則・番号・画面名・パスを変えるときは、まず全文検索して写しを数え、結果を計画に書く。**
  スコープ外に写しが残るなら、**意図的に残したことを引き継ぎへ書く**。
- **分量が大きいと判断したら分割案（例：4a / 4b）を出す。** 分けるなら a の完了時に
  検証・記録・コミットまで行って止まる（`Design.md` 11.2.1）。**既定は「分けない」**

## 4. ブランチの作成

```
git switch develop && git switch -c feature/step-<2桁>-<スラッグ>
```

## 5. 実装
- **文書を直す手順では、コードより先に文書を当てて終わらせる。** 手順3の一括確認で決めたことを
  設計文書へ書き写す工程にしてからコードへ入る
- 設計文書の記述を**そのまま反映**する。独自の設計判断を加えない
- **ただし「そのまま反映」は「機械的に写す」ではない。** 写す前に、その規則がこの画面・この API で
  何を起こすかを1行で言う。**数・条件・既定値が書いてある規則は、その数のまま写す**
- 手順 $1 のスコープ外のファイルを変更しない。必要が生じたらユーザーに相談する
- DDL は `docs/design/DbDesign.md` 6〜7章の記述を変更せずに転記する。秘密をコードに書かない
- **APIを追加・変更したら `docs/design/openapi.yaml` も同じブランチで更新する**（実装したとおりに）
- **新しい名前を書く前に、全部並べて一度に数える**（`grep -c` 1回）。`_test.go` はパッケージ内で
  1つの名前空間を共有するので、**ファイルを分けても衝突する**。「無ければ作る」ではなく
  **「あるか探してから作る」**。**逆向き（存在しない名前を使う）も同じコマンドで出る**
- **自分が書いたものを、自分で破らない。** 手順書のとおりに実行し、コメントや設計文書に書いた
  注意を別の層でも守る。**曖昧さが残るなら手順ではなく `make` のターゲットにして機械に守らせる**
- **コマンドは cwd に依存しない形で書く。** `cd` した状態は次の Bash 呼び出しへ持ち越され、
  そこから先の相対パスが静かにずれる。**壊れるのは次の1コマンドではなく、そのセッションの残り全部である**

  | 書くもの | 既定 |
  |---|---|
  | `make` / `go` | `make -C <直下>` / `go -C <モジュール>` |
  | `npm` / `npx` | `npm --prefix <ディレクトリ>`（`npx` には `-C` が無い。**ここで手が `cd` を打つ**） |
  | `grep` / `ls` / `find` 等 | **リポジトリ直下からの絶対パスを引数に書く。** `-C` の有無と関係なく `cd` しない |
  | ファイルパス・`-f` の引数 | リポジトリ直下からの絶対パス |
  | 検証スクリプトが作るファイル | スクラッチパッドの絶対パス |

  **`cd A && B` の形を最初から書かない。** 道具の都合ではなく手癖で出る。**打ちたくなったら引数を絶対パスにする。**

**コミットの前に、次のセッションが同じことを調べ直さずに済む状態を作る。**
以下を**上から順に、1件ずつ**見る。該当が無い項目は「該当なし」と述べる（黙って飛ばさない）。

| 見るもの | すること |

| 設計文書との食い違い | **修正提案を出し、承認を得て設計文書を直す** |
| 迷った点・却下した案 | 関わるチケットにコメントで残す。**再検討の条件**まで書く（手順3） |
| 作ったファイル・検証結果 | コミットメッセージと、関わるチケットのコメントに残す |
| 節目になる確定・大きくつまずいたこと | `docs/history/chronicle.md` に1行足す |

| 手順の範囲外で気づいた問題 | **stg の PB に起票する**（`Development.md` 12章）。リポジトリには写さない |
| 検証で作った資源 | 片付け、**片付いたことを測って**報告する（`Testing.md` 7章） |
| 作業ツリー | `make clean-webui`（`make build` した場合）と `git status` |
| 文書の分量 | **`make docs-size` を実行する**（下記） |
| 次のセッションの入口 | 次の手順に着手する人が、PB のチケットだけで前提を把握できるか読み返す |

- 最後に**5〜10行の要約を画面に出す**。何をどこへ書いたか、片付けた資源、次への申し送り
- **書かないと判断したものも1行で述べる**（判断を隠さない）

### 文書の分量（`make docs-size`）

**予算は毎セッション読む3文書の合計 80KB**（`CLAUDE.md` / `LEARNINGS.md` / 本ファイル）。個別の閾値は持たない——片方を減らして片方を増やすのを許してしまうため。

- **4ステップごとに必ず棚卸しする**（超過していなくても）。超えてから動くと毎回大手術になる
- 超過したら次の順に行う。**いきなりファイルを分割しない**
  1. **完了して今後の手順に不要な情報を消す**（日付と結果が確定していて、もう変わらないもの）
  2. **重複を削る。** 機械が答えられる事実を手で写していないか見る（版番号は `make version` が正本）
  3. 1と2で収まらないときに、初めて分割を検討する
- **閾値の引き上げを提案してはならない。** 引き上げるかどうかは利用者だけが判断する

## 8. 進め方の振り返り

**手順7が成果物を扱うのに対し、ここでは「利用者と自分のやり取り」そのものを扱う。**
見るのは**このセッションの会話**。以下を1件ずつ見て、該当が無ければ「該当なし」と述べる。

| 見るもの | 具体 |
|---|---|
| 手戻り | 完成させた後に直させた箇所。**なぜ最初からそうしなかったか**まで書く |
| 往復の多かった論点 | 3往復以上した話題。前提が欠けていたのか、説明の順序が悪かったのか |
| 利用者が自分で見つけた問題 | **私が先に気づくべきだった**もの |
| 私の空振り | やり直した作業・失敗した検証 |
| 指示の解釈 | **確認すべきだったのに進めた／進めてよいのに止まった** |
| 利用者に手を動かさせた場面 | 自分でファイルを消した・コミットした等 |
| うまくいった型 | **悪かったことだけを書かない** |

### 昇格・退役の判定（移動窓）

**`LEARNINGS.md` の各行は「発生」列に手順番号を最大4件持つ。** 直近10ステップを窓として数える。

| 判定 | 条件 | すること |
|---|---|---|
| **昇格** | 発生が4件たまり、**最古と最新が10ステップ以内** | 規約へ移す提案を出す。**移したら行を消す** |
| 据え置き | 4件たまったが**11ステップ以上に散っている** | **最古を捨てて3件に戻す**（頻度が足りない） |
| **退役** | 最新の発生から**10ステップ**再発していない | 消す。Phase の途中でもよい |

- **回数の累積では、続けていれば全項目がいつか閾値に届く。** 窓から出た発生は数から落とす
- ステップ数で数えるのは、日付だと開発が止まった期間も窓が進み、
  **開発量あたりの頻度**を測れないため。枝番（22a/22b/22c）はそれぞれ1ステップ
- **昇格先で基準が違う**——「どう書くか」（`GuiDesign.md` / `Development.md` / `Testing.md`）は
  **1回で即書く**（毎セッション読まないので予算に乗らない）。
  「どう進めるか」（`CLAUDE.md` / 本ファイル）だけが上の窓の対象である
- **「良かった型」は窓の対象外。** 守れているときは何も起きないので再発を数えられない。
  **1回で手順書に書けるなら即書いて消す。書けないなら記録に残さない**

- 画面には3〜5行で要約する

## 9. 記録とコミット

**記録は書き分ける。** 現況と約束は PB のチケットに置き、リポジトリには写さない。

| 書くこと | 書き先 |
|---|---|
| 状態・完了・残る要点 | 関わるチケット（状態とコメント） |
| 次の手順以降に持ち越す約束 | **stg の PB に起票** |
| いま効いている環境の制約 | `Development.md`（自分の端末に固有のものは `LEARNINGS.md`） |
| 判断の理由・却下した案 | 関わるチケットのコメント。プロジェクト全体に効く判断は PB の「判断の記録」 |
| 作ったファイル・検証結果 | コミットメッセージとチケットのコメント |
| 節目になる確定・大きくつまずいたこと | `docs/history/chronicle.md` に1行 |
| 検証の基準・落とし穴 | `docs/Testing.md` |
| 手順外で気づいた問題 | **stg の PB に起票** |

- 設計文書との差異が生じた場合、**コードではなく設計文書を直す提案**を出す
- **上記の更新を同じブランチに含めて**コミットする。**版番号を先に約束した場合はとくに**
  ——記録のためだけに `docs/` ブランチを後から1本切ると、そのマージがビルド番号を1つ消費して
  約束が壊れる（ビルド番号は develop へのマージ回数の実測であるため）

```
git add -A
git commit -m "step $1: <要約>"
```

- `git log --oneline` と `git status` を示し、コミット内容を報告する

## 10. マージの提案
以下を**提案するだけ**とし、実行はユーザーの承認後に行う。

```
git switch develop
git merge --no-ff feature/step-<2桁>-<スラッグ>
```

## 禁止事項
- 承認前に実装を始めてはならない
- **`develop` に直接コミットしてはならない**
- **マージ・push・ブランチ削除を独断で実行してはならない**
- 設計文書に書かれていない仕様を発明してはならない。不明なら質問する
- 手順 $1 のスコープを超える変更を独断で行ってはならない
- 持ち越す約束の起票を省略してはならない
- **振り返り（手順7・手順8）を省略してはならない。** 「特に無い」で済ませず、表の項目を1件ずつ見る
- **一度きりの事象で規約を増やしてはならない**（手順8の移動窓）
- **文書の閾値の引き上げを提案してはならない**（手順7）
