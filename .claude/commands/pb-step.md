Phase 1 の手順 **$1** を実装する。以下を順守すること。

## 1. 前提の確認
- `docs/PROGRESS.md` を読み、手順 $1 より前が完了しているか確認する
- 未完了の前提があれば、実装せずユーザーに報告する
- `git status` で作業ツリーが綺麗であることを確認する。未コミットの変更があれば報告し、指示を仰ぐ

## 2. 仕様の取得
- `docs/Design.md` 11章から手順 $1 の内容を確認する
- 手順 $1 に関係する設計文書の**該当章のみ**を読む。全文を読まない
  - DB・マイグレーション → `docs/DbDesign.md` の該当章
  - API → `docs/ApiDesign.md` の該当章
  - 画面 → `docs/GuiDesign.md` の該当章
  - 認証・認可 → `docs/Design.md` 6章

## 3. 計画の提示
- 変更・作成するファイルの一覧、実装方針、検証方法を提示する
- **作成する feature ブランチ名も計画に含める**（`feature/step-<2桁>-<スラッグ>`）
- **ユーザーの承認を得るまで実装を開始しない**
- 設計文書に書かれていない判断が必要な場合、この時点で選択肢と推奨を提示して確認する
- **手順の分量が大きいと判断した場合は、分割案（例：4a / 4b）を提示する。**
  1回のセッションで扱う量が多いほど、後半の実装品質が落ちるため

## 4. ブランチの作成
承認後、`develop` を最新化してから feature ブランチを切る。

```
git switch develop
git pull
git switch -c feature/step-<2桁>-<スラッグ>
```

- **`develop` 上で直接実装してはならない**
- 既に同名ブランチがある場合は、作業を中断してユーザーに確認する

## 5. 実装
- 設計文書の記述を**そのまま反映**する。独自の設計判断を加えない
- 手順 $1 のスコープ外のファイルを変更しない。必要が生じたらユーザーに相談する
- DDL は `docs/DbDesign.md` 6〜7章の記述を変更せずに転記する
- 秘密（パスワード・トークン・接続文字列）をコードに書かない

## 6. 検証
- 実行するコマンドと期待される結果を示し、実際に実行して確認する
- ビルド・テストが通ること、および手順ごとの確認項目を満たすことを確認する

## 7. 記録とコミット
- `docs/PROGRESS.md` の該当行を更新する（状態・完了日・実際に作ったファイル・気づいた点）
- 設計文書との差異が生じた場合、**コードではなく設計文書を直す提案**を出す
- **`docs/PROGRESS.md` の更新を同じブランチに含めて**コミットする

```
git add -A
git commit -m "step $1: <要約>"
```

- `git log --oneline` と `git status` を示し、コミット内容を報告する

## 8. マージの提案
以下を**提案するだけ**とし、実行はユーザーの承認後に行う。

```
git switch develop
git merge --no-ff feature/step-<2桁>-<スラッグ>
```

## 禁止事項
- 承認前に実装を始めてはならない
- **`develop` に直接コミットしてはならない**
- **マージ・push・ブランチ削除を独断で実行してはならない**
- 設計文書に書かれていない仕様を発明してはならない。不明なら質問する
- 手順 $1 のスコープを超える変更を独断で行ってはならない
- `docs/PROGRESS.md` の更新を省略してはならない
