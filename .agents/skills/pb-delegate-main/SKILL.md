# PB 自律実行の main

指定された根のチケットを、計画から成果の提出まで管理する。規約は PB の「規約」、自律実行の設計は `docs/design/Delegation.md` が正本である。通常のチケットの担当者だけで役割を判断せず、PB が指定した main の principal として動く。番号が無ければ利用者へ確認する。

## 1. 毎回の入口（初回も、強制停止後も）

会話の記憶を前提にしない。**次の順で状況を取り直す。**

1. 作業ディレクトリ直下の `.pb-local/delegation/pb-<根の番号>-main.md` を読む。無ければ初回として扱う。
2. `pb_get_context(seq=<根の番号>)` を読み、「6. 自律実行」の役割・主状態・次の一手・計画の版・制約の使用状況・止まる条件・開いている確認待ち・最近の回答・引き継ぎノート・役割の指示（共通を含む）を確認する。憲章の `vision` は全文を読む。本文を手元に持つ憲章だけ、その版を次回の `charter_versions` に渡す。
3. **食い違えば PB を正とする。** ローカルにしか無い途中の作業は、ブランチ・worktree・`git status`・実行中のコマンド・既存の報告を確かめてから続ける。最近の回答を読み、既に答えられた問いを重ねない。
4. `pb_get_task` で根の本文・完了条件・子を読み、必要な計画・評価・完了レポートを `pb_list_comments` で取得する。PB に接続できない、自律実行の節が無い、役割が main でない場合は、書き込まず利用者へ伝える。

参画情報は `pb_get_project`、不足する文書は `pb_list_docs` の目次から必要な章を読む。設計を確認する場合は、Delegation.md の4.3・5・6・8・9.2・11・12.1を参照する。

| PB の状態と次の一手 | すること |
|---|---|
| `planning`・未提出、または差し戻し | ヒアリング・計画の提出、または指摘への対応 |
| `planning`・評価／PM 承認待ち | `pb_wait` で待つ。合格だけで実行を始めない |
| `approved`・作業を進める | 承認された計画と範囲で管理する |
| 評価待ち | 待つ。評価役の注意に応えて直したら、根の完了レポートを出し直してよい（評価の対象が新しい報告へ替わる）。許可される、成果と関係しない子の作業は進めてよい |
| `hearing` 以外の確認待ち | 木への作業を止め、PM の回答を待つ |
| `paused` | 引き継ぎを残して止まる。再開は PM が行う |
| `ended`（受け入れ・取り下げ） | PB へ書き込まず、ローカルの引き継ぎファイルを消して終了する |

## 2. 計画中

目的は根の本文と完了条件、触ってよい場所はスコープ境界、制約は `scope.budget` と `scope.stop_conditions` である。書かれた目的を写すだけで計画にしない。

- 必要に応じて `pb_raise_confirmation(seq=<根の番号>, reason="hearing")` で、目的・成功の姿・制約・優先・避けたいこと・使える資源を掘り下げる。問いは何回かに分け、答えを受けて深める。選択肢と推奨を `options` に添える。ヒアリングは書き込みを止めないので、回答を待つ間に計画案を練ってよい。
- `pb_submit_plan` に `skeleton`（根の直下の枝・予算配分・チェックポイント）、`body_md`（作業の木の案と、どの価値観にどう沿わせたか）、`reason_md`（初版、または前の版から変えた理由）を渡す。
- `scope` は範囲を変えるときだけ渡す。現行の範囲を踏まえ、予算と止まる条件を明示する。計画の変更は `declared_class` を申告し、応答の `measured_class` と `status` を確認する。PB の判定と申告の厳しい方が採られる。
- 提出の前後にローカルの引き継ぎを残し、提出後は `pb_update_handoff(trigger="plan_version")` を更新して待つ。評価が不合格なら、指摘ごとに直した内容・直さない理由を書いて出し直す。

**計画の承認前に起票・実装・完了レポートを進めない。** 初版と範囲の変更は、評価の合格の後に PM の承認を待つ。

## 3. 承認済の作業

- PB に何も送らずに長くかかる作業（目安20分以上）の途中で、PB にノートを1件書く（`kind=progress`）。PB は main のトークンが一定時間使われないと止まったとみなし、評価役を止める（`Delegation.md` 10.4）。
- 全体の管理に専念する。使えるサブエージェントへ個々の作業を渡す場合は、子の番号・範囲・完了条件を渡し、`pb-implement` 相当の実装・検証・報告を行わせる。渡す前と戻った後にローカルの引き継ぎを書く。人が行う作業は人の担当として管理する。
- 個別作業の範囲と方法が承認済み計画で定まっていれば、その承認を根拠に進める。委任内の通常作業で毎回 PM の承認を求めない。設計判断・範囲の変更・不可逆な操作など、確認が必要な条件は4節に従う。
- **起票の直前に親を `pb_get_task` で読み、`children` に同じ作業が無いかを確認する。** 強制停止直前の起票が通っていることがある。`pb_create_ticket` の `parent_seq` は必ず根か木の中のチケットとし、起票後すぐ番号を記録する。
- 子の作業は各チケットの完了条件を満たし、許可された範囲で実装・検証する。ブランチ・worktree・バージョンはプロジェクト規約に従い、変更をこまめにコミットする。
- 骨格の変更は計画の新版で出す。軽微な変更はその場で反映、構造の変更は評価待ち、範囲の変更は `planning` に戻って評価と PM 承認待ちとなる。承認前の新版を根拠に作業しない。
- 子の成果は子に `pb_submit_result` で報告する。`findings` に実行者（main・どの sub・人）の内訳を書き、`cost` に測れるコストを書く。トークン数を推定で埋めない。遷移は `pb_list_transitions` で確認し、完了以外の許可された状態まで進める。**チケットのクローズは PM が行う。**
- 作業記録はチケットごとに開いて閉じる。委任の木の中なら同じトークンでも同時に複数開ける（1チケット1件まで）。自分の管理の時間は根で `pb_start_work(note="main")` を開き、待ち受けの間は pause する。サブエージェントには、着手時に子で `pb_start_work(note="sub-<番号>")`、報告前に `pb_record_work(action=finish)` と子の累積 `change_metrics`、完了レポートに `work_session_id` を指示する。落ちて残った記録は理由付きの `abandon` で閉じる。
- 根の目的を満たしたら根に `pb_submit_result` を提出し、引き継ぎを更新して成果の評価を待つ。差し戻されたら指摘ごとに改善して新版の成果を提出する。評価合格後も、根の受け入れは PM が行う。

## 4. 待ち受けと停止

待つ前に、待っている対象をローカルへ書く。`pb_wait(seq=<根の番号>, since=<保存した cursor>)` を呼び、応答の `next` に従う。初回だけは `since` を省ける。**返った `cursor` を毎回ローカルへ保存し、呼び直しもその値から待ち受ける。** 変化が無ければ繰り返す。エラー時も最後に受け取った cursor を保持して再度呼ぶ。
`pb-wait`（PATH か環境変数 `PB_WAIT`）が使えるなら、待ち受けはそれに任せる（`Delegation.md` 10.3）。前で `pb-wait --url <接続設定の PB の URL> --token-env <接続設定の変数名> --seq <根の番号> --since <保存した cursor> --max 9m` を走らせ、出力（`pb_wait` と同じ JSON）の `next` に従う。終了コード 2 は時間切れで、出力の `cursor` でもう一度走らせる。3 は main が止まっている（`main_stopped`）。1 は失敗で、`pb_wait` に切り替える。シェルのコマンドを何分まで待てるかは実機未確認なので、打ち切られたら `--max` を縮める。

長い待ち受けは非同期で呼び、進捗を通知しながら応答を待つ。評価・承認・回答が届いたら `pb_get_context` から状況を取り直す。`paused` / `ended` または利用者の停止指示を確認したら待ち受けを終了する。

| 確認が必要な操作 | `pb_raise_confirmation` の `reason` |
|---|---|
| 範囲の外への変更 | `scope_change` |
| マージ・push・デプロイ・外部送信・削除 | `irreversible_external` |
| 憲章の変更 | `charter_change` |
| 機微な領域への接触 | `sensitive_area` |
| 止まる条件への到達 | 内容に近い上記の理由。問いに該当する条件を書く |

確認待ちを立てる前に両方の引き継ぎを書き、問いに選択肢・推奨・理由を添える。`hearing` 以外は作業を止め、回答を `pb_wait` で待つ。ノートと引き継ぎ以外の木への書き込みをしない。

**403 の `delegation_stage` / `delegation_budget` で拒まれた、または PB が一時停止を返したら、ローカルと PB の引き継ぎを書いて止まる。** 権限を回避したり別の入口から再試行したりしない。予算超過への回答だけで再開せず、PM による再開を待つ。

## 5. 引き継ぎ

初めてローカルへ書く前に、`git rev-parse --git-path info/exclude` が返すファイルへ `.pb-local/` を1行、無ければ追加する。**`.gitignore` は変えない。** 次の項目を `.pb-local/delegation/pb-<根の番号>-main.md` に書く。

- 最終更新時刻、自律実行の状態、直近にしたこと
- やりかけのこと（ブランチ・worktree・未コミットの変更・実行中のコマンド・未提出の報告）
- PB にまだ反映していないこと、次にすること、最後の `pb_wait` の cursor

計画・評価の受領・完了レポートの前後、確認待ちを立てる前、待ち受けの前、sub へ渡す前と戻った後、長い作業中（目安30分ごと）、セッション終了前に更新する。ローカルには秘密を書かない。共有する記録からは端末固有のパスと個人情報も除く。

**main は PB の引き継ぎノートも書く。** `pb_update_handoff` の `body` に、目的と現在の計画の版・決めたこと・未決事項・進行中の作業・次の一手・予算の消費・直近の評価の7項目を入れる。`trigger` は計画／承認時に `plan_version`、評価受領時に `evaluation`、成果報告時に `report`、確認待ち前に `before_confirmation`、待ち受けや sub への受け渡し・長い作業中の区切りとセッション終了時に `session_end` を使う。
